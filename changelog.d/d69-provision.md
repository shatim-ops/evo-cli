### Миграция

- **`provision` по MCP отвечает не позже ~45 с; повтор того же вызова доделывает ВМ** (DECISIONS D69, второй PR).
  Было: `provision` по MCP ждал ВМ до 25 мин в одном вызове, и клиент обрывал его; повтор с тем же именем после обрыва или отмены отвечал `USAGE`, код 1: «ВМ с именем уже есть» (Cloud.ru — 409), и ВМ оставалась без проверки внешнего IP и без открытых портов.
  Стало: `provision`, не дождавшийся ВМ за ~45 с, отвечает **не ошибкой**: `status: creating`, `vm_id`, `vm_status` (состояние, прочитанное последним), `name`, пароль ВМ (один раз) и следующий шаг — `next`, `next_tool: provision`, `next_args` (тот же вызов с именем ВМ, без `wait` и `image_metadata`). Повтор `provision` с тем же именем из того же каталога подхватывает ВМ, которую записал прошлый вызов (запись `creating`), дожидается её, даёт внешний IP и открывает порты, второй ВМ не создаёт; пароля в его ответе нет. Превью повтора называет эту ВМ (`adopts`). ВМ этого имени без записи в state не подхватывается. Аргумент `wait` (`evo vm create --wait=false`): `false` — ответ сразу, как облако приняло создание, `true` — ждать без предела. CLI по умолчанию ждёт, как раньше. Шаг ВМ в `stack_apply` ждёт ВМ в вызове, как раньше.
  Что поменять: агент, который ждал от `provision` по MCP только готовую ВМ или ошибку, читает `status: creating`, сохраняет пароль и вызывает `next_tool` с `next_args`. Скрипт, который после обрыва ждал `USAGE` «имя занято», получает подхваченную ВМ с `status: ok`.
