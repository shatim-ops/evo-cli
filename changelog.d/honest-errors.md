### Миграция

- **Честный код там, где он скрывал настоящее** (DECISIONS D31). (1) `evo deploy --dry-run` без ключа доступа показывает превью — что известно, недостающие настройки названы в `missing`, — как `evo tools call deploy --dry-run`; было: `AUTH_REQUIRED`, код 2; стало: код 0. Без `--dry-run` ключ по-прежнему нужен. (2) на сервере `evo mcp --allow-project`: `vm_get` с именем ВМ своего проекта в `vm_id` находит её, как без флага; было: `NOT_FOUND`, код 4. Ошибка настройки сервера при проверке, чей ресурс (битый профиль, нет ключа), приходит как она есть — обычно `CONFIG_INVALID` или `AUTH_REQUIRED`, код 2; было: `NOT_FOUND` «… не найден в проектах этого сервера». Ресурс другого проекта — по-прежнему `NOT_FOUND`. (3) `evo vpc fip-release` (MCP `release_floating_ip`) с адресом шлюза SNAT или адресом, занятым ВМ, отказывает до вопроса о согласии; было: без `--yes` — код 3 и вопрос, отказ `USAGE` — после «да»; стало: `USAGE`, код 1, `status: refused` сразу. Что поменять: скрипту, который ждал код 2 от `evo deploy --dry-run` без ключа, — смотреть `missing` в превью; клиенту сервера с `--allow-project` — `CONFIG_INVALID`/`AUTH_REQUIRED` вместо `NOT_FOUND` означает, что сломана настройка сервера, а не что ресурса нет; скрипту `evo vpc fip-release` — ждать код 1 у адреса шлюза SNAT или занятого ВМ уже без `--yes`.

### Добавлено

- Ошибка отказа в правах (HTTP 403) любого сервиса несёт `access_denied: true` и `http_status: 403` — в ответе MCP и в `details` ошибки CLI с `--json`; `reason` и код выхода прежние. «Нет роли» теперь отличимо от прочих ошибок не только по тексту.

- `evo cert import` (MCP `cert_import`) принимает сертификат, ключ и цепочку как PEM, а не только Base64 от PEM: значение, которое начинается с `-----BEGIN`, evo кодирует сам. Base64 принимается, как раньше.
