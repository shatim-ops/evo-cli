### Миграция

- **`deploy` по MCP с SSH, который не отвечает, кончается `SSH_TIMEOUT`, как в CLI** (DECISIONS D80; агентный прогон 1.7.0).
  Было: каждый вызов `deploy` по MCP начинал ожидание SSH заново — и счёт попыток, и время. Поэтому при закрытом исходящем порте 22 или ВМ без сети он отвечал `status: deploying`, код 0, с `next_tool: deploy` без конца. Причину — исходящий 22, проверка `nc -vz` — CLI называет через 5 минут ожидания, а по MCP она не приходила вовсе. ВМ всё это время оплачивалась.
  Стало: ожидание SSH хранится в записи развёртывания (`deployment.ssh_wait`: `since`, `attempts`, `limit`), и следующий `deploy` его продолжает. Через 5 минут ожидания ответ `deploying` несёт `warning` с причиной и проверкой, а `next` отсылает к нему. Когда попытки кончились (60 у новой ВМ), ответ — `SSH_TIMEOUT`, код 1, как в CLI, без `next_tool`; запись — `ssh_timeout`. Подсказка на обеих поверхностях говорит, что дальше решает человек: сначала проверить исходящий 22 (`nc -vz <адрес> 22`), затем перезагрузить ВМ в консоли; удалить ВМ она больше не советует. `deploy` после `SSH_TIMEOUT` ждёт заново. Счёт общий для папки: `evo deploy` в одном вызове ждёт, как раньше, а ожидание, начатое по MCP, продолжает по записи.
  Что поменять: агент, который повторял `deploy`, пока ответ `deploying`, при `SSH_TIMEOUT` останавливается, читает `hint` и спрашивает человека. При `warning` до этого — проверяет сеть (`nc -vz <адрес> 22`) или говорит человеку. Скрипт, разбирающий запись state, допускает поле `ssh_wait`.

### Исправлено

- **`logs` и `verify` во время `deploy`, прерванного пределом вызова MCP на ожидании SSH, отвечают `DEPLOY_IN_PROGRESS`** (D76). Запись развёртывания получала `ssh_timeout`, хотя ответ `deploy` был `deploying`; `logs` и `verify` шли по SSH и отвечали `SSH_TIMEOUT`. Теперь запись остаётся незавершённой, как обещают D76 и «Миграция» 1.7.0.
