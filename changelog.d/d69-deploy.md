### Миграция

- **`deploy` по MCP отвечает не позже ~45 с; установка Docker и `docker compose up` идут на ВМ без вызова** (DECISIONS D69, вариант C — решение владельца 03.11).
  Было: `deploy` по MCP ждал ВМ, SSH, установку Docker и `docker compose up` в одном вызове — минуты, и клиент MCP обрывал его; обрыв сессии рвал `apt` и `compose up` посредине.
  Стало: долгие этапы — установка Docker и `docker compose up` — запускаются на ВМ отсоединённо от SSH-сессии (каталог `~/.evo/stage` на ВМ: маркер, лог, замок) и переживают её конец. По MCP вызов ждёт ВМ, SSH и этап до предела; не дождался — ответ **не ошибкой**: `status: deploying`, `phase` (`vm`, `ssh`, `docker`, `compose-up`), `phase_state` или `output` (последняя строка лога этапа, помечена `_untrusted`), запись развёртывания и следующий шаг — `next`, `next_tool: deploy`, `next_args`. Повтор того же вызова берёт ВМ из state и читает этап: идёт — ждёт, готов для того же compose-файла — не запускает снова, потерян на ВМ (перезагрузка, остановка процесса) — запускает снова и отвечает это ошибкой с последними строками лога. `force` запускает `compose up` снова, как раньше. CLI ждёт, как раньше, коды выхода прежние; ход этапа в выводе — строками его лога, а не потоком SSH.
  Что поменять: агент, который ждал от `deploy` по MCP только готовое развёртывание или ошибку, читает `status: deploying` и вызывает `next_tool` с `next_args`, пока ответ не станет `ok`.
