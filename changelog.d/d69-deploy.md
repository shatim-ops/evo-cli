### Миграция

- **`deploy` по MCP отвечает не позже ~45 с; установка Docker и `docker compose up` идут на ВМ без вызова** (DECISIONS D69, вариант C — решение владельца 03.11).
  Было: `deploy` по MCP ждал ВМ, SSH, установку Docker и `docker compose up` в одном вызове — минуты, и клиент MCP обрывал его; обрыв сессии рвал `apt` и `compose up` посредине.
  Стало: долгие этапы — установка Docker и `docker compose up` — запускаются на ВМ отсоединённо от SSH-сессии (каталог `~/.evo/stage` на ВМ: маркер, лог, замок) и переживают её конец. По MCP весь вызов — ВМ, SSH, загрузка compose-файла, этапы, проверка — укладывается в предел; не дождался — ответ **не ошибкой**: `status: deploying`, `phase` (`vm`, `ssh`, `docker`, `upload`, `compose-up`, `verify`), `phase_state` (состояние словами evo), у этапа ещё `output` (последняя строка его лога, помечена `_untrusted`), запись развёртывания и следующий шаг — `next`, `next_tool: deploy`, `next_args`. Повтор того же вызова берёт ВМ из state (ВМ, которая ещё создаётся, он сначала дожидается) и читает этап: идёт — ждёт, готов для того же compose-файла — не запускает снова, потерян на ВМ (перезагрузка, остановка процесса, оборванный запуск) — запускает снова и отвечает это ошибкой с последними строками лога. `force` запускает `compose up` снова, как раньше, один раз: когда он начался, `next_args` повтора идут без `force`.
  Что поменять: агент, который ждал от `deploy` по MCP только готовое развёртывание или ошибку, читает `status: deploying` и вызывает `next_tool` с `next_args`, пока ответ не станет `ok`.

### Изменено

- **`evo deploy`: этапы на ВМ идут без сессии CLI** (DECISIONS D69, вариант C). Ход установки Docker и `docker compose up` в выводе — последней строкой лога этапа раз в ~3 с, а не потоком SSH. Ctrl-C останавливает `evo deploy`, но **не** `docker compose up` на ВМ: этап доходит до конца, повтор `evo deploy` его подхватывает. Остановить его самому — на ВМ: `pkill -f 'evo-stage.sh run compose-up'`, затем `docker compose -f /opt/app/docker-compose.yml down`. Этап, потерянный на ВМ (перезагрузка, остановка процесса), `evo deploy` запускает снова и завершается ошибкой `SSH_TIMEOUT` с последними строками лога; повтор следит за новым запуском. Коды выхода прежние.

### Известные ограничения

- Этап `deploy` на ВМ (установка Docker, `docker compose up`) переживает конец SSH-сессии через `setsid nohup`. На образе, где `systemd-logind` работает с `KillUserProcesses=yes`, этап оборвётся вместе с сессией. В Ubuntu по умолчанию `no`; для образов Cloud.ru это гипотеза, её проверяет cloud-e2e `deploy` кандидата 1.7.0. Оборванный так этап читается как прерванный на ВМ, и повтор `deploy` запускает его снова.
