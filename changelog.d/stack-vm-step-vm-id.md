### Миграция

- **Стек: повтор шага ВМ не создаёт вторую ВМ, если первая пропала** (DECISIONS D102 — то же правило для шага стека). Было: шаг ВМ, чья ВМ ещё поднималась, когда кончился предел вызова (`stack_apply`, `stack_status`), следующий прогон повторял `provision` без `vm_id`. Если ВМ к этому времени пропала (удалена в консоли или другим агентом), создавались новая платная ВМ и публичный IP, и задание завершалось успешно, код 0. Стало: повтор несёт `vm_id` ВМ шага. Шаг, чьей ВМ больше нет, отказывает `VM_NOT_FOUND`, задание уходит в ошибку, новая ВМ не создаётся. Что поменять: задание в ошибке не довести — удалять ли созданное (`stack_destroy`) и планировать ли заново (`stack_plan`), решает человек. Обычный путь не меняется: ВМ на месте — шаг подхватывает её и доводит, как раньше.

- **Стек: шаг, у которого есть id своего ресурса, сверяется только по этому id** (DECISIONS D102 для стеков, дополнение 14.11). Было: если ВМ шага пропала, повтор `provision` отказывал `VM_NOT_FOUND`, но шаг затем искал ВМ по имени. Другую ВМ с тем же именем, созданную позже старта шага, он подхватывал и завершался `done` с чужим id. Если же такой ВМ не находилось, повторял попытку и уходил в ошибку только на четвёртой. Стало: отказ шага с id своего ресурса (`VM_NOT_FOUND`, `NOT_FOUND`) окончательный с первого раза. «Ресурс шага пропал» говорится только при `VM_NOT_FOUND`; при `NOT_FOUND` ресурс шага оставлен для `stack_destroy`. Чужой ресурс с тем же именем не подхватывается, и шаг, ждущий свою операцию, по её концу тоже сохраняет свой id: задание уходит в ошибку, а `stack_destroy` не тронет чужую ВМ или сеть. Что поменять: то же, что выше — удалять ли созданное (`stack_destroy`) и планировать ли заново (`stack_plan`), решает человек.

- **Стек: шаг, ждущий свой ресурс, кончается ошибкой, если ресурса больше нет** (DECISIONS D102 для стеков, дополнение 14.11). Было: шаг PostgreSQL, Kafka, Redis или Kubernetes, ожидающий готовности кластера, при `NOT_FOUND` по своему id оставался в ожидании, и задание отвечало `running` без причины. Шаг, ждущий свою операцию (VPC, балансировщик, целевая группа), по её концу закрывался `done` с id ресурса, которого уже нет. Стало: по концу операции шаг читает свой ресурс адресно по id (`vpc_get`, `lb_get`, `tg_get`). Если ресурс не находится не меньше 4 раз и не меньше 10 минут от первого промаха, шаг и задание уходят в ошибку `NOT_FOUND`; если чтение отказывает по другой причине (`AUTH_FAILED`, `API_UNREACHABLE`, `API_RATE_LIMITED`), непроверенный id не становится результатом: шаг ждёт, опрос называет причину, а по тому же сроку шаг и задание уходят в ошибку с причиной чтения. То же — у шага, ждущего готовности кластера. Чтение сразу после создания может отставать, поэтому частый опрос ошибку не ускоряет. Ответ говорит, что установлено («не найден по id»), а не что ресурса нет. Он называет чтение, которое проверит это, и напоминает: `stack_destroy` удаляет созданное заданием по id, а новый план с теми же именами откажет, пока ресурс есть. Что поменять: то же, что выше.
