### Изменено

- **`stack_apply` и `stack_status` по MCP отвечают не позже ~45 с и со стеком с ВМ** (DECISIONS D69, третий PR). Было: шаг ВМ ждал ВМ в вызове — `stack_apply` по MCP шёл минутами, и клиент обрывал его. Стало: ВМ, которая ещё поднимается к концу предела, — шаг остаётся в `pending` с `details.vm` «VM … is creating», без потраченной попытки; следующий `stack_status` повторяет `provision`, тот подхватывает ВМ и доделывает её. `stack_destroy` видит ВМ такого шага. CLI (`evo stack apply`, `evo stack status`) ждёт ВМ, как раньше.
- **`provision` по MCP: ожидание внешнего адреса после запуска ВМ тоже кончается с пределом вызова** — ответ `creating` с `vm_status: active`; повтор того же вызова дожидается адреса.

### Исправлено

- **Пароль ВМ шага стека больше не теряется** (FB121-7, аудит Fable 1.2.1; известное ограничение с 1.3.0). Ответ `stack_apply` или `stack_status`, в котором шаг создал ВМ, называет пароль, сгенерированный evo, в `passwords{шаг}`, один раз; в файл задания он не пишется.
