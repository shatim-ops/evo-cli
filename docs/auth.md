# Доступ к Cloud.ru: ключ, проект, профили, переменные окружения

evo ходит в API Cloud.ru от имени **сервисного аккаунта**: пара
Key ID + Key Secret его ключа доступа обменивается в IAM
(`iam.api.cloud.ru`) на токен на час, токен кэшируется на диске. Срок
токена — меньший из `expires_in` ответа IAM и `exp` самого токена, по часам
системы: после сна машины или паузы ВМ долгий `evo mcp` не держит истёкший
токен. Токен, на который сервис ответил `401`, evo сбрасывает из памяти и
кэша — следующий вызов обменивает ключ заново. Кроме ключа
нужен **UUID проекта**, в котором создаются ресурсы.

Подойдёт и персональный ключ доступа пользователя (та же пара Key ID / Key
Secret, тот же обмен), но для скриптов, CI и MCP-сервера лучше отдельный
сервисный аккаунт с правами только на нужный проект.

> Термины. У Cloud.ru есть ещё «API-ключ» — отдельная сущность
> (`Authorization: Api-Key …`), evo её **не использует**. Переменная
> `CLOUDRU_API_KEY` исторически означает пару `keyId:secret` и устарела.

## 1. Сервисный аккаунт

Пути по меню личного кабинета [console.cloud.ru](https://console.cloud.ru) —
по документации Cloud.ru на 14.10.2026; подписи кнопок могут меняться.

1. «Пользователи» → «Сервисные аккаунты» → «Создать аккаунт» (справа вверху).
2. Название и описание (например, `evo-ci`).
3. Уровень аккаунта — **«Проект»**, если аккаунт нужен для одного проекта.
4. «Продолжить» → назначьте роли (см. [раздел 3](#3-роли)) → «Создать».

Аккаунт должен перейти в статус «Активен».
Документация: [создание сервисного аккаунта](https://cloud.ru/docs/console_api/ug/topics/guides__service_accounts_create?source-platform=Evolution).

## 2. Ключ доступа

1. «Пользователи» → «Сервисные аккаунты» → название аккаунта.
2. Блок «Учетные данные доступа», вкладка «Ключи доступа» → «Создать ключ».
3. Описание ключа (по нему вы потом отличите ключи при ротации) и **срок
   жизни**: по его истечении ключ перестаёт работать. Бессрочный ключ Cloud.ru
   не рекомендует; ограничьте срок или меняйте ключ сами не реже раза в год.
4. «Создать». **Key Secret показывается один раз** — сохраните его сразу
   (в менеджер паролей или сразу в `evo configure`).

На один сервисный аккаунт — до 20 ключей.
Документация: [создание ключа доступа](https://cloud.ru/docs/console_api/ug/topics/guides__service_accounts_key-create?source-platform=Evolution).

## 3. Роли

Честно о том, что известно:

- Cloud.ru публикует роли уровня платформы — `platform.project.admin`,
  `platform.project.user`, `platform.project.viewer` (в части документации —
  `iam.project.admin`) и `iam.serviceaccount.*`. Сервисные роли `compute.*` и
  `vpc.*` в документации не опубликованы; опубликованы роли части сервисов,
  в том числе:
  - Managed Kubernetes — `k8s.admin` (создание и удаление кластеров и групп
    узлов, установка плагинов; в кластере — `cluster-admin`) и `k8s.user`
    (kubeconfig и чтение; в кластере — `view`, `kubectl apply` получит `403`).
    Для дерева `evo k8s` нужна `k8s.admin`
    ([документация](https://cloud.ru/docs/kubernetes-evolution/ug/topics/access));
  - Object Storage — `s3e.viewer`, `s3e.editor`, `s3e.admin`, `s3e.auditor`
    ([документация](https://cloud.ru/docs/s3e/ug/topics/security__role)).
- **Проверено 14.10.2026** (облачная приёмка этапов 2, 5 и 8): полный сценарий
  `configure → whoami → init → deploy → verify → logs → destroy` и чтение
  зон/образов/ВМ работают на сервисном аккаунте **с правами на уровне
  проекта**.
- **Точный минимальный набор ролей — открытый вопрос**: роли на запись по
  отдельности не проверялись. Если нужна минимальная выдача, начните с роли
  пользователя проекта и расширяйте по ошибкам `403`.

Что видно в ошибках: `403` при обмене ключа — `AUTH_FAILED`, код выхода `2`;
`403` от compute API (ВМ, диски, `deploy`) — `AUTH_FAILED`, код `2`; от других
сервисов (vpc, dns, …) — код `5` с текстом ответа Cloud.ru. Подсказка у обоих
говорит, что ключ принят, а роли нет, и где её выдать; `401` — про сам ключ.
Подробнее — [troubleshooting.md](troubleshooting.md#403-forbidden-от-сервиса-код-5).

Organization API (`organization.api.cloud.ru/v3/projects`) **не отдаёт
сервисному аккаунту список проектов** (проверено 14.10.2026: ответ `400`
«user not found»). Поэтому `configure` для сервисного аккаунта просит
`project_id` вручную — это ожидаемо, а не ошибка ключа.

## 4. UUID проекта

UUID проекта (вида `3f2a8c1e-…`) возьмите в консоли Cloud.ru, в сведениях о
проекте, в котором сервисный аккаунт получил роли. Персональный ключ
пользователя видит свои проекты сам — `configure` покажет список.

## 5. `evo configure`

Интерактивно (в терминале):

```console
$ evo configure
Настройка профиля "default" в /home/me/.config/evo
Key ID: 7b1e…
Секрет:                                   ← не отображается
Список проектов этому ключу недоступен — так Cloud.ru отвечает сервисным аккаунтам проекта. Введите UUID проекта: он в консоли Cloud.ru, в сведениях о проекте.
ID проекта: 3f2a8c1e-…
Зоны доступности для новых ВМ:
   1) ru.AZ-2  9c4d…
   2) ru.AZ-1  1a7e…
Выберите зону (номер, имя или ID) [1]:
Профиль "default" сохранён в /home/me/.config/evo
```

`configure` сначала обменивает ключ на токен — неверный ключ не сохранится.
Повторный запуск показывает текущие значения в скобках; Enter их оставляет.

После проекта `configure` спрашивает зону доступности — в ней `evo vm create`
создаёт ВМ, если `--region` не передан. Зоны те же, что в `evo vm zones`, и
предлагаются, как в `evo init`: только открытые для новых ресурсов, первой —
зона с подсетью проекта (ru.AZ-2, если подсеть есть и в ней). Сам evo зону не
выбирает: Enter берёт показанную по умолчанию. Ответ — номер, имя зоны или её
UUID; в профиль записывается UUID. Если список зон не получен (сеть, роль
ключа), шаг пропускается одной строкой, ключ и проект сохраняются; зону
можно задать позже — `evo configure --region <зона>`. Профиль без зоны
(например, созданный до 1.2.1) работает, но `evo vm create` без `--region`
отказывает до вопроса о согласии ([troubleshooting.md](troubleshooting.md#config_invalid-код-2-не-задана-зона-доступности-region-no-availability-zone-is-set)).

Без терминала (CI, скрипты). Секрет — только через stdin, не флагом: флаг
виден в `ps` и истории оболочки.

```sh
printf '%s' "$CLOUDRU_SECRET" | evo configure \
  --key-id "$CLOUDRU_KEY_ID" --secret-stdin --project-id "$CLOUDRU_PROJECT_ID"
```

Флаги: `--key-id`, `--secret-stdin`, `--project-id` (пропускает список
проектов), `--region` (зона по умолчанию для профиля, без вопроса: имя,
например `ru.AZ-2`, или UUID; имя evo находит в списке зон, в профиль
записывается UUID; неизвестное имя — `USAGE`, код 1, со списком зон). Без
терминала зону спрашивать некому: без `--region` она не меняется.

Проверка:

```sh
# профиль, Key ID (маскирован), проект, срок токена; код 2 при отказе IAM
evo whoami
# файлы и права, откуда взята каждая настройка, доступность API, kubectl/helm
evo doctor
```

### Профили

Профиль — именованный набор «ключ + проект + умолчания». По умолчанию —
`default`.

```sh
# создать/изменить профиль
evo configure --profile staging
# использовать разово
evo --profile staging vm list
# использовать в этой оболочке
export CLOUDRU_PROFILE=staging
# профили; активный помечен *
evo configure list
# удалить профиль и его кэш токена
evo configure delete staging
```

Имя профиля: латиница, цифры, `-`, `_`, `.`, до 64 символов. Профиль, названный
явно (`--profile`, `CLOUDRU_PROFILE`), обязан существовать — иначе код `2`.

### Ключи Object Storage (S3)

Команды `s3` и инструменты `s3_*` ходят в Object Storage по протоколу S3.
Отдельный ключ не нужен — подходит тот же ключ доступа (персональный или
сервисного аккаунта), но в формате S3
([документация](https://cloud.ru/docs/s3e/ug/topics/api__api-key)):

- `access_key` — `<tenant_id>:<Key ID>` (или `<tenant_id>.<Key ID>`);
  `tenant_id` — в консоли: «Хранение данных → Object Storage → Параметры
  работы с API»;
- `secret_key` — Key Secret того же ключа;
- аккаунту нужна роль Object Storage: `s3e.viewer` для чтения, `s3e.editor`
  для записи.

`configure` их не спрашивает: задайте переменными
`CLOUDRU_S3_*` (таблица ниже) или секцией `s3` профиля в `credentials.yaml`:

```yaml
profiles:
  default:
    key_id: 7b1e…
    secret: …
    s3:
      endpoint: https://s3.cloud.ru     # по умолчанию
      access_key: <tenant_id>:7b1e…     # tenant_id и Key ID
      secret_key: …                     # Key Secret
      region: ru-central-1              # по умолчанию
```

## 6. Откуда берутся настройки

От высшего приоритета к низшему:

1. **флаги** (`--project-id`, `--region`, `--profile`, флаги `deploy`…);
2. **переменные окружения** (таблица ниже); пустая переменная = не задана;
3. **файл проекта** `./.evo.yaml` в текущем каталоге (его создаёт
   `init`; его можно коммитить — секреты из него **не читаются**, `doctor`
   предупредит, если они там есть);
4. **профиль** — `config.yaml` и `credentials.yaml` (см. [раздел 8](#что-хранится-на-машине));
5. значения по умолчанию.

Ключ берётся парой целиком: если задана хотя бы одна из `CLOUDRU_KEY_ID` /
`CLOUDRU_SECRET` (или `CLOUDRU_KEY_SECRET`, или пара `EVOLUTION_*` — см.
[раздел 7](#7-переменные-окружения)), ключ профиля не используется. `evo doctor` показывает,
откуда взята каждая настройка (`flag`, `env`, `project`, `profile`,
`default`).

## 7. Переменные окружения

Полный список переменных, которые читает evo. Тест в CI
(`TestAuthDoc_ListsEveryEnvVar`) проверяет, что каждая переменная из кода
упомянута в этом файле.

### Ключ и профиль

| Переменная | Что задаёт | Флаг / файл |
|---|---|---|
| `CLOUDRU_KEY_ID` | Key ID ключа доступа | `credentials.yaml: key_id` |
| `CLOUDRU_SECRET` | Key Secret ключа доступа | `credentials.yaml: secret` |
| `CLOUDRU_KEY_SECRET` | то же, что `CLOUDRU_SECRET` (имя из [MCP-гайда Cloud.ru](https://cloud.ru/docs/container-apps-evolution/ug/topics/guides__mcp-server)); читается, если `CLOUDRU_SECRET` не задана | — |
| `EVOLUTION_SERVICE_ACCOUNT_KEY_ID`, `EVOLUTION_SERVICE_ACCOUNT_KEY_SECRET` | ключ, который AI Agents передаёт MCP-серверу ([переменные MCP-сервера](https://cloud.ru/docs/ai-agents/ug/topics/concepts__variables-mcp-server)); читаются, только если не задана ни одна `CLOUDRU_KEY_ID` / `CLOUDRU_SECRET` / `CLOUDRU_KEY_SECRET` | — |
| `CLOUDRU_API_KEY` | **устарела**: пара `keyId:secret` одной строкой; читается, только если не задана ни одна из переменных ключа выше, и печатает предупреждение | — |
| `CLOUDRU_PROFILE` | профиль вместо `default` | `--profile` |
| `CLOUDRU_CONFIG_DIR` | каталог конфигурации вместо стандартного; кэш токена — в его подкаталоге `cache/` (одна переменная изолирует всё: CI, тесты, несколько окружений) | — |

### Проект и параметры развёртывания

| Переменная | Что задаёт | Флаг / ключ в `.evo.yaml` и профиле |
|---|---|---|
| `CLOUDRU_PROJECT_ID` | UUID проекта. Нужен и для чтений, и для создания ресурсов проекта (`vm list`, `vpc subnets`, `k8s list`, `pg list`, секреты, …): без него — `CONFIG_INVALID`, код `2`, запрос в облако не уходит. Без проекта работают каталоги (зоны, флейворы, образы, Marketplace, типы дисков), `org_projects`, `org_quotas`, `billing_*` с договором (`CLOUDRU_AGREEMENT_ID`), Object Storage и локальные `status`/`list` | `--project-id` / `project_id` |
| `EVOLUTION_PROJECT_ID` | то же (имя AI Agents); `CLOUDRU_PROJECT_ID` важнее | — |
| `CLOUDRU_REGION` | зона доступности (`evo vm zones`): имя (`ru.AZ-2`) или UUID; имя, которого нет в списке зон, — отказ до вопроса о согласии (`USAGE`, код 1) | `--region` / `region` |
| `CLOUDRU_IMAGE_ID` | UUID загрузочного образа для `deploy` (`evo image list`, `evo image get <имя>`) | `deploy --image-id` / `image_id` (по имени или UUID — `deploy --image` / `image:`) |
| `CLOUDRU_FLAVOR` | конфигурация ВМ, например `lowcost10-2-4`; `auto` — подобрать (по умолчанию) | `deploy --flavor` / `flavor` |
| `CLOUDRU_DISK_SIZE` | размер загрузочного диска, ГБ (по умолчанию 10) | `deploy --disk-size` / `disk_size` |
| `CLOUDRU_COMPOSE_FILE` | путь к compose-файлу (по умолчанию `docker-compose.yml`) | `deploy -f` / `compose_file` |
| `CLOUDRU_PROJECT_NAME` | имя развёртывания (по умолчанию — имя текущего каталога) | `project_name` |
| `CLOUDRU_TIMEOUT` | сколько секунд `deploy`, `vm create` и MCP `provision` ждут, пока ВМ станет активной (по умолчанию 1500 — 25 минут) | `timeout` |
| `CLOUDRU_AGREEMENT_ID` | ID договора для инструментов биллинга (`billing_*`): расход и баланс всего договора. Его видят только администратор организации и администратор затрат ([где найти](https://cloud.ru/docs/billing/ug/topics/faq__api_id_agreement)). Без него `billing_consumption` и `billing_finops` считают расход проекта (`CLOUDRU_PROJECT_ID` или аргумент `project_id`; роль ключа — администратор проекта, `platform.project.admin`, [документация](https://cloud.ru/docs/billing/ug/topics/api-ref_start)), а `billing_balance` отказывает: баланса по проекту в API нет | — |

### Object Storage (S3)

| Переменная | Что задаёт | В `credentials.yaml` |
|---|---|---|
| `CLOUDRU_S3_ENDPOINT` | адрес S3 (по умолчанию `https://s3.cloud.ru`) | `s3.endpoint` |
| `CLOUDRU_S3_ACCESS_KEY` | ключ доступа Object Storage | `s3.access_key` |
| `CLOUDRU_S3_SECRET_KEY` | секрет Object Storage | `s3.secret_key` |
| `CLOUDRU_S3_REGION` | регион S3 (по умолчанию `ru-central-1`) | `s3.region` |

### MCP-сервер

| Переменная | Что задаёт |
|---|---|
| `MCP_BEARER_TOKEN` | токен, который клиенты `mcp --http` присылают в `Authorization: Bearer …`; без него HTTP-сервер не стартует (кроме `--auth none` на loopback). Только переменной — флага нет, чтобы токен не светился в `ps` |
| `MCP_HEALTHCHECK_URL` | адрес для `evo mcp healthcheck` (HEALTHCHECK Docker-образа); по умолчанию `http://127.0.0.1:8080/healthz` |

### Вывод

| Переменная | Что задаёт |
|---|---|
| `NO_COLOR` | если задана и не пуста — без цвета, как `--no-color` ([no-color.org](https://no-color.org)) |
| `TERM` | `TERM=dumb` — без цвета |
| `EVO_LANG` | язык сообщений CLI: по умолчанию русский, `EVO_LANG=en` (или `en_US` и т. п.) — английский. `LANG` и `LC_*` не учитываются. `evo mcp` всегда отвечает по-английски |

Переменные `CLOUDRU_*` и `MCP_BEARER_TOKEN` **не передаются** в дочерние
`kubectl` и `helm`.

Переменные установщика (`CLOUDRU_VM_VERSION`, `INSTALL_DIR`,
`CLOUDRU_VM_BASE_URL`) — в [install.md](install.md#linux-и-macos-installsh).

## Что хранится на машине

| Что | Где | Права |
|---|---|---|
| настройки профилей (проект, зона, умолчания) | `config.yaml` в каталоге конфигурации | `0600`, каталог `0700` |
| ключи профилей (Key ID, Key Secret, S3) | `credentials.yaml` там же | `0600` |
| кэш IAM-токена (на час, привязан к Key ID и секрету: со сменой секрета кэш не используется) | `token-<профиль>.json` в каталоге кэша | `0600` |
| настройки проекта (без секретов) | `./.evo.yaml` | `0644`, можно коммитить |
| состояние развёртываний (ID ВМ, IP, floating IP, порты) | `./.evo/state.json` | `0644` в каталоге `0700` |
| **приватный SSH-ключ к созданным ВМ** | `./.evo/id_ed25519` (+ `.pub`) | `0600`, каталог `0700` |
| ключи хостов ВМ из `deploy_apply` (свой `known_hosts`: команда `ssh` из ответа проверяет ключ хоста по нему) | `./.evo/known_hosts` | `0600` |
| планы MCP `deploy_plan` | `./.evo/plans/` | `0600`, каталог `0700` |
| задания `stack_*` (MCP) | `~/.evo/stack-jobs/` | `0600`, каталог `0700` |
| своя таблица цен (необязательно, создаёте вы) | `~/.evo/pricing.json` | |

Каталоги конфигурации и кэша:

| ОС | Конфигурация | Кэш токена |
|---|---|---|
| Linux | `~/.config/evo` (или `$XDG_CONFIG_HOME/evo`) | `~/.cache/evo` (`$XDG_CACHE_HOME`) |
| macOS | `~/Library/Application Support/evo` | `~/Library/Caches/evo` |
| Windows | `%AppData%\evo` | `%LocalAppData%\evo` |
| с `CLOUDRU_CONFIG_DIR=D` | `D` | `D/cache` |

Без `HOME` (в Windows — без `APPDATA`) и без `CLOUDRU_CONFIG_DIR` (бывает под
systemd, launchd, в контейнере) каталога конфигурации нет: `evo configure`
отказывает (`CONFIG_INVALID`), ключ берётся только из переменных окружения,
токен не кэшируется, задания `stack_*` не сохраняются. Путь относительно
текущего каталога evo не подставляет: там может быть репозиторий.

Профили и проекты, созданные под старым именем `cloudru-vm` (каталог
конфигурации `…/cloudru-vm`, `./.cloudru-vm/`, `./.cloudru-vm.yaml`), до v2.0
читаются — как именно, в [rename.md](rename.md).

`./` — каталог, из которого запущена команда (для MCP по stdio — рабочий
каталог, в котором клиент запускает сервер). SSH-ключ создаётся по одному на
каталог проекта при первом `deploy` после подтверждения (`deploy --dry-run`
и отказ без `--yes` ключа не создают). **`.evo/` не коммитьте**:
утёкший ключ — это доступ к вашим ВМ. Вместе с ключом в каталоге создаётся
`.evo/.gitignore` со строкой `*`, так что `git add .` его не берёт.

Как пишутся эти файлы:

- секреты и ключ — через временный файл, который создаётся сразу с правами
  `0600`, и `rename`: ни на миг не читаемы другими, а прерванная запись не
  оставляет половину файла;
- символическая ссылка на месте `.evo/`, `id_ed25519` или
  `id_ed25519.pub` (такое может прийти с чужим репозиторием) — ошибка, а не
  запись по ссылке: иначе ключ переписал бы, например, `~/.ssh/authorized_keys`
  или достался бы владельцу файла, на который ведёт ссылка. Удалите ссылку —
  ключ создастся заново. Так же — с жёсткой ссылкой (у файла больше одной
  ссылки): содержимое доступно по другому пути, это может быть чужой файл
  или чужой ключ. Свой ключ копируйте (`cp`), а не связывайте (`ln`);
- если каталог конфигурации открыт другим на запись, команды предупреждают:
  права `0600` у `credentials.yaml` не мешают подменить сам файл;
- значения секретов (`secrets[].value`) и содержимое объектов (`s3[].content`)
  из манифеста `stack_plan` лежат в задании, только пока шаг не выполнен;
  после выполнения шага (и после `stack_destroy`) в файле остаётся пометка
  `<redacted…>`, а путь секрета и ключ объекта — для удаления.

**Windows.** Права `0600`/`0700` там ничего не значат (`chmod` меняет только
атрибут «только чтение»), а новый файл по умолчанию наследует ACL каталога: в
папке из корня диска (`C:\work`) его читали бы все «Прошедшие проверку».
Поэтому `credentials.yaml`, `config.yaml`, кэш токена, `.evo\id_ed25519`,
задания `stack_*` и каталоги с ними создаются сразу (через `SECURITY_ATTRIBUTES`
у `CreateFile`/`CreateDirectory`) с собственным ACL без наследования: полный
доступ только у вас, SYSTEM и Администраторов — тот же набор, который OpenSSH
для Windows требует от `~\.ssh` и приватных ключей. Файлы, созданные внутри
`.evo\` (`state.json`, планы), наследуют ACL этого каталога.

Файлы и каталоги прежних версий: каталог `.evo\` (или `.cloudru-vm\`), открытый другим,
закрывается при первом обращении к ключу (как `chmod 700` на Unix), а если
`credentials.yaml`, его каталог или ключ доступны кому-то ещё, команды и
`doctor` предупреждают с готовой командой `icacls`. `credentials.yaml` и
`config.yaml` можно и просто пересоздать: `evo configure` переписывает
оба файла с новым ACL. Закрыть вручную:

```powershell
icacls "$env:APPDATA\evo\credentials.yaml" /inheritance:r /grant:r "$($env:USERNAME):F"
icacls .evo /inheritance:r /grant:r "$($env:USERNAME):(OI)(CI)F"
```

На FAT/exFAT (флешки) ACL нет вовсе — держите проекты на NTFS.

### Удалить всё

```sh
evo destroy                          # в каждом каталоге проекта: ВМ и floating IP
evo configure delete default         # профиль и его кэш токена (и другие профили)
rm -rf ./.evo ./.evo.yaml            # состояние и SSH-ключ проекта
rm -rf ~/.config/evo ~/.cache/evo ~/.evo   # Linux; пути других ОС — в таблице выше
# то же под старым именем, если остались (см. docs/rename.md):
rm -rf ./.cloudru-vm ./.cloudru-vm.yaml ~/.config/cloudru-vm ~/.cache/cloudru-vm ~/.cloudru-vm
```

Затем удалите ключ доступа в консоли (раздел «Ключи доступа» сервисного
аккаунта), если он больше не нужен. Старый файл `~/.cloudru-vm.yaml` (версии
до 1.0) больше не читается — удалите его, если остался.

## Ротация ключа

1. Создайте новый ключ у того же сервисного аккаунта ([раздел 2](#2-ключ-доступа)).
2. `evo configure` (или `--profile …`): введите новый Key ID и секрет;
   проект сохранится. Без терминала — та же команда с `--key-id` и
   `--secret-stdin`. Кэш старого токена не мешает: он привязан к Key ID.
3. `evo whoami` — новый ключ принят.
4. Обновите ключ везде, где он задан переменными: секреты CI, окружение
   MCP-сервера / контейнера.
5. Удалите старый ключ в консоли. Токены, выданные по нему, перестают
   обновляться, а живут не дольше часа.

Если ключ утёк — сначала удалите его в консоли, потом выполняйте шаги 1–4.
