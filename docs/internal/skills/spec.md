Статус: ТЗ для «1.3 — разработки», 24.10.2026. Автор — сессия «Продукт и
стратегия»; поручение владельца передано сессией «1.3 — релиз (2)», старт по

describe` сборки `main` на 24.10 и помечено **[сверить]**. Где документ
расходится с кодом, побеждает код; разработка правит текст скилла, а не
наоборот.

## 1. CJM: от установки evo до уборки

| Шаг пользователя | Что происходит сегодня (1.3.0-rc.3) | Место скиллов в 1.3.0 |
|---|---|---|
| Ставит evo, `evo configure`, `evo doctor` | как в `docs/guide.md` §2–3 | — |
| Подключает агента: `evo agent setup --client <X> --skill` | конфигурация MCP плюс встроенные правила (`docs/agent-skill.md`) в `.claude/skills/evo/SKILL.md` или раздел `AGENTS.md` / `GEMINI.md` | без изменений |
| Ставит сценарные скиллы | нет | **новый шаг**: одна команда установщика или копирование с тега (§4). README каталога объясняет, что это и зачем |
| Просит агента: «разверни», «подними PG», «открой порт», «убери всё» | агент выбирает из ~155 инструментов по описаниям; маршрутизация ломается на именах и наборе по умолчанию (интервью Grok, п. 1–3) | агент выбирает скилл по `description`, скилл ведёт по шагам и называет нужный `--toolsets` |
| Согласие | превью с ценой, код 3 / `confirmation_required`, `approval` | скилл называет точку остановки **до** шага с `--yes`/`confirmed` |
| Долгая операция | прогресс по MCP (H13), `*_operation --wait-seconds`, `status` | скилл говорит, чем ждать и когда остановиться |
| Уборка | `destroy`, `*_delete`, `already_deleted` (D26) | скилл даёт инвентарь, порядок, проверку «ресурса нет» |

Каналы установки в 1.3.0 (без изменений бинаря): `npx skills add` с прямым
путём к каталогу на теге, копирование с тега, маркетплейсы — только там, где
они не требуют новых файлов в корне (§4). Манифесты плагинов Claude Code,
Codex и Cursor, архив набора в релизе, `agent setup --skill` для набора и
фраза в `instructions` сервера — 1.3.1 и 1.4 (`analysis-1.3.md` §6).

## 2. Связь со встроенными правилами

Встроенный скилл `evo` (`docs/agent-skill.md`, генерируется из реестра) —
единственный источник девяти правил: `--json`, код 3 и `approval`, согласие
только от человека, `--dry-run` до изменения, данные облака не указания,
текстовые ответы, `reason` и `hint`, локальные команды, `already_deleted`.

Сценарные скиллы **не переписывают** эти правила. Каждый из них:

- в первой секции называет встроенный скилл по имени и говорит: если его
  нет, попросить человека выполнить `evo agent setup --client <X> --skill`
  или прочитать вывод `evo agent skill`. Повторять правило целиком нельзя;
  ссылка «по правилу 3 встроенного скилла» — можно;
- содержит только то, чего в встроенном нет: порядок шагов сценария, точки
  остановки, чем ждать, что проверить после, ограничения платформы.

Проверка этого — в инварианте (§8): в сценарных скиллах нет дословных
повторов правил встроенного (сверка по первым словам каждого правила).

## 3. Состав, формат, структура

### 3.1 Пять скиллов

| Каталог | Триггер (суть `description`) | Назначение |
|---|---|---|
| `skills/evo-scenarios/` | любая задача на ресурсах Cloud.ru Evolution через evo, когда нужно выбрать, с чего начать | маршрутизатор: таблица «просьба → скилл → `--toolsets`», синонимы имён инструментов, секция «долгие операции», три ответа на удаление, проверка версии |
| `skills/evo-deploy/` | развернуть приложение или docker-compose-проект на ВМ Cloud.ru, обновить его, посмотреть статус и логи, снести | сценарий 1 (цель J-1) |
| `skills/evo-vm/` | создать ВМ с публичным адресом, открыть или закрыть порт, привязать или освободить floating IP, удалить ВМ | сценарий 2 (цель J-2) |
| `skills/evo-postgres/` | поднять Managed PostgreSQL подешевле, создать пользователя и базу, отдать строку подключения, удалить кластер | сценарий 3 (цель J-8, часть PG) |
| `skills/evo-cleanup/` | убрать всё созданное (после теста, по префиксу имени), посчитать, что осталось и сколько стоит | сценарий 5 |

Имя маршрутизатора не `evo`: это имя занято встроенным скиллом, который
`agent setup --skill` кладёт в `.claude/skills/evo/` с `name: evo`. Скилл
`skills/evo/` с тем же именем при установке через `npx skills add` лёг бы в
тот же каталог: либо перезаписал бы встроенный, либо был бы перезаписан
следующим `agent setup`, либо продублировал бы правила (два источника одного
правила, §2). Рассмотрены три варианта (сверка с релизом 24.10):

- **(а) маршрутизатор под своим именем `evo-scenarios`** — только направляет
  к четырём сценариям и ссылается на правила встроенного, не повторяя их;
  встроенный ставится как раньше. **Принято.**
- (б) `skills/evo/SKILL.md` как копия вывода `evo agent skill` с тестом на
  совпадение, маршрутизация только в `description` сценариев — отклонено:
  маршрутизатора нет, а именно его отсутствие Grok назвал главной
  причиной промахов (интервью, п. 1–3, 13).
- (в) маршрутизация внутри встроенного `evo` — правка бинаря, условие 1;
  это путь 1.3.1 и 1.4, тогда `evo-scenarios` усохнет до таблицы сценариев.

**Непересечение описаний.** `description` маршрутизатора не должен
перехватывать то, что и так закрывает встроенный `evo` («any task on
Cloud.ru resources»), иначе агент грузит оба. Формулировка маршрутизатора
— про выбор сценария и набора инструментов: «Choose which evo scenario
skill and tool groups to use for a multi-step task on Cloud.ru Evolution
(deploy an app, a VM with ports, PostgreSQL, cleanup). Not the rules of
evo: those are in the built-in skill `evo`.» Инвариант §8 проверяет, что
в `description` маршрутизатора нет фразы встроенного «any task on Cloud.ru
resources» и что сценарные `description` называют свой сценарий, а не
«Cloud.ru» вообще.

Стек (цель J-3) в набор не входит: проверки его шагов переезжают на
планировщики в 1.4, до этого сценарий слишком зависит от оговорок W7 и
«Известных ограничений» (пароль ВМ шага `provision`). Диагностика только на
чтение — 1.4 вместе с предустановками `--toolsets`.

### 3.2 Формат

Спецификация Agent Skills (agentskills.io/specification):

```
skills/<name>/
├── SKILL.md            # обязательно
└── references/         # необязательно, грузится по ссылке
```

Frontmatter каждого `SKILL.md`:

```yaml
---
name: evo-deploy                       # = имя каталога; [a-z0-9-], до 64
description: <что делает и когда брать; ключевые слова просьб; до 1024>
license: Apache-2.0
metadata:
  evo-version: "1.3"                   # major.minor бинаря, под который написан
  evo-mode: human-in-the-loop          # все пять; read-only-варианты — 1.4
---
```

Правила текста:

- **Язык — английский**: читает агент; встроенный скилл английский; Р-6
  отложен (вопрос владельцу — §11).
- **Длина**: маршрутизатор до 100 строк, сценарий до 200, `description`
  одной строкой до 1024 символов. Таблицы длиннее 15 строк — в
  `references/`.
- **`description`** пишется под выбор агентом: что делает, когда брать,
  слова, которыми люди это просят, и когда **не** брать («bare VM without an
  app: use evo-vm, not evo-deploy»). Это главный элемент: по нему агент
  решает, грузить ли тело (прогрессивное раскрытие).
- Имена инструментов и команд — в обратных кавычках, точно как в реестре:
  это ключ инварианта §8.
- Нет указаний агенту ставить пакеты, менять настройки клиента или
  переходить в режим без вопросов. Нет внутренних сведений Cloud.ru, ID,
  адресов.

### 3.3 Шаблон сценарного скилла

Одинаковые секции во всех четырёх, в этом порядке:

1. **Use this skill when** — формулировки просьб; когда не брать и какой
   скилл брать вместо.
2. **Prerequisites** — встроенный скилл `evo` установлен (§2); `evo doctor
   --json` (`doctor`) без ошибок: ключ, проект, зона; нужный `--toolsets`.
3. **Procedure** — пронумерованные шаги, в каждом команда CLI и инструмент
   MCP (паритет D13/D14: одна строка на обе поверхности), что из ответа
   взять дальше (`plan_id`, `vm_id`, `operation_id`).
4. **Stop and ask** — где именно остановиться: что показать человеку
   (превью: что создаётся, цена, зона, группа безопасности), и только после
   его «да» повторить вызов с `confirmed=true` / `--yes`. Маркер-фраза
   обязательна (§8).
5. **Waiting** — чем ждать (`*_operation --wait-seconds`, прогресс MCP,
   `status`), что считать терминальным состоянием, после чего остановиться
   и спросить человека, а не продолжать опрос.
6. **If it fails or is interrupted** — таблица `reason` → что делать;
   первый шаг после обрыва — инвентарь, а не память.
7. **Cleanup** — что создал сценарий, чем удалить, как убедиться, что
   ресурса нет (ось 3 `CLAUDE.md` §6).
8. **Known platform limits** — пункты реестра расхождений одной строкой с
   номером (DB-21, DB-22, G1…), без внутренних сведений.
9. **Never** — три-пять запретов этого сценария.

## 5. Маршрутизатор `evo-scenarios`

Содержание (до 100 строк):

1. **Version check** — см. §4.
2. **Which skill** — таблица: просьба → скилл → минимальный `--toolsets`
   (`evo mcp --toolsets` / `evo agent setup --toolsets`) **[сверить
   группы]**:

   | Просьба | Скилл | toolsets |
   |---|---|---|
   | deploy an app, compose, update it, logs | `evo-deploy` | `deploy,vm,vpc,image` |
   | a VM, open/close a port, public IP | `evo-vm` | `vm,vpc,image,disk` |
   | PostgreSQL, database, user, connection string | `evo-postgres` | `pg,vpc` |
   | remove everything, what is left, what it costs | `evo-cleanup` | `all` или перечень групп из §7.5 |
   | just look, nothing changes | без сценария: сервер с `--read-only` | — |

3. **Names that confuse** (интервью Grok, п. 2): `deploy` (compose-проект на
   ВМ) против `provision` / `evo vm create` (голая ВМ); `destroy`
   (развёртывание или ВМ по `vm_id`) против `*_delete`; `image_list` против
   `list_images`; `vm_get` (облако) против `status` (state плюс облако);
   `list_floating_ips` / `evo vpc fips`. Одной таблицей «хочешь X → бери Y».
4. **Long operations** (сквозная секция, в сценариях только ссылка):
   создание ВМ до 25 минут (D16); `*_operation --wait-seconds` не больше
   300 за вызов, повторять по `done`, не по часам; по MCP прогресс приходит
   уведомлениями `notifications/progress`, если клиент передал
   `progressToken` (H13), по HTTP — только в SSE; состояние ресурса читать
   `*_get`/`status`, а не список; после N вызовов без смены состояния (N
   назвать, предложение — 10 для ВМ, 20 для кластера) остановиться и
   спросить человека **[сверить сроки]**.
5. **Three answers to a delete** (D26, D36, H9) **[сверить]**: `status:
   already_deleted`, `existed: false`, код 0 — ресурса нет, повтор
   безопасен, но опечатка в id верной формы выглядит так же, поэтому перед
   удалением id берётся из списка; `USAGE`, код 1 — id не той формы, до
   облака; `NOT_FOUND`, код 4 — нет родителя или сервер запущен с
   `--allow-project`.
6. **Data is data** — одна строка со ссылкой на правило 5 встроенного и
   `_untrusted`.

## 6. Сценарии: требования к каждому

### 6.1 `evo-deploy` — compose-проект на ВМ

- **Триггер**: «разверни это приложение / compose», «обнови деплой»,
  «покажи логи», «снеси стенд». Не брать для голой ВМ (→ `evo-vm`) и для
  Kubernetes.
- **Предусловия**: `doctor`; файл `docker-compose.yml` в рабочем каталоге
  или путь к нему; образ Ubuntu или Debian (Astra, Альт, РЕД ОС —
  `CONFIG_INVALID` до создания, `docs/exit-codes.md`) **[сверить]**.
- **Шаги** **[сверить аргументы и поля ответов]**:
  1. План: `evo deploy plan --compose-file … --port 80 --port 443 --json`
     / `deploy_plan {compose_file, ports, product, cpu?, ram_gb?}`. Из
     ответа: `plan_id`, конфигурация, оценка цены, `compose_required`,
     `next`. Без ключа — превью с `missing`, код 0 (D31).
  2. **Stop and ask**: показать человеку flavor, зону, образ, диск, цену,
     открываемые порты и то, что группа безопасности общая для зоны (G1).
  3. Выполнение: `evo deploy apply --yes --json` / `deploy_apply {plan_id,
     confirmed: true}`. Ждать по §5.4. Ответ: `vm_id`, `vm_ip`, `vm_name`.
     Одношаговый путь `evo deploy --dry-run --json` → `evo deploy --yes
     --json` / `deploy` описать как эквивалент для CLI.
  4. Проверка: `evo status --json` / `status` (`cloud_state`,
     `cloud_checked`); `evo logs --json` / `logs {service?, tail?}` —
     поле `_untrusted`.
  5. Обновление: повтор `deploy` с изменённым compose; `unchanged: true`
     без `force` — ничего не делает.
- **Отказы и обрыв**: `SSH_TIMEOUT` — ВМ есть, Docker не поднялся; `evo
  status`, затем решение человека: ждать, `logs` или `destroy`.
  `CONFIG_INVALID` (ОС без Docker) — ВМ остаётся, `destroy`. `AUTH_EXPIRED`
  посреди ожидания — повтор той же команды продолжает, не пересоздаёт
  (`.evo/state.json`) **[сверить]**. Ctrl-C на ожидании ВМ: вопрос «удалить
  ВМ?», без терминала — код 130, id в сообщении. Первый шаг после обрыва:
  `evo deploy list --json` / `list` и `status`, не память.
- **Уборка**: `evo destroy --yes --json` / `destroy {confirmed: true}`
  (`release_ip` по умолчанию true, закрывает правила портов развёртывания)
  **[сверить]**; проверка: `status` → нет развёртывания; `vm_get {vm_id}` →
  `NOT_FOUND`; повтор `destroy` → `already_deleted`. Несколько
  развёртываний в каталоге — `CONFIG_INVALID` со списком, удалять по
  `vm_id`.
- **Ограничения**: группа безопасности общая для зоны (G1; `open_ports`
  без `cidr` открывает из `0.0.0.0/0`); только Ubuntu/Debian; исходящий 22;
  FB130-1 (`fip_attach` с занятым адресом) — поведение rc.3 против 1.3.0
  **[сверить по CHANGELOG на теге]**.
- **Критерии приёмки**: агент с этим скиллом на тестовом compose проходит
  план → согласие → apply → status → logs → destroy без единого
  `confirmed`/`--yes` до показа превью; после `destroy` `vm_list` и
  `list_floating_ips` не содержат ресурсов сценария; число вызовов
  инструментов не больше заданного (предложение — 12) **[уточнить по
  догфуду]**.

### 6.2 `evo-vm` — ВМ с публичным адресом и портом

- **Триггер**: «создай ВМ», «открой порт 8080», «закрой порт», «дай ВМ
  публичный адрес», «удали ВМ». Не брать для приложения из compose
  (→ `evo-deploy`).
- **Предусловия**: `doctor`; образ по имени (`evo image list <запрос>`,
  `image_list`); зона из профиля или `region`.
- **Шаги** **[сверить]**:
  1. Превью: `evo vm create <имя> --image Ubuntu-24.04 --port 80 --dry-run
     --json` / `provision {name, image, ports}` без `confirmed`. Образ,
     недоступный проекту, — `NOT_FOUND` на превью. Подсети или группы в
     зоне нет — `CONFIG_INVALID` до вопроса (W5).
  2. **Stop and ask**: flavor (по умолчанию наименьший lowcost, не
     free-tier), цена, зона, публичный адрес, порты и источник `0.0.0.0/0`
     **и** что группа общая для зоны.
  3. `--yes` / `confirmed: true`; ждать по §5.4; ответ: `vm_id`, адрес,
     пароль для образов с паролем — **не повторять пароль в чате**, по
     HTTP он замаскирован (H7).
  4. Порты: `evo vpc open-ports --port 8080 --cidr <CIDR> --json` /
     `open_ports {security_group, ports, cidr?, protocol?}` — превью
     называет группу, протокол, источник и уже открытые порты (G13-23);
     скилл рекомендует указывать `cidr` и спрашивать человека отдельно,
     если источник `0.0.0.0/0`. Обратная операция: `evo vpc close-ports` /
     `close_ports` с теми же аргументами (D37); «правил нет» —
     `already_deleted` без вопроса.
  5. Адрес: `vm_get` → `public_ip`; `fip_attach {fip, vm}` только для
     свободного адреса; занятый — отказ до вопроса (FB130-1, **[сверить на
     теге]**); `release_floating_ip {id | ip_address}` отказывает адресу,
     занятому ВМ или шлюзом SNAT (D31).
- **Отказы и обрыв**: имя занято — отказ до создания; Ctrl-C — как в 6.1;
  после обрыва `vm_list` по имени.
- **Уборка**: `evo vm delete <id> --yes` / `destroy {vm_id, confirmed}` с
  `release_ip`; затем `close_ports` для открытых вручную портов (destroy
  закрывает только правила развёртывания **[сверить]**); проверка
  `vm_get` → `NOT_FOUND`, `list_floating_ips` без адреса.
- **Ограничения**: G1 (общая группа, в 1.4 `--source`); пароль ВМ в ответе
  создания (2.0 — только по запросу).
- **Критерии**: см. 6.1; дополнительно — ни одного `open_ports` без
  явного `cidr` в журнале прогона или с отдельным «да» человека на
  `0.0.0.0/0`.

### 6.3 `evo-postgres` — PostgreSQL подешевле с пользователем и базой

- **Триггер**: «подними PostgreSQL», «самый дешёвый PG», «создай базу и
  пользователя», «дай строку подключения», «удали кластер».
- **Предусловия**: `doctor`; подсеть (`list_subnets`), если не первая
  проекта.
- **Шаги** **[сверить]**:
  1. `evo pg versions --json` / `pg_versions`; `evo pg specs --version 17
     --json` / `pg_specs {version}` — выбрать наименьшую `standard` по cpu
     и memory; `min_storage_gb` — минимум хранилища (W6: меньше минимума
     отказ до вопроса).
  2. Превью: `evo pg create <имя> --specification-id … --dry-run --json` /
     `pg_create {name, specification_id | cpu+ram, storage_gb?, subnet_id?,
     instances: 1}`. Занятое имя — отказ до вопроса. Цена в превью:
     **[сверить, что превью `pg_create` называет цену или `tariff_url`
     (A5)]**.
  3. **Stop and ask**: конфигурация, хранилище, подсеть и зона, резервные
     копии (включены по умолчанию, после создания не изменить), цена.
  4. `--yes` / `confirmed`; ответ `operation_id` → `evo pg operation <id>
     --wait-seconds 300 --json` / `pg_operation {operation_id,
     wait_seconds: 300}` до `done: true`; затем `pg_get {id}` → `status`,
     `connection_string` **[сверить имена полей]**.
  5. Пользователь: `evo pg user-create <cluster> <name> --password-file -`
     / `pg_user_create {cluster_id, name, password}`. Пароль **берётся от
     человека или генерируется и передаётся ему вне чата**; evo его не
     возвращает; в CLI предпочитать `--password-file`. Скилл запрещает
     агенту печатать пароль в ответе.
  6. База: `evo pg db-create <cluster> <name> --owner <user>` /
     `pg_db_create {cluster_id, name, owner}` (занятое имя — отказ до
     вопроса, D28).
  7. Выдача: строка подключения без пароля, с пометкой, где пароль.
- **Отказы и обрыв**: после обрыва `pg_list` по имени, не повторный
  create; `creating` дольше ожидаемого — спросить человека; кластер в
  `FAILED` — см. ограничения.
- **Уборка**: `evo pg delete <id> --dry-run` — превью предупреждает, что
  удаляются данные и все резервные копии (G13-27); **Stop and ask**;
  `--yes` / `confirmed`; `pg_operation` до `done`; проверка `pg_get` →
  `NOT_FOUND` **[сверить: 404 или `already_deleted`]**; `pg_backups`
  удалённого кластера отвечает 400 (DB-22) — это не ошибка агента, копии
  не тарифицируются.
- **Ограничения**: DB-21 — кластер в `FAILED` через API не удалить, evo
  отвечает ошибкой платформы; путь — поддержка или консоль; агент не
  повторяет delete и не считает «успехом» пустой ответ. DB-22 — список
  копий после удаления 400. Пароль пользователя — только через человека.
- **Критерии**: кластер создан на минимальной конфигурации версии по
  умолчанию; пароль не появился ни в одном ответе агента; после удаления
  `pg_list` пуст; `confirmed` только после превью с ценой.

### 6.4 `evo-cleanup` — убрать всё созданное

- **Триггер**: «убери всё после теста», «что осталось и сколько стоит»,
  «удали всё с префиксом X». Не брать как первый шаг другого сценария:
  там своя секция Cleanup.
- **Предусловия**: `doctor`; префикс имён от человека (единственный
  надёжный ключ инвентаря в 1.3: тегов нет, учёт есть только у `deploy
  list` и `stack_status`); набор инструментов `all` или перечень групп.
- **Шаги** **[сверить]**:
  1. Инвентарь: в каждом каталоге с `.evo/` — `status`/`list`; затем
     списки: `vm_list`, `disk_list`, `list_floating_ips`, `snat_list`,
     `vpc_list` (+ `vpc_routes`), `lb_list`, `tg_list`, `dns_zones`,
     `pg_list`, `kafka_list`, `redis_list`, `k8s_list`, `s3_buckets`,
     `secret_list`, `cert_list`, `ar_list`, `ca_list`, `image_list`
     собственных образов. Фильтр по префиксу; ресурсы без префикса —
     отдельным списком «не трогаю без вашего слова».
  2. Стоимость: `evo billing consumption --start <дата> --end <дата>` /
     `billing_consumption` за период теста; диски без ВМ и адреса без ВМ —
     помечать как «платные без пользы» (CMP-11 **[сверить номер]**).
  3. **Stop and ask**: таблица «что удалю, в каком порядке, что останется».
  4. Порядок зависимостей: развёртывания (`destroy`) → балансировщики
     (`lb_delete`) → группы целей (`tg_delete`) → записи DNS → зоны →
     базы и пользователи PG → кластеры (`pg_delete`, `kafka_delete`,
     `redis_delete`, `k8s_delete`) → ВМ (`destroy {vm_id}`) → диски →
     floating IP (`release_floating_ip`) → маршруты → VPC → SNAT →
     объекты S3 → бакеты → секреты, сертификаты, реестры, приложения,
     образы. Таблица «что чем удаляется» — из `createdIDs`
     (`internal/tools/created.go`), в `references/delete-map.md`
     **[сгенерировать или переписать вручную — вопрос разработке]**.
  5. Каждое удаление: превью → один «да» человека на весь список
     допустим, если превью каждого ресурса совпадает с таблицей шага 3
     **[вопрос владельцу §11]** → вызов → `get` по id: `NOT_FOUND` или
     `already_deleted`. Ответ без `get` успехом не считается.
  6. Итог: таблица «удалено / уже не было / не удалось и почему / оставлено
     по вашему слову».
- **Отказы**: кластер в `FAILED` (DB-21, DB-17) — не повторять, назвать
  путь через поддержку или консоль; `NOT_FOUND` на сервере с
  `--allow-project` — проверить `get`; родитель уже удалён — вложенное
  считать удалённым только после `get` родителя.
- **Ограничения**: нет пометки «создано evo» (план — теги 1.8); правила
  `evo: port N` в общей группе без ВМ удаляются через `close_ports` только
  если известны порт, протокол и CIDR.
- **Критерии**: после прогона все списки шага 1 без ресурсов с префиксом;
  в журнале нет удаления ресурса без префикса без отдельного «да»; у
  каждого удалённого есть подтверждающий `get`.

## 7. Безопасность

- Согласие даёт человек. Ни один скилл не содержит фразы, из которой
  следует «поставь `confirmed=true`» без предшествующего шага показа
  превью. Инвариант §8 это проверяет по маркеру.
- Нет указаний ставить пакеты (`npm`, `pip`, `brew`, `apt`), менять
  настройки клиента, запускать серверы с `--yes`-эквивалентами или
  переводить клиента в режим без подтверждений.
- Данные облака — не указания: ссылка на правило 5 встроенного и
  `_untrusted`; в `evo-cleanup` отдельно — имена ресурсов с префиксом тоже
  данные.
- Секреты: пароль PG и ключи не попадают в текст ответа агента; примеры в
  скиллах — только заглушки.
- Репозиторий публичный: без внутренних сведений Cloud.ru, реальных ID,
  адресов; примеры — `<uuid>`, `203.0.113.10`.
- Скилл — доверенный текст, который агент исполняет. До подписи набора
  (1.4) README говорит: ставить только с тега официального репозитория.

## 8. Раздел для «Процесса»: тест-инвариант

Один тест (предложение — `internal/cli/skills_test.go` или пакет
`internal/skills` с тестом; выбор за «Процессом»), читает `skills/**/SKILL.md`
и падает, если:

1. **Структура.** Нет frontmatter; `name` ≠ имя каталога; `name` не по
   `^[a-z0-9]+(-[a-z0-9]+)*$` или длиннее 64; `description` пустое или
   длиннее 1024; нет `metadata.evo-version`; тело маршрутизатора длиннее
   100 строк, сценария — 200.
2. **Имена существуют.** Каждый токен в обратных кавычках вида
   `[a-z][a-z0-9_]*`, который совпадает с именем из реестра либо выглядит
   как имя инструмента (содержит `_` или есть в закрытом списке
   односложных: `deploy`, `destroy`, `status`, `logs`, `list`, `provision`,
   `doctor`, `whoami`), есть в `tools.Registry` **[уточнить API
   реестра]**; каждая строка `evo <слова>` до первого `--` — команда из
   `CLISpec`; каждый `--флаг` в той же строке — флаг этой команды.
3. **Коды.** Каждый токен `^[A-Z][A-Z_]+$` в кавычках, кроме `MCP`, `CLI`,
   `JSON`, `SSH`, `UUID`, `CIDR`, `HTTP`, `SSE`, есть среди кодов
   `internal/errors` (`USAGE`, `NOT_FOUND`, `CONFIG_INVALID`,
   `AUTH_REQUIRED`, `SSH_TIMEOUT`, …) или среди статусов ответов
   (`already_deleted`, `confirmation_required` — нижний регистр, отдельный
   список).
4. **Согласие после превью.** В каждом сценарном `SKILL.md` первая строка,
   содержащая `confirmed=true`, `confirmed: true` или `--yes`, стоит
   **после** строки с маркером `Stop and ask:` (точная фраза, оговорена в
   §3.3), и в тексте нет фраз из запретного списка: `confirmed=true` в одной
   строке с `always`, `immediately`, `without asking`; `--yes` в одной
   строке с `always`.
5. **Нет дублей встроенного.** Ни одна строка сценарного скилла не
   начинается с первых пяти слов любого из девяти правил
   `docs/agent-skill.md` (сверка по сгенерированному тексту, не по файлу).
6. **Нет запрещённого.** Нет `npm install`, `pip install`, `brew install`,
   `apt install`, `apt-get`, `curl … | sh`; нет строк вида UUID
   (`[0-9a-f]{8}-…`), IPv4 вне `203.0.113.0/24` и `198.51.100.0/24`;
   нет `CLOUDRU_SECRET=` со значением.
7. **Версия.** `metadata.evo-version` одинакова во всех пяти и равна
   константе в тесте, которую релиз меняет при смене minor (строка в
   `docs/RELEASING.md`, шаг тега) **[согласовать с релизом]**.
8. **Корень.** `internal/repolayout`: `skills` в `rootDirs`; внутри
   `skills/` только каталоги с `SKILL.md`, `README.md` и `references/*.md`.

Внешний валидатор `skills-ref validate` (Node) — по желанию в CI,
инвариант от него не зависит.

Прогон сценариев в мире паритета (вызовы из `Procedure` против фейков) —
не в этом PR: нужен парсер шагов. Бэклог «Процесса» на 1.4.

## 10. Раздел для догфуда: со скиллами и без

Цель — измерить, что даёт набор, а не только собрать отзывы. Базовая
линия — волна 3 на стабильном 1.3.0 без набора (решение владельца 24.10),
прогон с набором — следующая волна или вторая половина той же, если
владелец решит иначе.

Дизайн: одни и те же задачи своими словами (четыре сценария §6 плюс «только
посмотри»), один тестовый проект, одинаковые клиенты (Claude Code и Cursor
обязательно, остальные по возможности), половина участников с набором,
половина без; затем смена. Участник фиксирует в чек-ине (`checkin.yml`,
добавить поле «со скиллами / без» **[«Процесс»]**).

| Метрика | Как считать | Источник |
|---|---|---|
| Успех задачи | задача доведена до критерия приёмки §6 без вмешательства человека сверх согласий | чек-ин |
| Вызовов инструментов | число вызовов до результата | журнал клиента |
| Нарушения согласия | `confirmed=true` / `--yes` без показа превью человеку; согласие, поставленное агентом самому себе | журнал клиента; у агентов атаки — `grok-consents.jsonl` |
| Полнота уборки | списки §6.4 после прогона: ресурсы с префиксом | `evo … list`, чек-ин «остались ли ресурсы» |
| Пароли и секреты в чате | строки пароля PG в ответах агента | журнал клиента |
| Ошибки маршрутизации | первый вызов не из нужного сценария; «нет инструмента» для того, что есть | журнал клиента |

Порог для решения «набор идёт в 1.3.1 как основной путь»: нарушений
согласия с набором не больше, чем без; полнота уборки выше; число вызовов
ниже. Иначе набор дорабатывается по журналам до 1.4.

## 11. Вопросы владельцу

1. **Имя маршрутизатора**: `evo-scenarios` (вариант (а) §3.1, согласован
   с релизом) или другое имя той же роли.
2. **Язык**: английский для всех пяти (предложение). Русская версия —
   отдельный набор с теми же тестами, когда решится Р-6.
3. **Согласие в `evo-cleanup`**: одно «да» на показанный список или «да» на
   каждый ресурс. Предложение — одно на список при совпадении превью с
   таблицей, иначе отдельное.
4. **Источник портов в `evo-vm`**: рекомендовать агенту всегда спрашивать
   `cidr`, или допускать `0.0.0.0/0` по умолчанию с отдельным «да».
   Предложение — спрашивать.
5. **Ouroboros**: какой из трёх проектов поддерживает Cloud.ru; от этого
   зависит строка README.
6. **Пороги** в критериях (число вызовов, N опросов до остановки): принять
   предложенные как стартовые и уточнить по догфуду.
