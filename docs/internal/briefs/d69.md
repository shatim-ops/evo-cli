## 1. Что есть сейчас (факты по коду)

| Инструмент | Сколько держит вызов MCP | Что при отмене |
|---|---|---|
| `provision` | ожидание ВМ до `VMPollTimeout` (25 мин, D16), затем привязка FIP (до 12 опросов) и порты (`tools.go`, `provisionVM`) | `VM_PROVISION_FAILED`: `ctx.Err()` вставлен через `%v`, отмены в цепочке нет; `vm_id` и пароль в ответе есть (`leftFields`) |
| `deploy_apply` | то же через `deployplan.ApplyWithTimeout`; возобновление по тому же `plan_id` уже есть | `API_UNREACHABLE` (`errResult` без полей): ни `vm_id`, ни `plan_id`, ни пароля — **пароль теряется** (`finishApply.interrupted` не несёт `Password`) |
| `deploy` (MCP) | весь `engine.Deploy`: ВМ, SSH, Docker, compose — минуты | `API_UNREACHABLE` (`waitForSSH`) |
| `stack_apply` | шаг ВМ синхронно зовёт `provision` через `callTool` (`stepOf`) | шаг помечается `Interrupted`, следующий crank подхватывает ВМ |
| `pg_create`, `k8s_create`, `k8s_add_nodepool` | **не ждут**: `creating` + `operation_id` сразу | — |
| `*_operation` с `wait_seconds` | до 300 с | `API_UNREACHABLE` |
| `dns_zone_delete` | ограниченное ожидание (D66) | `errResult` без `id`, `visibility`, `operation_id` (FB160-14) |
| `k8s_helm` | до 9 мин | **нет в D69 и в строке плана** — вопрос ниже, п. 7 |

Корень `API_UNREACHABLE` при отмене — **факт**: `unreachable()` в
`internal/tools/errreason.go` считает `context.Canceled` сетевой ошибкой, а
`uncodedHint` добавляет к ней «проверьте сеть». CLI при Ctrl-C отвечает
`INTERRUPTED`/130 мимо ответа инструмента: `internal/cli/main.go` оборачивает
ошибку в `context.Canceled`.

## 2. Одна точка: бюджет ожидания вызова (предложение)

- `Registry.SetCallBudget(d)` — политика сервера, как `SetReadOnly` и
  `SetProjectBound`. `evo mcp` ставит её всегда (`mcp.New`), значение одно:
  `tools.MCPCallBudget = 45 * time.Second`. CLI собирает свой реестр без
  бюджета, поэтому ждёт, как раньше. Это и есть различие поверхностей **H14**.
- Отсчёт идёт от входа во **внешний** вызов: метка времени в `ctx` ставится в
  `outer` (рядом с `journaled`), если её ещё нет. Шаги стека (`callTool`)
  наследуют метку внешнего `stack_apply`, поэтому crank стека тоже укладывается
  в предел.
- `s.waitBudget(ctx, args) (rest time.Duration, capped bool)` — единственное
  место, где решается, сколько ждать:
  - `wait=false` → 0 на обеих поверхностях: ответ сразу после того, как облако
    приняло создание. В CLI это флаг `--wait=false`; нужен ли алиас
    `--no-wait`, решается по механизму `CLISpec`;
  - `wait=true` → без предела («обратное по запросу» D69): клиент сам поднял
    тайм-аут (`MCP_TOOL_TIMEOUT`);
  - без `wait` → остаток бюджета реестра (MCP) или без предела (CLI).
- Время — `time.Now` (решение по стенке, не значение ответа). `elapsed_sec` в
  ответе — через `internal/clock`, как сейчас (§5, `TestWallClockReadsDeclared`).
- Бюджет не превращается в отмену `ctx`: ожидание выходит по своему таймеру,
  и ресурс продолжает создаваться. Отмена — только от клиента.

## 3. Ответ, когда бюджет кончился

Это не ошибка (`isError=false`, код CLI 0):

```json
{"status": "creating", "vm_id": "…", "vm_status": "creating", "plan_id": "…",
 "password": "… (один раз)", "elapsed_sec": 44,
 "next": "Call deploy_apply again with plan_id … and confirmed=true to wait and finish (public IP, ports, SSH); vm_get vm_id=… shows the state."}
```

- `operation_id` — только там, где его даёт платформа. **Факт:** создание ВМ
  compute v1.1 операции не возвращает (`provision.VM`), поэтому у ВМ его нет, и
  ответ так и говорит. Текст D69 правится: «`operation_id`, где его даёт
  платформа; иначе id ресурса и состояние».
- Пароль — в первом ответе, где ВМ уже есть: при `creating`, при отмене и при
  успехе. Повтор, который подхватывает ВМ, пароля не знает и говорит это.
- Ход операции (ось 2): `vm_status` — последнее прочитанное состояние, а не
  «прошло N с».

## 5. «Миграция» (CHANGELOG 1.7, ломающее для MCP)

- Долгий изменяющий вызов MCP без `wait` отвечает не позже ~45 с. Ресурс ещё
  создаётся: `status: creating`, id, состояние, пароль, `next`. Раньше вызов
  ждал до 25 мин. Чтобы ждать, как раньше, — `wait: true` и тайм-аут клиента
  (`MCP_TOOL_TIMEOUT`).
- Отмена вызова (клиент ушёл, `notifications/cancelled`, остановка сервера)
  отвечает `reason: INTERRUPTED` с id созданного. Раньше было `API_UNREACHABLE`
  или `VM_PROVISION_FAILED`. Код CLI при Ctrl-C не меняется (130).
- CLI: умолчание прежнее; новый флаг `--wait=false`.
- Строка `docs/RELEASING.md` (смена `reason` — ломающее) покрыта «да»
  владельца по #597, п. 47.

## 6. Чего разработка ждёт от «Процесса · 1.7»

1. Инвариант «ни один вызов MCP не дольше предела»: мир, где ВМ, операция или
   шаг стека не кончаются, и каждый изменяющий инструмент реестра под
   `SetCallBudget(малый)` отвечает в пределах бюджета с запасом. Сначала
   красный, с перечнем инструментов сверх предела и сроком «Closes by 1.7»
   (#717, очередь, п. 3); разработка сокращает перечень своими PR.
2. Инвариант паритета отмены: отменённый вызов любого инструмента отвечает
   `INTERRUPTED` на обеих поверхностях, и если ресурс создан — с его id
   (бэклог процесса, п. 2 (1.7); #704).
3. Инвариант «пароль не теряется»: в каждом ответе, где ВМ с сгенерированным
   паролем уже создана (успех, `creating`, отмена, срок), пароль есть ровно
   один раз; по HTTP его маскирует H7.
4. Строка H14 в `HTTPRestrictions` с пометкой «и по stdio» (как H9 и H11) и
   сверка `TestHTTPPolicy_ClosedList`. Разработка добавляет строку в своём PR,
   если «Процесс» не против, что таблица HTTP несёт правило обеих поверхностей.
5. Бриф агентного прогона 1.7: пределы клиентов, кроме Claude Code
   (**гипотеза** #717: 45 с подобраны под 60 с Claude Code).

## 7. Открытые вопросы — «релизу», при необходимости владельцу

1. **`k8s_helm` (до 9 мин) и `k8s_kubectl` (до 90 с).** Это изменяющие вызовы
   дольше предела, но в строке D69 их нет. Предложение: в инвариант «Процесса»
   их внести, а `k8s_helm` получает тот же бюджет и ответ «идёт»
   (`helm status`) отдельной строкой плана. «Релиз» передал вопрос владельцу
   31.10; ответа пока нет.
2. **`operation_id` у ВМ.** Платформа его не даёт. Принято «релизом» 31.10:
   «`operation_id`, где его даёт платформа; иначе id ресурса и состояние» —
   уточнение формулировки в PR решения D69, строкой в описании PR.
3. **Хвост после запуска ВМ.** У `deploy_apply` привязка FIP (до 12 опросов)
   и добавление ключей пользователя по SSH идут после `running` и могут
   перевалить за 45 с. В PR 1 они остаются: они ограничены и короче ожидания
   ВМ. Если «Процесс» хочет строгий предел, они тоже уходят под бюджет и в
   повтор.
