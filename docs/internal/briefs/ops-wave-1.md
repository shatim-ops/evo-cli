## 1. Общие правила волны — для каждой операции

Правила не зависят от вида ресурса; раздел операции называет только свои
таблицы и отступления, отступление — с причиной.

- **П1. Одна точка действия.** Операции над одним запросом платформы — одна
  таблица действий, один метод клиента и один планировщик; инструменты —
  записи реестра над ними. Частных случаев по имени инструмента нет (§2).
- **П2. Автомат состояний.** У действия объявлены исходное, переходное и
  целевое состояния ресурса. Планировщик читает ресурс до вопроса и решает
  по таблице «состояние → ответ»; таблица — в разделе операции, и на каждую
  её строку есть мир.
- **П3. Повтор.** Цель уже достигнута — `already_<итог>`, код 0, без вопроса
  и без записи (класс D26, D81). Ресурс в переходном состоянии этого же
  действия — вызов продолжает ждать без вопроса и без записи: прерванная
  операция продолжается (§1). Действие, у которого каждая отправка — новое
  изменение (перезагрузка), повтора-успеха не имеет и говорит это в
  описании.
- **П4. Отказ до вопроса.** Всё, что видно чтением: ресурса нет — отказ
  «не найден», код 4 (опечатка в id — не успех); состояние, из которого
  действие заведомо невозможно, — `USAGE`, код 1, с состоянием и чтением
  ресурса как следующим шагом; подсказка не называет удаление шагом —
  удалять или нет, решает человек; чужое переходное состояние — ожидание до 30 с тем же механизмом,
  что у дисков (D53), обобщённым, а не скопированным. Состояние, исход
  которого неизвестен, — не отказ: превью называет его и неизвестность.
- **П5. Ход.** После отправки evo читает состояние ресурса и называет его в
  ходе одинаково в CLI и MCP (`progressOf`). Итог — `status`, id, имя,
  `state`, `elapsed_sec` (`internal/clock`). Предел вызова MCP (D69) до
  целевого состояния — не ошибка: `status` — переходное состояние и
  следующий шаг «тот же вызов» (`nextStep`); повтор идёт по П3. У повторов
  есть конец: предел ожидания операции считается от `StartedAt` намерения
  согласованного вызова (D92); за ним ответ называет состояние и срок и идёт
  без `next_tool` — «повтор не поможет, решает человек». Нет своего
  намерения (переход начат не этим evo) — одно ожидание в пределах вызова,
  затем состояние без шага повтора. Значение предела — в разделе операции,
  из двух прогонов пробы. Ресурс ушёл
  из переходного состояния не в целевое — `API_ERROR`, код 5, с состоянием.
  Где платформа даёт id операции — ход читается ею (`operationReads`), где
  не даёт — чтением ресурса; раздел операции называет, что из двух.
- **П6. Отказ платформы после согласия.** evo перечитывает ресурс: цель
  достигнута или ресурс идёт к ней — успех или ход по П5; ресурса нет —
  «не найден»; иначе `API_ERROR`, код 5, с состоянием ресурса. Причина
  отказа — одним машинным полем `details.cause`, той же формы, что
  `"quota"` (Вп-8): значение evo (`"state"`), а код причины платформы —
  рядом, `details.platform_code`, недоверенным (`untrustedFields`). Отказ, который повтор не снимет (запрет
  изменений в зоне, отказ из состояния с неизвестным исходом), — без
  `next_tool`, с путём «консоль или поддержка». Нехватка прав ключа (`403`)
  — существующий разбор; права ключа агента ради операции не расширяются.
- **П7. Согласие и политика сервера.** Обработчик — `gated` (D35), каждый
  вызов требует согласия; намерение пишется до отправки (D92, `intended`);
  `--read-only` отказывает; `--allow-project` и проект в превью —
  объявлениями (`project_bound.go`, механизм блока 0в). Необратимое и
  удаляющее — в `destructiveTools` с необратимостью в превью.
- **П8. Превью и цена.** Превью называет действие, ресурс (id, имя и поля,
  по которым человек узнаёт ресурс), текущее состояние и всё, что evo шлёт;
  имена из облака — недоверенные (`untrustedFields`). Цена — число только
  после пробы цены или со ссылкой на тариф; иначе «цена неизвестна, ресурс
  платный».
- **П9. Опись и тесты.** Запрос и поля тела — в `scripts/api-contract.json`
  в том же PR (Н2). Тесты до кода: паритет, мир на каждую строку таблицы
  состояний, повтор (Н1), ход и предел MCP (Н3), матрица сбоев на запрос
  (обрыв до и после отправки, `429`, `5xx`, отказ при достигнутой цели,
  `403`), превью называет каждое поле.
- **П10. Бюджет.** Рост `tools/list` — замером в описании PR; предел —
  `internal/mcp/limits_test.go`.

## 2. Действие над ВМ

### 2.1. Что даёт платформа (факт, спецификация)

Источник — OpenAPI Compute со страницы
`cloud.ru/docs/virtual-machines/ug/topics/api-ref` (чтение 12.11.2026,
OpenAPI 3.1.0; файл в репозитории не хранится, `scripts/cloudru-specs.py`).

| Что | Спецификация |
|---|---|
| Запрос | `POST /api/v1/vms/{vm_id}/set-power`, тело `{"state": "<команда>"}`, других полей нет (`additionalProperties: false`) |
| Команды | `power_on`, `power_off`, `reboot` |
| Успех | `204` без тела: id операции нет |
| Отказ | `422` на три случая сразу: ВМ не найдена (пример кода `bad_vm_id`), «ВМ с текущим статусом не может быть изменена», «изменения в зоне запрещены»; `404` и `409` не объявлены |
| Состояния ВМ | `running`, `stopped`, `starting`, `stopping`, `rebooting`, `creating`, `updating`, `deleting`, `error`, `error_creating`, `error_deleting` |
| Чтение | `GET /api/v1/vms/{vm_id}` — уже в описи; `404` объявлен |

Следствия (факт): ход операции читается только состоянием ВМ — операции с
id нет; «не найдена» и «не в том состоянии» платформа отдаёт одним кодом,
различие — в поле `code` тела.

Не в описи `scripts/api-contract.json` (факт): `set-power` целиком; у
карточки ВМ объявлены только три состояния из одиннадцати.

### 2.2. Таблица действий (П1, П2)

**Предложение.** Три инструмента — `vm_start`, `vm_stop`, `vm_reboot`
(имена — решение владельца 11.11) — три записи реестра на одном
планировщике и одной таблице действий; частных случаев по имени
инструмента нет (§2).

| Действие | Команда | Исходное | Переходное | Целевое | Повтор |
|---|---|---|---|---|---|
| `vm_start` | `power_on` | `stopped` | `starting` | `running` | `already_running` |
| `vm_stop` | `power_off` | `running` | `stopping` | `stopped` | `already_stopped` |
| `vm_reboot` | `reboot` | `running` | `rebooting` | `running` | повтора-успеха нет: каждая перезагрузка — действие |

- Клиент: один метод `CloudAPI` — «задать питание ВМ» — в
  `internal/provision`; оба фейка `CloudAPI` получают автомат состояний ВМ
  по этой таблице (правка общего мира паритета — называется в описании PR).
- Ход (П5) — чтением ВМ (`vm_get`): id операции платформа не даёт.

### 2.3. Аргументы и команда (паритет, §1)

- `vm_id` или `name` — как у `vm_get` и `destroy` (`requiredOneOf`, отказ
  «не оба»); `vm_id` — UUID по схеме (D36). Команда — `evo vm start
  <vm_id|имя>`, `evo vm stop`, `evo vm reboot`; `--yes`, `--json` — общие.
- Имя ВМ в проекте уникально (**факт**: спецификация Compute называет `vm`
  среди типов с уникальным именем в проекте; повторное создание с тем же
  именем платформа отвергает `409` — `internal/provision/findvm.go`,
  `IsNameTaken`, вживую 2 из 2). Защитой остаётся проверка в общей точке
  разрешения имени: под именем две ВМ и больше — `USAGE`, код 1, до вопроса,
  с id каждой, действие ВМ само не выбирает (`resolveVM` сейчас берёт первое
  совпадение, `tools_disk.go:29`). Строгость — одним объявлением «какие
  инструменты строгие» в этой функции, не веткой по имени; для операций
  волны — сразу, ответ выпущенных инструментов над той же точкой не
  меняется (смена — ломающее, отдельным решением).
- Проект ВМ для `--allow-project` — вид `kindVM`, как у `disk_attach` (П7).
- Группа инструментов — `vm`; рост `tools/list` — три описания (П10).

### 2.4. Отказы и ошибки (П4, П6)

Новые инструменты: ломающего нет. Коды — существующие:

| Случай | Когда | Ответ |
|---|---|---|
| Аргументы не по схеме, оба `vm_id` и `name`, пустая строка | до облака | `USAGE`, код 1 |
| ВМ не найдена (чтение до вопроса) | до вопроса | `VM_NOT_FOUND`, код 4 — опечатка в id не успех (ось 3) |
| ВМ в состоянии, из которого действие невозможно | до вопроса | `USAGE`, код 1, с состоянием и следующим шагом — как у диска (D53) |
| Ключу не хватает прав (`403`) | после согласия | существующий разбор `403`; права ключа агента ради операции не расширяются |
| `422` после согласия | после согласия | evo перечитывает ВМ: цель достигнута или идёт к ней — успех или ход; ВМ нет — `VM_NOT_FOUND`; иначе `API_ERROR`, код 5, с состоянием ВМ |
| Отказ по квоте | — | не ожидается у `vm_start` (**гипотеза**: остановленная ВМ держит квоту; проверяет Г-10); если платформа так отказывает — `details.cause: "quota"` (Вп-8) |

## 3. `vm_start` — эталон

Запускает остановленную ВМ. Платное: после запуска ВМ снова тарифицируется
по своей конфигурации (**гипотеза** о том, что остановленная ВМ
тарифицируется иначе, — Г-20, Г-21). Не разрушительное: в
`destructiveTools` не входит.

### 3.1. Ось 1 — выполнимость до согласия

Планировщик читает ВМ (`GET /vms/{id}`; по имени — `resolveVM`) и решает по
состоянию:

| Состояние ВМ | Ответ | Вопрос | Запись |
|---|---|---|---|
| `stopped` | превью | да | после «да» |
| `running` | `status: already_running`, код 0 | нет | нет |
| `starting` | ждёт `running` в пределах вызова; ход и итог — как после своей команды (прерванная операция продолжается, §1) | нет | нет |
| `stopping`, `rebooting`, `creating`, `updating` | ждёт устоявшегося состояния до 30 с (как D53), затем решает по нему; не устоялось — `USAGE` с состоянием и «повторите вызов» | по итогу | по итогу |
| `deleting`, `error_deleting`, `error_creating` | `USAGE`: ВМ удаляется или не создана, запускать нечего; следующий шаг — `vm_get`; удаление подсказка не называет | нет | нет |
| `error` | превью с предупреждением «ВМ в состоянии error; примет ли платформа запуск — неизвестно» | да | после «да» |
| нет ВМ | `VM_NOT_FOUND`, код 4 | нет | нет |
| незнакомое состояние | превью с названным состоянием — решает платформа (как у диска до D53) | да | после «да» |

**Вопрос «Риску»: запуск из `error`.** Факта нет, и пробой его не получить
— состояние не создаётся по заказу.

| Вариант | Что видит вызывающий | За | Против |
|---|---|---|---|
| А (умолчание) | превью с предупреждением «исход неизвестен»; отказ платформы после «да» — по строке `422` раздела 2.4 | запуск из `error` — возможный путь восстановления; отказывать до вопроса можно только в заведомо невыполнимом (§4) | согласие спрашивается на вызов, который может не пройти |
| Б | `USAGE` до вопроса: «ВМ в состоянии error, запуск не выполняется; путь — `vm_get`, консоль, поддержка» | вопроса на сомнительный вызов нет | evo закрывает путь, который платформа, возможно, даёт; обход — тот же ключ мимо evo |

**Исход (заключение «Риска» 111): вариант А.** Условия: отказ платформы
после «да» из `error` — ответ без `next_tool`, «повтор не поможет; консоль
или поддержка» (П6); первое живое наблюдение — в `evo-internal/runs/` и
обратно в эту таблицу.

### 3.2. Ось 2 — честный ход

- После команды evo читает состояние ВМ и сообщает его в ходе: «ВМ
  <имя>: starting, N с» — тем же механизмом хода, что у ожидания диска
  (`progressOf`), одинаково в CLI и MCP.
- Итог: `status: started`, `vm_id`, `name`, `state: running`, `public_ip`
  (если есть), `elapsed_sec`
  (время — `internal/clock`).
- Предел вызова MCP (D69, 45 с) достигнут, ВМ ещё `starting`: ответ не
  ошибка — `status: starting`, `state`, `elapsed_sec` и следующий шаг
  «тот же вызов» с теми же аргументами (`nextStep`); повтор попадает в
  строку `starting` таблицы 3.1 и ждёт без записи и вопроса.
- **Остаток по условию У1 (не сделано в PR `vm_start`).** Повтор не знает,
  что запуск начал он сам: намерение D92 закрывается, когда вызов получил
  ответ, в том числе незавершённый. Поэтому повтор, заставший `starting`,
  ждёт один предел вызова и отвечает состоянием со следующим шагом-чтением
  (`next_tool: vm_get`), а не повтором, — как на чужой переход; круга
  нет, но и «свой» запуск дольше двух пределов вызова
  агент дальше ведёт чтением `vm_get`. Предел от `StartedAt` намерения
  требует, чтобы общий слой намерений держал запись при ответе с
  `next_tool` того же инструмента, — правка общего файла `intent.go`,
  отдельной строкой плана; значение предела — после Г-10. В CLI предел ожидания — продовая
  константа; значение — после Г-10 (**гипотеза**: запуск занимает меньше
  минуты).
- ВМ ушла из `starting` не в `running` (`error`, `stopped`): `API_ERROR`,
  код 5, с состоянием — не успех.
- Объявление для инварианта Н3 — в форме, которую задаст тест «Процесса»;
  чтение ресурса — `vm_get` по `vm_id`.

### 3.3. Ось 3 — уборка и повтор

- Ничего не создаёт: записи в `created.go` нет. Запущенная ВМ убирается тем
  же `destroy`, останавливается `vm_stop`.
- Намерение пишется до отправки (D92) общим слоем `intended`.
- Обрыв после отправки, Ctrl-C, потерянный ответ: команда могла дойти —
  повтор вызова читает состояние и попадает в `starting` или `running`
  (таблица 3.1): дубля и второго вопроса нет. `429`/`5xx` — повторы
  `httpretry`; повтор `power_on` по ВМ, которая уже запускается, безопасен
  по таблице (**гипотеза**, что платформа отвечает на него `204` или `422`,
  а не ошибкой сервера, — Г-10, «действие повторно в достигнутом
  состоянии»).
- Запись развёртывания (`.evo/`) действие не правит: её `status` — ход
  развёртывания (`provisioned`, `running`, `compose_failed`…), а не питание
  ВМ (**факт**: `internal/state/types.go:34`). Что отвечают `status`,
  `verify` и повторный `deploy` по записи, чья ВМ остановлена, — вопрос
  раздела `vm_stop`; для `vm_start` запись после запуска снова верна, если
  ВМ сохранила публичный адрес (**гипотеза**, Г-10): итог `vm_start`
  называет публичный адрес ВМ, каким он прочитан после запуска.

### 3.4. Ось 4 — полнота

- Превью называет всё, что evo шлёт и что изменится, в объекте `preview`,
  как у создающих инструментов: `command` (`power_on` — поле тела `state`),
  `vm_id`, `name`, `vm_state` (состояние, прочитанное до вопроса),
  `public_ip`, если есть; проект — механизмом 0в (`project_id`). Имена из
  облака помечены недоверенными (`untrustedFields`).
- Цена — машинным полем, а не только текстом: `price_classes` с классом
  `paid_unpriced` для ВМ и `tariff_url` — «цена неизвестна, ресурс платный»,
  тем же механизмом, что у превью создания. Число по расчёту конфигурации
  (`price-calculation`, как у `provision`) — только после проб Г-20 и Г-21
  и отдельной правкой.
- Параметров платформы, которые evo выбирает сам или не трогает, у действия
  нет: тело — одно поле.
- Человеческий вывод CLI называет каждое поле превью (инвариант 1.5).

### 3.5. Опись запросов (в том же PR)

- Новая запись: `POST /api/v1/vms/{vm_id}/set-power`, поле тела `state`,
  значение `power_on`, статусы `204`, `422`.
- Карточка ВМ: к объявленным состояниям добавляются те, по которым решает
  планировщик (`stopped`, `starting`, `stopping`, `rebooting`, `updating`,
  `deleting`, `error_creating`, `error_deleting`).

### 3.6. Тесты до кода (падают без правки)

1. Паритет: `evo vm start --json` = ответ `vm_start`; превью, код выхода,
   согласие (`TestParity_*`, `TestContract_*`, `TestReadOnly_*`).
2. Повтор: мир «ВМ уже running» — `already_running` без вопроса и без
   записи (Н1, `alreadyFor`; И2).
3. Отказ до вопроса: по миру на каждую строку таблицы 3.1 — ни вопроса, ни
   записи там, где их нет в таблице.
4. Ход: мир «ВМ долго starting» — ход называет состояние; на пределе MCP —
   `status: starting` со следующим шагом, повтор не пишет.
5. Сбои: матрица сбоев на `set-power` — обрыв до и после отправки, `429`,
   `5xx`, `422` при достигнутой цели, `403`.
6. Превью называет действие и каждое поле (ось 4), цена — «неизвестна,
   ресурс платный».
7. Опись: запрос и поле тела — в `api-contract.json` (Н2).

### 3.7. Для «Риска»: матрица и шесть вопросов (черновик автора)

| Принцип | Агент автономен | Человек + агент | Только человек |
|---|---|---|---|
| Паритет CLI–MCP | один планировщик, одна таблица | то же | то же |
| Качество логики | решение по состоянию, прочитанному до вопроса; гонка «состояние сменилось после чтения» — строка `422` | то же | то же |
| Надёжность | повтор безопасен по таблице 3.1 | то же | Ctrl-C не теряет операцию |
| Безопасность | секретов нет; имена из облака недоверенные; права ключа не расширяются | согласие на каждый вызов | то же |
| Отказоустойчивость | потерянный ответ → повтор читает состояние | то же | то же |
| Эффективность | агент не опрашивает список: ход и следующий шаг в ответе | то же | — |
| Масштабируемость | +1 описание в `tools/list` (три на тройку) | — | — |
| Производительность | одно чтение до вопроса, ожидание в пределе D69 | то же | ожидание до продовой границы |

1. *Паритетный обход.* Тем же ключом `curl` шлёт `set-power` без превью;
   evo не граница прав, граница — роль ключа. Отличие evo — согласие и
   намерение в журнале.
2. *10×.* Десять агентов запускают одну ВМ: один получает превью, остальные
   — `starting` или `already_running` без записи. Чтение — один `GET` на
   вызов.
3. *Человек недоступен.* Без «да» записи нет; ВМ остаётся остановленной,
   агент видит `confirmation_required`.
4. *Сценарий у людей.* Дежурный: «запусти после ночной остановки» —
   ежедневно; сегодня — консоль.
5. *Доказательство.* Запрос и состояния — спецификация; поведение повтора,
   время запуска, тарификация — гипотезы до двух прогонов Г-10 и Г-20.
6. *Цена разворота.* Новый инструмент; снять — удалить запись реестра до
   выпуска, после выпуска — ломающее.

Главный остаточный риск (оценка автора): платное действие с превью «цена
неизвестна» до проб цены — агент без присмотра не может сравнить стоимость;
снижается пробой Г-20/Г-21 до rc.1.
