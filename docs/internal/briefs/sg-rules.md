# ТЗ: правила групп безопасности — `sg_rule_create`, `sg_rule_delete` (1.9, волна В1)

Автор — «1.9 — разработка A». Основание: план 1.9, строка «Первая волна
операций IaaS и k8s» (`sg_rule_create` — источник, направление, протокол
вкл. ICMP; превью прямо называет «открыто в интернет»; `open_ports` — над
той же точкой; `sg_rule_delete` — не отрезать доступ); решение владельца
Вп-4 (`docs/internal/phase-0/1.9.md`, 2.4); D99 (общие правила волны —
`docs/internal/briefs/ops-wave-1.md`, раздел 1, действуют и здесь).

До кода: заключение «Риска» (§0, правило 7) — согласие и безопасность, текст
для модели. Статус утверждений: «факт» — спецификация Compute (прочитана
12.11) или код в `main`; остальное — «гипотеза» до пробы Г-11 (два прогона).

## 1. Что даёт платформа

Факт, спецификация:

- `POST /api/v1/security-groups/{id}/rules` — тело: `direction`
  (`ingress` | `egress`), `ether_type` (`IPv4` | `IPv6`), `ip_protocol`
  (`tcp` | `udp` | `icmp` | `any`), `port_range` (строка) — обязательные;
  `remote_ip_prefix`, `remote_security_group_id` или `…_name`,
  `description` (до 255). Ответ `201` — правило с `id` и `state`
  (`created`, `creating`, `updating`, `deleting`, `error`,
  `error_creating`, `error_deleting`). Id операции нет. `422` — группа не
  найдена, группа в состоянии, где правило не создать, изменения в зоне
  запрещены.
- `DELETE /api/v1/security-groups/{id}/rules/{rule_id}` — `200`; `404` —
  правила нет; `422` — группа не найдена, правило не из этой группы,
  изменения в зоне запрещены, правило в состоянии, где его не изменить.
- `GET …/rules`, `GET …/rules/{rule_id}` — чтение правил и одного правила.
- Группа: `default` (группа зоны по умолчанию), `has_interfaces`,
  `ingress_rules_count`, `egress_rules_count`, `state`.
- `GET /api/v1/interfaces?project_id=` — интерфейсы проекта с
  `security_groups` и `vm`: по нему считается, сколько интерфейсов и каких
  ВМ под группой. Запроса в evo ещё нет — новая строка описи.

Факт, код в `main`: `open_ports` и `close_ports` шлют те же два запроса для
входящих TCP и UDP правил одного порта (`port_range` вида `80:80`), читают
правила перед вопросом, считают порт открытым по одному правилу
(`sgrules.Coverage`, D52).

Гипотезы до Г-11 (подробности наблюдений — только `evo-internal`):

| Гипотеза | Что от неё зависит |
|---|---|
| Что платформа принимает в `port_range` для `icmp` и `any` | тело запроса для этих протоколов |
| Ответ на создание правила, которое уже есть (дубль, `409`, второе правило) | повтор: evo не шлёт дубль сам (читает до вопроса), ответ платформы нужен только для гонки |
| Что платформа хранит для «откуда угодно» (`0.0.0.0/0` или пустой источник) | сравнение «уже есть» и текст «открыто в интернет» |
| Сколько правило живёт в `creating` и `deleting` | ожидание итога, статусы «идёт» |
| Правило исходящего трафика: что разрешено по умолчанию и что меняет первое `egress`-правило | текст превью исходящего правила |
| Удаление правила, под которым идёт соединение | текст «не отрезать доступ» |

## 2. Одна точка с `open_ports` (§2 CLAUDE.md)

`open_ports` и `close_ports` — выпущенные инструменты; их ответы не
меняются. Новые инструменты не дублируют их механизм, а становятся его
общим случаем:

- Одна функция строит правило из аргументов и одна решает «такое правило
  уже есть» — `internal/sgrules`; `open_ports` — её частный случай
  (входящее, TCP или UDP, один порт на правило). `Coverage` остаётся
  правилом «порт уже открыт» для `open_ports` и `deploy` (D52); для
  `sg_rule_create` вводится точное сравнение правила (см. 3.3).
- Одна функция превью называет группу, её общность и «открыто в интернет»
  (см. 3.2); `open_ports` получает те же поля превью добавлением, без смены
  существующих.
- Отказ Вп-4 («весь интернет» на общей группе без подтверждения) — новое
  поведение **только** новой операции: `open_ports` выпущен и остаётся с
  предупреждением (`WideOpen`); перенос отказа на него — ломающее, вопрос
  владельцу отдельно (см. В3).

## 3. `sg_rule_create`

Команда: `evo vpc sg-rule-create <security_group>` (рядом с
`evo vpc open-ports`).

### 3.1. Аргументы

| Аргумент | Значения | Обязателен | В тело |
|---|---|---|---|
| `security_group` | имя или UUID (как у `open_ports`; два одноимённых — `USAGE` с id) | да | путь |
| `direction` | `ingress`, `egress` | да — умолчания нет: направление называет вызывающий | `direction` |
| `protocol` | `tcp`, `udp`, `icmp`, `any` | да | `ip_protocol` |
| `ports` | порт `443` или диапазон `8000:8100`; для `icmp` и `any` не задаётся | для `tcp`, `udp` — да | `port_range` |
| `cidr` | источник (для `egress` — назначение), IPv4 или IPv6 | один из `cidr`, `remote_group` — да; умолчания «откуда угодно» нет | `remote_ip_prefix`, `ether_type` — по семейству адреса |
| `remote_group` | имя или UUID группы-источника | — | `remote_security_group_id` |
| `description` | до 255 знаков | нет | `description` |
| `allow_internet_on_shared_group` | `true` | только для случая 3.2, п. 3 | — |
| `confirmed` | согласие | — | — |

Одно правило на вызов. Статические правила (перечисления, форма порта и
CIDR, «`ports` только для tcp/udp», «ровно один из `cidr` и
`remote_group`») — в схеме (D36): отказ до облака.

`icmp` и `any`: что слать в `port_range`, спецификация не говорит
(«гипотеза»). До двух прогонов Г-11 значения есть в схеме, а вызов с ними
отвечает отказом до вопроса «формат запроса для этого протокола ещё не
подтверждён прогоном» — evo не шлёт тело, которое придумал. После Г-11 —
отдельной правкой в 1.9, без смены контракта остальных протоколов. Это
порядок внутри версии, а не перенос из объёма.

### 3.2. Превью (оси 1 и 4): группа, общность, интернет

До вопроса evo читает группу, её правила и интерфейсы проекта. Превью
(ключ `preview`) называет:

1. Правило целиком, как оно уйдёт: `direction`, `protocol`, `port_range`,
   источник (`cidr` или `remote_group` с id), `ether_type`, `description`.
2. **Группу и её общность:** `security_group` (имя, id, зона), `shared`:
   `true`, если группа — группа зоны по умолчанию (`default`) или под ней
   больше одного интерфейса; `interfaces` — число интерфейсов под группой и
   `vms` — имена ВМ (до 10, остальное числом). Текст: «группа общая:
   правило подействует на N интерфейсов M ВМ». Интерфейсы не прочитались —
   превью говорит «сколько интерфейсов под группой, evo не узнал», а
   общность считается по `default` и `has_interfaces`.
3. **Интернет.** Источник `0.0.0.0/0` или `::/0` у входящего правила —
   поле `open_to_internet: true` и текст «открыто в интернет: любой адрес
   сможет обратиться к <протокол/порты> каждой ВМ группы». На **общей**
   группе такой вызов без `allow_internet_on_shared_group: true` —
   **отказ до вопроса** (`USAGE`, решение владельца Вп-4): причина, число
   интерфейсов, и два пути — сузить `cidr` или повторить с аргументом (его
   задаёт человек; описание аргумента говорит это). С аргументом — превью и
   вопрос как обычно. На необщей группе — превью с предупреждением, без
   отказа.
4. Цена: правило бесплатно при создании? — тарифа, который это утверждает,
   у evo нет: `price_classes` не называет «0 ₽»; инструмент — в
   `noPriceInPreview` с причиной «не создаёт тарифицируемого ресурса»
   только после сверки с тарифом VPC (вопрос В4), иначе «цена неизвестна».

### 3.3. Повтор (ось 3, П3)

«Такое правило уже есть» — точное сравнение с активным правилом группы:
направление, протокол, диапазон, источник (после нормализации CIDR;
пустой источник платформы равен «откуда угодно» только после Г-11 — до
него не приравнивается). Есть — `status: already_exists` с `rule_id`, код
0, без вопроса и без записи (мир `alreadyFor` в `consentWorlds`). Правило
шире запрошенного (диапазон вокруг порта, `any`, более широкий источник) —
не «уже есть»: превью называет `covered_by` (id более широкого правила) и
спрашивает — человек решает, нужно ли узкое.

Правило в `creating` с теми же полями — ожидание итога без второй команды;
в `error*` — не считается существующим, превью называет его id.

### 3.4. Ход и итог (ось 2)

После `201` evo читает правило (`GET …/rules/{id}`), пока `state` не
`created`: итог — `status: created`, `rule_id`, правило и группа. Предел
вызова MCP — `status: creating`, `rule_id`, `next_tool:
list_security_groups` с `rules: true` (чтение; отдельного `sg_rule_get`
волна не вводит). `error*` — ошибка с состоянием и `rule_id`: правило
объявлено созданным (`created.go`), `sg_rule_delete` его убирает.

Сбои запроса: потерянный ответ — evo перечитывает правила и ищет точное
совпадение: нашёл — идёт дальше как после `201`, не нашёл — ошибка запроса
без шага повтора с согласием. `422` — ошибка с кодом платформы
(`details.platform_code`), без шага.

### 3.5. Уборка (ось 3)

Правило, созданное `sg_rule_create`, записывается в `created.go` с
`rule_id` и группой; удаляет `sg_rule_delete`. Метки ВМ в `description`
(как у правил `deploy`, `sgrules.RuleLabel`) нет: правило не привязано к
развёртыванию, `destroy` его не трогает — превью `destroy` и документация
говорят это (вопрос В5).

## 4. `sg_rule_delete`

Команда: `evo vpc sg-rule-delete <security_group> --rule-id <id>`.

Аргументы: `security_group`, `rule_id` (UUID из `list_security_groups
rules=true`; удаление по описанию полей — `close_ports`, не здесь),
`confirmed`. Объявление в `deleteTargets` (`arg: rule_id`, `parent:
security_group`), правило D26/D61 — общим механизмом.

| Что прочитано | Ответ | Вопрос | Запись |
|---|---|---|---|
| правило есть, `created` | превью: правило целиком, группа и её общность (3.2, п. 2), `cuts_access` (ниже) | да | после «да» |
| правила нет (`404`, или нет в списке группы) | `already_deleted`, код 0 (D26) | нет | нет |
| `deleting` | `status: deleting`, `already_deleting: true` (D61) | нет | нет |
| `creating`, `updating` | ждёт до 30 с, затем по итогу; не устоялось — `USAGE` с состоянием | по итогу | по итогу |
| `error*` | превью с предупреждением «исход неизвестен» | да | после «да» |
| правило не из этой группы (`422`) | `USAGE`: правило принадлежит другой группе; id группы — если чтение правила её назвало | нет | нет |
| опечатка в `rule_id` (не UUID) | отказ схемы | нет | нет |

**Не отрезать доступ.** Превью называет, что перестанет проходить: «после
удаления <протокол/порты> с <источник> к ВМ группы не пройдёт, если другое
правило этого не разрешает» — и, если разрешает, id этих правил
(`still_allowed_by`). Отдельно, отказом до вопроса без аргумента
`allow_cut_ssh: true`: удаление **последнего** активного входящего правила,
которое пропускает TCP 22 к группе, под которой есть ВМ развёртываний evo
(по записям папки): evo управляет развёртыванием по SSH (`deploy`,
`logs`), и агент этим удалением отрезает себя и человека. Какой адрес у вызывающего, evo не знает, поэтому
правило простое: «последнее правило на 22» — и только для входящего TCP.
Остальные порты — предупреждение в превью, без отказа.

Итог: `status: deleted` после того, как правило исчезло из чтения (или
`404`); предел вызова — `status: deleting`, `next_tool:
list_security_groups`. Повтор — `already_deleted`.

## 5. Вопросы «Риску»

- **В1. Имя аргумента-подтверждения Вп-4** — `allow_internet_on_shared_group`
  (длинно, но само себя объясняет) или короче. Важнее: описание говорит
  «задаёт человек», а модель с согласием может поставить его сама — мера та
  же, что у `confirmed`: отказ без аргумента показывает человеку причину;
  второй вызов с аргументом всё равно проходит превью и вопрос.
- **В2. «Общая» группа** — `default` или больше одного интерфейса
  (умолчание), либо только `default`.
- **В3. `open_ports` и отказ Вп-4.** Умолчание: не переносить (выпущен,
  ломающее); в превью `open_ports` добавить поля `shared`, `interfaces`,
  `open_to_internet` — добавление полей не ломает. Перенос отказа — вопрос
  владельцу к 2.0.
- **В4. Цена правила** — «цена неизвестна» или `noPriceInPreview`.
- **В5. Правило вне развёртывания:** `destroy` не убирает правила
  `sg_rule_create` — достаточно ли текста, или нужна строка в `doctor`.
- **В6. `allow_cut_ssh`:** отказ только для последнего правила на TCP 22
  (умолчание) или предупреждение без отказа.
- **В7. `icmp`/`any` до Г-11:** отказ до вопроса «формат не подтверждён»
  (умолчание) или не включать значения в схему до прогона.

## 6. Опись, тесты, инварианты

- Опись запросов (в PR каждой операции): `POST …/rules`, `GET
  …/rules/{id}`, `DELETE …/rules/{id}` — есть в описи для `open_ports`;
  новое — `GET /api/v1/interfaces`, поля `default`, `has_interfaces`
  группы, `remote_security_group_id` в теле.
- Тесты до кода, мир на строку: `sg_rule_create` — каждое сочетание
  направления и протокола строит ожидаемое тело; точный дубль —
  `already_exists` без записи (с согласием и без); более широкое правило —
  вопрос с `covered_by`; общая группа + интернет без аргумента — отказ до
  вопроса, с аргументом — вопрос; необщая — предупреждение; интерфейсы не
  прочитались — превью говорит это; предел вызова — `creating` с чтением
  как шагом; потерянный ответ не создаёт второго правила; `icmp`/`any` —
  отказ до вопроса. `sg_rule_delete` — каждая строка таблицы раздела 4;
  последнее правило на 22 — отказ без аргумента; `still_allowed_by`.
- `open_ports`/`close_ports`: существующие тесты не меняются; новые поля
  превью — добавлением.
- Инварианты «Процесса»: Н1 (повтор), Н2 (опись), Н3 (ход), таблица
  `deleteTargets`, превью называет всё, что evo шлёт.
