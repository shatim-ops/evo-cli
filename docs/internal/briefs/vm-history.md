# История задач ВМ

Команда `evo vm history <vm-id>` и инструмент `vm_history` читают `GET /api/v1/tasks` в Compute. На каждой странице обязательны проект текущего вызова, UUID ВМ и тип сущности `vm`. Удалённая ВМ может иметь историю. Для вызова не требуется её живая карточка.

| Ответ сервиса | Ответ evo |
|---|---|
| Все строки принадлежат этой ВМ, получено объявленное число уникальных задач | Источник Compute Tasks, проверенные задачи, число записей и `partial=false`. |
| Пустой список и `total=0` | Ноль видимых задач для данного запроса. |
| Отказ на первом запросе или повреждение до получения проверенных записей | Ошибка с причиной. |
| Отказ после полученных записей, повтор ID, посторонняя или неполная запись, противоречивые границы страниц | Ошибка с причиной, `partial=true`, число и список проверенных записей. |
| После 32 страниц остаются непрочитанные задачи | Частичный результат. |

Каждый запрос запрашивает до 100 записей. Время создания и обновления относится к задаче. Поля источника, ID, действия и состояния позволяют сопоставить её с платформой. Локальный журнал намерений читается отдельно. При одновременном изменении списка пагинация по смещению не гарантирует неизменного снимка.

В пробе 21 ноября 2026 года профиль agent видел собственные задачи создания и удаления двух разрешённых ВМ одного проекта. Раздельный фильтр вернул две уникальные задачи для каждой ВМ, включая чтение после удаления. Минимальная IAM-роль, видимость действий другого субъекта и срок хранения истории остаются неизвестными.
