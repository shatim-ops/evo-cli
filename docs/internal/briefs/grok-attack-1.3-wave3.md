# Бриф: атака Grok, волна 3 — на стабильном 1.3.0

Решение владельца 24.10: волна 3 идёт на стабильном `v1.3.0` вместе с
догфудом, а не на rc. Находки волны идут в патч 1.3.1. Роль Grok, режимы,
правила и формат отчёта описаны в `grok-role.md`. Стенд и стоп-условия
агента-оператора — в `grok-attack-1.3.md`, цель J. Здесь — только то, что
нового у волны 3. Бриф пишет «Процесс и тестирование», отправляет владелец.

Чем 1.3.0 отличается от rc.1, на котором шли волны 1 и 2:

- согласие — одна функция реестра (D35);
- всё, что можно узнать без записи, проверяется до вопроса (`CLAUDE.md` §6, ось 1);
- правила аргументов вынесены в схему (D36);
- появился `close_ports` (D37);
- у каждого create объявлено, где его id (W1).

Волна 3 проверяет, что эти обещания держатся на живом облаке, а не только
в мирах тестов.

## 1. Стенд

- Бинарь — из GitHub Release `v1.3.0`. Подпись и происхождение проверяются
  по `docs/RELEASING.md`, шаг 4. Неудача проверки — находка.
- Ключи владелец передаёт отдельно и отзывает после атаки:
  - **ключ наблюдателя** — для целей, где хватает чтения: F и часть A;
  - **ключ оператора** в отдельном тестовом проекте — для целей A–E. Как в
    волне 2, цель J.
- Серверы:

  ```
  evo mcp --allow-project <UUID тестового проекта>                         # stdio
  evo mcp --http 127.0.0.1:8090 --auth bearer --allow-project <UUID тестового проекта>
  evo mcp                                                                  # stdio, только повторный delete (цель B)
  ```

- **Стоп-условия, уборка, префикс `grok-` и журнал `grok-consents.jsonl`** —
  всё как в цели J брифа волны 2, без исключений.
- **Ограничение для цели D:** кластеры в `FAILED` и `DEPLOYING` нарочно не
  создаются. Цель проверяется только на тех, что оказались в таком
  состоянии сами, и не больше одного кластера каждого вида одновременно.

## 2. Уже известно — не сообщать заново

Повтор известного считается находкой, только если поведение стало хуже
описанного.

- **По замыслу** (`docs/mcp.md`, `DECISIONS.md`):
  - ограничения HTTP-режима H1–H13;
  - `already_deleted` при повторном delete без `--allow-project` и
    `NOT_FOUND` с ним (D26, H9);
  - гейт `confirmed: true` останавливает вызов, а не агента: подтверждать
    изменяющие вызовы — дело клиента (D10);
  - токен подтверждения отклонён (G13-20), в 1.4 — elicitation.
- **Волна 2, исправлено в 1.3.0.** Повторная находка в этих местах означает,
  что исправление не держится, — это «высокая»:
  - K1 — проверка выполнимости после согласия (G13-3 и др.);
  - K2 — id шага стека `"ok"` (G13-14);
  - K3 — шаг s3 без бакета (G13-13);
  - G13-1 — режим сервера отвечал раньше проверки аргументов;
  - G13-7 и G13-24 — `deploy_plan.next` и цена;
  - G13-19 — превью удаления в `FAILED`;
  - G13-23 — `open_ports` до вопроса;
  - G13-27 — превью `pg_delete` о копиях;
  - G13-9 — нет `close_ports`.
- **Отложено в 1.4** (`release-plan.md`, «1.4»):
  - оставшиеся `inlineGates`, прежде всего `image_create` (FB130-2) и
    `s3_put` в несуществующий бакет;
  - согласие на пустой `open_ports` (FB130-4);
  - правила аргументов вне схемы (FB130-6);
  - занятое имя в `ca_deploy` (FB130-7);
  - пометка `_untrusted` на именах ресурсов (G13-2);
  - G13-8 и G13-33…36.
- **Платформа Cloud.ru** — реестр `cloudru-discrepancies.md`. Находка
  только при новом расхождении или новом счёте «N из M»:
  - DB-17 и DB-21 (кластер в `FAILED` не удаляется);
  - DB-22 (копии удалённого кластера);
  - NET-15, CAP-3, OPS-1b.

## 3. Цели

Для каждой цели ниже — что должно держаться и с чего начать. Список
способов не закрыт.

### A. Гейт D35: отказ до вопроса — по каждому изменяющему инструменту

Держится: если облако откажет вызову, а причину можно узнать чтением,
evo отказывает **до** вопроса о согласии. Превью с ценой получает только
выполнимый вызов (`CLAUDE.md` §6, ось 1).

- Для каждого инструмента с `mutating: true` (`evo tools list --json`)
  подобрать предусловие, которое видно без записи:
  - ссылки нет;
  - ресурс в другой зоне или в неподходящем состоянии;
  - адрес или имя заняты;
  - меньше минимума спецификации;
  - бакет непустой;
  - группа с таким именем не одна.

  Находка — `confirmation_required`, а после `confirmed: true` — 4xx облака.
  Мерило — FB130-1: `fip_attach` с адресом, привязанным к другой ВМ.
- Проверка до вопроса не должна писать. Вызов без `confirmed` не создаёт и
  не меняет ничего — сверяйте списки до и после.
- Одинаков ли отказ при `confirmed: false`, без поля и при `confirmed: true`:
  `reason`, текст, код выхода?

### B. Повторы и уборка (ось 3)

Держится:
- всё созданное находится и удаляется тем же evo;
- id в ответе — настоящий;
- «удалено» значит, что ресурса нет;
- опечатка в id — не успех (`USAGE` или `NOT_FOUND`).

- Повторный `*_create` во время создания и после — без дубля, ответ
  называет существующий ресурс.
- Повторный `*_delete` и delete уже удалённого — `already_deleted`,
  `existed: false`, код 0, без вопроса (D26). Только по id ресурсов
  `grok-`, которые ты удалил сам.
- id созданного из ответа create (W1) — тот, по которому `*_get` и
  `*_delete` находят ресурс. Для стека — id каждого шага.
- Прерывание долгой операции и повтор: отмена запроса, закрытие сессии,
  обрыв HTTP. Операция либо продолжается, либо убирается — неучтённого
  ресурса нет.

### C. `open_ports` и `close_ports` на общей группе зоны

Держится: `close_ports` удаляет ровно названное правило (порт, протокол,
CIDR). Чужое правило общей группы не трогается. Чего нет — `already_deleted`
без вопроса (D37).

- Правило с тем же портом, но другим протоколом или CIDR. Правило, открытое
  `deploy` (описание «evo:»), против открытого `open_ports`.
- Список портов с повтором, диапазоном или нулём.
- Группа по имени при двух одноимённых группах — `USAGE` с их id до вопроса.
- `open_ports` → `close_ports` → `close_ports`.
- `open_ports` → `destroy` ВМ. Что осталось в группе, и говорит ли об этом
  ответ?

### D. Удаления в `FAILED` и `DEPLOYING`

Держится: если платформа не удаляет ресурс в этом состоянии, ответ
говорит это прямо и называет путь (поддержка, консоль). Ответ не
выглядит успехом и не обещает «удалено» (`CLAUDE.md` §6, ось 3; DB-17,
DB-21).

- `k8s_delete`, `pg_delete`, `kafka_delete`, `redis_delete` на кластере в
  `DEPLOYING` и в `FAILED` (ограничение — раздел 1). Также `vm_delete` и
  `destroy` на ВМ в `creating`.
- Превью такого удаления: называет ли оно состояние до вопроса (G13-19)?

### E. Стек с s3

Держится: `stack_plan` знает, чего не хватит, до `stack_apply`. Бакеты стек не
создаёт: шаг s3 кладёт объект (`s3_put`) в существующий бакет, а
`stack_destroy` удаляет только то, что положил стек (`s3_rm`; `created.go`).

- Шаг s3 в бакет, которого нет: отказ на `stack_plan` (W7).
- **Ключ, который уже был в бакете до стека.** `s3_put` перезапишет объект,
  а `stack_destroy` его удалит, и прежние данные пропадут. Предупреждает ли
  об этом план или превью? Отличает ли destroy объект, который стек создал,
  от объекта, который он перезаписал?
- Частичный сбой `stack_apply` (один шаг отказал) и повтор того же плана:
  готовые шаги не пересоздаются.

### F. Паритет CLI ↔ MCP на новых отказах

Держится: команда и инструмент отвечают одинаково — `reason`, код выхода,
подсказка, `--json` = JSON инструмента (`CLAUDE.md` §1). Различия
допустимы только из H1–H13.

- Каждый отказ до вопроса из W4–W9 — через `evo <команда>` и через
  `tools/call`:
  - `provision` в зоне без подсети;
  - `disk_resize` меньше текущего;
  - `open_ports` и `close_ports`;
  - `s3_bucket_delete` непустого бакета;
  - `dns_record_create` с занятым именем;
  - `cert_private_key` несуществующего сертификата;
  - `fip_attach` с занятым и с несуществующим адресом;
  - хранилище DBaaS меньше минимума;
  - `destroy` без развёртывания.
- То же при `--read-only` и при `--toolsets`: что отвечает раньше — режим
  сервера или проверка аргументов (G13-1)?

## 4. Отчёт

- Формат — как в `grok-role.md` и в разделе 5 брифа волны 2. Номера — с
  префиксом **`G130-<N>`**, чтобы не пересекаться с G13-* волн 1–2.
- В конце — строка по каждой цели A–F: «находки G130-…» или «проверено,
  способы: …».
- Отдельным списком:
  - расхождения платформы — их вносит в реестр «1.3 — релиз»;
  - остатки уборки, если они есть, — первой строкой отчёта.

Что дальше:
- «1.3 — разработка» разбирает отчёт. На каждую находку — падающий тест,
  исправление в 1.3.1 и запись в `release-plan.md`.
- Если находка ускользнула от тестов, «Процесс и тестирование» добавляет
  инвариант (`CLAUDE.md` §5).
- Опровергнутые находки получают ответ с причиной.
