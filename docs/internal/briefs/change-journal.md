# ТЗ: журнал изменений evo CMCP (D43, 1.4)

Черновик релиза, 25.10.2026. Решение владельца 25.10: журнал нужен, версия
1.4. Ревью — «разработка» и «Процесс» (их советы 25.10 уже учтены ниже).
Код — «разработка», инварианты — «Процесс». Начинать после первой строки 1.4
(перевод всех обработчиков на `gated`): без неё часть мутаций пройдёт мимо
точки записи.

## 1. Цель: опись изменений, а не аудит

Решение владельца 25.10. evo CMCP работает локально (D32), и журнал отвечает
на вопрос: **«что сделал evo CMCP на этой машине и как это найти и убрать»**
(ось 3 §6). Он не отвечает на вопрос «кто что сделал» — это аудит.

- **Нужен потому, что:** агент не помнит прошлых сессий; «что создал evo»
  знают только `.evo/state.json` каталога и задания стека; `evo-cleanup`
  собирает ресурсы по префиксу имени и включает чужие (G130-01); стек
  удалял то, что не создавал (G130-03, -24). Аудит платформы этого не
  закрывает: ключу проекта Audit Logging отвечает 401 (AUD-1), действия
  evo в нём не отличить от консоли, связи с заданием и планом нет.
- **Не обещаем:** защиту от злонамеренного агента, неизменяемость,
  идентичность клиента, срок хранения, SIEM. Файл на машине пользователя,
  агент с shell может его стереть. Для ИБ — только Audit Logging платформы;
  это сказано в описании инструмента и в `docs/`.
- **Публичный или командный MCP-сервер** (если D32 пересмотрят) — аудит
  станет отдельной задачей на сервере, с идентичностью клиента. Этот журнал
  её не закрывает.

## 2. Две части

1. **Метка в облаке** — «создано evo CMCP» в самом ресурсе (описание, метка,
   label), где API это принимает. Видна с любой машины и из CI. Так уже
   работают правила групп безопасности (`evo: port …`).
2. **Локальный журнал** — для того, что метка не покрывает: сервисы без
   поля метки, оборванные операции, связь шага с заданием стека и планом.

**Первый шаг 1.4 — проба меток**, до кода журнала: по спецификациям каждого
сервиса с create — есть ли поле, куда evo может записать метку, и
сохраняется ли оно. Итог — таблица ниже. Метки у большинства сервисов —
делаем их первыми, журнал остаётся вспомогательным; у немногих — журнал
основной.

| Сервис | Поле метки | Пример значения | Нет поля — что делаем |
|---|---|---|---|
| (заполняет проба: ВМ, диск, FIP, VPC, SNAT, группа, DNS, k8s, PG, Kafka, Redis, S3, секрет, сертификат, AR, Container Apps, NLB, образ) | | `created-by: evo-cmcp` | только журнал |

## 3. Журнал: устройство

- **Одна функция** `journal.Record(tool, args, answer)`. Вызовы — только в
  реестре: в `Execute` плана (`gated`) и в `engineGated` **в обеих ветках** —
  `execute` и `live` (CLI `evo deploy` и `destroy` идут через `live(c)`,
  иначе выпадут). Стек проходит через `callTool` → тот же гейт, шаги пишутся
  сами; плюс по одной записи `stack_apply` и `stack_destroy` с `job_id`.
  Второго механизма нет: обработчик, который пишет в облако мимо гейта, —
  уже нарушение W4.
- **Два шага:** «намерение» до вызова, «итог» после (ревью Qwen на #342).
  Запись без итога — операция оборвалась; `history` показывает её как
  «итог неизвестен — проверьте `get`».
- **id** — из ответа инструмента через `createdIDs`/`createdRef`
  (`created.go`), не из аргументов. Удалённое — по `deleteTargets[tool].arg`.
  Запись `delete` — только при `existed: true` или `already_deleted`.
- **Поля записи:** время (`internal/clock`), инструмент, поверхность (CLI или
  MCP), проект, зона, маскированные аргументы, id, итог (`created`,
  `deleted`, `already_deleted`, `error` с `reason`), id операции, `job_id` и
  `state_dir`, если есть.
- **Маска секретов — своя, не H7.** H7 работает только на выходе MCP по
  HTTP, а журнал пишется локально. Секретные поля — из схемы инструмента
  (`value`, `password`, `private_key` и т. п.); одна точка с объявлением в
  реестре, новый инструмент с секретом без объявления роняет сборку.
- **Хранение:** `StateDir` движка (у тестов — `t.TempDir()`), JSONL 0600,
  файл на дату, блокировка как у stack-jobs (на Windows — `LockFileEx`).
  Сбой записи не меняет ответ инструмента: одна строка в stderr.
- **Не сводим** `.evo/state.json` и stack-jobs к журналу: это текущее
  состояние, на нём держится повтор (§1). Журнал — история, ссылается на
  них (`state_dir`, `job_id`), не копирует.

## 4. Инструмент `history`

`history` в реестре и `evo history` (`CLISpec`), `readOnlyHint`, вне
согласия. Фильтры: `since`, вид ресурса, проект; `--json` = ответ
инструмента. Описание: «журнал этой машины — подсказка, а не истина: перед
удалением всегда `get`; это не аудит».

## 5. Потребители

- `evo-cleanup`: таблица на удаление — только id из журнала и метки, каждый
  проверен `get`; ресурсы по префиксу без записи — отдельной строкой «не
  трогаю без вашего слова».
- cloud-e2e: журнал раннера — артефактом; сверка «создано = удалено» в конце
  job; `cleanup_only` — по меткам, журнал — второй источник.
- Бриф Grok: инвентарь агента не нужен, если журнал агент не может править.

## 6. Инварианты (Процесс)

- каждая мутация пишет запись: тест обходит реестр, инструмент с
  `NeedsConsent` без записи роняет сборку;
- запись = маскированный ответ: значения секретных полей не попадают в файл;
- матрица сбоев: «диск недоступен / файл занят» — ответ не меняется;
  обрыв после «намерения» — запись без итога;
- `history` объявлен только для чтения и не входит в согласие.

## 7. Размер и порядок

M без ротации и фильтров; L — с ротацией, `since` и фильтрами. Порядок: проба
меток → метки → журнал → `history` → `evo-cleanup` → cloud-e2e.
