## 0. Минимум в 1.9 (обновление «1.9 — релиза (4)», 17.11.2026)

Решение владельца 17.11 (опрос «1.9 — релиза (4)»): минимум журнала — в
1.9, волной rc.2; rc.1 не сдвигается. Предусловие этого ТЗ («все обработчики
на `gated`») выполнено в 1.9: `inlineGatesLeft = 0`. Разделы 1–8 ниже —
прежнее ТЗ; где они расходятся с этим разделом, действует этот раздел.

**Что входит в минимум**

1. **Строка журнала — в каждой точке, где запись намерения D92 закрывается
   или остаётся.** Не новый механизм рядом с D92, а его продолжение:
   намерение (`internal/intent`, `beginIntent` в `internal/tools/intent.go`)
   пишется до отправки, на каждую мутацию. Точки: `Close` (исход известен —
   успех, отказ 4xx или ни одной записи в облако), `End` (исход неизвестен,
   запись остаётся), `Hold` (операция идёт, запись держится до шага), и
   поздние закрытия другим вызовом — `Settle`, закрытие по списку (`made`),
   `closeAsked`, `HoldCut`. Второго «намерения» в журнале нет: открытая
   запись D92 и есть «итог неизвестен» (предложение «разработки B (3)»
   17.11). **Порядок в каждой из семи точек: сначала строка
   журнала, потом закрытие или оставление записи намерения** — обрыв между
   ними оставляет и строку, и открытое намерение (`history` показывает одну
   запись по id намерения), а не ни того, ни другого (условие «Риска» 296,
   У4).
2. **Журнал только на дозапись; у одного id намерения может быть несколько
   строк.** Запись, оставленную `End` или `Hold`, позже решает другой вызов
   (`Settle`, повтор, список показал имя) — он пишет вторую строку «итог
   найден» с тем же id намерения. `history` показывает по каждому id
   последнюю строку; без второй строки решённое навсегда оставалось бы
   «итог неизвестен».
3. **Поля строки:** время (`internal/clock` — значение идёт в ответ
   `history`, §5), инструмент, поверхность (CLI или MCP), проект, зона, id
   ресурса из ответа (`createdID(tool, res)`, `createdRef(tool, args, res)`,
   у удаления — `deleteOf(tool)` → `deleteTarget`), итог (`created`,
   `deleted`, `already_deleted`, `changed`, `error` с `reason`, `unknown`, `found`, `not_found`; `changed` — успешная мутация, которая не создаёт и не удаляет ресурс: `vm_reboot`, `vm_resize`, правило группы на существующей, `k8s_kubectl`; сама строка закрытая, но она **не закрывает** строку `created` того же ресурса: ВМ после `vm_reboot` или `vm_resize` остаётся в описи живой, пока нет строки `deleted`, `already_deleted` или `not_found` (условие «Риска» 296 к коду). Где запись намерения закрывается потому, что человека спросили (`closeAsked`, ответ на оборванный вызов), а исход не известен, пишется повторная строка `unknown` — последняя строка по id остаётся живой; вызов, который ничего не отправил, строки не пишет — изменения не было), id
   операции, id записи намерения, `job_id` и `state_dir`, если есть. Значений
   аргументов нет — только их имена, как у записи намерения; имя ресурса и
   путь секрета — да, значение секрета — нет. Секретов нет по построению, а
   не по маске (раздел 3, «Маска секретов», для минимума не нужен).
4. **Место и чей журнал:** каталог `history/` рядом с `intents/` —
   `config.DataDir(root)` папки состояния; для `evo login` — `ConfigDir`,
   как у его намерения. JSONL 0600, файл на дату, запись под
   `state.FileLock`. Журнал — на папку состояния: MCP-сервер с одним
   `--state-dir` и CLI в другой папке ведут разные журналы; `history` в
   ответе называет, чей журнал читает (папку). Сбой записи не меняет ответ
   инструмента: одна строка в stderr. Срок и потолок — пункт 9.
5. **`evo login`** создаёт ключ сервисного аккаунта и пишет своё намерение
   (`internal/login/flow.go`, `intent.Begin`) мимо гейта: ключ — ресурс,
   строка журнала пишется и там, в `ConfigDir`.
6. **Инструмент `history`** (`evo history`, раздел 4): только чтение, вне
   согласия, паритет CLI–MCP; фильтры минимума — `since` и проект.
   Открытые записи намерения — «итог неизвестен — проверьте `get`».
   **Файл — недоверенный ввод (У5):** каждая строка проверяется —
   инструмент из реестра, итог и `reason` из закрытых списков, id по форме;
   битая строка пропускается и считается, ответ не падает. Имя ресурса и
   путь секрета в строке — свободный текст: пишутся и отдаются как данные
   облака, с пометкой `_untrusted`, одной строкой. Ответ ограничен по
   умолчанию (последние 30 дней и не больше 500 строк) и говорит, что
   обрезан. Каталог и файл открываются кодом `internal/journal` (отказ на
   символической ссылке, 0700/0600), а не копией. **Политика сервера
   (У6):** `history` — чтение, есть на `--read-only` и по HTTP; при
   `--allow-project` — только строки этого проекта; `state_dir` (локальный
   путь с именем пользователя) по MCP не отдаётся.
7. **Уборка (поправка «релиза» 17.11: скилла `evo-cleanup` в продукте нет —
   D68, выведен в 1.7; уборки как поверхности в 1.9 нет).** Агент или человек
   находит созданное по `history` (настоящие id) и проверяет каждый ресурс
   чтением evo; префикс имени — запасной путь для созданного до журнала. **Строка журнала — способ найти ресурс, а не право его удалить
   (У1):** файл лежит на машине, строку с чужим id может дописать кто
   угодно с терминалом. Удаление из уборки идёт через тот же гейт согласия
   и превью, что любое удаление; таблица уборки называет источник каждой
   строки («журнал папки <папка>») и имя ресурса из `get`, а не из файла.
   Возврат уборки как поверхности — пересмотр D68, только решение
   владельца. **Живая строка закрывается (У7; в 1.9 — PR 3б):** когда
   `get` evo отвечает, что ресурса нет (`history` с проверкой, чтение карточки),
   пишется строка `not_found` с тем же id — строка перестаёт быть живой;
   иначе ресурс, удалённый в консоли или с другой машины, остаётся живым
   навсегда. В cloud-e2e `cleanup_only` идёт отдельным job на чистом раннере
   (гипотеза «разработки B», проверить по workflow до кода): журнала прогона
   там нет, а артефакт журнала в минимум не входит — в CI основным остаётся
   префикс, журнал в CI — кандидат 1.10.
8. **Инварианты «Процесса»:** строка журнала у каждого вызова `Close`,
   `End`, `Hold`, `Settle`, закрытия по списку, `closeAsked`, `HoldCut` и
   `intent.Begin` в `evo login` — по всем местам, не только в гейте; новое
   место закрытия записи без строки журнала роняет сборку; в строке нет
   значений аргументов.

9. **Наполнение, срок и потолок (решение владельца 17.11, опрос «1.9 —
   релиза (4)»: 90 дней, 64 МБ).** Оценка объёма — гипотеза до первого
   прогона: строка 300–500 байт (запись журнала сессии D46 — «несколько
   сотен байт»), пишутся только мутации; активный агент ~500 мутаций в день
   — ~0,2 МБ в день, 60–90 МБ в год; человек — единицы МБ в год. Замер —
   строкой плана после первого прогона с журналом. Правила:
   - **живое не удаляется никогда:** строка ресурса, созданного и не
     удалённого, и строка с неизвестным итогом переносятся при чистке в
     `history/live.jsonl`; уборка и `history` читают его всегда;
   - **строка не на своём месте** (evo так не пишет; «Риск», 324-3;
     Астра, #2346, #2347): в файле дня — строка другого дня, в
     `live.jsonl` — строка дня позже метки `retired` (чистка пишет метку
     до `live.jsonl`). `history` её не берёт и считает в `skipped`, и она
     не затеняет копию, которую взять можно; чистка не удаляет её (#2297:
     непонятое хранится), а переносит в `history/stray.jsonl`, строки
     которого читатель не берёт;
   - **живое до и после чистки одно:** до первой записи чистка читает
     журнал в каждом состоянии, в котором её может оставить обрыв (после
     `stray.jsonl`, `live.jsonl`, метки `retired` и каждого удалённого
     файла), и в конце; если живое изменилось бы хоть в одном (строки,
     которых evo не пишет, закрывают оставляемое), журнал не трогается:
     метка `deferred` называет мешающие файлы (имя, число строк не от
     evo и живых — не содержимое), `evo doctor` предупреждает «очистка
     отложена» и называет их в тексте и в поле `files`; удалять или
     переносить файл не советует — в нём могут быть живые строки (агент
     с терминалом исполнит совет буквально; «Риск» к 324-3). Чистка
     пробует снова каждый день (метка `pruned` — «попытка сегодня была»,
     а не «очищено»); удачная снимает `deferred`. Из этого состояния
     выводит только уход строк не от evo из журнала: evo сам их не
     удаляет (#2297) — предупреждение остаётся, пока они есть.
     Порядок записи: `stray.jsonl`, `live.jsonl`, метка, файлы — старые
     первыми. Чтение и проверки — без замка журнала; замок берётся только
     на запись, и запись идёт, только если прочитанное не изменилось
     (файлы, их размер и время, метка `retired`), иначе — при следующем
     вызове: строка, записанная во время чистки, её не ждёт («Риск» к
     324-3). Предел: перезапись файла на месте той же длины с тем же
     временем не видна — так пишет только подложивший файл (evo дописывает
     или пишет через переименование);
   - **строка `live.jsonl` не на месте без копии в файле дня** (метка
     `retired` потеряна или старше `live.jsonl`, папка скопирована
     частично) может быть строкой evo: чистка её не переносит, а
     откладывается, `doctor` называет `live.jsonl` («Риск», 356, У1);
   - **предел времени** покрывает чтение и проверки (10 с — гипотеза до
     замера на журнале пользователя; синтетический журнал 100 МБ — ~5 с);
     не уложилась — метка `unfinished`, `doctor` предупреждает, повтор на
     следующий день, а не на каждом вызове (356, У2). Проверка состояний
     обрыва — по одному состоянию за раз; в журнале, где все строки на
     месте и файлы дней новее метки, промежуточные состояния читаются как
     итог, и проверяется только итог; в день, когда нечего удалять и
     переносить, — ни одной (356, У3). Цена — гипотеза до замера на журнале пользователя: на
     синтетическом журнале 59 МБ (91 файл, все строки живые) чистка идёт
     ~7 с после ответа вызова, раз в сутки; замок — ~2 мс (было 2,4 с в
     #2261 при ожидании записи `lockWait` 2 с);
   - **срок:** дневные файлы старше 90 дней удаляются — только после
     переноса живого;
   - **потолок 64 МБ:** если журнал больше и после срока, удаляются самые
     старые закрытые строки (`deleted`, `already_deleted`, `error`); живые —
     никогда; живого больше потолка — не режем, а предупреждаем в
     `evo doctor` и в ответе `history`;
   - **когда (У8):** не на пути мутации — после того как строка записана и
     ответ инструмента готов, не чаще раза в сутки, с пределом времени
     (не уложилась — продолжит в следующий раз); ожидание блокировки
     записью строки ограничено, сбой — строка в stderr; фонового процесса
     нет; перенос живого — запись целиком во временный файл и `rename`,
     затем удаление старых файлов;
   - **чужого не теряет (У8):** строку, которую чистка не разобрала или
     итог которой ей неизвестен (писала более новая версия evo), она не
     удаляет — считает живой; строки проверяются, как в `history` (У5), срок
     — по времени строки;
   - **видимость:** `evo doctor` — размер, самая старая дата, число живых
     строк; `history` прямо говорит «строки до <даты> убраны по сроку»;
   - **отказ иначе, чем у D46:** журнал сессии на пределе перестаёт писать
     (одна строка «полон»); журнал изменений так не может — это опись для
     уборки — поэтому чистит закрытое и держит живое.
   Инварианты «Процесса» (к пункту 8): чистка не удаляет ни одной живой
   строки; обрыв посреди чистки (`kill` между переносом и удалением) не
   теряет строк и не дублирует их в выдаче `history`; сбой чистки не
   меняет ответ инструмента; время для срока — `internal/clock`.

10. **Документация:** где лежит файл, что в нём (имена ресурсов и пути
    секретов — не значения), как его удалить руками (выключателя нет по
    решению владельца); журнал изменений и журнал сессии D46 (`evo diag`)
    названы по-разному, `evo diag export --public` журнал изменений не
    захватывает.

**Что не входит в минимум:** метки в облаке и их проба (разделы 2 и 7 —
кандидат 1.10), фильтр по виду ресурса, артефакт журнала в
cloud-e2e.

**Решение владельца 17.11 (опрос «1.9 — релиза (4)»), раздел 8 закрыт:**
журнал включён всегда, выключателя нет; каталог — `history/` рядом с
`intents/`, файл на дату. Основание: журнал не хранит ни значений, ни
секретов, а выключатель — второй путь в каждой точке записи.

**Порядок:** заключение «Риска» к этому разделу (новая поверхность: файл с
id ресурсов на машине пользователя) →
инварианты «Процесса» (раздел 6 и пункт 8 выше) → код «разработки B (3)» → `history` → уборка. Оценка срока — после
заключения «Риска»; до него любая цифра — гипотеза.

## 1. Цель: опись изменений, а не аудит

Решение владельца 25.10. evo CMCP работает локально (D32), и журнал отвечает
на вопрос: **«что сделал evo CMCP на этой машине и как это найти и убрать»**
(ось 3 §6). Он не отвечает на вопрос «кто что сделал» — это аудит.

- **Нужен потому, что:** агент не помнит прошлых сессий; «что создал evo»
  знают только `.evo/state.json` каталога и задания стека; `evo-cleanup`
  собирает ресурсы по префиксу имени и включает чужие (G130-01); стек
  удалял то, что не создавал (G130-03, -24). Аудит платформы этого не
  закрывает: ключу проекта Audit Logging отвечает 401 (AUD-1), действия
  evo в нём не отличить от консоли, связи с заданием и планом нет.
- **Не обещаем:** защиту от злонамеренного агента, неизменяемость,
  идентичность клиента, срок хранения, SIEM. Файл на машине пользователя,
  агент с shell может его стереть. Для ИБ — только Audit Logging платформы;
  это сказано в описании инструмента и в `docs/`.
- **Публичный или командный MCP-сервер** (если D32 пересмотрят) — аудит
  станет отдельной задачей на сервере, с идентичностью клиента. Этот журнал
  её не закрывает.

## 2. Две части

1. **Метка в облаке** — «создано evo CMCP» в самом ресурсе (описание, метка,
   label), где API это принимает. Видна с любой машины и из CI. Так уже
   работают правила групп безопасности (`evo: port …`).
2. **Локальный журнал** — для того, что метка не покрывает: сервисы без
   поля метки, оборванные операции, связь шага с заданием стека и планом.

**Первый шаг 1.4 — проба меток**, до кода журнала: по спецификациям каждого
сервиса с create — есть ли поле, куда evo может записать метку, и
сохраняется ли оно. Итог — таблица ниже. Метки у большинства сервисов —
делаем их первыми, журнал остаётся вспомогательным; у немногих — журнал
основной.

| Сервис | Поле метки | Пример значения | Нет поля — что делаем |
|---|---|---|---|
| (заполняет проба: ВМ, диск, FIP, VPC, SNAT, группа, DNS, k8s, PG, Kafka, Redis, S3, секрет, сертификат, AR, Container Apps, NLB, образ) | | `created-by: evo-cmcp` | только журнал |

## 3. Журнал: устройство

- **Одна функция** `journal.Record(tool, args, answer)`. Вызовы — только в
  реестре: в `Execute` плана (`gated`) и в `engineGated` **в обеих ветках** —
  `execute` и `live` (CLI `evo deploy` и `destroy` идут через `live(c)`,
  иначе выпадут). Стек проходит через `callTool` → тот же гейт, шаги пишутся
  сами; плюс по одной записи `stack_apply` и `stack_destroy` с `job_id`.
  Второго механизма нет: обработчик, который пишет в облако мимо гейта, —
  уже нарушение W4.
- **Два шага:** «намерение» до вызова, «итог» после (ревью Qwen на #342).
  Запись без итога — операция оборвалась; `history` показывает её как
  «итог неизвестен — проверьте `get`». Записи без итога не удаляются и не
  «закрываются» сами: только `get` даёт ответ, есть ли ресурс.
- **id** — из ответа инструмента через `createdIDs`/`createdRef`
  (`created.go`), не из аргументов. Удалённое — по `deleteTargets[tool].arg`.
  Запись `delete` — только при `existed: true` или `already_deleted`.
- **Поля записи:** время (`internal/clock`), инструмент, поверхность (CLI или
  MCP), проект, зона, маскированные аргументы, id, итог (`created`,
  `deleted`, `already_deleted`, `error` с `reason`), id операции, `job_id` и
  `state_dir`, если есть.
- **Маска секретов — своя, не H7.** H7 работает только на выходе MCP по
  HTTP, а журнал пишется локально. Секретные поля — из схемы инструмента
  (`value`, `password`, `private_key` и т. п.); одна точка с объявлением в
  реестре, новый инструмент с секретом без объявления роняет сборку.
  Такого объявления в реестре сейчас нет — это часть работы 1.4.
- **Хранение:** `StateDir` движка (у тестов — `t.TempDir()`), JSONL 0600,
  файл на дату, блокировка — `state.FileLock` (`internal/state/lock.go`:
  `flock` на Unix, `LockFileEx` на Windows), как у state и stack-jobs.
  Сбой записи не меняет ответ инструмента: одна строка в stderr.
- **Не сводим** `.evo/state.json` и stack-jobs к журналу: это текущее
  состояние, на нём держится повтор (§1). Журнал — история, ссылается на
  них (`state_dir`, `job_id`), не копирует.

## 4. Инструмент `history`

`history` в реестре и `evo history` (`CLISpec`), `readOnlyHint`, вне
согласия. Фильтры: `since`, вид ресурса, проект; `--json` = ответ
инструмента. Описание: «журнал этой машины — подсказка, а не истина: перед
удалением всегда `get`; это не аудит».

## 5. Потребители

- `evo-cleanup`: таблица на удаление — только id из журнала и метки, каждый
  проверен `get`; ресурсы по префиксу без записи — отдельной строкой «не
  трогаю без вашего слова».
- cloud-e2e: журнал раннера — артефактом; сверка «создано = удалено» в конце
  job; `cleanup_only` — по меткам, журнал — второй источник.
- Бриф Grok: инвентарь агента не нужен, если журнал агент не может править.

## 6. Инварианты (Процесс)

- каждая мутация пишет запись: тест обходит реестр, инструмент с
  `NeedsConsent` без записи роняет сборку;
- запись = маскированный ответ: значения секретных полей не попадают в файл;
- матрица сбоев: «диск недоступен / файл занят» — ответ не меняется;
  обрыв после «намерения» — запись без итога;
- `history` объявлен только для чтения и не входит в согласие.

## 7. Размер и порядок

M без ротации и фильтров; L — с ротацией, `since` и фильтрами. Порядок: проба
меток → метки → журнал → `history` → `evo-cleanup` → cloud-e2e.

## 8. Открытые вопросы владельцу

- Название файла и каталога журнала, видимое пользователю.
- Включён ли журнал по умолчанию (рекомендация — да) и можно ли его
  выключить. Решить до начала кода: если выключается — проверка внутри
  `journal.Record` (одна точка), а `history` честно отвечает «журнал
  выключен», а не пустым списком.
