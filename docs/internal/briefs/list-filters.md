# ТЗ: фильтры списков (1.8.2)

Решение владельца 11.11 (чат «релиза (4)»): общая логика отбора по всем
спискам evo, выпуск — 1.8.2 по исключению из `docs/RELEASING.md` (patch —
только исправления; фильтры — новые необязательные аргументы чтения, ничего не
ломают), отбор на стороне API — только Compute, код — сессия «1.8 — разработка
C» (Fable). Повод — отзыв: «Покажи ВМ в этой зоне и состоянии» решается у
другого CLI одной командой, у evo — нет; разрыв касается всех списков, не
только ВМ.

## Что делаем

Каждый список evo принимает фильтры одного словаря — одинаково в CLI (флаги) и
MCP (аргументы инструмента), с одним ответом. Пользователь и агент не знают
диалектов фильтра Cloud.ru (у Compute — параметры запроса, у VPC и DNS — CEL,
у Managed Kubernetes v3 — свой синтаксис, у IAM — строка через `AND`): evo
переводит сам или отбирает сам.

## Семантика — одна, у evo

- **Правило отбора определяет evo, и evo всегда проверяет им выборку**, даже
  если облако уже отфильтровало. Отбор в облаке — только ускорение и только
  там, где облако заведомо отдаёт надмножество ответа evo (точное совпадение
  зоны, состояния, id). Где семантика облака не проверена (часть имени,
  регистр) — фильтр не передаётся в облако до пробы.
- Несколько фильтров — «и». Одно значение у фильтра (список значений — позже,
  по спросу).
- `zone` — имя (`ru.AZ-2`) или UUID; проверяется по списку зон до запроса;
  неизвестная — `USAGE`, код 1, с перечнем зон (ось 1 §6).
- `state` — значения, которые evo знает для этого ресурса, объявлены в
  реестре; сравнение без учёта регистра; неизвестное значение — `USAGE` со
  списком допустимых, а не пустой список.
- `name` — часть имени без учёта регистра.
- Поля ресурса — только те, что evo уже отдаёт в элементе списка (таблица
  ниже). Нет поля в ответе — нет фильтра; добавить чтение поля — решение
  разработки по оси 4 §6, с записью в `scripts/api-contract.json`.
- Пустая выборка — успех, `count: 0`, с названными фильтрами; не ошибка и не
  «ресурса нет».

## Ответ

Прежние поля элемента без изменений. Дополнительно — применённые фильтры в
нормализованном виде (зона — «имя (id)»), сколько подошло и, где известно,
сколько всего, и где шёл отбор (облако или evo). Форма — решение разработки,
паритет `--json` команды и ответа инструмента — как у остальных (D13, D14).
Человеческий вывод CLI называет применённые фильтры строкой над таблицей.

## Согласованность — для человека и агента (требование владельца 11.11)

Фильтры — не отдельная функция, а часть одной модели команд, ответов и
подсказок evo. Правила:

1. **Что видишь — тем и фильтруешь.** Имя фильтра совпадает с именем поля
   элемента в ответе (`--json` команды = ответ инструмента): у Compute поле
   `state` — фильтр `state`, у ресурса с полем `status` — фильтр `status`;
   синонимов не вводим. Значение — в том виде, в каком оно стоит в ответе
   (регистр не важен); зона — имя или UUID, как в выводе «имя (id)».
2. **Ссылки — как у существующих аргументов.** `zone` — имя или UUID (как
   `--zone` у `disk create`, `image list`); `vpc_id`, `subnet_id` — имя или
   UUID (как `--subnet-id` у `vm create`); `flavor` — имя (как `--flavor` у
   `vm create`). Резолверы — те же функции, что у этих аргументов.
3. **CLI ↔ MCP.** Флаг `--vpc-id` ↔ аргумент `vpc_id` — существующее правило
   `CLISpec`; одна проверка `tools.CheckArgs`; один ответ; отказ до запроса —
   `USAGE`, код 1, с `reason` и списком допустимых значений, одинаково в обеих
   поверхностях. Различия поверхностей — только задокументированные (H1–H13).
4. **Человеческий вывод CLI** называет отбор строкой над таблицей: «Отбор:
   зона ru.AZ-2 (id), состояние running — 3 из 12». Пустая выборка — «Под
   отбор ничего не подошло: …», подсказка, какой фильтр снять, код 0.
5. **Справка и дополнение.** У каждого списка — пример с фильтром в справке;
   Tab дополняет значения `zone`, `state`/`status` и ссылки тем же механизмом,
   что дополняет имена сейчас.
6. **Агенту.** Словарь фильтров — один абзац во встроенном скилле и в
   карточках групп; описание инструмента перечисляет фильтры из схемы, без
   повторения общих правил. Подсказки других инструментов, которые сейчас
   говорят «найдите id в списке», могут называть список с фильтром `name`.
7. **Связность команд.** id из отфильтрованного списка — тот же, что берут
   `get`, `delete` и остальные; подсказка `NOT_FOUND` «проверьте по списку»
   ведёт к списку с фильтром. Уборка и удаление фильтрами не пользуются
   (раздел «Механизм»).
8. **Политика сервера без изменений:** фильтры доступны в `--read-only`, не
   обходят `--allow-project`, не принимают и не отдают секретов.
9. **Документы** — из реестра (`docs/tools.md`, `docs/commands.md`); README
   «В 1.8.2» и анонс называют фильтры одним абзацем с примером для человека
   и для агента.

Где правило выше расходится с тем, что уже есть (например, у `cert_list`
значения состояния — константы API `CERTIFICATE_STATE_*`, а не короткие
слова), — прежнее остаётся, чтобы не ломать; разработка называет такие места
в описании PR, выравнивание — отдельным решением.

## Подсказки, справка и агент — дёшево (требование владельца 11.11)

Фильтр, о котором не знают, не работает. Требования:

1. **Справка.** `evo <ресурс> list --help` — фильтры отдельной группой флагов,
   у каждого — допустимые значения или откуда их взять, и один пример с
   фильтром («ВМ в зоне ru.AZ-2 в состоянии running»). `docs/guide.md` —
   короткий раздел «Отбор в списках» со словарём; `docs/tools.md` и
   `docs/commands.md` — из реестра.
2. **Подсказки в ответах.**
   - Список без фильтра, в котором больше порогового числа элементов (порог —
     решение разработки, один на все списки), — одна строка-подсказка, какими
     фильтрами сузить (в CLI — внизу вывода, в ответе — поле подсказки, как у
     остальных подсказок evo). Меньше порога — без подсказки: не тратим
     токены.
   - Пустая выборка с фильтрами — подсказка, какой фильтр снять (раздел
     «Согласованность», п. 4).
   - Отказ на неверное значение — допустимые значения в самом отказе, без
     второго вызова.
   - Подсказки других инструментов, которые ведут к списку («проверьте по
     списку», `NOT_FOUND`), называют список с фильтром `name`.
3. **Агент понимает без лишних вызовов.**
   - Допустимые значения `state`/`status` — `enum` в схеме инструмента: агент
     видит их в `tools/list` и не вызывает список ради них.
   - Описание аргумента фильтра — короткое (одна строка); общий смысл словаря
     («что видишь — тем и фильтруешь», «и», пустая выборка — не «ресурса нет»)
     — **один** абзац во встроенном скилле и строка в карточке группы, а не
     повтор в каждом инструменте.
   - Встроенный скилл учит: сначала сузить список фильтром, а не читать весь
     проект; пустая выборка с фильтром — не основание создавать ресурс
     заново (проверить без фильтра или по имени).
4. **Дёшево — с числом, а не на словах.**
   - Бюджет роста `tools/list` на всю правку — в тесте бюджета описаний
     (порог называет разработка в описании PR, «Риск» сверяет); рост
     встроенного скилла — не больше одного абзаца.
   - Отбор уменьшает ответ: в тесте на мире паритета — ответ списка с
     фильтром короче ответа без него на том же мире.
   - Проверка агентом («Процесс», вместе с пробой): задача «покажи ВМ в зоне
     X в состоянии Y» — агент решает **одним** вызовом списка с фильтрами,
     без чтения всего проекта и без вызова ради допустимых значений.
     Сценарий — в волну догфудинга 1.8.

## Механизм — одна точка

- Фильтры объявляются декларативно у инструмента в реестре (`internal/tools`):
  имя, тип, допустимые значения или резолвер (зона, VPC, flavor по имени),
  поле элемента, необязательный параметр API для отбора в облаке. Один
  обработчик: проверка до запроса (`tools.CheckArgs` и резолверы) →
  параметры API, где объявлены → проверка выборки правилом evo → ответ.
  Частных случаев по имени инструмента нет (`CLAUDE.md` §2).
- Флаги CLI, схема MCP, `docs/tools.md` и `docs/commands.md` — из реестра,
  как сейчас.
- Фильтры — только у инструментов чтения. Уборка, `destroy`, «уже удалено»
  (D26), инвентари `evo-cleanup`-логики, `evo doctor` по прерванным вызовам и
  стек фильтрами не пользуются: фильтр не может спрятать ресурс от уборки.
- Уже существующие фильтры `cert_list` и `image_list` переходят на тот же
  механизм без смены имён аргументов и ответа (не ломающее).
- Новые параметры запросов API — в `scripts/api-contract.json` (job
  `contract`).

## Тесты и проверки

- Сначала тест («Процесс» — падающие тесты и инвариант класса): каждый список
  объявляет фильтры по своим полям `zone`, `state`, `name`, если элемент их
  несёт, или причину; неизвестное значение — `USAGE` до запроса; отбор в
  облаке и проверка evo дают одну выборку на мире паритета; ни один путь
  уборки и удаления не вызывает список с фильтром.
- Паритет (`TestParity_*`, `TestContract_*`, `TestReadOnly_*`); фильтры
  доступны в `--read-only`.
- Рост `tools/list` — в бюджете описаний; описания для модели — короткие,
  один абзац словаря в встроенном скилле, а не по абзацу на инструмент.
- Проба семантики отбора в облаке — job `readonly` cloud-e2e (ключ
  наблюдателя, ничего не создаёт и не тратит), два прогона: для каждого
  параметра Compute из таблицы — выборка облака против выборки evo на ресурсах
  тестового проекта. Расхождение — параметр остаётся у evo, пункт в реестр
  расхождений (`evo-internal`).
  Проба читает одну страницу (`limit=100`). На тестовом проекте её хватает:
  в run 197 самый длинный список — 78 flavor, у остальных 2–3 элемента.
  Список, заполнивший страницу, проба не проверяет и называет
  (`::warning::`): иначе обе выборки строились бы по его части (Г2 аудита
  1.8.2).
- Фрагмент `changelog.d/` — «Добавлено»; не ломающее.

## Заключение «Риска» — до «го» (`CLAUDE.md` §0, правило 7) — дано: 104

Новая поверхность аргументов у ~25 инструментов и текст для модели. Вопросы:
как фильтр обойдёт модель с терминалом тем же ключом (ничего нового: только
чтение); может ли фильтр привести агента к ложному «ресурса нет» перед
созданием дубля или уборкой; рост описаний для модели.

## Условия заключения «Риска» 104 (снизить так, 11.11)

Обязательны для PR «разработки C»; каждое — тестом или прямой строкой в
описании PR.

1. **Ни один путь записи и проверки до записи не принимает фильтров:**
   проверка свободного имени перед созданием (`nameFree`), «уже удалено»
   (D26), уборка, `destroy`, стек и прерванные вызовы читают полный список.
   Инвариант «Процесса» — на весь этот класс, а не только на уборку.
2. **Пустая выборка называет применённые фильтры и `total`** (сколько
   элементов было до отбора). Встроенный скилл говорит прямо: `count: 0` под
   фильтром — не «в проекте нет».
3. **Отбор в облаке — только после пробы** (два прогона `readonly`). Под
   фильтром список читает все страницы или отвечает ошибкой — не частичную
   выборку как полную.
4. **Ошибка резолвера ссылки** (зона, VPC, подсеть, flavor не найдены или не
   прочитались) — отказ, а не пустой список.
5. **Допустимые значения `state`/`status`** — из спецификации Cloud.ru
   (enum в описи `scripts/api-contract.json`), а не придуманные.
6. **Описания для модели** — одно заключение «Риска» на голову PR перед
   слиянием (сверка текста всех описаний фильтров разом).

## Готово, когда

Все списки из таблицы принимают фильтры в CLI и MCP; справка, подсказки и встроенный скилл называют их, агент решает задачу отбора одним вызовом; условия заключения «Риска» 104 выполнены; тесты и инвариант
зелёные; заключение «Риска» — «приемлем» или «снизить так» с выполненными
условиями; дельта-аудит другой сессией Fable без блокеров; проба — два
прогона; README «В 1.8.2» и анонс называют фильтры.
