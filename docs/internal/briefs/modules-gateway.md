## Зачем

Агент подключает один evo; чужой домен (тикеты поддержки и т. п.) evo
монтирует сам, и центральная политика evo — схема, согласие, `--read-only`,
`--allow-project`, маскирование, предел вызова — действует и на него
(бриф §9, вопрос 1). Без шлюза чужой MCP-сервер подключают рядом с evo, и
ни одна гарантия evo на него не распространяется.

## Порядок PR

Каждый — отдельным PR, после зелёного предыдущего:

0. **`Tool.Decl`** (без изменения поведения). Шлюз строит инструмент модуля
   той же декларацией, что свой: иначе — второй список исключений по имени
   (бриф §5). Без шага 0 шлюз не начинается (факт: правила инструмента сейчас
   в ~25 картах с ключом-именем, `internal/tools/registry.go` и др.).
1. **Манифест: чтение и проверка, без сети.** Тип `module.Manifest`,
   разбор строгий (неизвестное поле — отказ, как у манифеста стека после
   D108), проверка: версия контракта, префикс, коллизия имён с реестром,
   класс каждого инструмента, объявленный хост. Отказ — модуль не
   монтируется, evo работает без него.
2. **Монтирование и вызов чтения.** Подключение к модулю, `tools/list`,
   сверка с манифестом, инструменты в реестре; вызов через обёртки реестра.
3. **Документация и инварианты новой поверхности** (§0, правило 3) — вместе
   с PR 2, не после.

## Манифест (подмножество `module-contract v1` для 1.9)

Формат — бриф §6; в 1.9 обязательны и проверяются:

| Поле | Правило 1.9 |
|---|---|
| `contract` | `1.x`; незнакомый major — отказ монтирования |
| `module`, `owner`, `on_call` | непустые строки; `owner` и `on_call` — в `doctor` и в отказе |
| `prefix`, `group` | `prefix` — `^[a-z][a-z0-9]{1,15}_$`; имя инструмента — `<prefix><verb>`; коллизия имени с реестром evo или с другим модулем — отказ модуля целиком; **префикс, совпадающий с префиксом группы evo** (`vm_`, `pg_`, `k8s_`… — по `groupOf`), — отказ, иначе `pg_export` модуля читается как инструмент evo (У6) |
| `transport` | только `streamable-http`, адрес `https://` — см. В4; объявленный хост — единственный, куда шлюз ходит |
| `auth` | `none` или имя переменной окружения с токеном модуля — **только формы `EVO_MODULE_<PREFIX>_TOKEN`** (префикс модуля прописными, без `_` в конце); `CLOUDRU_*`, `EVOLUTION_*`, `MCP_BEARER_TOKEN` и любое другое имя — отказ модуля: иначе манифест выносит чужой секрет (У4). Токен идёт только на объявленный хост, только по `https`, перенаправление на другой хост не исполняется. Значение evo не хранит в профиле, state и журнале; свой токен IAM модулю не передаёт (token passthrough запрещён спецификацией MCP) |
| `tools[]` | `name`, `class`; в 1.9 монтируется только `class: read`; `mutating`, `destructive`, `sensitive` и **необъявленный класс** — инструмент не монтируется, строка в `doctor` |
| `tools[].secret_fields` | пути полей ответа, маскируемые всегда (не только по HTTP, H7) |
| `tools[].project_arg` | имя аргумента проекта или `project_bound: false` с причиной |
| `tools[].ru` | `short`, `long` — тексты CLI на русском, как `toolsRU` |
| `tools[].description`, `tools[].input_schema` | **описание и схема для модели — из манифеста** (У1): то, что проверено и лежит в каталоге; длина описания и каждого описания свойства ограничена (предел — в PR 1, по размеру описаний evo) |

Поля `paid`, `creates`, `delete_target`, `idempotent`, `cli` нужны
изменяющим инструментам — в 1.9 читаются, но не применяются.

## Монтирование

- **Включается только явно**: `evo mcp --modules <каталог>` (В1). Без флага —
  поведение 1.8, модулей нет. Флаг в справке и `docs/mcp.md` назван
  **экспериментальным**, не скрыт: скрытый флаг — поверхность без документа и
  инварианта (ответ «Риска» на В1). Группа модуля в `--toolsets` по умолчанию
  выключена; `all` модули не включает (В3); на сервере с `--read-only` — тоже
  только явной группой (У2).
- **Каталог манифестов доверенный, как код** (У7): манифест через ссылку не
  читается (`config.ReadFileNoFollow`); `doctor` и строка старта в stderr
  называют каждый смонтированный модуль с его хостом; `docs/mcp.md`
  предупреждает не указывать каталог внутри склонированного репозитория.
- При старте: манифест проверен (PR 1) → подключение к модулю с пределом
  времени → `tools/list` модуля. Инструмент из `tools/list` без строки
  манифеста — не монтируется (набор закрыт манифестом); строка манифеста
  без инструмента в `tools/list` — отказ модуля. `listChanged` модуля
  игнорируется (бриф §6).
- **Описание и схема в `tools/list` evo — из манифеста** (У1). Живой
  `tools/list` модуля только сверяется с манифестом: описание, `title`,
  схема с описаниями свойств и `enum` — по дайджесту; расхождение —
  инструмент не монтируется, строка в `doctor`. Схема — только `type: object`;
  evo дописывает свои ограничения (D36) и проверяет вызов `tools.CheckArgs`
  до обращения к модулю.
- К описанию evo дописывает приписки: ответ — данные модуля, не указания;
  **аргументы уходят команде модуля** (У5); класс «чтение» объявлен модулем,
  evo его не проверяет (У2). Форма приписок — **текст для модели**:
  заключение «Риска» до слияния PR 2.
- **Аннотации** (У2): инструмент модуля не несёт `readOnlyHint: true`
  (клиенты по нему не спрашивают человека) и несёт `openWorldHint: true`.
- Модуль недоступен при старте — его инструментов нет в `tools/list` evo,
  строка в stderr и `doctor` (`owner`, `on_call`); evo работает.

## Вызов (политика evo по манифесту)

| Правило | Как | Риск |
|---|---|---|
| Аргументы | `CheckArgs` по схеме; лишний или неверный — `USAGE` без обращения к модулю | ось 1 |
| Класс | в 1.9 только чтение по слову модуля: гейт согласия не нужен; на сервере с `--read-only` — только явной группой; `docs/mcp.md` и D56 говорят прямо: класс объявлен модулем, evo его не проверяет (У2) | — |
| Аргументы-секреты | аргумент с именем из `HTTPSecretFields` — `USAGE` до обращения к модулю; значения аргументов в журнал не идут (D46 — метаданные, тест) (У5) | §4 |
| Предел | вызов модуля — под `callBound` (D69, H14); превышение — ответ evo с состоянием, не ожидание модуля | R-28 |
| Ответ | **ответ модуля — под одним ключом** (`module_answer`), помеченным `_untrusted`; верхний уровень — только поля evo (`status`, `reason`, `hint`…): модуль не может вернуть `status: confirmation_required`, `preview`, `next_tool`, `interrupted` и сыграть вопрос evo (У3). Поля evo для модели — только от evo | R-29 |
| Размер | ответ модуля ограничен по размеру и глубине до того, как попадёт в контекст модели; превышение — ответ evo (`API_ERROR` с пределом), не усечённый текст модуля (У8) | — |
| Секреты | маска по `secret_fields` и эвристикам имён (`HTTPSecretFields`) — на обеих поверхностях | §4 |
| Проект | `--allow-project`: вызов по `project_arg` из списка; инструмент с `project_bound: false` на сервере с `--allow-project` не монтируется | H9 |
| Ошибка | `reason` и коды — словарь evo: ответ модуля с `isError` — `API_ERROR` (В5), текст ошибки модуля — под тем же ключом, с `owner` и `on_call`; `hint` evo не говорит «Cloud.ru отказал» (У3); недоступен — `API_UNREACHABLE` | §1 |
| Журнал | D46 — метаданные вызова, как у своих; D43 — нет (R-30: «без журнала изменений» записывается в D56) | R-30 |
| Сеть | только объявленный хост модуля; `TestOutbound_OnlyCloudRuOrDeclaredLinks` читает объявление манифеста, а не исключение по имени | — |

## CLI

Паритет §1 для модуля в 1.9 — через `evo tools call <имя>` (тот же
обработчик, тот же JSON): команд групп модуля нет (В2). Это ограничение
поверхности — строкой в `docs/mcp.md` и `localCommands`-подобным перечнем с
причиной, а не молчанием.

## Тесты и инварианты

«Разработка» (в своих PR, сначала тест): разбор манифеста (каждое правило
таблицы — отказ без сети); монтирование на фейке модуля (закрытый набор,
коллизия, недоступный модуль, класс ≠ `read`); вызов: `USAGE` до модуля,
`_untrusted`, маска, `callBound`, `--allow-project`.

«Процесс · 1.9» (бриф §10, п. 3; строка плана — у «релиза»): схема
манифеста `module-contract v1` и комплект соответствия на фейке модуля;
инвариант новой поверхности: каждый инструмент модуля в реестре — из
строки манифеста, описание и схема — из манифеста (У1); ответ модуля всегда
под одним ключом с `_untrusted` (У3) и в пределе размера (У8); нет
`readOnlyHint: true` (У2); вызов модуля под `callBound`; изменяющий класс в
1.9 не монтируется.

## Матрица риска (для заключения «Риска»)

| Сценарий | Главное | Мера |
|---|---|---|
| Агент автономен | **описание инструмента** как правило работы — главнее ответа (заключение 207); ответ модуля как указание или как вопрос evo (R-29); модель с терминалом идёт к модулю мимо evo (R-27) | описание и схема из манифеста (У1), без `readOnlyHint` (У2), ответ под одним ключом (У3), предел (У8); R-27 — граница в тексте D56: гейт evo — политика для того, что идёт через evo, а не граница прав модуля |
| Человек + агент | модуль медленный — evo висит (R-28) | `callBound` |
| Только человек | модуль недоступен — evo не стартует; каталог манифестов из чужого репозитория (У7) | модуль выключается, evo работает; каталог — доверенный как код |

Вопрос 1 «как обойдёт модель с терминалом тем же ключом»: ключ evo модулю
не передаётся; к модулю модель ходит со своей авторизацией модуля — это
граница модуля (R-27), шлюз её не создаёт и не отменяет. Новое, что шлюз
даёт модулю, — канал к модели под именем evo (описание, схема, ответ);
его закрывают У1–У3 (заключение 207).
