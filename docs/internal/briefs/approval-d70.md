# ТЗ D70: одобрение человеком вне агента (1.7, блок C, первым)

Черновик «1.7 — релиза», 31.10.2026. Основание: резерв D70 в `DECISIONS.md`,
строка D70 блока C в `release-plan.md`, решения владельца 31.10 (опросы
«1.7 — релиза» после пересмотра решений 1.7 с Fable). Код — только после «го»
владельца. Документ для владельца, «1.7 — разработки» и «Процесса · 1.7».

Пометки: **решено** — решение владельца; **предложение** — выбор релиза,
сессии могут оспорить до «го»; **открыто** — решает владелец по ТЗ;
**гипотеза** — нужна проверка.

## 1. Задача

Мерило 1.7 (**решено**): агент с LLM, который сам ставит `confirmed` (D10),
работает без присмотра в гибридной инфраструктуре — в проекте есть и то, что
он создал, и то, что создали люди, и ему бывает нужно удалить чужое. Сейчас
«да» модели и «да» человека неотличимы: в прогоне с LLM GLM-5.2 на 1.6.0
90 % `confirmed=true` поставлены без превью, агент удалил чужие бакет,
секреты, ВМ и адрес (`evo-internal/runs/grok-1.6.0-llm/`).

Нужно: действие **класса одобрения** (любое удаление и перезапись) выполняется
только после «да» человека по каналу, которого у агента нет. Всё остальное
агент делает сам, как сейчас.

Чего D70 не обещает (**решено**, текст D70 и H-строка `docs/mcp.md`): защиты от
обхода. Агент с терминалом и ключом, у которого есть право удаления, вызовет
API напрямую. D70 — защита от услужливой модели, которая подтверждает сама
(наблюдаемое поведение), а не от злонамеренной. Жёсткая граница — ключ агента
без права удаления и одобрение правами человека (1.8, D55).

## 2. Класс одобрения (решено)

**Любое удаление и перезапись — чьё бы ни было.** «Своё» — не критерий
(решение владельца 31.10): агент создал ресурс, через несколько дней человек
начал им пользоваться — удалять без человека нельзя.

| Инструмент | Когда в классе |
|---|---|
| `*_delete`, `destroy`, `stack_destroy`, `release_floating_ip`, `s3_rm` | всегда |
| `s3_put` | ключ уже существует |
| `k8s_kubectl`, `k8s_helm`, `k8s_apply` | изменяющий вызов (`NeedsConsent(args)`) |
| `k8s_add_addon` | `resolve_mode` `OVERWRITE` |

Без одобрения — только откат evo недоделанной части **своей же сорвавшейся
операции** в том же вызове или при его продолжении (ВМ создана, адрес не
привязался — evo убирает; `deploy_apply` по тому же `plan_id`): §1
«прерванная операция продолжается или убирается», ось 3. Это не решение
агента удалить, а часть операции создания. **Предложение:** откат — только
внутри обработчика операции, без отдельного вызова инструмента удаления;
инвариант — откат не проходит через инструменты класса.

**Предложение:** класс вызова — одна функция реестра
`approvalNeeded(tool, args)` поверх существующего объявления
(`destructiveTools` + `*_delete`, `IsDestructive`) и `NeedsConsent(args)`.
Новой карты инструментов нет; state для класса не нужен.

## 3. Ход вызова

1. Агент зовёт инструмент класса одобрения без `confirmed` — превью, как
   сейчас, с новым полем `approval: "human"` и текстом: «выполнится только
   после одобрения человеком».
2. С `confirmed=true` (CLI: `--yes`) — **не выполнение**, а ответ
   `pending_approval`: `request_id`, превью, `expires_at`, как одобрить
   (команда для человека). Код выхода и `reason` — **открыто (О2)**.
3. Человек одобряет (§4). Одобрение привязано к хэшу инструмента и
   аргументов — тот же хэш, что у S4 `preview_id`: другие аргументы — другой
   запрос.
4. Выполнение — **открыто (О3)**:
   - (а) агент повторяет вызов с `approval_id` — evo сверяет хэш, срок и
     одобрение и выполняет обычным путём (гейт, превью, D26);
   - (б) сервер выполняет сам по одобрению, агент читает
     `approval_status <id>`.
   Предложение — (а): одна точка выполнения (существующий обработчик),
   нет фоновых процессов в сервере (D69), паритет CLI и MCP без новой
   поверхности исполнения.
5. Отказ человека или истёкший срок — ответ на повтор: `approval_denied` /
   `approval_expired`, без выполнения.

Повтор безопасен (§1): повторный `confirmed` с теми же аргументами
возвращает тот же `request_id`, а не новый запрос.

## 4. Каналы одобрения 1.7 (решено)

**PIN человека.** `evo approve <request_id>` (и `evo approve --list`):
показывает превью запроса и спрашивает PIN. Одобрение списком
(**решено**, чтобы одобрение не стало рутиной): `evo approve --all` — человек
видит все ждущие запросы с превью и одобряет выбранные одним вводом PIN.
- PIN вводится только с клавиатуры, из TTY без эха; не флаг, не переменная
  окружения, не stdin из трубы — нет TTY, нет одобрения.
- В профиле — только хэш PIN (медленная функция с солью, **предложение:**
  `scrypt` или `argon2id` из `golang.org/x/crypto` — новая зависимость, решает
  «разработка»); перебор ограничен (например, 5 неверных — блок на 15 минут,
  запись в журнале).
- PIN задаёт `evo agent setup` при включении режима; выключение режима и
  смена PIN — тоже по PIN.
- Значение PIN нигде не печатается и не пишется (§4 CLAUDE.md).

**Запрос в клиенте MCP (elicitation).** Где клиент MCP объявил возможность
`elicitation`, сервер на `pending_approval` сам спрашивает человека через
интерфейс клиента (`elicitation/create`): превью и «одобрить / отклонить».
Модель ответить на него не может. **Гипотеза:** поддержка elicitation в
Claude Code и других клиентах — проверить до «го» (строка «Процессу»);
клиент без неё — только PIN. Сервер evo — свой (`internal/mcp`), запрос
сервера к клиенту — новая часть протокола у нас.

**Открыто (О4):** нужен ли PIN, если одобрение пришло через elicitation?
Предложение — нет: канал уже вне модели; но клиенты с автоподтверждением
elicitation (если такие есть) делают его модельным — тогда elicitation только
у клиентов из списка, проверенного «Процессом».

1.8 (**решено**): одобрение учёткой человека через IAM (D55), удалённый
канал (бот, push).

## 5. Где живёт политика (решено)

- Профиль `config.yaml`: `unattended: true`, хэш PIN, потолок D71 (если
  задан). Читают обе поверхности: CLI с `--yes` получает тот же
  `pending_approval`, что MCP (§1).
- `evo agent setup` по умолчанию включает режим и спрашивает PIN; уже
  настроенные профили не меняются — не ломающее.
- Голый `evo mcp` без режима — предупреждение (строка P10).
- Флаг `evo mcp --unattended=false` — **открыто (О5):** выключить режим
  флагом сервера без PIN значит дать модели, которая пишет `.mcp.json`,
  выключатель. Предложение — флаг может только включить режим, выключение —
  `evo agent setup` с PIN.

## 6. Хранилище запросов (предложение)

Файл в каталоге состояния профиля, `0600`, под блокировкой (как state):
`request_id`, хэш, инструмент, цель, превью (без значений секретов), создан,
срок (**предложение:** 24 ч), статус, кто одобрил (`pin` / `elicitation`).
Агент может прочитать и испортить файл (терминал) — это обход, вне обещания
D70; одобрение без PIN всё равно не появится, если хэш PIN хранится отдельно
и запрос подписан ключом, выведенным из PIN (**открыто (О6):** нужна ли
подпись или достаточно файла).

## 7. Ломающее и паритет

- Новые поля ответа и новый `reason` — **открыто (О2):** `pending_approval`
  — это не ошибка и не успех. Предложение — код выхода 0 нельзя (агент
  прочтёт как «удалено»; ось 3), новый `reason` `APPROVAL_REQUIRED` с
  отдельным кодом выхода; по `docs/RELEASING.md` новый код у новых путей не
  ломает старые (режим включён только у новых профилей).
- Паритет: CLI `--yes` ≡ MCP `confirmed` ≡ `evo tools call --yes`; одна точка
  — гейт реестра. Но 28 обработчиков решают о согласии сами (`inlineGates`,
  K1 — 1.8): **факт** из пересмотра с Fable. **Открыто (О7):** проверка
  одобрения — в общем гейте (тогда сначала перевести обработчики класса
  одобрения: `*_delete` там уже в общем пути? — проверить; `k8s_*`, `s3_put`,
  `stack_destroy` — в `inlineGates`) или явным вызовом в каждом из них с
  тестом-инвариантом «Процесса» (обход всех инструментов класса).

## 8. Инварианты «Процесса» (до слияния)

1. Каждый инструмент класса одобрения в режиме: `confirmed` на чужом →
   `pending_approval`, ничего не удалено (мир «чужая ВМ», «чужой бакет»,
   «чужой ключ s3», «kubectl delete»).
2. Откат недоделанной части своей сорвавшейся операции — без одобрения и
   без вызова инструмента класса; удаление ресурса, созданного агентом
   раньше, — `pending_approval`.
3. Одобрение с другими аргументами не действует; истёкшее не действует;
   повтор `confirmed` — тот же `request_id`.
4. PIN: нет TTY — нет одобрения; PIN не в выводе, ошибках, журнале, state,
   ответах MCP; ограничение перебора.
5. Паритет CLI / MCP / `evo tools call`.
6. Новый инструмент класса удаления без объявления — сборка падает.
