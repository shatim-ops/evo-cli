Версия 2, «1.7 — релиз», 31.10.2026 — после разбора Fable (два прохода),
«1.7 — разработки» (по коду `main`) и «Процесса · 1.7»

в `DECISIONS.md`, строка D70 блока C в `release-plan.md`, решения владельца

Пометки: **решено** — решение владельца; **принято** — выбор реализации,
согласованный релизом, разработкой, «Процессом» и Fable (правило 6);
**гипотеза** — нужна проверка. Вопросы владельцу закрыты 31.10.

## 1. Задача

Мерило 1.7 (**решено**): агент с LLM, который сам ставит `confirmed` (D10),
работает без присмотра в гибридной инфраструктуре и трогает и своё, и
чужое. Сейчас «да» модели и «да» человека неотличимы: в прогоне с LLM на
1.6.0 90 % `confirmed=true` поставлены без превью, агент удалил чужие бакет,
секреты, ВМ и адрес (`evo-internal/runs/grok-1.6.0-llm/`).

Нужно: действие **класса одобрения** (любое удаление и перезапись)
выполняется только после «да» человека по каналу, которого у агента нет.
Остальное агент делает сам, как сейчас.

Чего D70 не обещает (**решено**, текст D70 и H-строка `docs/mcp.md`): защиты от
обхода. Агент с терминалом и ключом с правом удаления вызовет API напрямую,
перепишет профиль или запустит evo с другим каталогом конфигурации
(`CLOUDRU_CONFIG_DIR`). D70 — защита от услужливой модели, которая
подтверждает сама (наблюдаемое поведение), а не от злонамеренной. Жёсткая
граница — ключ агента без права удаления и одобрение правами человека (1.8,
D55).

## 2. Класс одобрения

**Решено:** любое удаление и перезапись, чьё бы ни было. «Своё» — не
критерий: ресурс агента через несколько дней может быть работой человека.

| Инструмент | Когда в классе |
|---|---|
| `*_delete`, `destroy`, `stack_destroy`, `release_floating_ip`, `s3_rm`, `close_ports` | всегда |
| `s3_put` | ключ уже существует (планировщик проверяет ключ до вопроса — после F5a) |
| `secret_add_version` | всегда: подменяет значение, которым пользуются |
| `fip_attach` | адрес уже подключён к другой ВМ |
| `k8s_kubectl`, `k8s_helm`, `k8s_apply` | изменяющий вызов (`NeedsConsent(args)`) — в 1.7 (**решено**); грант «кластер на N часов» — 1.8 |
| `k8s_add_addon` | `resolve_mode` `OVERWRITE` — вместе с `k8s_*` |

**Принято:**
- Класс — существующая карта `destructiveTools` + `*_delete` (`IsDestructive`),
  пополненная `close_ports`, `secret_add_version`, `fip_attach`; условие по
  аргументам — планировщик инструмента. Новой карты нет.
- Повторный `deploy` на ту же ВМ (D62) перезаписывает приложение, а не
  облачный ресурс — вне класса; сказано в тексте D70.

**Откат — единственное исключение (принято, граница проверяемая):** без
одобрения удаляется только ресурс, чей id получен **в этом же вызове
обработчика** из ответа облака на создание — не из аргументов, не из state,
не из файла плана или задания стека; удаление — клиентом облака, не
инструментом реестра. Сегодня это одно место: загрузочный FIP после
неудачного создания ВМ (`releaseBootFIP`: `engine/deploy.go`, `provision` в
`tools.go`). Следствия:
- «продолжение операции» (`deploy_apply` по `plan_id`, повтор `provision`)
  создаёт и достраивает, никогда не удаляет;
- хвост прошлого вызова (FIP после неудачного `provision`, ВМ после сбоя
  `deploy_apply`, шаги стека) — класс; подсказки в режиме называют
  `evo approve`, а не инструмент удаления.

## 3. Ход вызова (принято)

1. Без `confirmed` — превью, как сейчас, плюс `approval: "human"`: «выполнится
   только после одобрения человеком».
2. С `confirmed=true` (CLI `--yes`, `evo tools call --yes`) — не выполнение,
   а ответ: `status: pending_approval`, `reason: APPROVAL_REQUIRED` (новый,
   в `knownCodes`), **код выхода 3** (уже значит «нужен человек»), `request_id`,
   превью, `expires_at` (24 ч), команда для человека. Не 0: агент не должен
   прочитать это как «удалено» (ось 3).
3. Текст ответа велит агенту не ждать и не повторять: закончить всё, что не
   требует одобрения, и одним сообщением отдать человеку `evo approve --list`.
4. Хэш запроса — инструмент + проект + вид и id цели **из плана** (а не
   имя из аргументов: `destroy --name` иначе при повторе разрешится в другую
   ВМ) + канонические аргументы без `confirmed`. Повтор `confirmed` с тем же
   хэшем — тот же `request_id`; ждущих запросов не больше 50.
5. Выполнение — агент повторяет тот же вызов; evo находит одобренный запрос
   по хэшу, сверяет срок и подпись и выполняет обычным путём (гейт, D26).
   Нового аргумента (`approval_id`) нет — схемы ~40 инструментов не растут.
   Фоновых процессов в сервере нет (D69).
6. Одобрение гасится, когда удаление завершено (`deleted`,
   `already_deleted`); частичный ответ (`destroying`) не гасит — повтор до
   срока идёт по тому же одобрению.
7. Вложенные шаги (`stack_destroy` → `*_delete` через `callTool`) одобрение не
   спрашивают: одобряется внешний вызов, превью называет все шаги списком.
8. Инструмент чтения `approval_list` — агент видит «ждёт / одобрено /
   отклонено / истекло».

## 4. Канал одобрения

**PIN человека (решено, принято в деталях):**
- `evo approve <request_id>`, `evo approve --list`, `evo approve --all`:
  `--all` показывает превью каждого запроса (удаление с данными — отдельной
  пометкой) и требует явного выбора номеров; один ввод PIN на выбранное.
- PIN — только из TTY без эха (`golang.org/x/term`), не флаг, не переменная,
  не stdin из трубы.
- **Подпись (принято):** `evo agent setup` создаёт пару ed25519; закрытый
  ключ зашифрован ключом из PIN (scrypt — `golang.org/x/crypto`, уже прямая
  зависимость), открытый — в профиле. `evo approve` подписывает хэш запроса;
  evo при выполнении проверяет подпись открытым ключом. Поле «approved» в
  файле без подписи ничего не значит — услужливая модель, переписавшая файл
  (как `state.json` в G2-18), одобрение не получит.
- Смена ключа и выключение режима подписываются старым ключом (по PIN);
  `evo approve --list` и `agent setup` показывают отпечаток ключа.
  Ограничение (честно): модель, переписавшая профиль целиком, создаст новую
  цепочку — это сознательный обход, вне обещания D70; отпечаток виден
  человеку.
- Блокировки перебора нет: файл блокировки агент стирает, а scrypt делает
  перебор медленным.
- `evo approve` — команда без инструмента: строка `localCommands` с причиной
  «ввод PIN человеком».

**Elicitation (запрос в клиенте MCP) — 1.8 (решено 31.10 по фактам разбора).** Факты
разбора: сервер evo не шлёт запросов клиенту (`internal/mcp/server.go`),
`initialize` не читает возможности клиента; в Claude Code ответ на
elicitation автоматизируется хуком из файла настроек проекта, который агент
может править; Codex отклоняет такие запросы без отдельной настройки;
спецификация MCP запрещает просить через elicitation чувствительное (PIN);
ждать человека внутри вызова нельзя (D69). В 1.8 — асинхронно (запрос после
`pending_approval`, ответ — в хранилище), только у клиентов, проверенных
пробой «Процесса», и только если владелец профиля включил этот канал по PIN.

## 5. Где живёт режим (принято)

- На каталог конфигурации, а не на профиль: новый профиль (`evo configure`,
  `--profile`, `CLOUDRU_PROFILE`) наследует режим — иначе «создать профиль без
  режима» становится услужливым обходом.
- `evo agent setup` по умолчанию включает режим и спрашивает PIN; уже
  настроенные каталоги не меняются — не ломающее.
- Без TTY (setup запустил агент): режим включён, PIN не задан — одобрение
  невозможно, пока человек не выполнит `evo approve --set-pin` в терминале;
  ответ говорит это прямо.
- `evo mcp` флагом может только включить режим; выключение — `agent setup`
  с PIN. Голый `evo mcp` без режима — предупреждение (строка P10).
- Хэш-материал PIN и ключи — в `credentials.yaml` (`0600`), не в `config.yaml`.

## 6. Где проверка (принято, по коду)

- Одна функция `approvalNeeded(plan)` — в `gated` после планировщика и до
  `Execute` (ось 1: отказ без записи — до вопроса) и в обеих ветках
  `engineGated` (`destroy` с целью и live-ветка `evo destroy`).
- Мимо `gated` сегодня из класса идут шесть обработчиков (`inlineGates`):
  `s3_put`, `k8s_kubectl`, `k8s_apply`, `k8s_helm`, `k8s_add_addon`,
  `stack_destroy` — переводятся на `gated` (частичный K1 по классу);
  `s3_put` — вместе с F5a; `k8s_*` — в 1.7 (решено).

## 7. Инварианты «Процесса» (до слияния; подробно — #730)

1. Каждый инструмент класса в режиме: `confirmed` → `pending_approval`, в облаке
   ничего не удалено и не перезаписано — включая созданное этим же процессом.
2. Откат: обход матрицы сбоев — откаты движка проходят без `pending_approval`
   и без инструментов класса; закрытый перечень мест, где не-delete
   обработчик зовёт `Delete*`/`Release*` облака (сейчас — `releaseBootFIP`),
   новое место без строки роняет сборку.
3. `callTool` инструмента класса — только из `handleStackDestroy`.
4. «Продолжение не удаляет»: `deploy_apply`/`provision` повтором ничего не
   удаляют.
5. Одобрение с другим хэшем не действует; истёкшее, неподписанное,
   погашенное — не действуют; повтор `confirmed` — тот же `request_id`.
6. PIN: нет TTY — нет одобрения; PIN и закрытый ключ не в выводе, ошибках,
   журнале, state, ответах MCP.
7. Паритет CLI / MCP / `evo tools call`; `already_deleted` без одобрения.
8. Инструмент класса в `inlineGates` роняет сборку; новый инструмент удаления
   без объявления — тоже.

## 8. Объём (оценки сессий)

Разработка ~4–6 дней (перевод шести обработчиков на `gated`, хранилище и
`approval_list`, `evo approve` с PIN и подписью, проверка на внешнем вызове,
H-строка, «Миграция»), «Процесс» ~3–4 дня инвариантов. Elicitation в 1.7 —
ещё ~2 дня разработки и проба клиентов — снято в 1.8. rc.1 сдвигается примерно на неделю — сдвиг принят владельцем 31.10.
