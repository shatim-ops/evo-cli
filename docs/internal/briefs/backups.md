## Зачем

Резервную копию ВМ или диска evo сегодня не делает, не находит и не
удаляет: в Compute-части кода нет ни одного запроса `/api/v1/backups` (факт:
`internal/provision`, `internal/tools`). Агенту, которому нужно «сделать
копию перед изменением», остаётся консоль; копия, сделанная там, evo не
видна — уборка её не найдёт (ось 3 §6). Волны В2 (`vm_resize`) и В7
(`vm_rebuild`) — изменения, перед которыми копия — первый шаг; без В5 у
них нет пути отката через evo.

## Что делаем

Пять инструментов с командами CLI, каждый — отдельным PR, в этом порядке:

| № | Инструмент | Команда | Класс | Запрос Cloud.ru (факт спецификации) |
|---|---|---|---|---|
| 1 | `backup_list` | `evo backup list` | чтение | `GET /api/v1/backups` |
| 2 | `backup_get` | `evo backup get <backup_id>` | чтение | `GET /api/v1/backups/{backup_id}` |
| 3 | `backup_create` | `evo backup create --vm-id <id> \| --disk-id <id> --name N` | создаёт, платно, с согласием | `POST /api/v1/backups` |
| 4 | `backup_delete` | `evo backup delete <backup_id>` | удаляет, с согласием | `DELETE /api/v1/backups/{backup_id}` |
| 5 | `backup_restore` | `evo backup restore <backup_id> --name N` | создаёт, платно, с согласием | `POST /api/v1/backups/{backup_id}/action` |

Группа реестра — новая, `backup` (карточка группы, `groupOf`), а не
`vm`/`disk`: копия — отдельный ресурс со своим id и своим списком, у неё
два вида исходного ресурса. Файл — `internal/tools/tools_backup.go`,
клиент — `internal/provision/backup.go` (тот же хост, токен, повторы и
ошибки, что у ВМ и дисков): отдельный интерфейс `BackupAPI`, который
реализует `CloudRuAdapter`, а не новые методы `CloudAPI` — интерфейс и его
фейки — файлы «разработки A» (план версии, раздел 3.2). Общие файлы (`tools.go`, `created.go`, реестр согласия,
`inventory.md`) — по одному продуктовому PR за раз, на свежем `main`.

Порядок: 1 и 2 (чтение) — сразу после заключения «Риска» на это ТЗ; 3 —
после строк «Процесса» (инварианты ниже) и до rc.1, аудит с чистого листа
открывает «релиз» (первая операция класса «платное создание»); 4 — после 3
(копию, сделанную evo, evo и удаляет); 5 — последним, после третьего
прогона Г-16.

Планы защиты (`protection_plan_*`) — отдельным ТЗ после копий (строка плана).

## Опись запросов

В каждом PR — строка `scripts/api-contract.json` своего запроса; новые
поля спецификации — в `api-contract-fields.json` только своим блоком.

| Запрос | Что шлём | Что читаем |
|---|---|---|
| `GET /api/v1/backups` | `project_id`, `limit` (≤ 1000), `offset`; отбор `name`, `state`, `resource_ids`, `resource_types`, `type` | `items[]`: `id`, `name`, `state`, `type`, `size` (МБ), `created_at`, `last_restore_time`, `resource.resource_id`, `resource.resource_type`, `resource.resource_state.name`; `total` |
| `GET /api/v1/backups/{backup_id}` | — | то же, плюс `description`, `protection_plan`, `resource.resource_exists`, `resource.resource_state` (диск: `size`, `disk_type`, `availability_zone`; ВМ: `flavor`, `disks[]`, `interfaces[]`, `availability_zone`), `tags` |
| `POST /api/v1/backups` | **только** `name`, `project_id`, `resource.resource_id`, `resource.resource_type`; `description`, если задан | копия: `id`, `state`, `type`, `size` |
| `DELETE /api/v1/backups/{backup_id}` | — | `204` без тела |
| `POST /api/v1/backups/{backup_id}/action` | `action: restore`, `resource.target_config` (диск: `name`, `disk_type_id`; ВМ: `name`, `flavor_id`, `disks[]`, `interfaces[]`) | копия (`UpdateBackupResponseSchema`); id нового ресурса — **не** в ответе (факт спецификации; см. вопрос 4) |

Факты спецификации, на которых стоит ТЗ:

- Состояния копии: `creating`, `created`, `error_creating`, `updating`,
  `error`, `deleting`, `error_deleting` (`BackupState`; у списка — тот же
  перечень под именем `CheckpointState`). Тип — `full` или `incremental`.
- `retention_policy` — «сейчас все копии хранятся бессрочно, значение —
  `null`»: копия не исчезает сама, пока её не удалят. Это довод в превью
  создания (ось 4).
- Обязательны при создании: `name`, `project_id`, `resource`. Необязательны:
  `description`, `tag_ids`/`tag_names` (одно из двух), `protection_plan_id`.
- Восстановление: `action` — только `restore`; `target_config` — по виду
  ресурса; у диска обязательно только `name`; у ВМ — только `name`, а
  `flavor_*`, `interfaces[]`, `disks[]` необязательны; спецификация
  «рекомендует добавить хотя бы один интерфейс».
- `resource.resource_exists: false` в карточке — «ресурс удалён»: копия
  живёт дольше своего исходного ресурса.
- Ответы `DELETE` — `204` без тела, отказов в спецификации — `422`
  (`HTTPValidationError`) и `401/403/500`; кодов вида
  `backup_restore_in_progress` спецификация не называет.

Что дали два прогона Г-16 (cloud-e2e 202, 206):

- копия диска 10 ГБ — `creating → created` около минуты; копия ВМ с таким
  диском — около 10 минут; обе `full`;
- в ответе копии есть поле `parent_full_backup_id`, которого нет в
  спецификации, а `retention_policy` из спецификации в ответе нет —
  кандидат в реестр расхождений (`evo-internal`, у «релиза»);
- восстановление диска создаёт **новый** диск за секунды; копия остаётся
  `created`, `last_restore_time` заполняется;
- фильтр списка `name` — по полному имени.

Гипотезы (один прогон): восстановление ВМ принимается только с типом диска
(`disks[].disk_type_name` или `disk_type_id`), хотя спецификация его не
требует; ВМ из копии создаётся дольше 5 минут; пока идёт восстановление,
копию нельзя удалить (`422` с кодом `backup_restore_in_progress`, состояние
копии при этом `created`); повтор удаления сразу — `422`
`backup_not_ready`, после исчезновения — `404`.

## Общее для волны

- **Ресурс evo.** Новый вид `backup` в реестре создаваемого
  (`createdIDs["backup_create"]`: `id`, список `backup_list`, удаление
  `backup_delete`), в описи (`inventory.md`) и в `project_bound.go`
  (`kindBackup`: проект копии — её `project_id`). Уборка cloud-e2e уже знает
  вид `backup` (`cloud-live.sh`, `KINDS`).
- **Недоверенный текст** (`untrustedFields`): `name`, `description`, имена
  тегов, `resource.resource_state.name` и имена дисков и интерфейсов в
  нём — их пишет любой с доступом к проекту.
- **Время.** Время в ответ — через `internal/clock`; ожидание — срезами в
  пределах вызова MCP (D69), не стенкой.
- **Размер** — `size` в МБ, как отдаёт платформа; человеческий вывод
  называет единицу. Пересчёта в ГБ нет: одна величина, без округлений.
- **Бюджет `tools/list`.** Рост называется замером в описании каждого PR;
  укладывается в текущий запас (строка плана «Бюджет `tools/list`»).

## `backup_list` (чтение)

- Аргументы: `resource_id` (UUID; копии одной ВМ или одного диска),
  `resource_type` (`disk` | `virtual_machine`), `name`, `state` — тем же
  механизмом фильтров реестра, что у списков волны Ф; пустой — `USAGE`.
- Строка: `id`, `name`, `state`, `type`, `size_mb`, `created_at`,
  `last_restore_time`, `resource_type`, `resource_id`, `resource_name`.
- Постранично до конца (`limit` 1000, `offset`), как остальные списки
  Compute; `total` сверяется с числом прочитанных — расхождение — пометка,
  а не тихий обрыв.
- `--allow-project`: список — проекта вызова.

## `backup_get` (чтение)

- Аргумент: `backup_id` (UUID по схеме).
- Ответ: поля строки списка, плюс `description`, `protection_plan` (id,
  имя), `resource_exists`, исходный ресурс (диск: размер, тип диска, зона;
  ВМ: flavor, диски с размером и типом, интерфейсы с подсетью, зона),
  `tags` (имена).
- Нет копии — `NOT_FOUND`, код как у остальных `*_get`.
- `resource_exists: false` — поле как есть и `note`: «исходного ресурса
  больше нет; копия хранится и тарифицируется, пока её не удалят».
- И1: человеческий вывод называет каждое поле ответа.

## `backup_create` (создаёт, платно, с согласием)

Аргументы: ровно одно из `vm_id` и `disk_id` (UUID; `RequiredOneOf`, D36),
`name` (обязателен; правило имени Compute — `create_names.go`),
`description`, `wait`.

До вопроса (ось 1):

- исходный ресурс читается (ВМ — той же функцией, что `vm_get`; диск —
  `GetDisk` клиента Compute, инструмента `disk_get` нет): нет —
  `NOT_FOUND`; его проект — проект записи (`--allow-project`);
- копия с тем же `name` у того же ресурса уже есть (`backup_list` по
  `resource_ids` и `name`) — П3: `already_exists` с её id и состоянием,
  код 0, без вопроса и без записи (повтор create не плодит копий, §1).
  **`already_exists` — не «свежая копия есть» (У1):** ответ называет
  `created_at` найденной копии и её возраст и говорит прямо, что новая
  копия не сделана: данные ресурса после этого времени в ней не сохранены.
  Мир: копия с тем же именем трёхмесячной давности — ответ называет
  возраст, а не просто `already_exists`;
- исходный ресурс в состоянии, которое копию заведомо не даст, — **не
  отказ до вопроса**, пока нет факта (гипотеза: ВМ в `error`, диск в
  `creating`); превью называет состояние и что исход неизвестен.

Превью (ось 4) называет:

- исходный ресурс: вид, id, имя, размер (у ВМ — сумма дисков и их число),
  зону;
- имя копии и что тип выберет платформа (`full` / `incremental` — evo его
  не задаёт: в запросе такого поля нет, факт);
- **цену**: «цена неизвестна, ресурс платный» — новый вид `backup` в
  `engine` (`price_class.go`, `create_preview.go`) со ссылкой на тариф,
  пока нет пробы Г-21 (ссылка на тариф хранения) и Г-23 (потребление на
  следующий день); `0 ₽` — только со ссылкой на тариф, который это
  утверждает (§6, ось 4);
- что копия хранится **бессрочно** и тарифицируется, пока её не удалят
  (`retention_policy: null`, факт спецификации), и что она переживает
  удаление исходного ресурса (`resource_exists`, факт);
- ожидание: копия диска — около минуты, ВМ — около 10 минут (два прогона);
- **сколько копий этого ресурса уже хранится и их суммарный размер (У2)** —
  из того же запроса списка, что проверка имени: хранение бессрочное и
  платное, и копия «перед каждым изменением» копит расход, которого иначе
  никто не видит.

Что evo не шлёт, с причиной (ось 4): `tag_ids`/`tag_names` — волна В6
(теги); `protection_plan_id` — планы защиты отдельным ТЗ.

После согласия (оси 2 и 3):

- `POST`; `201` — id копии в ответе сразу, `created` объявлен (D-объявление
  создаваемого, W1) с этим id;
- ожидание `created` — срезами (D69): по MCP в пределах вызова (~45 с),
  затем `status: creating`, `next_tool: backup_get` с `backup_id`; CLI ждёт
  до конца с одной строкой хода; `wait=false` — ответ сразу после `201`;
- `error_creating` / `error` — ошибка с id копии и путём: копию удалить
  `backup_delete` (она платная и в ошибке), повтор создания — после;
- потеря ответа `POST` (обрыв, 5xx после отправки) — `lostCreate`: поиск
  копии по имени и ресурсу, найдена — продолжение ожидания, не вторая
  копия;
- запись намерения (D92) называет цель — ресурс и имя копии (У5, урок
  заключения 145): вызов после оборванного спрашивает заново, а не шлёт
  второй запрос, пока копии ещё нет в списке;
- **CLI печатает id копии до ожидания (У6)** — строкой хода с id: Ctrl-C
  на десятой минуте не оставляет платную копию без id на экране (ось 3);
- отказ по квоте — `details.cause: "quota"` (#1488, #1522);
- `Billable.` — слово класса из `consentWords`.

## `backup_delete` (удаляет, с согласием)

Аргументы: `backup_id` (UUID), `confirmed`, `wait` (D74). Общий механизм
`deletePlan` / `deleteTargets` (`delete_preview.go`, `delete_gone.go`):

- нет копии (`404`) — `already_deleted` по D26, код 0, без вопроса;
- `deleting` — `deleting` по D61, без вопроса и без второго запроса;
- `error_creating`, `error`, `error_deleting` — финальные состояния по D103:
  превью называет состояние и что исход неизвестен (`failedUnseen` с
  причиной, пока Г-16 не покажет отказ платформы на копию в ошибке);
- превью называет копию (имя, размер, исходный ресурс, существует ли он) и
  что **восстановленные из неё ресурсы остаются** (диск — два прогона;
  ВМ — гипотеза), а исходный ресурс копия не трогает;
- **`resource_exists: false` (У3а)** — отдельное поле превью и
  предупреждение: «это копия данных ресурса, которого больше нет: после
  удаления данные не восстановить». Отказа без аргумента нет — согласие с
  таким текстом того же уровня, что у `pg_delete`;
- **зависимые копии (У3б)** — копии, у которых `parent_full_backup_id` —
  удаляемая (поле вне спецификации, два прогона), превью перечисляет с
  пометкой «что станет с ними, evo не проверял»; их судьба — в третий
  прогон Г-16;
- `last_restore_time` в последние 10 минут — предупреждение в превью:
  «восстановление может ещё идти; платформа отвергает удаление, пока оно
  идёт» (гипотеза: окно до ~6 минут; по состоянию копии не видно). Отказа
  до вопроса нет — нет факта, по которому его ставить.

После согласия:

- `204` — ответ по D74: ожидание исчезновения (`goneWatch`, 404 — `deleted`;
  в пределах ожидания не исчезла — `deleting` с `next_tool: backup_get`);
- `422` с кодом `backup_restore_in_progress` (гипотеза) — **не**
  `API_ERROR`-неудача удаления, а отказ «идёт восстановление»: копия не
  удалена, повтор — через несколько минут, `next_tool: backup_delete` с теми
  же аргументами без `confirmed` (R-85: согласие не переносится). Причина
  ответа — открытый вопрос 2 (новый `reason` — решение владельца);
- `422` `backup_not_ready` на повтор сразу после `204` (гипотеза) —
  `deleting` (удаление уже идёт, D61), не ошибка.

## `backup_restore` (создаёт, платно, с согласием)

План версии ставит `backup_restore` в класс «удаляет» «с превью о
перезаписи». **Факт двух прогонов другой**: восстановление диска не
перезаписывает исходный диск, а создаёт новый. Предложение ТЗ — класс
«платное создание» (как `backup_create`), с тем же отказом до вопроса и
объявлением создаваемого; что восстановление не перезаписывает, превью
говорит прямо. Это отступление от плана — вопрос 1.

Аргументы: `backup_id`, `name` (имя нового ресурса; обязателен),
`disk_type` (тип диска; по умолчанию — тип диска в копии, `resource_state`),
у ВМ — `flavor` (по умолчанию — flavor в копии), `subnet` и
`security_group` интерфейса, `public_ip` (`new_floating_ip`); `confirmed`,
`wait`.

До вопроса:

- копия читается: нет — `NOT_FOUND`; не `created` — отказ до вопроса с
  состоянием (восстанавливать не из чего);
- имя занято ресурсом того же вида в проекте — отказ до вопроса
  (`create_names.go`, как у `disk_create` и `provision`);
- у ВМ: flavor, тип диска, подсеть, группа безопасности существуют — та же
  проверка, что у `provision`; нет подсети — превью говорит, что ВМ будет
  **без сети** (спецификация: интерфейсы необязательны), а не молчит.

Превью называет: что создаётся (новый диск или новая ВМ с её дисками),
что исходный ресурс и копия не меняются, параметры нового ресурса и откуда
каждый (из копии или из аргумента), цену — как у `disk_create` /
`provision` (тот же расчёт превью), публичный IP — отдельной строкой
цены, если он запрошен.

У ВМ превью говорит прямо (У4): рядом с исходной заработает её **двойник**
— те же данные и службы на момент копии (cron, репликация, отправка почты
— всё, что было запущено), доступ как у исходной (evo пароль не задаёт);
называет подсеть, группу безопасности и её общность (`sgUseFields`) и что
публичного адреса нет, пока он не запрошен.

После согласия:

- ответ платформы — копия, а не новый ресурс (факт спецификации): id нового
  ресурса evo находит по имени **и** времени создания не раньше запроса
  (У5; `disk_list` / `vm_list`) и объявляет созданным; не нашёл в пределах
  ожидания — `status: restoring` с `next_tool` на список по имени; два
  совпадения — evo не выбирает: `restoring` с обоими id и «спросите
  человека»;
- запись намерения (D92) называет цель — копию и имя нового ресурса (У5):
  вызов после оборванного спрашивает заново; `last_restore_time` копии
  позже записи намерения — признак «восстановление из неё уже начато после
  этого вызова», второго запроса нет;
- ожидание: диск — секунды (два прогона), ВМ — больше 5 минут (гипотеза):
  срезами, как у `provision` (D69);
- потеря ответа — поиск по имени, а не второй запрос.

ВМ — отдельным PR после диска; класс «платное создание» для ВМ
подтверждается третьим прогоном Г-16 до её PR (ответ «Риска» на вопрос 1):
выход восстановленной ВМ в `running`, её диски и адреса.

## Отличия от общей части и от плана

- `backup_restore` — «платное создание», а не «удаляет» (вопрос 1).
- `backup_delete` получает отказ платформы, которого нельзя увидеть
  чтением (восстановление идёт при `created`): П4 «отказ до вопроса» для
  него неприменим; вместо — предупреждение в превью и отдельный ответ после
  согласия (вопрос 2).
- У создания копии нет операции (`operation_id`): ход читается по
  состоянию копии, `next_tool` — `backup_get`, а не `*_operation`.

## Тесты и инварианты

Каждый PR — сначала тест, падающий без правки (§4).

  `creating → created` по числу чтений, удаление с переходом
  `deleting → 404`, восстановление, отказы `422` с кодами в теле-массиве
  (как отвечает Compute, #1483).
- Паритет CLI–MCP (`TestParity_*`), `TestContract_*`, `TestReadOnly_*`:
  чтения — в `--read-only`, изменяющие — нет.
- `TestConsentNote_OneWordingAtEveryToolThatAsks`, `consentWords`:
  `backup_create`, `backup_restore` — `Billable.`; `backup_delete` —
  `Deletes data.` (копия — данные).
- Повтор: `backup_create` с тем же именем — `already_exists` с возрастом
  копии (У1);
  `backup_delete` дважды — `already_deleted` / `deleting`; потеря ответа —
  одна копия.
- Превью называет всё, что evo шлёт (ось 4), и цену по правилу «неизвестна,

- Строки «Процесса · 1.9 (инварианты)» до слияния первого изменяющего PR
