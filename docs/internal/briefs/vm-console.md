# ТЗ: консоль ВМ — `vm_console`, D110, вариант (а) (1.9)

Автор — «1.9 — разработка A (6)». Основание: решение владельца 14.11
(опрос «1.9 — релиза (3)»), строка плана 1.9 «Консоль ВМ `vm_console`
(D110) — вариант (а)», заключение «Риска · 1.9» 229 (#1838, пять условий
У1–У5). Эта редакция заменяет ТЗ под выдачу ссылки (заключения 204, 210,
214, дополнения Д1 и Д2): по варианту (а) evo выдачу консоли не заказывает
и полей консоли не отдаёт. Порядок: ТЗ → сверка «Риска» → код → заключение
«Риска» на тексты для модели до слияния (12 ч, У4).

Статус утверждений: «факт» — публичная спецификация Compute
(`virtual-machines/…/openapi-v3.yaml`) или код в `main`; поведение
платформы по прогонам — только в `evo-internal` (CMP-35, CMP-36, R-98),
здесь — правило evo и его основание без сценария.

## 1. Исходные данные

Факт, спецификация: карточка ВМ (`GET /api/v1/vms/{id}`) несёт `state`,
`is_serial_ready` («серийная консоль доступна на ВМ») и поля консоли
(`remote_console_url`, `remote_console_ws`, `remote_console_protocol`,
`vnc_url`, `vnc_ws`). Поля консоли есть также в элементе
`GET /api/v1/vms`, в ответе `PUT /api/v1/vms/{id}` (его шлёт
`vm_resize`) и `POST …/rebuild`. Выдачу консоли заказывает
`POST …/remote-console`; evo этот метод не вызывает и вызывать не будет.

Факт, код: `provision.VM` и `provision.VMDetail` полей консоли не
декодируют (`TestConsoleFieldsAreNotRead`); `is_serial_ready` тоже не
декодируется. Разрешение ВМ по имени — одна точка `resolveVMFor`;
строгий путь (два совпадения — отказ с обоими id) включается
`strictVMRef`.

Поля консоли заполняются не только по запросу evo — например, когда
человек открыл консоль в личном кабинете. Поэтому правило — «evo не
выносит», а не только «evo не выдаёт» (заключение 229).

## 2. Поверхность (У1)

- Инструмент `vm_console`, команда `evo vm console <vm_id|name>`;
  аргументы `vm_id` | `name` (ровно один, как у `vm_get`). Протокола нет:
  evo ничего не выдаёт, выбирать нечего. Одна проверка аргументов
  (`tools.CheckArgs`), паритет §1.
- **Класс — чтение.** Не `Mutating`, не в `sensitiveTools`, не в
  `destructiveTools`, не в строке H5; согласия и превью нет; на
  `--read-only` инструмент есть. Аннотация MCP — `readOnlyHint`, как у
  `vm_get` (общая точка решения).
- Привязка к проекту на сервере с `--allow-project` — существующее
  объявление цели ВМ (`kindVM`, `project_bound.go`), без нового механизма.
- **Имя ВМ (У5).** `vm_console` — в `strictVMRef`: две ВМ с одним именем —
  `USAGE` с обоими id; имени нет — `VM_NOT_FOUND`. Не «первая из списка».
- Отдельного «только для оператора» нет: агент и человек получают один
  ответ теми же флагами (решение владельца 13.11).

## 3. Ход вызова

1. Разбор ссылки на ВМ (строгий, §2).
2. Одно чтение карточки (`GetVMDetail`).
3. Ответ. Записи нет, ожидания нет, повторного опроса нет.

Ошибки чтения — общие (`errResult`); текст ошибки и тело отказа
платформы не несут полей консоли (инвариант §5, У2).

## 4. Ответ

```
{vm_id, name, state, serial_ready, console_available, where, note}
```

- `state` — состояние ВМ из карточки, через `quoteCloud` в тексте.
- `serial_ready` — `is_serial_ready` карточки; нет поля в ответе
  платформы — поля нет и в ответе evo (не `false` по умолчанию).
- `console_available` — `true` только при `state` = `running`. Основание —
  решение владельца (строка плана: «на ВМ не в `running` ответ говорит, что
  консоль недоступна»); поведение платформы — CMP-36, `evo-internal`.
- `where` — где открыть консоль. **До факта по У3** — текст «откройте
  консоль ВМ <имя> в личном кабинете Cloud.ru», без адреса и без пути по
  меню (путь не проверен — гипотеза). После факта — `url` страницы ВМ в личном кабинете
  по шаблону evo (§6), и `where` его называет.
- `note` — текст для модели (§7): страницу открывает человек после входа;
  агенту по ней идти незачем; получить консоль через evo нельзя.
- ВМ не в `running`: `console_available: false`, `note` называет
  состояние. Шаг: при `stopped` — `next_tool: vm_start` (это запись с
  согласием, не опрос); при переходных состояниях (`starting`,
  `rebooting`, `stopping`, …) — без `next_tool`: опрос ведёт к циклу, У4.
  Вопрос 2 к «Риску», раздел 9.
- Код выхода — 0 во всех случаях выше: это ответ о состоянии, не отказ.
- CLI: человеческий вывод называет каждое поле ответа (ось 4); `--json`
  = ответ инструмента.

Чего в ответе нет никогда: полей консоли, их длины, хоста, признака
«консоль кем-то открыта» (замечание 229 — кандидат, не в объёме без
строки плана), `next`, ведущего к опросу.

## 5. Секреты — инвариант (У2)

Исключений ноль: ни один инструмент, `vm_console` тоже, не отдаёт поля
консоли. Инвариант — у «Процесса · 1.9» (строка плана «Консоль ВМ
`vm_console` (D110) — вариант (а)»); код
`vm_console` сливается после него или вместе с его расширением на
`vm_console`, по согласованию с автором инварианта (правило 3 §0).
Охват по 229, У2:

1. мир подаёт метки в поля консоли карточки, элемента списка, ответа
   `PUT` и **тела отказа платформы** на запросах к ВМ;
2. вызываются все инструменты реестра, которые читают ВМ (список — по
   объявлению в реестре; новый инструмент карточки ВМ без объявления
   роняет тест), в CLI и MCP;
3. меток нет в ответе, тексте ошибки, превью, человеческом выводе, state,
   журнале, записях намерений, `evo diag export`, сыром файле записи
   ответов cloud-e2e;
4. новое поле карточки с тем же смыслом без объявления роняет сборку:
   перечень полей консоли — одна точка в `provision` рядом с типами ВМ.

Своим тестом PR кода закрепляет: `VMDetail` декодирует `is_serial_ready`
и по-прежнему роняет поля консоли (`TestConsoleFieldsAreNotRead`
расширяется полем); ответ `vm_console` на карточку с метками меток не
несёт.

## 6. Ссылка на страницу (У3)

- Адрес — шаблон evo из `vm_id` (и `project_id` конфигурации, если
  страница его требует); ни одного значения из полей консоли и никакого
  иного значения карточки, кроме `id`.
- Шаблон входит в код только после факта: человек вошёл в личный кабинет,
  открыл адрес по шаблону и попал на консоль этой ВМ. Факт записывается в
  `evo-internal` (`runs/`), сюда — «факт» с датой. Это действие в живом
  облаке — по «да» владельца.
- До факта поля `url` нет, `where` — текст (§4). Код и тесты от этого не
  зависят: шаблон — одна константа; её появление — отдельный PR
  «(продукт, 1.9)» с тестом «шаблон берёт только id».

## 7. Тексты для модели (У4)

Заключение «Риска» до слияния, 12 ч. Черновик описания:

> Where a human opens the console of one VM, by vm_id or name: state,
> serial_ready and console_available (true only while the VM is running).
> The console opens in the Cloud.ru web console after the person signs in;
> evo does not open it, hand out a console link or connect to the VM, and
> an agent has no use for the page. A stopped VM: next_tool vm_start.

Не говорит: метод выдачи API, «готово» по одному флагу без двух прогонов,
`next_tool`, ведущий к опросу.

## 8. Что снято из прежней редакции

Класс `Mutating` и `consentReveals`, H5 и `--allow-secret-export`,
`destructiveHint` и вопрос на каждый вызов, аргумент `protocol`, POST
выдачи, Д1 (ссылка этого вызова), Д2 (проверка формы ссылки перед
выводом), исключение `remote_console_*` в инварианте, проба до кода
(раздел 6 прежней редакции). Проба области `console` в cloud-e2e — у
«Процесса», условия заключения 215 в силе; к `vm_console` она не
относится.

## 9. Вопросы к «Риску»

1. Модель с терминалом тем же ключом обходит (а) прямым вызовом API —
   остаток ключа, R-98 (229). Нужно ли что-то в `note` сверх «получить
   консоль через evo нельзя»? Предложение — нет: называть путь обхода в
   тексте для модели — подсказка.
2. `next_tool: vm_start` у `stopped`: запись с согласием как следующий шаг
   чтения консоли. Альтернатива — шаг только текстом в `note`.
   Предложение — `next_tool`: так агент спросит человека, а не запустит ВМ
   сам.
3. `console_available` по одному `state` без `is_serial_ready` для VNC:
   у VNC признака готовности в карточке нет. Принимаете?
4. До факта по У3 — текст без адреса. Нужен ли вопрос владельцу на пробу
   адреса до rc.1, или (а) выходит с текстом?

## 10. Текст D110 для PR кода

`vm_console`: где человек открывает консоль ВМ — инструмент чтения
(состояние, `serial_ready`, `console_available`, где открыть); evo не
заказывает выдачу консоли и не отдаёт поля консоли ни в одном ответе,
логе, state и журнале (инвариант «Процесса»); `vm_console` по имени —
строгий (`strictVMRef`). Решение владельца 14.11, вариант (а);
заключение «Риска» 229.
