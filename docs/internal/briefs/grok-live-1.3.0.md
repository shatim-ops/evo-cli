# Бриф: живой прогон Grok на стабильном 1.3.0

Решение владельца 24.10: полный живой прогон evo `v1.3.0` агентом Grok.
Прогон начинается с чистой установки и заканчивается уборкой. Он проходит
все инструменты и сценарии: заданные здесь и придуманные самим агентом.
Скиллы сравниваются с прошлым прогоном. Расхождения живого облака с
документацией Cloud.ru собираются в реестр.

Роль Grok, серьёзность находок и формат отчёта описаны в `grok-role.md`.
Атакующие цели A–F и замер скиллов G — в `grok-attack-1.3-wave3.md`. Этот
бриф их объединяет и задаёт порядок работы: что делать параллельно, как не
тронуть чужое и что сдать в конце. Бриф пишет «Процесс и тестирование»,
отправляет владелец.

## 0. Главное правило: удаляешь только то, что создал сам

Деньги в этом прогоне не ограничение, а чужие ресурсы неприкосновенны.
Граница задаётся тремя слоями, и нарушение любого из них — остановка:

1. **Снимок до старта** (шаг 1.3). Всё, что было в проекте до первого
   create, — чужое. Его не меняешь, не удаляешь, не открываешь в нём порты,
   не привязываешь к нему адреса. Это касается и ресурсов `grok-` прошлых
   волн: их называешь в отчёте, но не трогаешь.
2. **Инвентарь созданного.** Каждый create сразу пишет строку в
   `grok-inventory-<трек>.jsonl` (раздел 4). Удалить можно только ресурс с id из
   инвентаря. Префикса имени для этого мало: имя может совпасть, id — нет.
3. **Префикс имени** `grok-<трек>-` (раздел 3.2) — для глаз человека и для
   поиска остатков.

Общая группа безопасности зоны, сеть по умолчанию, чужая ВМ — не твои,
даже если сценарий к ним ведёт. Найти такое правило — находка про evo
(G13-9: `open_ports` писал в общую группу), а не повод его удалить.

## 1. Стенд и чистая установка

### 1.1. Удалить evo полностью

Цель шага — пройти путь нового пользователя. Удаляется всё, что evo
оставил на машине (`docs/install.md`, `docs/auth.md`, «Что хранится на
машине»):

- бинари `evo` и `cloudru-vm` из `~/.local/bin` и `/usr/local/bin` (и из
  других мест, которые покажет `command -v`);
- конфигурация и кэш: `~/.config/evo`, `~/.cache/evo` и пути своей ОС по
  таблице `docs/auth.md`, а также старые `~/.config/cloudru-vm`, `~/.cloudru-vm`;
- скиллы прошлых прогонов: каталоги `evo` и `evo-*` в каталогах скиллов
  твоих клиентов, раздел evo в `AGENTS.md` / `GEMINI.md`;
- записи evo в конфигурации MCP-клиентов.

**Перед удалением** найди рабочие каталоги прошлых прогонов с `./.evo/state.json`.
Это записи о развёртываниях, и ресурсы по ним могут быть живы. Перепиши
их id в отчёт (раздел «Остатки прошлых прогонов»), а каталоги не удаляй:
это чужие ресурсы по правилу 0, их уберёт владелец.

Проверка: `command -v evo` ничего не находит, каталогов конфигурации нет.

### 1.2. Поставить 1.3.0 с нуля

По `README.md` и `docs/install.md`, как новый пользователь:

```sh
curl -fsSL https://raw.githubusercontent.com/shatim-ops/evo-cli/main/install.sh \
  | CLOUDRU_VM_VERSION=v1.3.0 sh
```

- Подпись и хэш проверяются по `docs/install.md`, «Проверка подписи»
  (cosign и `sha256sum -c`). Если cosign не установлен — поставь его и
  проверь. Неудача проверки — находка уровня «критично».
- Затем `evo version`, `evo configure` (ключ владелец передаёт отдельно),
  `evo doctor`, `evo whoami`, `evo agent setup --client <твой клиент> --skill`.
- Засеки время от скачивания до первого `evo vm list`. Каждое место, где
  пришлось угадывать или читать код, запиши: это раздел отчёта «Путь
  новичка».
- Если доступны другие ОС или Docker-образ evo, повтори установку там
  отдельным агентом. Минимум — одна ОС полностью.

### 1.3. Снимок проекта

До первого изменения выполни все списочные инструменты (`*_list`,
`list_*`, `vpc_*` списки, `s3_buckets`, `s3_ls`, `k8s_list`, `pg_list` и т. д.) и сохрани
их ответы в `grok-baseline.json`. По снимку в конце сверяется уборка
(раздел 6), и по нему же определяется чужое (правило 0).

### 1.4. Ключ и серверы

- Проект и ключ оператора владелец передаёт отдельно, на окно прогона, и
  отзывает после. Деньги не ограничены. Ограничения задают ёмкость
  платформы (DB-23: PostgreSQL в зоне без ёмкости отвечает 429) и
  атрибуция остатков.
- Каждый агент запускает свой сервер (раздел 3):

  ```
  evo mcp --allow-project <UUID тестового проекта>                                   # stdio
  evo mcp --http 127.0.0.1:<порт агента> --auth bearer --allow-project <UUID тестового проекта>
  ```

  Повторный delete уже удалённого (D26: `already_deleted`) — на сервере
  без `--allow-project`: с флагом evo по замыслу отвечает `NOT_FOUND` (H9).
  Такой сервер запускает только трек attack, на отдельном порту, и только
  для повторного delete id из своего инвентаря: ничего не создаёт. Свои
  ресурсы для целей A–D трек attack создаёт на втором сервере, с флагом,
  как остальные.
  Атакующие цели A–F берут флаги из брифа волны 3.

## 2. Что проверить

### 2.1. Каждый инструмент — и в CLI, и в MCP

Источник перечня — `evo tools list --json` установленного бинаря (имя,
группа, `mutating`). Для каждого инструмента нужен хотя бы один успешный
вызов и хотя бы один отказ. Оба делаются в MCP (`tools/call`) и той же
командой CLI (`evo <группа> <действие> … --json`). Сравниваются:

- аргументы и их проверка (одна ошибка на одну и ту же опечатку);
- ответ: `--json` команды совпадает с JSON инструмента;
- превью, `reason`, код выхода, поведение согласия.

Различия допустимы только из H1–H13 (`docs/mcp.md`). Любое другое — находка
о паритете (`CLAUDE.md` §1).

Результат — **матрица покрытия** `grok-coverage.csv`, по строке на
инструмент:

```
инструмент,группа,mutating,mcp_ok,mcp_refusal,cli_ok,cli_refusal,паритет,находки,не проверено_почему
```

Инструмент, который нельзя вызвать в тестовом проекте (нет домена для
`cert_issue_le`, нет прав организации для `org_*`), получает строку с
причиной. Пустых строк нет.

### 2.2. Заданные сценарии

Каждый сценарий проходится от превью до уборки, на каждом согласии — запись
в журнал (раздел 4). Сценарии S1–S15 волны 2 повторяются целиком: это база
сравнения 1.3.0 с rc.1. К ним добавляется то, что появилось в 1.3:

| № | Сценарий | Что держится |
|---|---|---|
| L1 | compose-проект: `deploy_plan` → `deploy_apply` → `status` → `logs` → обновление compose → `destroy` | превью с ценой; ход операции, а не только секунды (§6, ось 2); `destroy` убирает ВМ и адрес |
| L2 | ВМ с публичным адресом: `provision`, `open_ports`, `close_ports` (D37), `fip_attach` занятого адреса и адреса этой же ВМ (`already_attached`), освобождение адреса | отказ до вопроса (D35, W8); правило только в своей группе (G13-9) |
| L3 | PostgreSQL подешевле: `pg_specs` → `pg_create` → пользователь и база → строка подключения → `pg_delete` | пароль не в чате; 429 `ResourceExhausted` — `API_RATE_LIMITED`, не `NOT_FOUND` (#330) |
| L4 | Kafka и Redis: create → get → delete; кластер в `FAILED` или `DEPLOYING`, если он оказался в нём сам | ответ «удалить нельзя» прямо, с путём (§6, ось 3; DB-17, DB-21) |
| L5 | Kubernetes: `k8s_plan` → `k8s_create` → группа узлов → `k8s_kubectl`, `k8s_helm` → дополнение → `k8s_delete` | вложенное убирается до кластера |
| L6 | Сеть: VPC, подсети, маршруты, SNAT, NLB с группой целей, DNS-зона и записи | порядок удаления; запись с занятым именем — отказ до вопроса |
| L7 | Хранилище и секреты: бакет, `s3_put`/`s3_get`/`s3_rm`, удаление непустого бакета; `secret_*`; `cert_*` | значение секрета нигде, кроме `secret_value` |
| L8 | Стек: `stack_plan` → `stack_apply` → повтор того же плана → частичный сбой → `stack_destroy` | повтор не пересоздаёт; id шагов настоящие (W1) |
| L9 | Container Apps и Artifact Registry: create → get → logs → delete | 499 «not found» — `already_deleted` при повторном delete (D26, #330) |
| L10 | Повтор и обрыв для каждого create и delete: повтор во время операции и после; отмена запроса, закрытие сессии MCP, обрыв HTTP; Ctrl-C в CLI | без дублей; «удалено» значит «нет»; опечатка в id — не успех; прерванное продолжается или убирается |

### 2.3. Свои сценарии агента

Каждый агент придумывает сам **не меньше пяти сценариев**, которых нет в
списке выше и в S1–S15, и проходит их так же, с журналом и уборкой. Это
сценарии реального пользователя. Направления, с которых можно начать
(список не закрыт):

- цепочки через несколько групп: приложение на ВМ → DNS-запись →
  сертификат → балансировщик перед двумя ВМ;
- «переезд»: создать в одной зоне, перенести данные, удалить старое;
- изменение живого: увеличить диск под нагрузкой, сменить группу узлов,
  обновить compose, повернуть секрет;
- то, что человек скажет неточно: «подними базу как у прошлого проекта»,
  «удали тестовое», «почему дорого»;
- сбои посреди сценария: ресурс удалён в консоли (владелец по просьбе),
  ключ отозван, сеть пропала.

В отчёте каждый свой сценарий — с формулировкой задачи человека, шагами и
итогом. Если сценарий нашёл дефект, укажи, почему заданные сценарии его не
покрывали: это нужно для инварианта (`CLAUDE.md` §5).

Отдельно ответь на пункты 1–3 и 13 своего интервью о скиллах: что

### 2.6. Реестр расхождений живого облака

Ты это уже делал на волне 2 (DB-17, NET-15, DB-22, CAP-3). По ходу прогона
каждое поведение API, которое расходится со спецификацией или
документацией Cloud.ru, записывай в файл `grok-discrepancies.md` в формате
`docs/internal/cloudru-discrepancies.md`:

```
#### G130-API-<N>. <одна строка: что не так>
<класс: расхождение | нет в документации | ошибка API> · <подтверждено вживую (N из M) | гипотеза>
- **Спека / Док:** <ссылка и цитата>
- **Живое:** <дата, время UTC, зона, метод и путь, код HTTP, суть тела — без id и адресов>
- **Влияние:** <что ломается у клиента>
- **Просим:** <что изменить>
```

- Сначала сверься с реестром. Уже описанное — строка «уже есть: <ID>,
  подтверждено N из M» или «поведение изменилось: …». Это не новый пункт.
- «Подтверждено» — только с повтором и счётом «N из M». Один раз —
  «гипотеза» с описанием пробы.
- Без ID проектов и ресурсов, IP, ключей, имён ресурсов проекта: реестр
  передаётся командам Cloud.ru и попадёт в публичный репозиторий. Имена
  образов общего каталога публичны. Тело ответа — коды и имена полей, а не
  значения. Пример строки «Живое»: «24.10, 14:30 UTC, ru.AZ-2, `POST
  /api/v1.1/vms` → 422, `code: wrong_image`, поле `message` — «Image with
  this id is not found»; образ есть в каталоге (3 из 3)».
- Дефект evo — не пункт реестра (он о платформе): это находка `G130-<N>`.

## 3. Параллельная работа

Последовательный прогон всех инструментов займёт слишком долго. Работай
командой агентов.

### 3.1. Роли

- **Координатор** — один. Делает снимок (1.3), выдаёт треки, ведёт общий
  инвентарь и сводную матрицу. Решает, когда трек может начать
  создавать кластер (3.3). Сам ресурсов не создаёт. В конце сверяет уборку
  со снимком.
- **Агенты треков** — по одному на трек, каждый со своим сервером MCP,
  своим рабочим каталогом и своими журналами.

### 3.2. Треки

| Трек | Префикс | Что |
|---|---|---|
| read | — | 2.1 для всех инструментов чтения; атака F; ничего не создаёт |
| vm | `grok-vm-` | L1, L2, диски, образы, плавающие IP |
| net | `grok-net-` | L6, SNAT, NLB, DNS |
| data | `grok-data-` | L3, L4 |
| k8s | `grok-k8s-` | L5 |
| store | `grok-st-` | L7, L9 |
| stack | `grok-stk-` | L8, цель E |
| skills-0, skills-1 | `grok-sk0-`, `grok-sk1-` | 2.5 без скиллов и со скиллами — **два разных агента** с одинаковой моделью и клиентом, без общего контекста |
| attack | `grok-atk-` | цели A–D, повтор и обрыв (L10) поверх ресурсов своего трека |

Свои сценарии (2.3) каждый агент проходит в своём треке и со своим
префиксом.

### 3.3. Чтобы параллельность не ломала прогон

- **Рабочий каталог — у каждого свой.** `deploy` хранит состояние в
  `./.evo/state.json` рабочего каталога: два агента в одном каталоге
  перепишут состояние друг друга.
- **Кластеры** (Kubernetes, PostgreSQL, Kafka, Redis): деньги не ограничены,
  но ёмкость зоны ограничена. Одновременно — не больше двух кластеров
  одного вида на весь прогон. Порядок:
  1. Перед `*_create` кластера агент пишет в свой `grok-inventory-<трек>.jsonl` строку
     `op: reserve` с видом кластера и ждёт ответа координатора.
  2. Координатор отвечает «ok» или «wait» по счёту строк `reserve` без
     парного `release`.
  3. После удаления кластера или отказа в создании агент пишет `release`.
  Без «ok» кластер не создаётся. На 429 `ResourceExhausted` — смена зоны,
  а не повтор в цикле.
- **Нагрузка на облако:** суммарно по всем агентам — не больше 10 запросов
  в секунду. Нагрузочные цели (H8, H12) — только против своего локального
  сервера.
- **Общие ресурсы проекта** (группа безопасности зоны, сеть по умолчанию)
  — только чтение, правило 0. Трек, которому нужна группа, создаёт свою.
- **Своё и чужое:** агент удаляет только то, что есть в инвентаре
  **с его треком**. Чужой трек — даже твой коллега — это чужое.

## 4. Журналы

Все файлы — JSON Lines, строка пишется сразу после ответа, а не в конце:
обрыв не должен стирать журнал. Каждая строка содержит `ts` (UTC), `agent`,
`track`.

| Файл | Строка на | Поля |
|---|---|---|
| `grok-inventory-<трек>.jsonl` (у каждого трека свой; координатор читает все и сводит в конце в `grok-inventory.jsonl`) | каждый create, delete, reserve и release | `op` (create/delete/reserve/release), `tool`, `surface` (mcp/cli), `id`, `name`, `kind`, `zone`, `status` (ответ) |
| `grok-consents-<трек>.jsonl` | каждый вызов с `confirmed: true` | вызов, превью (целиком), результат; совпали ли превью и результат |
| `grok-calls-<трек>.jsonl` | каждый вызов | инструмент, аргументы без секретов, `reason`, код выхода, время |

Журналы и `grok-baseline.json` содержат реальные id. Они идут только
владельцу, отдельно от отчёта: не коммитятся, не прикладываются к issue и
PR, не вставляются в чат с другими. Обезличены — то есть без id проектов и
ресурсов, адресов и имён ресурсов проекта — только `grok-coverage.csv` и
`grok-discrepancies.md`.

## 5. Стоп-условия

Остановись, убери **своё** и сообщи владельцу, прежде чем продолжать, если:

- вызов изменил, удалил или затронул ресурс не из инвентаря своего трека;
- результат не совпал с превью: другой ресурс, лишний ресурс, цена выше
  превью;
- создание дало дубль после повтора;
- после уборки сценария что-то осталось и не удаляется. Останавливается
  только этот трек, остальные продолжают. Остаток с id и ответом evo — в
  отчёт; следующий сценарий трека начинается только по слову владельца;
- ключ отозван или окно прогона закончилось. Незавершённая уборка —
  первой строкой отчёта.

Кластер, который не создался, повторяется по одному разу в другой зоне. Дальше
— только по слову владельца.

## 6. Уборка и сверка

1. Каждый трек убирает своё после каждого сценария, в порядке, обратном
   созданию: вложенное раньше родителя. Пример: группы узлов и дополнения —
   раньше кластера, базы и пользователи — раньше PostgreSQL, маршруты —
   раньше VPC, диск — после отсоединения, адрес — после отвязки.
2. В конце координатор снимает те же списки, что в 1.3. Разница со снимком
   должна быть пустой: каждый id из инвентаря с `create` имеет `delete` и
   отсутствует в списках.
3. Удалить нельзя (платформа отвергает удаление: `FAILED`, DB-17, DB-21) —
   ответ evo обязан сказать это прямо (§6, ось 3). Такой ресурс идёт в
   отчёт: id, вид, что ответил evo, что ответила консоль.
4. Проверь расход: `billing_consumption` за окно прогона и начисления за
   ресурсы, которых уже нет (DB-22).

## 7. Отчёт

Один файл отчёта и приложения. Номера новых находок — `G130-<N>`, общие с
волной 3. Обход исправленной находки волн 1–2 — её старый номер с суффиксом
(`G13-9b`, `grok-role.md`, раздел 7), а не новый `G130`. Серьёзность — по
`grok-role.md`, раздел 6.

1. **Первая строка:** остатки после уборки (или «остатков нет, сверка со
   снимком пустая»).
2. **Находки** `G130-<N>` по шаблону `grok-role.md`. В «Шагах» — точные
   вызовы обеих поверхностей.
3. **Строка по каждой цели:** A–G волны 3, L1–L10, S1–S15, 2.1, 2.3, 2.6 —
   «находки G130-…» или «проверено, способы: …». Цель без строки
   считается не проверенной.
4. **Свои сценарии** (2.3): задача, шаги, итог, почему заданные их не
   покрывали.
5. **Скиллы** (2.5): таблица «задача × прогон (rc.1 / 1.3.0 без / 1.3.0
   со)» с метриками и вывод по порогу §10.
6. **Сравнение с волной 2:**
   - сколько находок волн 1–2 исправлено на деле;
   - сколько вернулось;
   - что стало лучше и хуже по числу вызовов и ошибок агента.
7. **Путь новичка** (1.2): время до первой команды, места, где пришлось
   угадывать.
8. **Остатки прошлых прогонов** (1.1, 1.3) — список для владельца, без
   действий.
9. **Приложения:** `grok-coverage.csv`, `grok-discrepancies.md`,
   `grok-baseline.json`, журналы раздела 4.

## 8. Чего не делаешь

- Не трогаешь ресурсы не из своего инвентаря (правило 0) и не удаляешь
  остатки прошлых прогонов.
- Не атакуешь API Cloud.ru и чужие проекты, не создаёшь нагрузку сверх
  раздела 3.3.
- Не пушишь, не открываешь PR и issue, не запускаешь workflow;
  GitHub-коннектор выключен (`grok-role.md`, 4.2).
- Не публикуешь реальные id, адреса, ключи: всё — только владельцу.
- Не исправляешь сам: находка и одна строка о направлении исправления.
