# ТЗ: `vm_get` с группами безопасности и сводная диагностика ВМ по id (1.9)

Автор — «1.9 — разработка A (4)». Основание: план 1.9, строки «Возможности
для дежурной смены» (сводная диагностика ВМ по id: состояние, интерфейсы,
адреса, подсети, группы безопасности и правила; проверка, не выполненная по
IAM, названа в ответе) и «Поручение преемнику «1.9 — разработки A» — A(4)»,
пункт (1). Новая поверхность и текст для модели — заключение «Риска · 1.9»
до кода (§0, правило 7). Получено 13.11 — заключение 209, «снизить так»:
вариант A принят, шесть условий (У1–У6) внесены ниже и сведены в разделе 8.

Статус утверждений: «факт» — публичная спецификация Compute
(`virtual-machines/…/openapi-v3.yaml`, прочитана 13.11) или код в `main`
(3b8f07c); остальное — «гипотеза».

## 1. Что даёт платформа

Факт, спецификация:

- `GET /api/v1/vms/{vm_id}` — карточка ВМ: `state`, `interfaces[]` с `id`,
  `name`, `ip_address`, `type`, `primary`, `state`, `floating_ip{id,
  ip_address, state}`. **Групп безопасности и подсети у интерфейса в
  карточке нет** (`api-contract.md`, 3.1). В той же карточке — `vnc_url`,
  `vnc_ws`, `remote_console_url`, `remote_console_ws`: поля консоли
  (заключение «Риска» 204, У1).
- `GET /api/v1/interfaces?project_id=…&vm_id=…` — интерфейсы ВМ;
  `project_id` обязателен, `vm_id` — фильтр. У элемента: `security_groups[]
  {id, name, state}` (обязательное поле), `subnet{id, name, state,
  routed_network, subnet_address}`, `floating_ip{id, ip_address, state,
  name}`, `state`, `primary`, `vm`. Ответы: 200, 401, 403, 422, 500.
- Правила групп — в `GET /api/v1/security-groups?project_id=…` (поле
  `rules`, его уже читает `list_security_groups`) и в
  `GET /api/v1/security-groups/{id}/rules`.
- Расхождение спецификации: `interface_security_enabled` в `required`
  ответа, но не в `properties` — уже записано для тела создания
  (`api-contract.md`, `scripts/api-contract.json`).

Факт, код: `ListInterfaces` (`internal/provision/adapter.go`) читает
`/api/v1/interfaces?project_id=` целиком (D105, `open_ports` —
`sg_shared.go`); тип `provision.Interface` берёт только `id`, `vm`,
`security_groups{id,name}`. `vm_get` строит ответ явным перечнем полей
(`tools_vm.go`, `handleVMGet`) — полей консоли в нём нет; закрепляющего
теста нет.

Гипотеза (один прогон, 204; заключение «Риска» 155): живой
`GET /api/v1/interfaces` ответил 422. Подробности — `evo-internal`. До
второго прогона код считает отказ списка обычным исходом, а не редкостью.

## 2. Поверхность — вариант и рекомендация

| | A. `vm_get` + аргумент `diagnose` (рекомендую) | B. Новый инструмент `vm_diagnose` |
|---|---|---|
| Точка сборки ответа о ВМ | одна (§2, §3) | две, расходятся со временем |
| Паритет | `evo vm get <id> [--diagnose]` | ещё одна команда и строка реестра |
| Цена обычного `vm_get` | +1 запрос (интерфейсы ВМ) | без изменений |
| Риск для агента | `vm_get` после `vm_start`/`vm_stop` (`next`) тоже получает группы | агент должен знать про второй инструмент |

Рекомендация — A: диагностика — это та же карточка ВМ с большим числом
проверок, а не другая сущность.

### 2.1. `vm_get` без `diagnose` (каждый вызов)

К каждой строке `interfaces[]` — `security_groups: [{id, name, state}]` и
`subnet: {id, name, cidr}` из `GET /api/v1/interfaces?project_id&vm_id`
(один запрос, сопоставление по `id` интерфейса). Остальное — как сейчас.

**У1.** Добавочный запрос без `diagnose` — одна попытка с коротким пределом
(порядка предела чтений превью), без цикла повторов `doWithRetry`: не
ответил — `not_checked`, а не ожидание. `vm_get` выпущен и стоит шагом
`next` после `vm_start`/`vm_stop`; секундное чтение не становится ожиданием
повторов из-за списка, отказ которого — гипотеза (один прогон). С
`diagnose` — обычные повторы транспорта.

### 2.2. `vm_get` с `diagnose: true`

Сверх 2.1:

- `security_groups[]` верхнего уровня — каждая группа ВМ один раз: `id`,
  `name`, `state`, правила (`direction`, `ip_protocol`, `port_range`,
  источник/назначение, `state`) и короткий вывод «открыто в интернет:
  порты …» тем же `sgrules`, что у `open_ports` (одна точка правила, без
  нового разбора);
- `checks[]` — что evo проверило и итог: состояние ВМ (`running`?),
  состояние каждого интерфейса (`created`?), у основного интерфейса есть
  адрес, публичный адрес в состоянии, где он работает, группа в рабочем
  состоянии. Итог проверки — `ok` | `problem` с фактом («интерфейс в
  состоянии `error`») | `unknown` — состояние, которого нет в перечне
  спецификации или смысл которого evo не знает, называется как есть
  («состояние `X`, evo его не знает»), не `ok` и не `problem` (**У3**;
  перечни — буквой спецификации, тест по каждому значению);
- `exposure` — факты доступа, без оценки (**У4**): какие входящие порты и
  с каких источников открыты правилами групп ВМ, отдельно — «открыто в
  интернет: порты …» (считает тот же `sgrules`, что у `open_ports`, с его
  известными пределами — правило с группой-источником, R-88; проверка
  говорит, чего не учла). Входящее правило на 22 из `0.0.0.0/0` — не
  `problem` (SSH с ним как раз доступен); отсутствие правила на 22 — тоже
  факт, не `problem` (ВМ может быть без SSH). Ответ не называет ни
  `close_ports`, ни `open_ports`, `next` нет;
- `result` — один итог верхнего уровня (**У2**): `ok` (всё проверено, ни
  одного `problem`) | `problem` (есть хотя бы один) | `incomplete`
  (проверено не всё: непустой `not_checked` или проверка `unknown`).
  Непустой `not_checked` никогда не читается как «в порядке» — ни в JSON,
  ни в первой строке человеческого вывода;
- `not_checked[]` — проверка, которую evo не выполнило, с причиной: `403` —
  «у ключа нет права читать …» (IAM), `422`/`5xx`/тайм-аут — «облако не
  ответило на …» с кодом. Поле то же, что у `k8s_add_addon` (`not_checked`).

Чего диагностика не делает: не ходит на ВМ (SSH, консоль), не читает
журналы и историю операций ВМ (в публичном REST Compute её нет — строка
плана «Возможности для дежурной смены»), ничего не меняет.

## 3. Отказы и частичные ответы

- Карточка ВМ не прочитана — ошибка, как сейчас (`NOT_FOUND` и прочее).
- Интерфейсы, группы или правила не прочитаны — ответ **не** ошибка: поля,
  которые не узнаны, отсутствуют, а `not_checked` называет, что и почему.
  Без `diagnose` — то же поле `not_checked`: `vm_get` не падает из-за
  дополнительного чтения (сейчас он им не пользуется — регрессия была бы
  ломающей).
- Ответ никогда не говорит «групп нет», если список не прочитан: пустой
  список и непрочитанный различаются (как `interfaces_unread` у
  `open_ports`).
- Повторы и тайм-ауты — общий `doWithRetry`; на сервере MCP — общий лимит
  вызова. Новых лимитов нет.

## 4. Политика и секреты

- Только чтение: без согласия, разрешён с `--read-only`; на сервере с
  `--allow-project` — привязка ВМ к проекту, как у `vm_get` сейчас
  (`project_bound.go`); класс в реестре не меняется.
- **Инвариант к У1 заключения 204** (вместе с D110, пишу в этом же PR кода):
  ни один читающий инструмент, чей ответ строится из карточки ВМ, не отдаёт
  `vnc_url`, `vnc_ws`, `remote_console_url`, `remote_console_ws`; тест
  подаёт карточку с этими полями и ищет их значения во всём ответе и
  выводе CLI. Ответ строится явным перечнем полей, а не копией карточки.
- Правила групп — не секрет (их уже отдаёт `list_security_groups`); новых
  данных о проекте инструмент не раскрывает.
- **У5. Чужой текст помечен.** Имена групп, имена и описания правил, имена
  подсетей приходят из облака: новые поля — в `untrustedFields` у `vm_get`
  (`internal/tools/untrusted.go`); в человеческом выводе и в текстах
  проверок — в кавычках, одной строкой (`quoteCloud`).
- **У6. Размер ограничен.** Правил группы в ответе — не больше N (число —
  в PR кода), с полями `rules_total` и строкой «и ещё K:
  `list_security_groups`».

## 5. Паритет и вывод

- CLI: `evo vm get <id|name> [--diagnose]`, `--json` = ответ инструмента.
  Человеческий вывод называет каждое поле (§6, ось 4): группы у
  интерфейса, при `--diagnose` — первой строкой итог `result`, затем
  таблица проверок, `exposure` и строка «не проверено: … (причина)». Код
  выхода 0 и при `problem`, и при `incomplete` (диагностика нашла — не
  ошибка вызова; скрипт читает `result`) — принято в заключении 209.
- Описание `vm_get` (текст для модели): «… security groups and subnet of
  each interface; diagnose: true also reads the rules of each group and
  returns checks and not_checked». Окончательный текст — в PR кода.

## 6. Тесты до кода

1. Карточка + список интерфейсов → у интерфейса группы и подсеть;
   сопоставление по `id`, чужие интерфейсы списка не попадают.
2. Список интерфейсов отвечает 403, 422, 500 → `vm_get` без ошибки,
   групп нет, `not_checked` с причиной; CLI и MCP одинаковы (паритет).
3. `diagnose`: группа с правилом `0.0.0.0/0` на 22 → `exposure` называет
   «открыто в интернет: 22», в `checks` — ни одного `problem` из-за этого и
   ни слова `close_ports`; группа в `error` → `problem`; правила не
   прочитаны → `not_checked` и `result: incomplete`, а не «правил нет».
4. Каждое значение перечней состояний спецификации (ВМ, интерфейс, адрес,
   группа) → `ok` или `problem` по таблице; значение вне перечня →
   `unknown` и `result: incomplete` (У3).
5. Без `diagnose` список интерфейсов не отвечает → одна попытка, ответ в
   пределе, `not_checked` (У1); с `diagnose` — повторы транспорта.
6. Имя группы и описание правила с переводом строки и управляющими знаками
   → в выводе одной строкой в кавычках; поля — в `untrustedFields` (У5).
7. Группа с правилами сверх N → N правил, `rules_total`, строка «и ещё K»
   (У6).
8. Инвариант консоли (раздел 4) — по всем читающим инструментам карточки
   ВМ, новый такой инструмент без объявления роняет тест.
9. Опись запросов: `GET /api/v1/interfaces` с `vm_id` — строка в
   `scripts/api-contract.json` (поля `subnet.*`, `security_groups[].state`).
10. `TestParity_*`, `TestContract_*`, `TestReadOnly_*`.

Мир паритета — общий файл: правку согласую с автором открытого PR, который
его трогает (§0, правило 3).

1. Вариант A против B: добавочный запрос в каждом `vm_get` (в том числе в
   `next` после `vm_start`/`vm_stop`) приемлем или группы — только при
   `diagnose`?
2. Код выхода CLI при `problem`: 0 (рекомендую: вызов удался) или
   отдельный ненулевой — для скриптов дежурной смены? Второй — новый код и
   ломающее для `evo vm get --diagnose` с первого дня не будет, но

3. Проверка «SSH открыт в интернет» — подсказывает ли она агенту закрыть
   порт без вопроса человеку? Ответ не даёт `next` на `close_ports`; это
   достаточно?
4. Как обойдёт модель с терминалом тем же ключом: прочтёт те же три пути
   API; evo нового доступа не даёт. Остаток — общий для ключа.

## 8. Заключение «Риска» 209 (13.11) — что принято

Вопросы 1–4 раздела 7: вариант A — да, группы в каждом `vm_get` — да при
У1; код выхода 0 — да, с полем итога (У2); «SSH открыт» — факт в `exposure`,
не `problem` и без `close_ports` (У4); обход моделью с терминалом — нового
доступа нет. Условия У1–У6 внесены в разделы 2.1, 2.2, 4, 5, 6.

Не установлено (заключение 209): отвечает ли живой список интерфейсов с
фильтром `vm_id` (один прогон без фильтра — отказ); полные перечни
состояний интерфейса и адреса. Дальше: описание `vm_get` и тексты проверок
(для модели) — на заключение до слияния кода.
