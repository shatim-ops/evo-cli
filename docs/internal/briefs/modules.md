# Модули в evo CMCP: как чужой домен встраивается в один MCP-сервер

Предложение сессии «Продукт и стратегия», 29.10.2026. Черновик для решения
владельца. Данные: срез кода на `c69b294` (1.5.0-rc.1), ответы сессий
«1.6 — разработка», «Процесс · 1.5 (2)» и «1.5 — релиз» от 29.10 (их
мнения — данные, не решения), первичные источники в конце.

## 1. Задача и вывод

**Задача.** Команды компании делают MCP-серверы для своих доменов. Компании
нужен один MCP, а не десять. Нужен контракт, по которому команда сама
встраивает свой домен в evo CMCP как модуль, а evo не пишет код за неё.

**Вывод в пять строк.**

1. Встраивать чужой код в бинарь evo нельзя: репозиторий публичный, сборка
   и подпись привязаны к нему; частная сборка — второй продукт с тем же
   именем (§4, вариант А).
2. Единственный реалистичный путь — **evo как шлюз**: модуль остаётся
   отдельным MCP-сервером своей команды, evo монтирует его по **манифесту
   модуля** и применяет свою политику (согласие, `--read-only`,
   `--allow-project`, маскирование H7, журнал D43) ко всему, что проходит
   через него (§4, вариант В).
3. Шлюз доказывает только то, что проходит через него. Класс инструмента
   («чтение» или «пишет») объявляет модуль; ложь в манифесте обходит гейт.
   Поэтому **первый этап — только модули на чтение**, умолчание для
   необъявленного — «изменяющий», выключен, пока не включат.
4. Перед шлюзом нужен **шаг 0 в самом evo**: свернуть 25 карт «имя
   инструмента → правило» в одну декларацию на инструмент (`Tool.Decl`).
   Без этого модуль не встроить ни по одному варианту; для своих
   инструментов это уже окупается (новый инструмент сегодня — около 20
   списков, #567).
5. Перед стартом владелец должен ответить на вопрос, который поставила
   сессия релиза: **руководству нужна одна точка входа или одна политика?**
   Клиенты агентов уже держат несколько серверов; «один MCP» сам по себе
   даёт мало. Если нужна политика — контракт модуля и комплект соответствия
   дают её и без шлюза; шлюз становится обязательным, когда появится
   hosted-поверхность evo для веб-клиентов (записка «локальный vs публичный
   MCP», этапы A–B).

Рекомендуемый порядок: шаг 0 (1.7) → контракт `module-contract v1` и
комплект соответствия (1.7–1.8, «Процесс») → пилот шлюза на одном модуле
только на чтение (1.8) → изменяющие чужие инструменты не раньше 2.0 и не
раньше, чем комплект соответствия докажет оси 1 и 3 на фейке модуля.

## 2. Что на самом деле просят и чего не просят

| Что звучит | Что за этим стоит | Что даёт решение |
|---|---|---|
| «Один MCP-сервер» | Агент видит одну точку, одну настройку клиента | Для локальных агентов (stdio) это удобство: `evo agent setup` и так пишет конфиг шести клиентов; для веб-клиентов и агентов платформы — только с hosted evo (D32 сейчас запрещает) |
| «Контракт для коллег» | Чтобы команды не изобретали каждая свою модель согласия, маскирования, ошибок | Это главная ценность: единая политика и единый словарь ответов (`status`, `reason`, коды выхода, `confirmation_required`) |
| «Они встраиваются сами» | evo не становится узким местом и не отвечает за чужой код | Значит, граница ответственности и SLA должна быть в контракте, а не в коде |

Критика исходной постановки:

- **Контекст агента.** `tools/list` evo — 155 инструментов, около 118 КБ и
  29 тыс. токенов при храповике `toolsListBytes`
  (`internal/mcp/limits_test.go:57`). Каждый модуль прибавляет. Anthropic и
  Cloudflare решают это ленивой загрузкой (tool search, code mode). «Один
  сервер со всеми доменами» без скоупа ухудшает агента, а не улучшает.
- **Радиус поражения.** Один процесс со всеми доменами — одна точка
  компрометации: токен шлюза даёт всё. Сегодня у evo один bearer-токен на
  сервер по HTTP (именованные токены — план 1.7).
- **Учётные данные.** У чужого домена своя авторизация, не IAM Cloud.ru.
  Спецификация MCP запрещает пробрасывать чужие токены через сервер (token
  passthrough: «MCP servers MUST NOT accept any tokens that were not
  explicitly issued for the MCP server»). Значит, модуль держит свои
  креды у себя, а evo к ним не прикасается — и не может их проверить.

## 3. Как это делают другие

| Кто | Модель | Что берём | Чего не повторяем |
|---|---|---|---|
| Спецификация MCP 2025-11-25 | Имена инструментов уникальны внутри сервера; коллизии между серверами решает клиент префиксом; аннотации `readOnlyHint`/`destructiveHint` — «untrusted unless from trusted servers»; proxy-сервер — отдельный класс с правилами (confused deputy, token passthrough) | Префикс домена в именах; аннотации — объявление, а не доказательство; шлюз обязан вести своё согласие на клиента | Доверие аннотациям чужого сервера |
| Docker MCP Gateway и MCP Registry | Каталог: `server.yaml` с объявленными секретами, env, инструментами (`tools.json`), источником и коммитом; PR с ревью команды Docker и CI; образы с подписью, SBOM, provenance; шлюз с интерцепторами и политикой регистрации (Cedar) | Манифест как единица приёмки; секреты объявлены, не угаданы; подпись артефакта до монтирования | Централизованный каталог как обязательный путь (у нас — конфиг внутри компании) |
| Cloudflare MCP Server Portals | Один HTTP-endpoint на много серверов; политика доступа на портал и на каждый сервер; логи вызовов; code mode для больших наборов | Видимость модуля по политике, а не «все видят всё» | Полагаться только на видимость: прямой URL сервера обходит портал, если у сервера нет своей авторизации |
| IBM ContextForge | Реестр инструментов + «виртуальные серверы» из подмножеств; федерация шлюзов | Виртуальный сервер = `--toolsets` на модули | Федерация шлюзов (не наш масштаб) |
| AWS AgentCore Gateway | Цели: Lambda, OpenAPI, MCP; агрегация в один MCP; семантический поиск инструментов | Разные типы целей за одним контрактом; поиск по инструментам вместо полного списка | — |
| Block (Goose) | Серверы пишут свои инженеры; курируемый набор одобренных серверов в поставке; аннотации read-only/destructive, подтверждение для destructive; серверы попадают в allow-list после ревью | Allow-list модулей и класс инструмента как вход в политику подтверждения | — |
| Yandex Cloud | Много серверов по сервисам (Toolkit, Functions, Containers, Docs, Search), stdio и Streamable HTTP | Противоположная модель: показывает, что «один сервер» — выбор, а не норма рынка | — |
| Terraform (core + providers) | Ядро владеет планом, состоянием и UX; провайдер — схема и CRUD по версионированному gRPC-протоколу (major = совместимость, minor = добавления); провайдеры подписаны в реестре | Версия контракта отдельно от версии ядра; ядро отвергает незнакомый major при монтировании | Свой бинарный протокол (у нас уже есть MCP) |
| Kubernetes (CRD vs aggregation) | Декларативное — CRD, императивное с вычисляемыми ответами — aggregation за основным API-сервером; авторизация делегируется ядру (SubjectAccessReview) | Ядро — одна точка авторизации и политики; расширение — отдельный процесс | mTLS между прокси и расширениями как обязательный минимум — рассмотреть для HTTP-модулей |

Общие уроки:

1. Единица контракта — **манифест**, а не код: имена, классы, секреты,
   источник, версия. Его проверяет автомат, его подписывают.
2. Шлюз применяет политику **к тому, что через него идёт**; что сервер
   делает у себя — зона доверия и ревью, не доказательства.
3. **Префикс и скоуп** обязательны: коллизии имён и бюджет контекста
   решаются на входе, а не постфактум.
4. **Версия протокола ядро ↔ модуль** живёт отдельно и проверяется при
   загрузке; ломающее изменение контракта — событие для всех модулей.

## 4. Варианты

| | А. In-tree модуль (Go-пакет в реестре) | Б. Out-of-process плагин (go-plugin, свой протокол) | В. Шлюз: чужой MCP-сервер по манифесту | Г. Контракт + комплект соответствия без шлюза |
|---|---|---|---|---|
| Публичный репозиторий и подпись | **Несовместим**: внутренний код в публичный репозиторий нельзя (§0); частная сборка — второй `release.yml`, другая идентичность cosign/attestation, SBOM раскрывает модули | Совместим | Совместим: evo публичный, модуль — внутри компании, манифест — в приватном конфиге | Совместим |
| Доказуемость политики (гейт, секреты, дубли) | Полная: тот же реестр, тот же гейт D35, AST-инварианты, ревью Qwen/Fable | Только чёрный ящик по манифесту | Только то, что проходит через evo: гейт до проксирования для объявленных мутирующих, H7 по объявленным полям, журнал, `--allow-project` по объявленным аргументам. Не доказуемо: что «чтение» не пишет, идемпотентность, побочные эффекты | Как В, но проверяется в CI команды, не в рантайме |
| Паритет CLI ↔ MCP (D13/D14) | Полный | Команды из манифеста | Команды из манифеста — реально (дерево CLI уже строится из `CLISpec`, `internal/cli/trees.go`); `--json = ответ инструмента` — «по построению», превью для человека — нет без кода | Нет: CLI модуля — дело модуля |
| Цена для команды-модуля | L: пишет на нашем Go по нашим правилам, ревью и выпуск через «релиз» — это «мы пишем за неё» | M + свой бинарь | M: свой сервер по спецификации MCP + манифест + фейк бэкенда для комплекта | S–M |
| Цена для evo | Шаг 0 + M на домен | L: жизненный цикл, дистрибуция, подпись бинарей, совместимость — выигрыша над В нет | Шаг 0 (M) + шлюз (M) + комплект (M, «Процесс») | Шаг 0 + комплект |
| Бюджет `tools/list` | Общий | Общий | Модуль выключен по умолчанию, включается через `--toolsets` или по запросу | Не затрагивает |
| Радиус поражения | Один процесс | Один хост | Один шлюз: компрометация даёт все домены | Разные процессы |
| Когда реально | 1.7+, только для своих сервисов (Data Platform, Workflow Studio так и планируются) | Не раньше 2.0, не рекомендуется | Чтение — 1.8; запись — 2.0 | 1.7–1.8 |

Вердикты сессий совпали: А — для чужих команд исключён (публичность,
«мы пишем за них»); Б — «это В со своим протоколом плагинов, зачем, если
MCP есть»; В — реалистичный путь с границей доверия в манифесте; Г —
дешёвая альтернатива, если нужна политика, а не точка входа. В остаётся
основной для своих in-tree сервисов и как внутренний стандарт качества.

**Рекомендация: В с опорой на Г.** Контракт и комплект соответствия (Г) —
обязательная часть В; они полезны даже если шлюз отложат. Шлюз даёт
единую точку входа и политику в рантайме; стоит делать его, если владелец
подтверждает, что точка входа нужна (вопрос 1 в §9).

## 5. Что в evo мешает и что надо сделать до любого варианта

Факты по коду на `c69b294` (отчёт сессии разработки и обзор реестра):

- Реестр — единственный источник, но правила инструмента лежат не в
  `Tool`, а в **25 картах с ключом-именем** в продуктовом коде (`cliSpecs`,
  `toolsRU`, `projectTools`, `groupByName`/`groupPrefixes`,
  `requiredOneOf`, `sensitiveTools`, `sideEffectTools`, `destructiveTools`,
  `partialConsent`, `untrustedOutput`, `untrustedFields`, `createdIDs`,
  `createNames`, `namelessCreates`, `deleteTargets`, `idArgs`, `valueRefs`,
  `toolRefs`, `noCompletion`, `opTerminalStates` и другие;
  `internal/tools/registry.go:286-529`, `created.go:51`,
  `delete_gone.go:32`, `project_bound.go:82`) и примерно столько же
  закрытых перечней в тестах-инвариантах (`parityArgs`, `consentWorlds`,
  `bodyUnnamed`, `humanUnnamed`, `noPriceInPreview`).
- Регистрация — один литерал `registerTools()` (`internal/tools/tools.go:46`)
  и одна карта обработчиков; хука «добавить инструменты» нет. Всё под
  `internal/`: внешний Go-модуль реестр импортировать не может.
- Гейт согласия — одна функция `gated()` (`internal/tools/gate.go:50`,
  D35); 34 обработчика через неё, около 23 ещё гейтят inline (`inlineGates`,
  перенос — 1.5). Консент = аргумент `confirmed` в схеме + ответ
  `confirmation_required` с превью; elicitation не используется (D10).
- `--toolsets` — не граница прав, а вид (`internal/mcp/server.go:199-202`);
  границы — `--read-only` (H11), `--allow-project` (H9), H1–H13 по HTTP.
- `--allow-project` проверяет «ресурс этого проекта» кодом evo на каждый
  тип ресурса (`boundToProjects`); для чужого домена такой проверки нет.
- Маскирование H7 работает по известным корням полей
  (`HTTPSecretFields`, `internal/mcp/http_redact.go:47`) и эвристикам имён;
  чужой ответ по умолчанию должен считаться недоверенным целиком.
- `TestOutbound_OnlyCloudRuOrDeclaredLinks` и job `contract` роняют сборку
  на любом новом хосте или пути: модуль по определению ходит на «новый
  хост» — правило нужно расширить объявлением в манифесте, а не
  исключением по имени.

**Шаг 0 — `Tool.Decl`.** Свернуть карты в одну декларацию на инструмент
(группа, класс, согласие, цена, секретные поля, привязка к проекту,
созданное/удаляемое, CLI, RU-тексты, автодополнение). Инварианты остаются
и читают декларацию. Размер M, версия 1.7, без изменения поведения
(«разработка»). Это и есть внутренняя форма будущего манифеста: модуль
поставляет ту же декларацию из внешнего источника, второго списка
исключений не возникает.

## 6. Контракт модуля `module-contract v1` (черновик)

Что модуль поставляет:

| Поле манифеста | Зачем | Проверка |
|---|---|---|
| `contract: 1.0` | Версия контракта; evo объявляет поддерживаемые, незнакомый major — отказ монтирования при старте, evo работает без модуля | автомат |
| `module`, `owner`, `on_call`, `changelog_url` | Хозяин, дежурство, кто чинит находки Grok и аудитов | ревью |
| `prefix` (`sup_`), `group` | Имена инструментов `<prefix><verb>`; группа для `--toolsets`; коллизии с реестром — отказ | автомат |
| `transport`: `streamable-http` внутри контура компании (TLS, своя авторизация) или `stdio` | evo не хранит креды модуля; свою IAM-авторизацию модулю не передаёт (token passthrough запрещён спецификацией) | автомат + ревью ИБ |
| `tools[]`: `name`, `class` (`read` / `mutating` / `destructive` / `sensitive`), `paid` (да/нет, `tariff_url`), `consent` (`confirmed` в схеме, превью по форме evo), `secret_fields[]`, `untrusted` (весь ответ или поля), `project_arg` или `project_bound: false` с причиной, `creates` (поле id, инструмент списка, инструмент удаления), `delete_target`, `idempotent` (`already_deleted` по D26), `cli` (verb, args, columns), `ru` (short, long, args) | Та же декларация, что `Tool.Decl`; необъявленное = `mutating`, скрыто при `--read-only` | автомат: валидация схемы манифеста, снимок манифеста против `tools/list` модуля (храповик, как job `contract`) |
| `artifact`: digest образа или бинаря, cosign-подпись, SBOM | Монтируется только проверенный артефакт | CI |
| `conformance`: команда запуска фейка бэкенда и комплекта соответствия | Комплект гоняется в CI команды-модуля; evo гоняет его на эталонном модуле | CI модуля |
| `journal`: `record` / `metadata_only` / `off` с причиной (персональные данные) | Журнал D43 должен уметь исключать модуль | ревью |

Что гарантирует evo (центральная политика по манифесту):

- Гейт согласия до проксирования для всех инструментов класса `mutating`,
  `destructive`, `sensitive`: без `confirmed=true` — `confirmation_required`
  с превью модуля в форме evo; `--read-only` скрывает их из `tools/list`
  (H11) и отказывает вызову.
- Проверка аргументов по схеме до вызова (`CheckArgs`, D36): лишний или
  неверный аргумент — `USAGE` без обращения к модулю.
- Маскирование H7 по `secret_fields` плюс эвристики имён; весь ответ
  модуля помечается `_untrusted` (ось «данные, не указания»).
- Журнал D43: намерение до вызова, итог после; маска по манифесту;
  `off` для модулей с персональными данными.
- `--allow-project`: только по объявленному `project_arg`; модуль без
  привязки объявлен таковым явно.
- `--toolsets`: модуль по умолчанию выключен; включается группой.
- Коды и словарь ответов evo: `status`, `reason`, коды выхода CLI,
  `already_deleted`, `confirmation_required`; команда CLI из `cli` —
  паритет по построению (`--json` = ответ модуля).
- Ограничения HTTP-транспорта H1–H13 распространяются на модули.

Чего контракт не допускает вовсе (позиция «Процесса», поддерживаю):

- произвольный код или шелл как инструмент;
- динамический `tools/list` (набор меняется в рантайме; манифест — про
  закрытый набор; `listChanged` модуля игнорируется);
- собственный диалог согласия или обход гейта evo;
- хранение учётных данных модуля в профиле, state или журнале evo;
- исходящие запросы модуля вне объявленного allowlist (правило S6 «никакой
  телеметрии» — распространяется на поставку в составе evo).

Комплект соответствия (переносится только чёрный ящик, по MCP, против
фейка бэкенда, который обязан поставить модуль):

| Инвариант | Что проверяет на модуле | Источник в evo |
|---|---|---|
| Схема строгая | лишний/неверный аргумент → `USAGE`, 0 записей в фейке | D36, `TestArgs_*` |
| Гейт | мутирующий без `confirmed` → `confirmation_required`, 0 записей; `--read-only` → отказ без записи | W8, `TestContract_GateNoWrite` |
| Повтор | create дважды → один ресурс; delete дважды → `already_deleted`; опечатка id ≠ успех | D26, `TestAlreadyDeleted_*` |
| Созданное объявлено | инструмент списка находит id из ответа create | W1, `TestCreated_*` |
| Превью называет всё | тело запроса фейка ⊂ превью | ось 4, `TestPreview_NamesWhatTheWriteSends` |
| Матрица сбоев | обрыв, 5xx, потерянный ответ — если фейк умеет отказы | матрица сбоев «Процесса» |

Не переносятся: AST-инварианты (`TestConfirmedReadOnlyInTheGate`,
wall-clock, «все клиенты через один транспорт»), паритет человеческого
превью, всё, что модуль делает мимо фейка. Это и есть граница доверия:
для записи в чужой домен она закрывается только ревью и ответственностью
команды-модуля, не тестом.

## 7. Владение, выпуск, приёмка

По правилам §0 `CLAUDE.md` (позиция «релиза», поддерживаю):

| Что | Хозяин |
|---|---|
| Контракт (схема манифеста, центральная политика, версия `module-contract`) | evo: код шлюза — «N — разработка»; инварианты по манифесту и комплект — «Процесс · N»; выпуск и версия контракта — «N — релиз» |
| Код и смысл модуля, его CHANGELOG, его cloud-e2e на своём стенде и за свои деньги, его аудит | команда-модуль; роли evo его не правят и не сливают |
| Включение модуля в поставку или конфиг по умолчанию | владелец (объём выпуска, правило 6) |
| Соответствие контракту | автомат в CI без облака: манифест валиден, комплект зелёный на фейке |
| Grok на модуль | по брифу «Процесса», только для модулей с платными или разрушительными действиями, по «да» владельца |
| Аудит Fable перед тегом evo | контракт, шлюз и автоматическая проверка манифестов — не код модулей, иначе аудит растёт без предела и зависит от чужих сроков |

Ломающее для контракта по `docs/RELEASING.md`: существующий манифест
перестал проходить проверку; у смонтированного модуля изменился класс
согласия, код выхода, `reason`, префикс или имена. Ломающее внутри модуля
(переименован инструмент, убран аргумент) решает команда-модуль, evo ловит
его храповиком снимка манифеста; кто пишет «Миграцию» для пользователя —
вопрос владельцу (§9).

Выпуск evo не зависит от модулей: `release.yml` собирает и тестирует evo
без них; модуль — свой job со своим комплектом; версии модулей в поставке
закреплены (lock), обновление — PR с прогоном комплекта.

Первое решение — **D56** (резерв «релиза» в `DECISIONS.md`, #572, по «да»
владельца 29.10; решение пишет PR шага 0): «Чужой домен входит в evo только
как внешний MCP-сервер через шлюз evo по манифесту (`module-contract v1`,
версия отдельно от evo); центральная политика применяется по манифесту;
кода модулей в репозитории и сборке evo нет».

## 8. Риски

| Риск | Вероятность | Что делаем |
|---|---|---|
| Манифест врёт о классе инструмента, «чтение» пишет | средняя | умолчание — `mutating`; пилот только на чтение; комплект на фейке; ответственность команды-модуля записана в контракте; Grok по брифу на запись |
| Шлюз растит налог контекста, агент тупеет | высокая | модуль выключен по умолчанию; `--toolsets`; позже — поиск по инструментам вместо полного списка (как AWS AgentCore, Anthropic tool search) |
| Один шлюз — все домены (радиус поражения) | средняя | именованные токены 1.7; `--read-only` как умолчание для агента без присмотра; модули с записью — не раньше потолка стоимости и режима без удалений (1.7) |
| Персональные данные домена в журнале и ответах evo | средняя | `journal: off` по манифесту; `_untrusted` на весь ответ; проверка ИБ и юристов до пилота |
| Ломающее в модуле видно пользователю как ломающее evo | высокая | храповик снимка манифеста; правило «Миграции» в контракте; версия контракта отдельно |
| «Один MCP» принят как цель, а нужна политика | средняя | вопрос 1 владельцу до старта; Г как минимальный результат |
| Расход ролей evo на чужие домены | высокая | аудит — только контракт; cloud-e2e модуля — на стенде модуля; очередь «релиза» не принимает PR модулей |

## 9. Решения владельца (29.10.2026, опрос в сессии «Продукт и стратегия»)

| # | Вопрос | Решение |
|---|---|---|
| 1 | Одна точка входа или одна политика | **Одна точка входа**: агент подключает только evo, чужие домены evo монтирует сам — шлюз по манифесту (вариант В); политика (контракт и комплект соответствия, вариант Г) входит в него как обязательная часть |
| 2 | Первый пилот | **Один модуль только на чтение** (например, тикеты домена поддержки), 1.8 |
| 3 | Инцидент от действия агента в чужом модуле | **Команды-модуля за всё, что идёт мимо гейта evo**: evo отвечает за гейт согласия, проверку аргументов, маскирование и журнал; ложный класс «чтение» и всё внутри модуля — его команда. Граница SLA письменно до первого модуля с записью |
| 4 | Версии | **Шаг 0 (`Tool.Decl`) — 1.7; шлюз — после D55, с инвариантом до слияния (§0, правило 3); изменяющие чужие инструменты — 2.0** |
| 5 | Где живут манифесты и кто подписывает | **Отдельный закрытый репозиторий манифестов**: PR команды-модуля, автоматическая проверка контракта в CI, подпись сборкой; не `evo-internal` |
| 6 | «Миграция» при ломающем изменении модуля | **Команда-модуль в своём CHANGELOG**; evo ловит ломающее сравнением снимков манифеста и требует ссылку на миграцию в манифесте; CHANGELOG evo — только контракт и шлюз |

Открытым остаётся вопрос hosted evo (D32): одна точка входа для веб-клиентов
и агентов платформы без него не работает; это отдельное решение из записки
«Локальный MCP и CLI против публичного MCP», этапы A–B.
