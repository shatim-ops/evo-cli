# Запуск этапа в Opus 5.5 — готовые промпты

Одна сессия Claude Code на этап. Модель исполнителя — Opus 5.5. Контекст
намеренно минимальный: бриф этапа самодостаточен.

## Универсальный промпт (подставить N и имя файла)

```
Ты выполняешь этап N плана превращения cloudru-vm в самостоятельный инструмент.

Прочитай ровно три файла и больше ничего до начала работы:
1. docs/internal/standalone/00-audit.md — только разделы 1 и 2
2. docs/internal/standalone/DECISIONS.md
3. docs/internal/standalone/stages/<NN-name>.md — твой бриф

Правила:
- Работай строго в Scope брифа. Всё, что заметил вне scope, допиши одной строкой
  в docs/internal/standalone/BACKLOG.md в формате файла — не чини.
- Ветка: claude/stage-NN-<name> от актуального origin/main. Один PR в main.
- Перед каждым пушем: gofmt -l . && go vet ./... && go test -race -count=1 ./...
  Все три должны быть чистыми. Если тест падает не из-за тебя — остановись и опиши.
- Коммиты по-русски в стиле репозитория: первая строка — что и почему, без
  префиксов feat:/fix:. Не упоминай модели и ассистентов в коде и коммитах.
- Критерии приёмки брифа — это чек-лист в описании PR. Каждый пункт: команда,
  фактический вывод, статус. Невыполнимый критерий — объясни, не ослабляй.
- Секреты: ключи Cloud.ru берутся только из переменных окружения сессии
  (CLOUDRU_KEY_ID, CLOUDRU_SECRET, CLOUDRU_PROJECT_ID). Никогда не печатай их,
  не пиши в файлы репозитория, не вставляй в описание PR и логи.
- Реальное облако (этапы 2, 5, 8): создавай только минимальные ресурсы,
  удаляй всё после проверки, в PR приложи вывод подтверждающей команды
  (list без наших ресурсов).
- Закончив, напиши в PR раздел «Что осталось / сомнения» — 3–5 строк максимум.
- Не мержи PR сам. Не трогай другие этапы.
```

## Параллельный старт (решение «Процесс»)

Две сессии одновременно:
- Сессия A: этап 0 (`00-license.md`) затем этап 1 (`01-foundation.md`) — один PR на каждый.
- Сессия B: этап 6 (`06-tests-ci.md`).

Файлы не пересекаются: A — `cmd/`, `internal/errors`, `internal/output`,
`internal/auth/envvar.go`, `LICENSE`; B — `*_test.go`, `internal/engine`
(поля интервалов), `internal/provision/adapter.go` (backoff), `.github/workflows/ci.yml`.
Единственное касание — `adapter.go`: A добавляет `http.Client` с таймаутом,
B — настраиваемый backoff. Конфликт тривиален; мержить B первым.

## Порядок после старта

```
0 ─┐
   ├─ 1 ──▶ 2 ──▶ 4a ──▶ 4b ──▶ 9 ──▶ 11

      ├──▶ 3 ──▶ 4a
      └──▶ 5
6 ──▶ 7 ──▶ 10 (после подтверждения имени)
```

Этапы 3 и 5 можно запускать параллельно с 2, как только смержен 1.
Этап 8 — после 2. Этап 7 — после 6 и 0.

```
- …

```

## Приёмка владельцем

1. Таблица критериев заполнена фактическими выводами, не «ок».
2. `go test` время — не больше, чем до этапа (после этапа 6 — < 10 с).
3. CI зелёный на всех ОС матрицы.
4. Diff не выходит за Scope брифа; всё лишнее — в BACKLOG, не в коде.
5. Для этапов с облаком — есть доказательство очистки ресурсов.
