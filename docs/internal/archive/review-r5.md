## 1. Резюме

**Общее впечатление.** Для продукта, у которого 139 коммитов за три дня
(14–16.10.2026), evo удивительно собран: один реестр инструментов для CLI
и MCP, одна модель подтверждений для человека и агента, стабильные коды
выхода, русские тексты без канцелярита, `--json` везде, `NO_COLOR` и
не-TTY учтены, `staticcheck` чист, `gofmt`/`vet` чисты, 624 тестовые
функции, полный прогон около 12 с. Запуск 7–9 мс, накладные расходы MCP
меньше миллисекунды на вызов — быстродействие не проблема и трогать его не
надо.

Слабые места — не дефекты, а швы между слоями, которые видны пользователю:

- **Деревья `vm`, `disk`, `k8s`, … — тонкая обёртка над MCP, и она
  протекает.** Русская справка на уровне команды, но флаги и описания —
  английский MCP-текст с жаргоном для агента («omitting the interface
  500s», «requires confirmed=true», «see list_images»). Превью `evo vm
  create` — сырой ответ инструмента с плейсхолдерами `default (env/config
  or auto)`, без цены, зоны и проекта, тогда как превью `evo deploy` —
  образцовое. В `--json` ошибка печатается дважды: тело инструмента в stdout
  и ошибка CLI в stderr.
- **Три пути создания ВМ** (`engine.Deploy`, `provision`, `deploy_plan` →
  `deploy_apply`) — три копии одной логики с 16 расхождениями, уже
  задокументированными в `docs/internal/command-model.md` §5. Пока они
  живут порознь, каждое исправление делается трижды, а инварианты state не
  доказуемы.
- **147 инструментов одним списком**: 87,5 КБ в `tools/list`, без MCP
  `annotations`, с 55 повторами одной и той же фразы про `confirmed=true`
  и 15 вариантами описания одного и того же поля. Агент платит за это
  контекстом при каждом подключении.

**Три самых ценных улучшения** (по убыванию отношения выигрыш/стоимость):

1. **MCP-аннотации и дедупликация описаний** (M1, M2 — S): `readOnlyHint`
   / `destructiveHint` из уже известного реестру `Mutating`, одна константа
   для свойства `confirmed`, фраза про подтверждение — из схемы, а не из
   описания. Минус 10–12 КБ из 87, и клиенты смогут автоодобрять чтения.
   Плюс флаг `evo mcp --toolsets` (M3 — M): типичная сессия deploy+vm+vpc
   получит 26 инструментов вместо 147.
2. **Человеческое превью для всех платных команд деревьев и чистый
   `--json`** (U1, U2 — S/M): то, что уже есть у `deploy` (`engine/
   preview.go`), — проект с источником, зона по имени, цена с пометкой
   «оценка» — распространить на `vm create`, `pg create`, `k8s create`,
   `disk create`. Это самое видимое место, где «ничего платного без
   согласия» сейчас выполняется формально.
3. **Одно ядро создания ВМ** (C1 — L, три PR): общий резолв спецификации
   (образ, flavor, тип диска, подсеть, группа безопасности), одна функция
   `CreateVM` с записью state сразу после POST и один набор имён FIP; затем
   `provision` и `deploy_apply` становятся её клиентами. Это закрывает
   разом половину находок command-model §5–6 и делает инварианты реестра
   проверяемыми тестом (C7).

## 4. Разбор по темам и сравнение с эталонами

Про эталоны: я опираюсь на их документацию и известное поведение; там, где
не уверен в деталях, так и пишу.

### 4.1. Первые 10 минут новичка

Прошёл `docs/guide.md` без ключей. Шаги: `install.sh` → `evo configure` →
`evo whoami`/`doctor` → `cd my-app && evo init` → `evo deploy --dry-run` →
`evo deploy`. Шесть команд — это норма (у `fly`: `install`, `auth login`,
`launch`, `deploy` — четыре; у `yc`: `install`, `init`, затем команды).

Что хорошо: `install.sh` объясняет, что и зачем проверяет; ошибка без
ключа одинаково внятная у всех команд («не задан ключ доступа … Выполните
'evo configure' или задайте CLOUDRU_KEY_ID и CLOUDRU_SECRET») и даёт код 2;
`deploy` без compose-файла проверяет файл до ключа; `status` без
развёртывания говорит «Создать: 'evo deploy'»; опечатка `vm lst` →
«может быть, get, list?» (`cli/main.go:172-188`).

Где спотыкаешься:

1. `doctor` печатает `ок config профиль default; key_id из default`, а
   строкой ниже `ошибка credentials нет ключа доступа`. Для новичка «ок» и
   «ошибка» про одно и то же — противоречие (U13).
2. `evo init` требует ключ, спрашивает зону и образ, но не смотрит, есть ли
   `docker-compose.yml`; про него узнаёшь на `deploy` (U13).
3. `.evo.yaml` после `init` содержит `# project_id: <UUID вашего проекта>`
   закомментированным, если проекта нет в профиле — хорошо, но `deploy` потом
   скажет «не задан CLOUDRU_PROJECT_ID» (`engine/deploy.go:366-371`), хотя
   новичок шёл через `configure`, а не переменные. Сообщение стоит вести от
   `evo configure`/`.evo.yaml`, переменную упоминать последней.
4. Корневой `--help` начинается с кодов выхода и алфавитного списка из 25
   команд. `gh --help` показывает сначала «CORE COMMANDS» (`auth`, `issue`,
   `pr`, `repo`…), потом «ADDITIONAL» — сценарий виден сразу (U5).

### 4.2. Структура команд и флагов

Модель «существительное глагол» выдержана в деревьях (`vm list`, `disk
attach`), сценарий compose живёт глаголами на верхнем уровне (`deploy`,
`destroy`, `logs`) — это та же пара, что `fly deploy`/`fly machines list`
или `gh pr create`/`gh repo clone`: приемлемо и привычно. Проблемы — в
краях модели:

- **Два словаря удаления.** `destroy` на верхнем уровне и `delete` в
  деревьях — нормально, если `destroy` означает «снести развёртывание
  целиком» (как `terraform destroy`, `fly apps destroy`). Но `evo vm
  delete` вызывает тот же инструмент `destroy` с другим поведением
  (`cli/trees.go:52`; command-model §6), а `s3 rm`, `fip-release`,
  `bucket-delete`, `db-delete` — третий и четвёртый словарь (U7).
- **Составные глаголы через дефис** (`route-create`, `db-create`,
  `user-delete`, `bucket-create`, `fip-attach`, `add-nodepool`) — у az,
  gcloud и yc это вложенные ресурсы: `az network vnet subnet create`, `yc
  vpc subnet create`, `gh repo deploy-key add`. Вложенность масштабируется
  (появится `pg user password-reset`), дефис — нет (U7).
- **Флаги** — имена берутся из схем инструментов, поэтому единообразие
  такое, каким его написали авторы инструментов: четыре имени для
  «гигабайты диска», два для памяти, три для подсети (U8). Механизм
  `Rename` уже есть — нужна только таблица и тест.
- **Глобальные `--project-id` и `--region`** принимают только UUID; `yc
  --folder-name`, `az --subscription <имя>`, `gcloud --project <id>`
  принимают и имя. Это уже в BACKLOG [cli-practice] (1) — поддерживаю,
  приоритет v1.0, потому что флаг потом не переименовать.
- **`deploy` объявляет свои `--region`/`--project-id` поверх глобальных**
  (`cli/main.go:533-534`) — в `--help` deploy они показаны как локальные, у
  остальных как глобальные. Работает, но выглядит как два разных флага.

Что у evo лучше эталонов: `evo tools describe <имя>` и `tools call --arg`
дают доступ ко всему без ожидания, пока появится дерево, — у gcloud это
`alpha/beta`-команды, у az — `az rest`. И единая модель подтверждения:
`--yes`, `--dry-run`, код 3 — одинаково для 64 изменяющих инструментов. У
`gh` подтверждения разные у разных команд (`--confirm`, `--yes`), у `az`
`--yes` есть не везде.

Чего брать не стоит: `--query`/`--format` (JMESPath у az/aws) — `--json |
jq` достаточно, а язык запросов — это ещё один контракт; интерактивные
оболочки (`az interactive`); `-q` как согласие (`hcloud`). BACKLOG уже это
отклонил — согласен.

### 4.3. Вывод, ошибки, подсказки

- Таблицы: `tabwriter` с отступом 2, заголовки жирным, ячейки очищены от
  управляющих символов (`output/printer.go:150-187`) — правильно. Нет
  усечения по ширине терминала: `vm list` печатает `created_time` в
  RFC 3339 (`tools/tools_vm.go:119`) и `id` UUID — 36 символов; на 100
  колонках строка не влезает. `gh` и `kubectl` печатают относительное
  время («about 2 hours ago», `AGE 2h`). Предложение: в текстовом режиме
  относительное время, в `--json` — RFC 3339.
- `renderAnswer` (`cli/trees.go:409-470`) — удачный приём: список → таблица
  с «предпочтительными» колонками, объект → ПОЛЕ/ЗНАЧЕНИЕ, составной ответ
  → секции. Это то, что у `hcloud` сделано руками для каждого ресурса.
- Ошибки: формат «Ошибка: что случилось / Подсказка: что делать» выдержан
  везде; в `--json` — `{"error":{code,reason,message,hint}}` в stderr и
  `{"warning":…}` строками. Это лучше, чем у большинства эталонов (у gcloud
  JSON-ошибок нет). Единственная трещина — U1.
- Прогресс: `==> [n/5]` синим жирным, детали dim — читаемо и без спиннера
  честно работает в CI-логах. Не хватает времени ожидания (U10).
- Цвета, `NO_COLOR`, `TERM=dumb`, не-TTY, отдельное решение для stderr
  (`output/printer.go:29-47`) — по clig.dev и no-color.org, без замечаний.

### 4.4. Визуальная идентичность и корпоративный цвет

Исходные данные из BACKLOG [cli-brand]: в snack-uikit зелёный есть только в
семействе `--sys-green-accent-default`, которое означает «успех»; консоль
перекрашивает Primary в зелёный у себя. Hex не называю — его должен дать
фронтенд консоли.

Что делают эталоны (по памяти, уверенность средняя, кроме clig.dev и
Charm):

- **gh** — брендового цвета нет: жирный для заголовков, зелёная `✓`, красная
  `X`, жёлтое `!`, cyan для ссылок/веток. Цвет — только смысловой.
- **Charm (lipgloss)** — `AdaptiveColor{Light, Dark}` и `CompleteColor{TrueColor,
  ANSI256, ANSI}`: автор задаёт три значения, библиотека определяет профиль
  терминала и тему фона. Это и есть «правильный» способ деградации.
- **Fly.io, Vercel, Stripe, Heroku** — акцент в приветственных строках и
  заголовках (у Heroku — magenta/purple в `heroku:`-строках, у Vercel —
  серый/cyan «Vercel CLI»), но статусы — стандартные зелёный/жёлтый/красный.
  Ни один не красит имена команд в цвет успеха.
- **clig.dev**: «use color with intention», не передавать смысл только
  цветом, выключать по `NO_COLOR`, не-TTY, `TERM=dumb` — у evo уже так.

Развилка и мой ответ:

1. **Где акцент уместен**: маркер шага `==>` (сейчас синий, `output/printer.go:82`)
   и заголовки секций `--help` («Использование», «Команды», «Флаги»). Не
   уместен: имена команд в примерах (зелёное имя команды читается как
   «успешно»), таблицы, строки с ценой и предупреждения. Баннер/версия —
   можно, но у evo нет баннера, и заводить его ради цвета не стоит.
2. **Что не трогать**: `Success` зелёный, `Warning` жёлтый, `Errorf` красный
   — ANSI 16, как сейчас. Чтобы «успех» не сливался с брендовым зелёным,
   успех обозначать символом `✓ ` + ANSI-зелёный (`✓` уже стандарт у gh,
   fly), а бренд-зелёный — только truecolor/256 на структурных элементах.
3. **Деградация**: truecolor (`COLORTERM=truecolor|24bit`) → 256 цветов
   (ближайший индекс, `TERM=*256color`) → 16 цветов: **жирный без цвета**,
   не ANSI-зелёный, иначе акцент совпадёт с успехом. Windows 10+ с VT —
   как truecolor; SSH — по тем же переменным; `NO_COLOR`/не-TTY — ничего.
   Светлая тема: один hex на обе темы читается плохо (у snack два значения
   `#…/#…` именно поэтому); терминал тему не сообщает надёжно, поэтому
   брать среднее по контрасту значение или не делать вовсе.
4. **Стоит ли делать.** Мнение: ценность небольшая — пользователи evo
   сидят в терминале рядом с `kubectl` и `gh`, и «похожесть на них» ценнее
   узнаваемости; риск — перепутать акцент с успехом на 16-цветных
   терминалах и в CI-логах. Если владельцу важна связь с консолью — делать
   по пункту 1–3, стоимость S (один файл `output/color.go`, детектор
   профиля ~60 строк, два теста), но после v1.0 и только с тестом «в
   16-цветном режиме акцент = bold».

### 4.5. Согласованность команд и ресурсов

`docs/internal/command-model.md` уже содержит полную матрицу «кто что
создаёт, читает, удаляет, пишет в state»; я её прочитал и выборочно сверил
с кодом (расхождения не нашёл). Поэтому здесь — не повтор, а решения.

**Кто убирает за кем.** Есть четыре писателя state (`engine.Deploy`,
`provision`, `deploy_apply`, `destroy vm_id`) и два ликвидатора
(`engine.Destroy`, `destroy vm_id`). Главные дыры: `deploy_apply` пишет
запись после ожидания ВМ (до 10 мин без записи), `provision` теряет ID
FIP после загрузки, `open_ports` не записывает правила, `destroy vm_id`
на удалённую в консоли ВМ оставляет запись и валит `stack_destroy` в
`destroy_failed`. Всё это следствия C1 — лечить по отдельности дорого.

**Расхождение state и облака.** ВМ удалили в консоли: `status`/`list`
покажут `running` (state только), `logs` упадёт на SSH, `verify` — на
портах, `deploy` будет ждать SSH и запишет `ssh_timeout`, `evo destroy`
сработает правильно (404 → «уже удалена», доочистит FIP и правила).
Команда сверки нужна, но не как `terraform refresh` (отдельный шаг,
который все забывают), а как `fly status`: `evo status` на TTY делает один
`GET /vms/{id}` и говорит «в облаке: не найдена». `--json` и не-TTY —
без запроса по умолчанию, чтобы скрипты не зависели от сети (U12).

**Имена и грамматика** — U6–U9 выше. Что сделать до v1.0, пока это не
ломающее изменение (`docs/RELEASING.md`: ломающие — только major):
решить U7 (глаголы и вложенность) и U8 (флаги), добавить `image`-дерево и
скрыть `list-*` (U6), `destroy --force` → алиас (U9). Старые имена
оставить алиасами (`cobra.Command.Aliases`, `Hidden`), удалить в v2.

### 4.6. Три пути создания ВМ: план сведения к одному ядру

Сейчас (command-model §5, проверено по коду):

| шаг | `engine.provisionVM` | `provision` | `deploy_plan/apply` |
|---|---|---|---|
| метаданные образа | `engine/deploy.go:384-473` | `tools/tools.go:1546-1620` (копия с правками) | `deployplan/resolve.go` `resolveAccess` |
| flavor | `sizer` по compose, `network.go:193` | «наименьший lowcost», `tools.go:1480-1530` | `selectFlavor` |
| тип диска | `resolveDiskType` (ошибка, если нет SSD) | всегда `SSD` | `ListDiskTypes`, иначе SSD |
| подсеть/SG | `resolveNetwork` (зона, `Default`, предупреждение) | первая/по имени | `pickSubnet`/`pickSecurityGroup` |
| FIP | до ВМ, `fip-<vm>-<ts>` | до ВМ | после `running`, `<vm>-fip` |
| запись state | сразу после POST | сразу после POST | после ожидания |

План:

1. **Фаза 1 (S, риск низкий, можно в v1.0):** пакет `vmspec` с одной
   функцией `Resolve(ctx, cloud, Input) (Spec, []Warning, error)`, куда
   переезжают метаданные образа, тип диска, подсеть/SG и резолв flavor по
   имени/UUID (без выбора «auto» — он у каждого пути свой и остаётся
   параметром). `deploy`, `provision`, `deploy_plan` вызывают её. Тесты:
   существующие тесты трёх путей на фейковом облаке должны пройти без
   правок — это и есть критерий, что поведение не изменилось. Расхождения
   10–12 из command-model закрываются здесь.
2. **Фаза 2 (M, риск средний, v1.1):** `engine.CreateVM(ctx, Spec,
   CreateOptions{BootFIP, OpenPorts, RecordStatus}) (Record, error)`:
   boot-FIP, POST, `FindCreatedVM` при потере ответа, запись state **сразу
   после POST**, ожидание `active`, FIP после загрузки с записью ID, одно
   имя FIP (`fip-<vm>-<ts>`; `destroy` ищет по ID из записи, по адресу и по
   этому имени). `provision` = `CreateVM` без Docker; `deploy_apply` =
   `CreateVM` по плану. Расхождения 1–9, 13, 15–16 закрываются. Риск —
   «усыновление по имени» у `deploy_apply` и FIP после `running`: оба
   поведения перед рефакторингом зафиксировать тестами с поддельным облаком
   (сейчас они проверены частично).
3. **Фаза 3 (M, v1.1+, обсуждаемо):** `deploy_plan` = `deploy --dry-run
   --json` с сохранением превью под `plan_id`; `deploy_apply` = `deploy
   --yes` по сохранённому превью. Тогда MCP «мастер» и CLI — буквально
   одна функция. Альтернатива — оставить `deploy_plan/apply` как отдельный
   продукт для агентов (у него есть `product`, `user_data`, усыновление),
   тогда фаза 3 не нужна. Решение за владельцем; я бы делал фазу 3 только
   если `deploy_apply` реально используется агентами (не проверял, есть ли
   телеметрия).

Стоимость суммарно L (три PR: ≈1, 3, 3 дня), выигрыш — одно место для
каждого исправления и возможность доказать инварианты state тестом (C7).

### 4.7. Инварианты реестра для теста

Добавить в `tools.Tool` поле `Lifecycle` (заполняется в `registerTools`,
тест требует его у каждого инструмента):

```go
type Lifecycle struct {
    Effect  string // "read" | "create" | "delete" | "modify" | "run"
    Records bool   // пишет .evo/state.json или job стека
    NoState string // почему не пишет (обязательно для create без Records)
    Pair    string // для create: имя удаляющего инструмента
}
```

Тесты, которые становятся возможны (все — по реестру, без облака):

1. `Effect != "read"` ⇔ `Mutating` (сегодня `Mutating` выводится из
   наличия `confirmed`, `tools/registry.go:211-219`; инвариант ловит
   инструмент, у которого забыли `confirmed`).
2. `Effect == "create"` ⇒ `Pair` существует в реестре и имеет `Effect ==
   "delete"` (сейчас не пройдут `open_ports`, `fip_attach`,
   `k8s_add_nodepool`, `pg_backup_create`, `secret_add_version` — для них
   либо парный инструмент, либо `NoState` с текстом).
3. `Effect == "create"` ⇒ `Records || NoState != ""`.
4. У каждого инструмента с `confirmed` описание свойства — одна константа
   (M2), а описание инструмента не содержит `confirmed=true`.
5. Имя ∈ `^[a-z0-9]+(_[a-z0-9]+)*$`, последний токен — из белого списка
   глаголов/существительных (ловит новые `list_*`).
6. Для деревьев: у аргумента с одинаковым смыслом (`*_gb`, `subnet_id`)
   одно имя флага во всех командах (U8).

Инварианты 4–6 — S; 1–3 требуют заполнить `Lifecycle` для 147
инструментов (M, механически, один PR).

### 4.8. ИИ-агент через MCP

Схемы — аккуратные: типы, `required` там, где надо (94 из 147), описания
аргументов конкретные («UUID … from list_floating_ips»). Описания
инструментов часто рассказывают агенту *почему* («the API answers
invalid_disk_state_to_create_image», `image_create`) — это ценно и
редкость среди MCP-серверов. Проблемы — объём и форма:

- **Нет `annotations`** (M1). Это самое дешёвое и самое полезное: клиенты
  2025 года читают `readOnlyHint`, чтобы не спрашивать человека о чтениях,
  и `destructiveHint`, чтобы спрашивать всегда. У evo эта информация есть,
  но только в прозе.
- **Повторы** (M2): одна фраза про `confirmed=true` 55 раз; 15 редакций
  одного поля. Это 10 КБ, которые читает каждая сессия.
- **147 в одном списке** (M3). Для сравнения (по памяти): GitHub MCP —
  ~50 инструментов, разбитых на `--toolsets` с набором по умолчанию;
  Cloudflare и AWS — отдельные серверы по продуктам; Playwright MCP — ~25.
  При трёх серверах в клиенте агент получает 300+ инструментов, и
  `tools/list` evo — крупнейший вклад. Флаг `--toolsets` по группам
  реестра ничего не ломает (по умолчанию `all`) и стоит день.
- **Имена** (M4): две школы в одном списке. Исправлять только алиасами —
  имена обещаны стабильными.
- **Ответы**: JSON в `text` — нормально для 2025; `structuredContent` —
  опция на v1.1 (M6). Ошибки `{"status":"error","error":"USAGE: …"}` —
  код в строке, `reason` не всегда (M5).
- **Гейт `confirmed=true`** — правильно сделан и честно описан в
  `docs/mcp.md` («граница для вызова, а не для агента»). Поле `approval`
  с одной и той же инструкцией — разумная подпорка до elicitation (D10).
  Единственное: `message` инструментов дублирует ту же инструкцию своими
  словами (M7).

### 4.9. Код и архитектура

Что бросается в глаза свежему человеку:

- **Слои различимы и честны**: `provision` (HTTP), `engine` (сценарий),
  `tools` (реестр), `cli`/`mcp` (транспорты). `cli/trees.go` — данные, а не
  код: добавить команду = одна строка. Комментарии объясняют «почему»
  (`stack/store.go:1-16` — образец).
- **Дублирование** — не в деревьях (они генерируются), а в трёх путях ВМ
  (C1) и в трёх рендерах `status` (C6).
- **Размеры**: `tools/tools.go` 2383 строки — единственный файл, где
  навигация страдает (C2). `engine/deploy.go` 1372 строки — большой, но
  линейный сценарий; делить не стоит.
- **i18n без каталога** (`i18n/i18n.go:8-10`): пара строк на месте вызова.
  Для двух языков и одного автора это лучше gettext — текст виден там, где
  используется. Цена — EN отстаёт без теста (U4, C5).
- **Тесты**: 624 функции, быстрые, с фейковым облаком через интерфейс
  `provision.CloudAPI`; хрупких мест не нашёл; `time.Sleep` — 7 мест ≤ 250
  мс. Не хватает тестов у 12 клиентских пакетов (C4) и названий по
  поведению вместо раундов QA (C10).
- **Для нового контрибьютора**: `docs/internal/architecture.md`,
  `command-model.md`, `api-contract.md` — редкий уровень документации для
  трёхдневного проекта. Не хватает одной страницы «как добавить
  инструмент и команду дерева» с чек-листом (схема, `toolShortRU`,
  `Lifecycle`, `TestCommandsDoc -update-docs`).

## 5. Что сделано хорошо и трогать не надо

- **Модель подтверждений** `internal/confirm`: один код для `--yes`,
  `--dry-run`, TTY-вопроса и кода 3; «нет ответа ≠ согласие»; `y`/`д` в
  любой раскладке (`confirm/confirm.go:84-91`). Превью `deploy` с проектом
  и источником, зоной по имени, ценой и пометкой «оценка, а не счёт»
  (`engine/preview.go:52-137`) — лучше, чем у любого из эталонов, где цену
  до создания не показывает никто.
- **Коды выхода и `--json`-ошибки** (`docs/exit-codes.md`): стабильный
  контракт, `reason` не зависит от языка, предупреждения — JSON-строки в
  stderr. `exit-codes.md` в самом `--help` — спорно по месту, но полезно.
- **Безопасность по умолчанию без занудства**: ключ 0600, симлинки в
  `.evo/` отвергаются (`cli/main.go:289-296`), `sanitizeCell` против
  escape-последовательностей из облака, HTTP-режим MCP с редактированием
  секретов и белым списком `kubectl`.
- **Один реестр для CLI и MCP** (`tools/registry.go`): `TestTrees_MatchRegistry`,
  `TestRegistry_*`, `TestQA_MutatingToolsWriteNothingWithoutConfirmed` —
  инварианты уже проверяются тестами, расширять их легко (C7).
- **Сетевой слой** (`provision/adapter.go:367-480`): повтор идемпотентных
  запросов при обрыве, backoff на 429 и 5xx только для GET, честная
  пагинация, 401/403/404 → свои коды. Кэш токена между процессами.
- **Прерывание** `deploy`: после создания ВМ Ctrl-C на терминале
  предлагает удалить ВМ, без терминала — оставляет и пишет, как удалить
  (`engine/deploy.go:1239-1290`); код 130. Редко где сделано.
- **`install.sh`**: только https по редиректам, sha256, cosign при наличии,
  понятные ошибки на русском.
- **Документация**: `guide.md` как сценарий, `commands.md` из бинаря с
  тестом на расхождение, `command-model.md` как карта для контрибьютора.
- **Быстродействие**: 8 мс запуск, < 1 мс на вызов MCP, 21 МБ RSS — не
  оптимизировать.

## 6. Где я не согласен с DECISIONS

- **D6 (пересмотр), «описания инструментов в деревьях — английские, как в
  MCP».** Согласен с русским CLI и английским MCP. Не согласен с тем, что
  граница проходит *внутри* одной справки: `evo vm create --help` — русская
  шапка, английские флаги, MCP-жаргон. Либо деревья полностью русские
  (U3: карта флагов + вырезание жаргона), либо честно английские целиком.
  Половинчатый вариант хуже обоих.
- **D9, `isError: true` у `confirmation_required`.** Согласен с
  аргументом (клиент, смотрящий только на `isError`, не примет превью за
  успех). Оговорка: аннотации (M1) дают клиентам второй, стандартный
  сигнал, и тогда к v2 можно вернуться к `isError: false` без риска.
- **D10, elicitation в v1.1.** Согласен. Но половину пользы — чтобы клиент
  *сам* спрашивал человека перед изменяющим вызовом — дают
  `destructiveHint`/`readOnlyHint` уже сейчас, бесплатно (M1). Это стоит
  вписать в D10 как шаг v1.0.
- **D11, `status` без развёртывания — 0.** Согласен. Но «есть запись, а
  ВМ нет в облаке» — это не «состояние сообщено», а ложное состояние;
  `status` должен уметь это увидеть хотя бы на TTY (U12). Код при этом
  может оставаться 0 с полем `cloud: not_found`.
- **D12, `mcp --http` по умолчанию без ограничения проектов.** Понимаю «не
  ломать», но предупреждение в лог при старте никто не читает. Мнение:
  для ключа, который видит больше одного проекта, в v1.1 требовать явный
  выбор — `--allow-project …` или `--allow-all-projects`; для ключа уровня
  проекта ничего не меняется (а это и есть «существующие серверы», которых
  боится D12). Это изменение флагов сервера, не CLI-контракта, и его можно
  провести в minor с предупреждением за релиз.
- **D7, деревья только для 7 групп.** Согласен для v1.0; единственное
  исключение — `image` (U6): три инструмента уже есть, а `list-images` на
  верхнем уровне — артефакт.
- **D2, D3, D4, D5, D8** — возражений нет.
