## Фаза 1 — критический разбор

### Архитектура: документ против кода

`docs/internal/architecture.md` — не описание архитектуры, а 40 строк
«откуда движок» (радар → сборщик → движок). Реальная структура, по
импортам:

| Слой | Пакеты | Кто вызывает |
|---|---|---|
| Транспорты | `internal/cli` (cobra, деревья, `tools call`), `internal/mcp` (stdio, HTTP, политика HTTP) | — |
| Реестр инструментов | `internal/tools` (147 обработчиков, `isMutating` по наличию `confirmed` в схеме — registry.go:211) | cli, mcp, сам реестр (`stack_*` зовут обработчики in-process с `confirmed=true` — tools_stack.go:251, 638) |
| Движок сценария | `internal/engine` (deploy/destroy/logs/verify/init), `internal/deployplan` (plan/apply), `internal/sgrules`, `internal/state` | cli напрямую; tools через `newEngine` |
| Клиенты облака | `internal/provision` (compute), `vpc`, `dns`, `mk8s`, … , `internal/httpretry` | engine, deployplan, tools |

Границы «транспорт не знает об облаке» и «MCP — только транспорт» держатся:
`internal/mcp` импортирует только `tools`; `internal/cli` зовёт движок и
реестр. Что расходится с заявленным «единственный путь, которым трогают
облако»:

- **Три независимых пути создания ВМ** с разным поведением:
  `engine.provisionVM` (deploy.go:325–639), `deployplan.Apply`
  (apply.go:40–220) и `handleProvision` (tools.go:1422–1868). Отличия
  (по коду): FIP при создании — deploy и provision всегда, `deploy_apply`
  только если в проекте уже есть свободный FIP (resolve.go:131–137); квота
  FIP до CreateVM — deploy/provision да (`createBootFIP`, deploy.go:788),
  `deploy_apply` нет; запись в state до опроса — deploy да (deploy.go:544),
  provision да (`saveState`), `deploy_apply` только после возврата `Apply`;
  таймаут ожидания — `CLOUDRU_TIMEOUT` только в deploy (PR #47), в provision
  5 мин зашито (tools.go:1791), в apply 7 мин (apply.go:17). Каждая
  починка (#39, #47, #50) ложится в один путь и не доходит до двух других —
  источник находок H3, H5, M2, M3.
- `deployplan.Apply` ходит в compute напрямую через `provision.CloudAPI`,
  минуя `engine` (где живут ожидания, квоты, запись state) — архитектурный
  документ об этом молчит.
- `stack` — оркестратор поверх реестра; гейт у него один, на `stack_apply`,
  а продвижение job живёт в `crankJob`, который зовут и `stack_status`
  (tools_stack.go:539–556) — см. C1.

### Открытые пункты BACKLOG: что блокирует v1.0

Блокируют (вместе с находками выше): ничего из открытых пунктов BACKLOG
само по себе; но два пункта стоит закрыть вместе с C1/H-находками —
`[qa-mcp] stack_apply на job в статусе error продолжает шаги` (то же место,
`advance`) и `[03] превью deploy/provision без цены` (превью `provision`
показывает «default (env/config or auto)» вместо значений — видно в
прогоне `vm create`). Не блокируют: keyring, OAuth 2.1, SBOM/provenance,
`install.ps1`, образ arm64, роли SA (нужен тестовый аккаунт), DNS
rebinding в helm, `set` в argv helm, `get.docker.com` без pin.

## Приложение: воспроизведение C1 без облака

```sh
export HOME=$(mktemp -d) CLOUDRU_CONFIG_DIR=$(mktemp -d); unset $(env | grep -o '^CLOUDRU_[A-Z_]*')
evo tools call stack_plan --args-json '{"manifest":{"name":"qa","secrets":[{"path":"qa/s","value":"x"}]}}' --json | jq -r .job_id
evo tools call stack_status --arg job_id=<job> --arg wait_seconds=1 </dev/null; echo $?   # 0, без --yes
jq '{status, steps:[.steps[]|{key,status,attempts,detail}]}' "$HOME/.evo/stack-jobs/<job>.json"
# status: "running", attempts: 2, detail: "secret_create: AUTH_REQUIRED: …" — создание было запущено
```
