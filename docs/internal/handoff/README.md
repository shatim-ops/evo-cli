# Передача дел между сессиями

Один файл на выпущенную версию: `<версия>.md` (`1.2.1.md`). Пишет релизная
сессия перед закрытием, после тега; новая сессия читает последний
(`CLAUDE.md`, «Старт сессии»). Одна страница, без внутренних сведений
Cloud.ru — репозиторий публичный; внутреннее — в приватных заметках
владельца.

Шаблон:

```markdown
# Передача: <версия> (<дата тега>)

## Выпущено
- тег, коммит, PR версии (ссылки); cloud-e2e — номер прогона.

## Метрики версии
- время PR от открытия до слияния: медиана и самые долгие с причиной;
- красные прогоны `ci` на `main` и в PR — с причиной;
- patch из-за дефекта в 48 ч после выпуска предыдущей версии;
- ускользнувшие дефекты: K из M найденных — дефект, кто нашёл (cloud-e2e,
  догфуд, Grok, пользователь), почему тесты не поймали, PR инварианта или
  «в бэклоге процесса» (`CLAUDE.md` §5);
- живые прогоны cloud-e2e за версию и их исход;
- открытые issue с меткой `деньги`.
- ревью Qwen: доля принятых находок — K из M, с PR (решение владельца 31.10:
  ревью остаётся, долю считает «N — релиз»).

## Открыто
- решения, которых ждёт владелец (вопрос — варианты — рекомендация);
- живые ветки и PR, кто их ведёт;
- известные риски и что их проверит.

## Следующая версия
- раздел `release-plan.md`, с чего начать и почему.

## Сессии
- какие сессии работают над продуктом и их роли.
```

## Ретро ролей

Решение владельца 27.10. Перед передачей каждая роль пишет ретро версии в
`handoff/<версия>-journal.md`, раздел «Ретро»: ≤ 150 слов на роль на версию;
сессия, закрывающаяся раньше конца версии, дописывает строки в раздел этой
версии. Каждый пункт — результат из закрытого списка и ссылка (`#N`, `run N`,
`Test…`): «правило» (diff — на «да» владельца), «проверка» (хозяину по §0),
«бэклог <версия>», «пример, до <версия>» (живёт одну версию, затем
закрепляется или удаляется). Наблюдение без результата не пишется. Релиз
сводит ретро ролей до передачи; в `handoff/<версия>.md` — одна строка счёта.

```markdown
### Ретро «<роль> · <версия>» (<дата>)
- Сработало: <что>, потому что <почему> — <ссылка>. Закрепить: <правило | проверка | пример, до <версия>>.
- Споткнулись: <событие> — <причина> — <ссылка>. Результат: <правило | проверка | бэклог <версия>>.
- Дороже всего (токены, время владельца): <что> — <число>. Результат: <…>.
- Повтор из прошлого ретро: <нет | пункт> → решение владельца.
```

## Сводка плана

Решение владельца 29.10. Релизная сессия перед закрытием — и перед тегом
версии — пишет сводку плана в `handoff/<версия>-journal.md`, раздел
«Сводка плана»: что из плана версии сделано, что
отстаёт и что с этим делать. Счёт — по строкам `release-plan.md`: строка
сделана, когда слит её PR; «в PR» — PR открыт. Отстающие строки текущей
версии и первого блока следующей — таблицей, у каждой умолчание из
закрытого списка: «держим» (и что делаем, чтобы успеть), «в <версия>»,
«снять». Решения — одним issue `решение` со ссылкой на сводку; ответ «по
умолчанию» принимает все умолчания, и релиз правит строки плана одним PR
«(процесс)». Больше 12 отстающих строк — сгруппировать. Сводку пишет
каждая закрывающаяся релизная сессия, даже если ретро версии она только
дописывает. Держит `TestPlanReview_Rules`.

```markdown
### Сводка плана «релиз · <версия>» (<дата>)
- <версия>: строк <N> — сделано <A>, в PR <B>, не начато <C>.
- <следующая>, следующая: строк <N> — в PR <B>, не начато <C>; первым блоком — <блок>.
- Новое за сессию: строк <K> (<откуда>).
- Решения владельца: #<issue>.

| Отстаёт | Хозяин | Почему стоит | Умолчание |
|---|---|---|---|
| `release-plan.md:<строка>` <суть> | <роль> | <почему стоит> | <умолчание> |
```

В скобках заголовка — дата и сессия (`(29.10.2026, сессия 2: …)`): ретро
одно на роль и версию, а сводку пишет каждая закрывающаяся релизная
сессия, и две сводки с одним заголовком тест не пропустит.
