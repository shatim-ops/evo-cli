## Заключение 111 — резерв D99, ТЗ первой волны: общие правила и эталон `vm_start` (ветка `claude/ops-wave-1-tz-1.9`, голова 2378a23, `docs/internal/briefs/ops-wave-1.md`) — снизить так — 12.11

Охват: разделы 1, 2 и 3 ТЗ. Разделы `vm_stop`, `vm_reboot`, `sg_rule_*` и
группы узлов — отдельными заключениями по мере появления (Вп-15). Факты о
коде сверены с `main` 094bf99.

**Привычный путь.** `aws ec2 start-instances`, `gcloud compute instances
start`, `az vm start`: запуск уже запущенной ВМ — успех, запуск из
неподходящего состояния — отказ платформы с названным состоянием, ход —
состоянием ресурса. ТЗ ложится на этот образец; `already_running` — тот же
словарь, что `already_deleted` (D26) и `already_attached`. Агент идёт
`vm_list` или `vm_get` → `vm_start` → тот же вызов по `next_tool` — без
опроса списка. Расхождений с привычным нет.

**Как обойдёт модель с терминалом тем же ключом.** `evo vm start --yes`
или прямой запрос: согласие — не граница, граница — роль ключа; ТЗ говорит
это само. Новое здесь не в обходе, а в цели: агент запускает ВМ, которую
человек остановил намеренно — ради денег или чтобы изолировать. Превью
называет публичный адрес (3.4) — этого достаточно, запрета не нужно.

**Матрица** (клетки без «—» — только с риском).

| Сценарий | Качество логики | Надёжность | Безопасность | Отказоустойчивость |
|---|---|---|---|---|
| Агент автономен | 2/2 — имя → не та ВМ (У2) | 2/2 — круг «тот же вызов» (У1) | 2/2 — подсказка с `destroy` (У3) | 2/2 — отказ платформы без кода (У4) |
| Человек + агент | 2/2 (У2) | — | 2/2 — адрес после запуска (У5) | — |
| Только человек | 1/2 (У2) | — | — | — |

Паритет, эффективность, масштабируемость, производительность — «—»: один
планировщик на обе поверхности, одно чтение до вопроса, три описания.

**Условия (правки текста ТЗ до «го»).**

- **У1. Конец у «того же вызова» (П5, 3.2).** ВМ, застрявшая в
  `starting`, даёт агенту бесконечный круг: каждый вызов честно отвечает
  `status: starting` и `next_tool` на себя, записи и вопроса нет — стопа
  тоже нет. Это класс R-2 и R-23 (`deploy` и SSH, 1.7.1). Мера: предел по
  времени от `StartedAt` намерения (D92 его уже хранит); за пределом ответ
  — без `next_tool`, с состоянием и словами «повтор не поможет, решает
  человек: консоль или поддержка». Значение предела — после Г-10; правило —
  в П5, для всей волны, а не в разделе `vm_start`.
- **У2. Имя, совпавшее у двух ВМ, — отказ до вопроса (2.3).** `resolveVM`
  берёт первое совпадение по списку и сравнивает аргумент и с id, и с
  именем (`internal/tools/tools_disk.go:38`). Для привязки диска это было
  терпимо; для питания — нет: `vm_stop` по имени остановит не ту ВМ.
  Уникальны ли имена ВМ в проекте — гипотеза. Мера в общей точке: два
  совпадения — `USAGE` с id обоих; строка в 2.3 и мир на неё.
- **У3. Подсказки отказа не велят удалять (3.1).** Строка `deleting`,
  `error_deleting`, `error_creating` называет путь «`vm_get`, `destroy`».
  Императив удаления в подсказке — класс R-1, R-6, R-56: агент исполняет
  подсказку. ВМ в `error_creating` могла создать не эта папка и не этот
  агент. Мера: подсказка называет состояние и чтение (`vm_get`); удаление —
  «решает человек». Инвариант «Процессу»: в подсказках отказов волны нет
  глагола удаления без «спросите человека».
- **У4. Отказ платформы называет её код (П6, 2.4).** Спецификация даёт
  `422` на три случая, различие — поле `code`. `API_ERROR` «с состоянием
  ВМ» не отличает «не то состояние» (повтор после ожидания возможен) от
  «изменения в зоне запрещены» (повтор не поможет). Мера: код причины
  платформы — в `details` ответа машинным полем, помеченным недоверенным;
  для запрета на уровне зоны — без `next_tool`. Форма — одна с
  `details.cause` (Вп-8), а не второе поле рядом. Почему это важно именно в
  1.9 — `evo-internal`, раздел R-77.
- **У5. Адрес после запуска (3.3, 3.4).** Сохраняется ли публичный адрес
  ВМ через остановку и запуск — гипотеза; в ТЗ её нет. Если адрес меняется,
  запись развёртывания в `.evo/` после `vm_start` неверна, и `verify` с
  `deploy` идут на прежний адрес, который может достаться чужой ВМ. Мера:
  строка в 3.8 и в пробе Г-10 («адрес до остановки и после запуска»); итог
  `vm_start` называет адрес; утверждение 3.3 «запись после запуска снова
  верна» — пометить гипотезой до пробы.

**Вопрос автора: запуск из `error`.** Закрывается исходом, issue владельцу
не нужен: это выбор реализации внутри принятого решения (правило 6).
**Превью с прямым «исход неизвестен» — приемлемо**, отказ до вопроса — нет:
§4 разрешает отказывать до вопроса только заведомо невыполнимое, а здесь
неизвестно; привычные CLI в этом случае тоже отдают решение платформе.
Два условия. (а) Отказ платформы после «да» из `error` — ответ без
`next_tool` и со словами «состояние error; повтор не поможет; консоль или
поддержка» — иначе агент с автоодобрением ходит по кругу «превью → да →
отказ». (б) Первое живое наблюдение запуска из `error` идёт в
`evo-internal/runs/` и возвращается в ТЗ: строка перестаёт быть
«неизвестно».

**Шесть вопросов.**

1. *Обход* — выше; остаток принят: граница — роль ключа.
2. *10×.* Десять агентов на одной ВМ — по таблице 3.1 один вопрос, девять
   ожиданий. Десять ВМ — `resolveVM` читает весь список проекта на каждый
   вызов по имени; при 429 — `httpretry`. Приемлемо; по `vm_id` списка нет.
3. *Человек недоступен.* Без «да» записи нет, ВМ стоит. Круг появляется
   только после «да» — У1.
4. *Сценарий у людей.* Есть, ежедневный: запуск после ночной остановки.
5. *Доказательство.* Всё поведение платформы в ТЗ помечено гипотезой до
   Г-10 и Г-20 — метки честные. Добавить две гипотезы: адрес (У5) и
   уникальность имён (У2).
6. *Цена разворота.* До выпуска — запись реестра; после — ломающее. Общие

   Поэтому У1 и У4 — в общую часть.

**К следующим разделам — заранее, чтобы условия не пришли к написанному.**
`vm_stop`: будет ли остановленная ВМ запущена обратно, платформа не

**Остаток, который принимается.** Платное действие с превью «цена

## Заключение 112 — резерв D99, ТЗ групп узлов Managed Kubernetes (#1378, голова 81c0320, `docs/internal/briefs/k8s-nodepools.md`): `k8s_operation`, `k8s_nodepool_get`, `k8s_nodepool_scale`, `k8s_nodepool_delete` — снизить так — 12.11

Основание общей части — ТЗ первой волны, голова 1147fe7 (заключение 111).
Факты о коде сверены с `main` 094bf99.

**Привычный путь.** `gcloud container clusters resize --node-pool`,
`az aks nodepool scale`, `eksctl scale nodegroup`: цель — число, а не
приращение; группа с автомасштабом — отказ или отдельная команда; удаление
группы — отдельная команда с подтверждением. ТЗ ложится на образец. Агент
идёт `k8s_nodepools` → `k8s_nodepool_get` → `k8s_nodepool_scale` →
`k8s_operation`: четыре вызова, без опроса списка.

**Как обойдёт модель с терминалом тем же ключом.** `--yes` или прямой
`PATCH`. Отличие от ВМ: прямой `PATCH`, собранный моделью по спецификации
с пустыми `labels` и `taints`, сотрёт метки узлов — evo здесь безопаснее
обхода, и это довод описанию инструмента сказать «масштаб меняет только
число узлов». Граница — роль ключа.

**Ответы на вопросы автора.**

- *Вопрос 1, `k8s_nodepool_get`* — приемлемо, добавлять. Без него оси 1 и
  4 для группы не выполняются, а `k8s_operation` не назовёт состояние
  ресурса. Цена — запись в `tools/list`; решение о бюджете — за «релизом».
- *Вопрос 2, `k8s_nodepool_scale` в `destructiveTools` целиком* —
  приемлемо. Лишний вопрос человеку при увеличении — цена, а не риск:
  увеличение платное. Два инструмента вместо одного — хуже по бюджету и
  против Вп-11.

**Матрица** (клетки с риском).

| Сценарий | Качество логики | Надёжность | Безопасность | Отказоустойчивость |
|---|---|---|---|---|
| Агент автономен | 2/2 — «уже столько» по желаемому числу (У2) | 2/2 — `ERROR` против общей части (У1) | 2/3 — подсказка ведёт на удаление кластера (У3) | 2/2 — удаление группы в `ERROR` не описано (У4) |
| Человек + агент | 2/2 — рост без названного размера (У5) | — | 2/2 — текст операции как указание (У6) | — |
| Только человек | — | — | — | — |

**Условия (правки текста ТЗ до «го»; У6 — до слияния первого PR).**

- **У1. `ERROR` — одно правило на волну.** Общая часть (П4): состояние с
  неизвестным исходом — не отказ, превью называет неизвестность; `vm_start`
  из `error` так и делает. Здесь масштаб группы в `ERROR` — отказ до
  вопроса «до Г-12». Под одним D99 два ответа на один класс. Мера: лечь на
  П4 либо записать отступление с причиной в «Отличия от общей части».
  Причина есть, и её стоит назвать: увеличение группы в `ERROR` добавляет
  платные узлы в неисправную группу — тогда отказ только для увеличения.
- **У2. «Уже столько» — по желаемому и по действительному.** Строка
  «`count` равен текущему числу и группа `RUNNING` — успех без вопроса» не
  говорит, что такое «текущее»: желаемое число политики или число живых
  узлов. Желаемое 3 при двух живых узлах — ответ «успех» ложен по сути.
  Мера: сравнение — с желаемым; ответ называет оба числа, когда они
  расходятся. Строка «уже масштабируется к этому же `count`» стоит на
  гипотезе, что желаемое число читается во время перехода, — вопрос к Г-12.
- **У3. Отказ на последней группе не ведёт на удаление кластера.** «Не
  разрешает — отказ до вопроса с путём (`k8s_delete` для кластера
  целиком)»: агент, которого просили убрать группу, получает подсказку
  удалить кластер. Класс R-56, и самый дорогой его случай. Мера — как П4
  общей части: подсказка называет состояние и чтение (`k8s_get`), без
  `next_tool` на удаление; «удалять ли кластер, решает человек».
- **У4. Удаление группы в `ERROR` и в незнакомом состоянии — строкой.**
  Раздел удаления называет «нет группы», `DELETING`, «создаётся» и общее
  «удалить нельзя». Группа в `ERROR` — главный случай уборки (ось 3,
  класс DB-17): превью и запрос, а отказ платформы — прямым текстом с
  путём. Добавить строку и вопрос к Г-12.
- **У5. Превью увеличения называет размер.** «Было → станет» при
  `count: 30` вместо 3 — одна цифра в строке; цена до Г-22 неизвестна,
  верхней границы в схеме нет. Мера: превью называет прирост в vCPU и RAM
  (flavor уже прочитан до вопроса). Платное без числа цены должно дать
  человеку хотя бы размер.
- **У6. Текст из облака — недоверенный, с первого PR.** `k8s_operation`:
  `description`, `resourceName`, текст `error`; `k8s_nodepool_get`: имя
  группы. Объявление в `untrustedFields` — в том же PR; условие слияния
  первого PR до Н1–Н3.
- **У7. Метки и ограничения узлов — видны или объявлены.** Правило тела
  стоит на том, что масштаб не трогает `labels` и `taints`, а карточка
  группы их не отдаёт: агент не может проверить, что они целы (ось 4).
  Мера: поля в `k8s_nodepool_get` (недоверенными) либо строка «evo не
  показывает, причина».
- **У8. Проект через родителя — закрыто по умолчанию.** `--allow-project`
  для группы читает кластер; кластер не прочитан — отказ, а не пропуск.
  Одной строкой в разделе `k8s_nodepool_get`.

**Не условия.**

- Гонка политики: группа стала автомасштабируемой между чтением и

- Группа безопасности узлов в карточке закрывает половину R-12: агент

## Заключение 113 — #1381 (голова на 12.11), своя очередь `cleanup_only`: уборка удаляет ресурсы только завершённых запусков — мера условия 4 заключения 110 — приемлем — 12.11

Короткий формат: правка workflow, продукт не меняется.

**Привычный путь.** Уборка по метке запуска с проверкой, что запуск
завершён, — обычный образец для общих тестовых проектов.

**Как обойдёт модель с терминалом.** Не применимо к продукту: это
договорённость workflow. Ключ проекта удаляет любой ресурс напрямую —
как и раньше (заключение 110).

**Сверено по diff.** Номер запуска — в имени ресурса; живые запуски —
все состояния, кроме завершённого; список не прочитан — уборка не удаляет
ничего и падает (тесты на оба скрипта уборки); код отказа не теряется в
подстановке аргумента — это держит `TestWorkflows_CleanupTouchesOnlyFinishedRuns`;
новый удаляющий шаг без фильтра роняет тот же тест. Повторная попытка
запуска с тем же номером считается живой. Общие правило и маршрут тестовой
сети рядом с чужим живым запуском не снимаются.

**Остаток, два замечания без условия.**

1. Проба цены Г-20 держит ВМ сутки *после* завершения своего запуска: для
   этой уборки она — остаток завершённого запуска и будет удалена. Исход
   безопасный (теряется проба, не деньги), но исключение по имени, которое
   называет план, — в PR пробы Г-20, с тестом.
2. Живыми считаются запуски только `cloud-e2e.yml`. Сегодня ресурсы с
   номером запуска создаёт только он. Новый workflow, который создаёт
   `evo-e2e-…` со своим номером запуска, попадёт под удаление живым —
   строка в шаблон «Процесса» для новых workflow.

Окно между чтением списка запусков (кэш 60 с) и первым ресурсом нового
запуска — минуты; принимается.
