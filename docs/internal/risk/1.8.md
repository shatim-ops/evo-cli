## Заключение 1. «1.7.1 или сразу 1.8» (решает «1.8 — релиз»)

Исход: **снизить так** — 1.7.1 узким составом, №1 и №2 — в 1.8.

**Шесть вопросов.**
1. *Обход моделью с терминалом.* №2: модель с терминалом обходит бесконечный
   `deploy` по MCP вызовом `evo deploy` — CLI через 5 минут даёт диагноз, после
   60 попыток кончается (факт, c0, c1). №4: обхода нет — модель доверяет итогу
   `stack_plan`, а другой суммы стека в evo нет. Граница не затронута.
2. *10×.* №2 с пределом в state — общий счётчик у процессов одной папки (R-3).
   №4 — нет.
3. *Человек недоступен.* №2 сейчас: агент опрашивает без конца, ВМ
   тарифицируется. После правки ВМ тарифицируется так же, но агент получает
   конец и подсказку `SSH_TIMEOUT` — с советом удалить ВМ без человека (R-1,
   факт: `internal/engine/deploy.go:1601`). Денег правка №2 сама не экономит
   (мнение): ВМ оплачивается, пока её не удалит человек, в обоих случаях.
4. *Сценарий у людей.* №2 — агенты в песочницах с закрытым исходящим 22: 3 из 9
   MCP-конфигураций прогона (факт). Внешних пользователей не считали — данных
   нет. №4 — любой стек с PG (3 из 9).
5. *Доказательство.* №1, №2, №4 — по 3 из 9 и код (факт).
6. *Цена разворота.* №1 и №2 трогают ответ `deploy` (`next_args`), по которому
   открыто решение владельца FB172-1 (два вида `next_args`, `handoff/1.7.md`).
   Правка до решения FB172-1 меняет контракт для модели дважды.

**Матрица.** Агент автономен × надёжность 3/2 (R-2), × безопасность 3/2 (R-1);
человек + агент × качество логики 3/2 (R-5), × надёжность 2/2 (R-3); все
сценарии × надёжность выпуска 2/2 (R-4). Остальные клетки — «—».

**Почему так (мнение на фактах выше).**
- №4 и тексты (№9 по ответу владельца, R-10) — локальны, без смены кода
  выхода и `reason`, проверяются юнит-тестом; №4 — цена перед согласием на
  стек. Это patch по `docs/RELEASING.md`.
- №1 и №2 — ломающие по §5 (MCP `deploy` получает конец с `SSH_TIMEOUT`,
  `logs` и `verify` — другой `reason`), нужны номер D и «Миграция»; без
  исправления подсказки (R-1) правка №2 вредит; без №2 правка №1 вредит (R-2);
  patch идёт без rc, а живой `deploy` в ru.AZ-2 не отличает регрессию от сети
  (R-4).

**Снизить так.**
1. 1.7.1 = №4 + R-10 + №9 (если владелец выберет текст CHANGELOG, R-6).
   cloud-e2e областей diff — только `stack_plan` с PG; решение о живом прогоне
   — владелец.
2. №1 + №2 + R-1 + R-3 — один PR 1.8 после ответа на FB172-1; номер D;
   заключение «Риска» к PR (12 ч: ломающее и текст для модели); проверка — rc и
   агентный прогон с закрытым исходящим 22 (стенд 1.7.0 его уже даёт).
3. Если релиз всё же берёт №1 и №2 в 1.7.1 — обязательны R-1 и R-2 в том же
   PR и cloud-e2e `deploy` в ru.AZ-1.

**Принимаемый остаток.** До 1.8 агент в песочнице с закрытым 22 опрашивает
`deploy` без конца; смягчение есть — превью `deploy` предупреждает «needs
outbound TCP 22» (факт, findings №2).

чинит ошибку (`CLAUDE.md` §5).

Общее условие: каждая ломающая строка — пункт «Миграции» и номер D до
слияния; ломающие одной версии — один раздел «Миграции», а не по PR.
