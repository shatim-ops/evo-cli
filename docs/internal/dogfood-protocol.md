# Протокол догфуда evo (волна 1)

Версия протокола: 21.10.2026, evo 1.2.1 (первая редакция — 18.10.2026,
evo 1.0.4; вторая — 20.10.2026, evo 1.1.0; третья — 21.10.2026, evo 1.2.0). Формат волны — свободное тестирование:
коллеги Cloud.ru пользуются evo в своих задачах. Этот документ — карта, а не
скрипт: что evo умеет, как попробовать, чего ждать, где известные
ограничения и где можно потерять деньги.

Бюджет участника — 4 000 ₽ облака на волну. Цены ниже — из публичной
документации cloud.ru (страницы «Тарификация», прочитаны 18.10.2026; на
всех стоит оговорка «цены из примеров могут отличаться от актуальных»), из
реестров расхождений `docs/internal/cloudru-discrepancies.md` (до 19.10) и
`docs/internal/cloudru-discrepancies-v2.md` (с 19.10) и из превью evo. Где
источника нет — пометка «допущение».

## 0. Что изменилось в 1.2.1 (21.10.2026)

Кто уже поставил 1.2.0 или раньше — обновитесь той же командой установки
(раздел 1, шаг 1) и проверьте `evo version`: `1.2.1`. Полный список —
версия 1.2.1 в `CHANGELOG.md`; для участников важно:

- **Зона в профиле.** `evo configure` после проекта спрашивает зону
  (Enter — предложенная); `--region` понимает имя (`ru.AZ-1`), не только
  UUID. `evo vm create` без зоны, образа или проекта отказывает до вопроса
  о согласии: без зоны — `CONFIG_INVALID`, код 2 (было: превью, вопрос и
  отказ после «y»). Это ломающая правка, раздел «Миграция» 1.2.1.
- **`evo vm create` показывает ход** (резерв IP, запрос, ожидание с
  таймером, адрес) и ждёт ВМ 25 минут вместо 10. После Ctrl-C или по
  таймауту называет следующий шаг: ВМ продолжает создаваться и
  оплачивается — `evo vm get` / `evo vm delete`.
- **Вход на новую ВМ.** Итог `evo vm create` — команда `ssh -i
  <каталог>/.evo/id_ed25519 …` с known_hosts проекта, сгенерированный
  пароль (показывается один раз — сохраните) и строка, что ключ и state —
  в `.evo` каталога запуска: `evo status` и `evo vm delete` запускайте
  оттуда.
- **Превью без цены говорит, что ресурс платный**, и даёт ссылку на тариф
  Cloud.ru (`evo k8s create`, `evo pg create`, бакет, группы узлов). Цену
  кластера смотрите по тарифу; оценка по тарифам — в 1.3.
- **`evo deploy apply <plan-id>`** до согласия показывает ВМ, проект и цену
  плана, а не «цена — в плане».
- **MCP**: `--allow-project` проверяет, чей ресурс по id (чужой — как
  несуществующий, `NOT_FOUND`); маскирование секретов по HTTP закрывает пары
  `Name`/`Value`, JSON внутри строк, числа и ключи `tls.key`, `id_rsa`;
  `deploy_plan` на `--read-only` ничего не пишет на диск. Если сервер с
  `--allow-project` отказывает на **свой** ресурс по id («names no project»,
  особенно PostgreSQL, Kubernetes, балансировщики, DNS) — пришлите вывод в
  issue: вживую проверены пока VPC и образы.
- **Секрет с терминала** (`--value-file -` и др.) — то же значение, что из
  файла; BOM в начале файла секрета отбрасывается.

Изменения 1.2.0 — для тех, кто переходит с 1.1.0:

- **Повторный `evo deploy` спрашивает подтверждение**, если обновляет уже
  созданную ВМ, — как первый `evo deploy` и как MCP `deploy`. В скриптах —
  `evo deploy --yes`; без терминала и без `--yes` — код 3, ничего не
  изменено. Тот же compose на работающей ВМ по-прежнему ничего не делает и
  ничего не спрашивает.
- **У каждого инструмента MCP — своя команда.** Появились `evo dns`,
  `evo cert`, `evo lb` и `evo tg`, `evo snat`, `evo kafka`, `evo redis`,
  `evo ar`, `evo ca`, `evo billing`, `evo stack`, `evo metrics` и другие;
  `evo tools call` для них больше не нужен. Мастер развёртывания, как у
  агента: `evo deploy plan` → `evo deploy apply <plan-id>`. `--json`
  команды — тот же ответ, что у инструмента MCP.
- **Превью агента с ценой.** MCP `provision` и `deploy` без `confirmed`
  показывают цену, как `evo vm create`; образ, недоступный проекту,
  отклоняется уже на превью (`NOT_FOUND`, в `evo tools call` — код 4).
- **Секреты из файла или stdin.** `--value-file`, `--password-file`,
  `--private-key-file`: путь к файлу или `-` (stdin; на терминале — без
  эха). Значение не остаётся в истории оболочки и не видно в списке
  процессов.
- **`evo mcp --read-only`** — для агента, чьи вызовы никто не
  подтверждает: сервер не выполняет ни одного изменения и не отдаёт
  секреты. Рецепт — `docs/mcp.md`, «Автономный агент только на чтение».
- **`whoami` и `doctor` — инструменты MCP**: агент сам проверяет ключ и
  окружение.

Изменения 1.1.0 — для тех, кто переходит с 1.0.x:

- **deploy надёжнее.** Docker ставится из репозитория Docker с ключом,
  встроенным в evo; если apt-зеркало образа не отвечает, evo переключается
  на официальное зеркало дистрибутива и пишет об этом строкой `evo: …`.
  Вживую переключение ещё не наблюдалось: увидите такую строку — пришлите
  вывод в issue, даже если deploy прошёл. Образ, на который Docker не
  ставится (не та ОС, нет нужных пакетов), — сразу `CONFIG_INVALID`, без
  повторов до 15 минут.
- **Секрет — только с согласием.** `evo secret value` без терминала и без
  `--yes` выходит с кодом 3; MCP `secret_value` сначала отвечает
  `confirmation_required`.
- **Неполный список — ошибка.** Если API Cloud.ru отдаёт страницы списка
  так, что evo не может прочитать его целиком, — `API_ERROR` «список не
  полон» (код 5), а не короткий список. Такую ошибку пришлите в issue: это
  почти всегда поведение платформы, которое стоит записать в реестр.
- **Биллинг без договора.** `billing_consumption` и `billing_finops`
  считают расход проекта без `CLOUDRU_AGREEMENT_ID`; `billing_finops`
  теперь суммирует стоимость, а не тариф.
- **Изменились коды и флаги:** `evo pg get|delete` — кластер только
  аргументом (флага `--id` нет); 404 на диск, IP, правило или образ —
  `reason: NOT_FOUND`; `release_floating_ip` для занятого адреса — код 1;
  `open_ports`, открывший часть портов, — `status: partial` и ненулевой код.
- **Справка CLI по-русски** во всех деревьях; MCP по-прежнему отвечает
  по-английски.

Допущение протокола: у каждого участника свой тестовый проект и свой ключ
сервисного аккаунта уровня проекта (`docs/auth.md` §1). Если проект общий,
обязателен префикс ресурсов `df-<логин>-` и раздел 7 читается с удвоенным
вниманием: группы безопасности общие на зону, `open_ports` открывает порт
всем ВМ группы.

## 1. Обязательное ядро (одинаково у всех)

Проходится первым, в день получения ключа. Отчёт о ядре — обязателен даже
если всё прошло: это единственная часть волны, где отчёты сравнимы
напрямую.

| Шаг | Команда | Ожидаемый результат | Источник |
|---|---|---|---|
| 0. Аккаунт GitHub | регистрация на github.com, если аккаунта нет | можно открыть форму «Ошибка CLI» в Issues репозитория; без аккаунта участвовать нельзя, другого канала отзывов нет (раздел 6) | — |
| 1. Установка | Linux/macOS: `curl -fsSL https://raw.githubusercontent.com/shatim-ops/evo-cli/main/install.sh \| sh`. Windows: zip из Releases, проверка sha256, `evo.exe` в `%LOCALAPPDATA%\Programs\evo`, каталог в `Path` | бинарь в `~/.local/bin` (под root — `/usr/local/bin`); скрипт сверяет sha256 и, если есть `cosign`, подпись | `docs/install.md` |
| 2. Версия | `evo version` | первая строка `Cloud.ru Evolution CLI CREW edition (evo) 1.2.1`, коммит, дата, `os/arch` | README |
| 3. Ключ и проект | `evo configure` (интерактивно: Key ID, секрет, UUID проекта) | профиль `default`, файлы `0600` в `~/.config/evo` (macOS `~/Library/Application Support/evo`, Windows `%APPDATA%\evo`); ID проекта принимается только как UUID | `docs/auth.md` |
| 4. Проверка ключа | `evo whoami` | профиль, маскированный Key ID, проект, `token_source` | `docs/auth.md` |
| 5. Окружение | `evo doctor` и `evo doctor --json` | таблица проверок: конфиг, права файлов, IAM, Compute API, kubectl/helm; код 0. За корпоративным прокси — зафиксировать, что прошло и что нет | `docs/troubleshooting.md` |
| 6. Первое чтение | `evo vm list`, `evo vm zones`, `evo vm flavors` | таблицы; `vm zones` показывает, какие зоны принимают новые ресурсы (`evo list-zones` — скрытый устаревший алиас: тот же список и предупреждение) | README |
| 7. MCP | Cursor: `~/.cursor/mcp.json` → `{"mcpServers":{"evo":{"command":"evo","args":["mcp"]}}}`. Claude Code: `claude mcp add --transport stdio --scope project evo -- evo mcp` | агент видит 154 инструмента; просьба «покажи мои ВМ» → `vm_list`; просьба «создай ВМ» → превью с ценой и вопрос, без создания | `docs/mcp.md` |
| 8. Отказ без согласия | `evo vm create t1 </dev/null; echo $?` | превью в stderr, ничего не создано, код `3` | `docs/exit-codes.md` |

Что приложить к отчёту о ядре: ОС и оболочка, сеть (прокси да/нет),
агент, `evo version`, `evo doctor --json`, время от скачивания до первого
`evo vm list` в минутах, что было непонятно.

## 2. Карта возможностей

Обозначения стоимости: ₽/ч — порядок цены пока ресурс существует;
«0» — ресурс не тарифицируется или укладывается в бесплатный лимит;
⚠ — ресурс опасен для бюджета 4 000 ₽ (см. раздел 5). Срок — сколько ждать
создания по наблюдениям из реестра расхождений.

### 2.1 Compose-проект на ВМ: `deploy` / `status` / `logs` / `verify` / `destroy`

- **Команды:** `evo init`, `evo deploy [--dry-run|--yes] [-f файл]`, `evo deploy plan|apply|list` (мастер по шагам), `evo status`, `evo logs [-f]`, `evo verify`, `evo destroy`. MCP: `deploy_plan` → `deploy_apply`, `deploy`, `status`, `logs`, `destroy`, `open_ports`.
- **Попробуйте:** (1) свой `docker-compose.yml` с одним веб-сервисом на порту 80: `init` → `deploy --dry-run` → `deploy` → `verify` → `logs -f` → `destroy`. (2) Изменить compose и повторить `deploy`: превью обновления той же ВМ и вопрос (с 1.2, как у MCP `deploy`; в скрипте — `--yes`, без него и без терминала — код 3), после «y» — обновить ту же ВМ, не создать вторую; тот же compose ещё раз — «развёртывать нечего» без вопроса. (3) Попросить агента развернуть тот же проект через MCP: ожидается `deploy_plan` с ценой, вопрос вам, затем `deploy_apply`; то же из CLI — `evo deploy plan --compose-file docker-compose.yml` → `evo deploy apply <plan-id>`.
- **Чего ждать:** ВМ активна за 1,5–7 мин (OPS-7; 20.10 — 1 мин 25 с в ru.AZ-2, 4 мин 50 с в ru.AZ-1), SSH ещё 2–3 мин (CMP-17); первые 1–2 попытки установки Docker иногда падают на apt («Unable to lock», «Couldn't find any package by regex 'containerd.io'», OPS-12) — evo повторяет сам, итог около минуты; одна попытка — до 5 мин, все — до 15; превью с ценой из API расчёта цены; `destroy` удаляет ВМ, floating IP и правила портов, которые создал сам. Коды выхода — `docs/exit-codes.md`.
- **Известное:** только Ubuntu/Debian; на ВМ уезжает один compose-файл (без `build:`, `.env`, локальных volumes); одно развёртывание на каталог; нужен исходящий порт 22; apt-зеркало образа периодически недоступно из ВМ (OPS-2: 4 из 6 прогонов 16.10 в ru.AZ-2) — с 1.1.0 evo переключается на официальное зеркало дистрибутива (раздел 0); ВМ бывает «Запущена», а порт 22 не отвечает 14 мин и дольше (CMP-17: 18.10 — 3 из 10, 20.10 — 1 из 3 в ru.AZ-2) — evo называет это диагнозом, ВМ остаётся и тарифицируется до `evo destroy`; в ru.AZ-2 15.10 у ВМ не было DNS (OPS-3).
- **Деньги:** ВМ `lowcost10-2-4` с диском 10 ГБ и публичным IP — порядка 1,8 ₽/ч, 1 300 ₽/мес по примеру превью в `docs/guide.md` (API расчёта цены; `deploy --dry-run` в FINAL_AUDIT показал ~800 ₽/мес для того же flavor без IP). Публичный IP 0,204 ₽/ч, диск 0,0156 ₽/ГБ·ч (cloud.ru/docs, примеры). Удаляется сразу: `evo destroy`. Один проход — до 20 ₽.
- **Уборка:** `evo status` в каталоге → «нет развёртывания»; `evo vm list`; `evo vpc fips` (адрес не должен остаться); `evo disk list` (диск без ВМ оплачивается, CMP-11).

### 2.2 ВМ и диски

- **Команды:** `evo vm list|get|create|delete|flavors|zones`, `evo disk list|types|create|attach|detach|resize|delete`. MCP: `provision`, `vm_get`, `vm_list`, `list_zones`, `list_flavors`, `disk_*`.
- **Попробуйте:** (1) `evo vm create web --image ubuntu-22.04 --port 80` → `evo vm get web` → `evo vm delete web`. (2) `evo disk create data --size-gb 20 --attach-to web`, затем `disk resize` до 30, `detach`, `delete`. (3) Через агента: «создай ВМ для тестов и удали её» — превью, подтверждение, `destroy` по имени.
- **Чего ждать:** превью с проектом, зоной, flavor, ценой; ВМ по имени; ошибка `USAGE` с кандидатами, если имя носят несколько ВМ; диск нельзя подключить первые секунды после создания (CMP-13, 422 «no openstack_id»), evo ждёт.
- **Известное:** `vm start/stop/reboot` нет (BACKLOG [04]); загрузочный диск в месте не растёт, free-tier диск не ресайзится; удаление ВМ в `creating` даёт 409/422 — evo ждёт удаляемости; лимит диска 16 ТБ.
- **Деньги:** как 2.1. Диск 20 ГБ — 0,31 ₽/ч. Один проход — до 20 ₽.
- **Уборка:** `evo vm list`, `evo disk list`, `evo vpc fips`.

### 2.3 Образы и Marketplace

- **Команды:** `evo image list [запрос]`, `evo image get <имя|UUID>`, `evo marketplace list [--kind vm-os|vm-app|k8s-addon]`, `evo vm create --image <имя> --meta поле=значение`. MCP: `image_list`, `image_get`, `marketplace_list`, `image_create`, `image_delete`.
- **Попробуйте:** (1) `evo image list ubuntu` — несколько совпадений; `evo image get ubuntu-22.04` — карточка с полями. (2) ВМ из продукта маркетплейса (`lemp`, `gitlab` и т. п.): превью должно сказать «лицензии в цене нет». (3) `evo image get` для Astra Linux — карточка с пометкой «недоступен проекту».
- **Чего ждать:** поиск по подстроке, регистр не важен; `image get` образа, недоступного проекту, — код 0 с пометкой, `vm create` из него — код 4 до создания.
- **Известное:** 23 из 86 образов общего каталога проекту недоступны, включая все отечественные ОС (IMG-1); в каталоге тестовые образы рядом с рабочими (IMG-3); цена лицензии маркетплейса в API расчёта всегда 0 (BIL-1) — у Windows Server по карточке 1 006 ₽/мес, которых в превью нет; `lamp` давал 500 в расчёте цены (BIL-3).
- **Деньги:** ⚠ образы с лицензией (Windows Server, часть продуктов): лицензия не видна в превью; тарифицируется ли лицензия почасово или помесячно — не проверено (допущение: почасово). Берите образ с лицензией только если готовы проверить счёт в консоли на следующий день. Собственный образ (`evo image create`) — хранение, квота организации (CMP-16). Один проход без лицензий — до 10 ₽.
- **Уборка:** `evo vm list`; `image_list` собственных образов → `image_delete`.

### 2.4 Сеть: VPC, подсети, группы безопасности, floating IP, маршруты, SNAT

- **Команды:** `evo vpc list|get|create|delete|subnets|security-groups|fips|fip-attach|fip-release|routes|route-create|route-delete|operation|open-ports`, `evo snat list|create|delete`. MCP: `vpc_*`, `list_subnets`, `list_security_groups`, `list_floating_ips`, `fip_attach`, `release_floating_ip`, `open_ports`, `snat_list|create|delete`.
- **Попробуйте:** (1) `evo vpc security-groups` с правилами до и после `deploy`: правила `evo: port 80` появились и исчезли. (2) `evo vpc fips` — свободный адрес → `fip-attach` к своей ВМ → `fip-release` после удаления ВМ. (3) `evo vpc open-ports <группа> --port 443 --dry-run` — превью «группа общая на зону»; агенту: «открой порт 443 для моей ВМ» → `open_ports` с тем же превью.
- **Чего ждать:** `release_floating_ip` отказывает, если адрес занят ВМ или шлюзом; `open_ports` пропускает уже открытые порты.
- **Известное:** группы безопасности общие на зону — правило затрагивает все ВМ группы; floating IP после удаления может зависнуть в `error_deleting` (NET-7) и через минуты достаться другой ВМ (NET-8); VPC после удаления может получить тот же UUID (NET-10); `new_external_ip` в API даёт 500, evo создаёт адрес заранее (CMP-2).
- **Деньги:** публичный IP 0,204 ₽/ч пока существует в проекте, даже не привязанный (cloud.ru/docs/public-ip). ⚠ SNAT-шлюз: один на зону, занимает публичный IP и квоту; цена шлюза в документации не найдена (допущение: не меньше IP). Для плагинов Kubernetes SNAT не нужен (K8S-3). Один проход — до 10 ₽.
- **Уборка:** `evo vpc fips` — ни одного адреса без ВМ; `evo snat list` пуст; созданные VPC удалены.

### 2.5 Network Load Balancer

- **Команды:** `evo lb list|get|create|delete|operation`, `evo tg list|get|create|delete`. MCP: `lb_*`, `tg_*`.
- **Попробуйте:** ВМ без публичного IP (`evo vm create <имя> --no-public-ip`) → `evo tg create <имя> --vm-id <ID ВМ>` → `evo lb create <имя> --target-group-id <ID группы> --port 80` → `evo lb get` → `evo lb delete` → `evo tg delete`.
- **Чего ждать:** асинхронно, `evo lb operation <ID операции>`; цели — только частные ВМ VPC.
- **Известное:** удаление используемой группы целей принимается (NLB-2); второй балансировщик с тем же именем — 409 с текстом про группу целей (NLB-1).
- **Деньги:** 0,4 ₽/ч за единицу + 0,24 ₽/ч публичный IP + трафик 1,5/3 ₽/ГБ (cloud.ru/docs/nlb). Один проход — до 5 ₽ плюс ВМ.
- **Уборка:** `evo lb list`, `evo tg list`, `evo vpc fips`.

### 2.6 DNS

- **Команды:** `evo dns zones|zone-get|zone-create|zone-delete|records|record-get|record-create|record-delete|operation`. MCP: `dns_*`.
- **Попробуйте:** приватная зона `evo dns zone-create df-<логин>.test. --type private` → A-запись на адрес ВМ (`evo dns record-create <ID зоны> www --record-type a --value <IP>`) → `evo dns records <ID зоны>` → удалить запись и зону.
- **Известное:** тип записи только в нижнем регистре (`a`, NET-9) — evo нормализует; публичная зона требует делегирования домена.
- **Деньги:** цена зоны в документации на 18.10 не прочитана (допущение: единицы рублей в месяц). Один проход — до 5 ₽.
- **Уборка:** `evo dns zones` без зон `df-*`.

### 2.7 Managed Kubernetes ⚠

- **Команды:** `evo k8s list|get|options|plan|create|delete|nodepools|add-nodepool|kubeconfig|kubectl|apply|helm|addons|addon-versions|add-addon`. MCP: `k8s_*` (15 инструментов).
- **Попробуйте:** (1) `evo k8s plan --name df-k8s --zone ru.AZ-2 --master-count 1` → `create` → ждать `RUNNING` → `add-nodepool --count 1` → `evo k8s kubectl df-k8s get nodes` → `add-addon df-k8s cert-manager` → поды Ready → `delete`. (2) `evo k8s helm df-k8s install --release df-nginx --chart bitnami/nginx --repo-url https://charts.bitnami.com/bitnami`, затем `uninstall`; `evo k8s apply df-k8s --manifest "$(cat deployment.yaml)"`. (3) Агенту: «поставь ingress-контроллер» — через `k8s_addons`/`k8s_helm` с подтверждением.
- **Чего ждать:** кластер `RUNNING` за 7–19 мин (K8S-11), пул ~5–6 мин, удаление 4–5 мин; `kubectl`/`helm` нужны локально (`docs/install.md`); `addon-versions` показывает совместимость.
- **Известное:** без `zones` плоскость управления встаёт не в зоне подсети VIP, узел `NotReady`, ошибки нет (K8S-10) — evo передаёт зону, но проверьте `get nodes`; `addonNamespace` в каталоге равен версии (K8S-1), поды ищите по всем namespace; удаление плагина — только консоль; на Windows `kubectl/apply/helm` без гарантий.
- **Деньги:** мастер 2 vCPU/4 ГБ — 7 ₽/ч; узел 4 vCPU/8 ГБ — 6 ₽/ч (3,5 ₽/ч при 30 % vCPU); эфемерное хранилище 0,01 ₽/ГБ·ч; публичный IP 0,5 ₽/ч (cloud.ru/docs/kubernetes-evolution, примеры). Минимальный кластер ≈ 13 ₽/ч ≈ 310 ₽/сутки. **Забытый кластер съедает бюджет за 13 суток.** Один проход 3 ч — до 60 ₽.
- **Уборка:** `evo k8s list` пуст; `evo vpc fips` — адреса кластера освобождены; диски томов — `evo disk list`.

### 2.8 DBaaS: PostgreSQL ⚠

- **Команды:** `evo pg list|get|versions|specs|create|delete|operation|databases|db-create|db-delete|users|user-create|user-delete|backups|backup-create`.
- **Попробуйте:** `evo pg specs` → `evo pg create df-pg --cpu 2 --ram 4` (минимальная спецификация подбирается по cpu/ram) → `pg operation` до `READY` → `db-create`, `user-create` → `backup-create` → `delete`.
- **Чего ждать:** создание ~6,5 мин в норме (OPS-9), удаление ~3 мин; повтор `pg create` с занятым именем — `USAGE` без создания; пароль пользователя не печатается.
- **Известное:** **кластер может висеть в `DEPLOYING` 2 ч 40 мин и уйти в `FAILED` (DB-20, 2 из 2 вечером 17.10); в `DEPLOYING` удалить нельзя (400), в `FAILED` через API удалить нельзя вовсе — только консоль (DB-21).** Пароль: 8–64 символа, заглавная латинская и спецсимвол (DB-9); удаление пользователя-владельца переназначает базу на `dbadmin` (DB-15); несуществующий кластер — 400, не 404 (DB-13).
- **Деньги:** 1,46 ₽/vCPU·ч, 0,4 ₽/ГБ·ч RAM, 0,01 ₽/ГБ·ч SSD, резервные копии не тарифицируются (cloud.ru/docs/paas-postgresql). Минимальный узел 2 vCPU/4 ГБ/20 ГБ — ≈ 4,7 ₽/ч ≈ 113 ₽/сутки (допущение по минимальной спецификации). Кластер в `FAILED` до конца волны (10 суток) — ≈ 1 100 ₽. Один проход — до 30 ₽.
- **Уборка:** `evo pg list` пуст. Если кластер в `FAILED` — удалить в консоли и написать в отчёте с ID.

### 2.9 DBaaS: Kafka и Redis ⚠

- **Команды:** `evo kafka list|get|versions|specs|create|delete|operation`, `evo redis` (те же). MCP: `kafka_*`, `redis_*`.
- **Попробуйте:** `evo kafka specs` → `evo kafka create df-kafka --brokers 1` → `evo kafka operation <ID операции>` до `READY` → `evo kafka get` → `evo kafka delete`. То же для Redis (`evo redis create`, `MASTER_REPLICA`, 1 шард).
- **Чего ждать:** Kafka с 1 брокером — 34–39 мин создания, 8 мин удаления (DB-10); Redis — 27–33 мин, удаление 7,5–10 мин (DB-12).
- **Известное:** **Kafka в `DEPLOYING` не удаляется — 500 (DB-17), повтор создания с тем же именем создаёт второй кластер на стороне API (DB-18; evo проверяет имя до создания).** Redis `replicas` в POST и GET означают разное (DB-11), evo это скрывает; `STANDALONE` API отвергает; спецификации без зоны — 400 (DB-2).
- **Деньги:** Kafka 1,49 ₽/vCPU·ч, 0,40 ₽/ГБ·ч, 0,017 ₽/ГБ·ч SSD (cloud.ru/docs/paas-kafka, с НДС): 1 брокер 2 vCPU/4 ГБ/40 ГБ ≈ 5,3 ₽/ч. Redis 1,46/0,4/0,01 (cloud.ru/docs/redis): 3 хоста 2 vCPU/4 ГБ ≈ 14 ₽/ч ≈ 335 ₽/сутки. Тарифицируется ли `DEPLOYING` — не проверено (допущение: да). Один проход обоих — до 60 ₽.
- **Уборка:** `evo kafka list`, `evo redis list` пусты; зависший кластер — консоль и отчёт.

### 2.10 Object Storage

- **Попробуйте:** `bucket-create df-<логин>` → `put` файла → `ls` → `get` → `rm` → `bucket-delete`. Без ключей S3 — ожидается `CONFIG_INVALID`, код 2.
- **Деньги:** 1,84 ₽/ГБ·мес, первые 15 ГБ и 1 млн GET в месяц бесплатно на организацию (cloud.ru/docs/s3e). Один проход — 0.
- **Уборка:** `evo s3 buckets` без `df-*`.

### 2.11 Секреты и сертификаты

- **Команды:** `evo secret list|get|value|create|add-version|delete`; `evo cert list|get|issue-le|import|renew|delete|usage|versions|private-key|operation`. MCP: `secret_*`, `cert_*`.
- **Попробуйте:** секрет → вторая версия → `value` → удалить. Сертификат Let's Encrypt — только при делегированной публичной DNS-зоне (CRT-3), иначе `evo cert import` самоподписанного.
- **Чего ждать:** `evo secret value` и `secret_value` отдают значение только после подтверждения (с 1.1.0; без терминала и без `--yes` — код 3), `evo cert private-key` и `cert_private_key` — тоже; по HTTP-MCP оба отключены (`docs/mcp.md`); несуществующий сертификат — 403, не 404 (CRT-2).
- **Деньги:** Let's Encrypt бесплатно (описание `cert_issue_le`); цены Secret Manager и импорта на 18.10 не прочитаны (допущение: единицы рублей). Один проход — до 5 ₽.
- **Уборка:** `evo secret list`, `evo cert list`.

### 2.12 Container Apps и Artifact Registry

- **Команды:** `evo ca list|get|deploy|delete|logs|start|stop`; `evo ar list|get|create|delete|operation`. MCP: `ca_*`, `ar_*`.
- **Попробуйте:** `evo ca deploy df-app --image <образ>` публичного образа (`nginx`) → `evo ca get df-app` с URL → `evo ca logs df-app` → `evo ca stop`/`start` → `evo ca delete`. `evo ar create` → push образа своим Docker → `evo ar get` → `evo ar delete`.
- **Известное:** несуществующее приложение — HTTP 499 (CA-1); невалидное имя/порт 9090 — 400 без поля (CA-2); `ca_logs` — последние 100 строк по времени из всех страниц (до 50 по 100 строк); порядок страниц API и задержка поставки логов не описаны — пустой ответ или `truncated` сверяйте с логами в консоли ([break-98] L-1); push в Artifact Registry зависал на финальном `PUT` (OPS-8); реестр с тем же именем создаётся дважды на стороне API (AR-1), evo проверяет имя; операция удаления дольше 300 с `done=false` (AR-3); на запрос следующей страницы список реестров повторяет уже прочитанные — с 1.1.0 evo считает это концом списка (AR-4 в реестре v2): если `ar_list` не видит реестр, который есть в консоли, — issue.
- **Деньги:** тарифы Container Apps и Artifact Registry на 18.10 не прочитаны; приложение масштабируется в ноль (описание `ca_deploy`) — допущение: единицы рублей за проход. Остановленное приложение (`ca_stop`) не обслуживает запросы.
- **Уборка:** `evo ca list`, `evo ar list` пусты.

### 2.13 Мониторинг, биллинг, аудит, IAM и организация (только чтение)

- **Команды:** `evo metrics history|scrape`, `evo billing balance|consumption|finops`, `evo audit events`, `evo iam service-accounts`, `evo org projects|quotas`; `evo project list|use` (`project list` — алиас `evo org projects`, инструмент `org_projects`). MCP: `metrics_*`, `billing_*`, `audit_events`, `iam_service_accounts`, `org_projects`, `org_quotas`.
- **Попробуйте:** `evo billing consumption --start <дата начала волны>` — ваш расход; `evo metrics history <метрика>` по своей ВМ; `evo audit events --since 1d`; `evo org quotas`.
- **Известное:** расход проекта без договора работает (BIL-5, проверено 19.10: 485 строк за 30 дней); вживую его отдаёт и ключ с ролью «Наблюдатель проекта», хотя документация называет только администратора проекта (BIL-7) — сообщите, какая роль у вашего ключа и ответил ли `billing_consumption`; баланс договора ключу проекта недоступен (BIL-4); `audit_events` — 401 вместо 403, если аудит не включён (AUD-1); `metrics_history` — окно не больше 24 ч (лимит сервиса, есть в документации); ключ уровня проекта не видит список проектов (IAM-3), `evo project list` объясняет это, код 0.
- **Деньги:** 0.

### 2.14 Стеки `stack_*`

- **Команды:** `evo stack plan --manifest <файл>` (манифест: ВМ, секреты, SNAT…) → `evo stack apply <job-id>` → `evo stack status <job-id>` (повторные вызовы продвигают) → `evo stack destroy <job-id>`. MCP: `stack_*`.
- **Попробуйте:** через агента: «подними ВМ с секретом для пароля БД одним стеком», затем «удали стек».
- **Известное:** `stack_apply` на job в `error` продолжает оставшиеся шаги (BACKLOG [qa-mcp]); job-файлы в `~/.evo/stack-jobs`.
- **Деньги:** по составу стека, обычно как 2.1. Один проход — до 20 ₽.
- **Уборка:** `evo stack status <job-id>` → `destroyed`; затем `evo vm list`, `evo vpc fips`, `evo secret list`.

### 2.15 MCP-агент как пользователь всего этого

- **Что:** те же области через Cursor или Claude Code; HTTP-режим (`evo mcp --http`, `MCP_BEARER_TOKEN`) и Docker-образ — по желанию, `docs/mcp.md`.
- **Попробуйте:** (1) задачи своими словами, без имён инструментов: «что у меня в проекте и сколько это стоит», «разверни этот compose», «удали всё, что ты создал». (2) Отказать агенту на превью и проверить, что ничего не создано. (3) `--toolsets deploy,vm,vpc` — агент видит 26 инструментов. (4) Отменить вызов в клиенте посреди долгой операции (раздел 4).
- **Чего ждать:** изменяющий инструмент без `confirmed=true` возвращает `confirmation_required` и превью; клиент сам спрашивает вас перед вызовом, если не переведён в автоматический режим.
- **Известное:** `confirmation_required` приходит с `isError: true` (DECISIONS D9); по HTTP часть инструментов отключена, а `k8s_kubectl` принимает только команду первым словом и без флагов, затрагивающих хост сервера (`cp`, `proxy`, `edit`, `-f` и т. п. — отказ); по stdio kubectl с файлами хоста (`-f`, `-k`, `--output-directory`, `--cache-dir`, `-o …file…`) — с подтверждением; агент может повторить вызов по своему таймауту — поведение проверяется живьём (план живых проверок, LC-3).

## 3. Распределение покрытия

Областей — 16 (ядро, 2.1–2.15). Ядро и MCP-агент проходят все. Число
участников заранее неизвестно, поэтому области не раздаются списком, а
выбираются самими участниками:

- в первом чек-ине каждый отмечает, что собирается пробовать, и своё
  окружение (ОС, оболочка, прокси, агент);
- Kubernetes и DBaaS (2.7–2.9) берут только те, кто готов смотреть расход
  каждый день;
- в пятничной сводке разбор показывает области, у которых меньше двух
  участников, и непокрытые сочетания платформ (Windows, корпоративный
  прокси, каждый из агентов); владелец зовёт добровольцев адресно.

Цель покрытия: каждая область — хотя бы у двух участников; 2.1, 2.7 и 2.8
— хотя бы у одного на Windows; оба агента (Cursor, Claude Code) и
корпоративный прокси — хотя бы у двух человек каждый.

## 4. Сценарии для каждого, кто использует область

Эти сценарии нужны в каждой области, где участник что-то создаёт. Они и есть
то, что юнит-тесты не видят.

| Сценарий | Как | Ожидание | Куда смотреть |
|---|---|---|---|
| Ctrl-C на ожидании ВМ, ответ `y` | `evo deploy` или `evo vm create`, после строки «ожидание ВМ…» нажать Ctrl-C | вопрос «Удалить ВМ <id>?», `y` → ВМ удалена, floating IP освобождён, код 130 | `evo vm list`, `evo vpc fips` |
| Ctrl-C, ответ Enter (нет) | то же | ВМ остаётся, код 130, подсказка `evo destroy`; `evo destroy` затем удаляет всё | `evo status` |
| Ctrl-C без терминала | `evo deploy --yes </dev/null &` и `kill -INT` | ВМ остаётся, код 130, id в сообщении | — |
| Отмена вызова в MCP-клиенте | попросить агента создать ВМ, во время вызова нажать «Stop»/отменить в клиенте | что видит агент; осталась ли ВМ; виден ли её id в `evo vm list`; делает ли клиент повторный вызов сам | `evo vm list`, лог клиента |

| Неполный список | любой список (`evo vm list`, `ar_list`, `billing_consumption`) | либо весь список, либо `API_ERROR` «список не полон», код 5 — урезанный список без ошибки считается блокером | `--verbose` |
| `--json` в скрипте | `evo vm list --json \| jq`, `evo deploy --yes --json; echo $?` | stdout — один JSON, stderr — строки JSON, коды по таблице | `docs/exit-codes.md` |

## 5. Бюджет

Как следить: `evo billing consumption --start <дата начала волны> --end <сегодня> --json` раз в день; смотрите `total_with_nds` (с НДС; `total` — без НДС). Договор (`CLOUDRU_AGREEMENT_ID`) не нужен: без него evo считает расход проекта из конфигурации (в ответе `scope: project`), по документации ключу нужна роль администратора проекта (`platform.project.admin`, [документация](https://cloud.ru/docs/billing/ug/topics/api-ref_start)), вживую хватает и «Наблюдателя проекта» (BIL-7). Ответ 403 (код 5, «нет доступа к потреблению проекта») — у ключа нет этой роли; другой отказ `billing_*` — сам по себе отзыв; в обоих случаях — консоль → «Контроль затрат». Стоп-правила: при 2 000 ₽ — не создавать новых кластеров; при 3 000 ₽ — только чтение и уборка; при превышении 4 000 ₽ — написать владельцу, ничего не удалять «в панике» (сначала `evo vm list`, `evo k8s list`, `evo pg list`, `evo kafka list`, `evo redis list`, `evo vpc fips`).

Раз в неделю (по пятницам) и в конце волны — чек-ин: форма «Чек-ин догфуда» в Issues, 3 минуты: области за неделю, расход, остались ли ресурсы, оценка. Это не отзыв, на него не отвечают; из чек-инов собирается покрытие и бюджет волны (раздел 8).

Вывод: по номинальной цене все области укладываются в 4 000 ₽ одного
человека с десятикратным запасом. Не укладываются при сбое: Kubernetes,
если кластер оставлен дольше 12 суток, и DBaaS, если за волну зависнут два
кластера (`FAILED`/`DEPLOYING`) и их не удалят в консоли в тот же день.
Поэтому эти области — только участникам с ежедневным контролем.

## 6. Что сообщать и как

Только через формы Issues репозитория (`bug.yml` — «Ошибка CLI», `idea.yml` —
«Идея, неудобство или вопрос», `checkin.yml` — «Чек-ин догфуда»); разбор — по `docs/internal/feedback-triage.md`, на
каждое issue приходит ответ. Другого канала нет: отзывы из почты, мессенджеров
и личных сообщений не принимаются и не переносятся в Issues, потому что ручной
перенос — нагрузка на владельца, которую волна не выдержит. Чат в Telegram —
только для вопросов. Репозиторий публичный: в выводе замените UUID
на `<uuid>`, адреса на `<ip>`, имена ресурсов на `<имя>`; ключи и секреты не
вставлять никогда; `evo doctor --json` маскирует Key ID сам, ID проекта
замените рукой.

Форма «Ошибка CLI» спрашивает всё нужное сама: версию, ОС, окружение
(оболочка, прокси, агент и модель), как запускали, область протокола, где
проблема (evo или платформа), остались ли платные ресурсы, повторяется ли,
точную команду или запрос агенту, вывод и код выхода (`echo $?`, для агента
— ответ инструмента), что ожидали, `evo doctor`. По полям формы issue сразу
получает метки области, ОС, «платформа», «деньги» — отчёты о деньгах
разбираются первыми.

| Что это | Куда | Признак |
|---|---|---|
| Ошибка CLI | `bug.yml` | поведение расходится с `docs/` или `--help`; паника; неверный код выхода; ресурс остался после `destroy`; деньги без превью |
| Идея, неудобство | `idea.yml` | всё работает, но непонятно, долго, не хватает команды, флага, подсказки |
| Известное ограничение | не присылать; ссылка на раздел 2 этого протокола или `docs/guide.md` §11 | есть в «Известное» области или в реестрах `docs/internal/cloudru-discrepancies.md` и `cloudru-discrepancies-v2.md` |
| Проблема платформы Cloud.ru | `bug.yml`, поле «Где проблема» — «В платформе Cloud.ru» | ошибка API в тексте (`API_ERROR` с HTTP-статусом), поведение консоли; разбор сверит с реестром и дополнит его |
| Вопрос, ответа на который нет в документации | `idea.yml`, «Что это» — «Вопрос» | такой вопрос — дыра в документации, разбор её закроет |
| Быстрый вопрос | чат тестировщиков в Telegram (README → «Поддержка») | ответ есть в `docs/`, нужно только подсказать, где |
| Покрытие, расход, остатки ресурсов | `checkin.yml` — «Чек-ин догфуда», раз в неделю и в конце волны | не ошибка и не идея; ошибку из чек-ина — отдельным issue со ссылкой |

Один issue — одна проблема. Повтор известного issue — комментарий к нему,
не новый.

## 7. Уборка в конце волны

Чек-лист участника (по каждому проекту, где работал):

1. В каждом каталоге с `.evo/`: `evo status` → «нет развёртывания», иначе `evo destroy`; `evo stack status <job-id>` → `destroyed`.
2. `evo vm list` — пусто (или только чужое, если проект общий: смотреть префикс `df-<логин>-`).
3. `evo disk list` — нет дисков без ВМ (CMP-11: оплачиваются).
4. `evo vpc fips` — нет адресов без ВМ; `evo snat list` — пусто; VPC и маршруты, созданные вами, удалены.
5. `evo k8s list`, `evo pg list`, `evo kafka list`, `evo redis list` — пусто. Кластер в `FAILED`/`DEPLOYING`, который не удаляется, — удалить в консоли и указать ID в отчёте.
6. `evo lb list`, `evo tg list`, `evo dns zones`, `evo ca list`, `evo ar list`, `evo cert list`, `evo secret list`, `evo s3 buckets` — без ваших ресурсов; собственные образы (`evo image list --type private`) удалены.
7. Итоговый чек-ин («Период: Итог волны»): расход за всю волну из `evo billing consumption` и ответ «Остались ли ресурсы».
8. Локально: `evo configure delete <профиль>` при желании; `.evo/` в проектах можно оставить.

Сверка владельцем после всех: те же списки по каждому тестовому проекту
через `evo --profile <проект>`; правила групп безопасности `evo: port N`
без ВМ `evo-*`/`df-*` — удалить через API (в evo команды удаления правила
нет); `cloud-e2e` → `cleanup_only` трогает только `evo-e2e-*` и для
догфуда не подходит. Расход по проектам — консоль «Контроль затрат».

## 8. Критерии

Блокер (волна останавливается до фикса): деньги без превью или без
подтверждения; ресурс, который evo создал и не записал (сирота после
`destroy` или после ошибки без id в сообщении); удаление не того ресурса;
ключ или токен в выводе, логе, файле с широкими правами; паника; потеря
`state.json`; `evo mcp` ломает агента (не-JSON в stdout).

Замечание: неверный код выхода или `reason`; расхождение CLI и MCP; текст
ошибки без подсказки; таблица поехала; долгий ответ без прогресса;
документация не совпадает.

Волна пройдена, когда: каждая из 16 областей отмечена хотя бы в двух
чек-инах (поле «Области», ядро — у всех); по областям 2.1, 2.7, 2.8 есть отчёт с Windows;
получено не меньше 20 issue; открытых блокеров нет; у всех участников
уборка подтверждена итоговым чек-ином («Нет, всё убрано»); суммарный
расход волны известен из итоговых чек-инов.
