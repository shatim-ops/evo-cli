# Протокол догфуда evo CMCP (волна 1)

Версия протокола: 25.10.2026, evo CMCP 1.3.0 (прошлые редакции: 18.10.2026 —
evo 1.0.4; 20.10 — 1.1.0; 21.10 — 1.2.0 и 1.2.1). Формат волны — каталог
сценариев: у всех участников одни и те же задачи, описанные по шагам, плюс
свободная часть. Этот документ — карта: что evo CMCP умеет, какие сценарии
проходят все, чего ждать, где известные ограничения и где можно потерять
деньги. Команда — `evo`.

Бюджет участника — 4 000 ₽ облака на волну. Цены ниже — из публичной
документации cloud.ru (страницы «Тарификация», прочитаны 18.10.2026; на
всех стоит оговорка «цены из примеров могут отличаться от актуальных»), из
реестра расхождений `docs/internal/cloudru-discrepancies.md` и из превью
evo. Где источника нет — пометка «допущение», где число посчитано по
тарифу — «расчёт».

Волна идёт на стабильном `v1.3.0` и не ждёт 1.3.1 (решение владельца
25.10). Пометка **[1.3.1]** — поведение, исправленное в 1.3.1
(`docs/internal/release-plan.md`, «В 1.3.1»): на 1.3.0 это известное
ограничение, а не новая находка (раздел 3, «Известные ограничения 1.3.0»);
после обновления до 1.3.1 прежнее поведение — уже дефект. Выйдет 1.3.1 во
время волны — участники обновляются той же командой установки и
переставляют скиллы с тега `v1.3.1`.

## 0. Что нового в 1.3 для участника

Полный список — версия 1.3.0 в `CHANGELOG.md`. Для волны важно:

- **Сценарные скиллы для агента** (`skills/`, D38): `evo-scenarios`,
  `evo-deploy`, `evo-vm`, `evo-postgres`, `evo-cleanup`. Ставятся с тега
  версии по `skills/README.md` из `main` — первым способом через агента,
  готовым промптом (в архиве тега `v1.3.0` промпта ещё нет; сам промпт
  клонирует тег той версии, что у бинаря). Они дополняют встроенные правила (`evo agent setup … --skill`),
  а не заменяют их. Главный вопрос волны — помогают ли они агенту (раздел 3).
- **Невыполнимое — без вопроса о согласии** (D35, D36): зона без подсети,
  занятое имя, уменьшение диска, непустой бакет, опечатка в id при
  удалении — отказ до превью; несуществующий образ и подсеть другой зоны —
  только с 1.3.1 (D39 [1.3.1]). Часть обработчиков ещё проверяет согласие сама — перевод в 1.4
  (сценарий С7).
- **Повтор безопасен** (D23, D25, D26, D28): повторное создание с занятым
  именем отказывает и называет `existing_id`; повторное удаление того, чего
  нет, — код 0, `status: already_deleted`; потерянный ответ создания находит
  ресурс по имени; отказ API (4xx) на создание — ошибка, а не «создано»,
  только с 1.3.1 (D42 [1.3.1]).
- **`evo vpc close-ports` и MCP `close_ports`** (D37) закрывают порт,
  открытый `open-ports`; правила нет — `already_deleted`.
- **Причину ошибки облака решает HTTP-статус**: 429 — `API_RATE_LIMITED`,
  код 5 (так отвечает нехватка ёмкости PostgreSQL, DB-23), а не `NOT_FOUND`.
- **Ход долгих вызовов по MCP** (`notifications/progress`) — клиенту,
  который передал `progressToken` (строка H13 в `docs/mcp.md`).
- **Имя продукта** — evo CMCP (D34); `evo version` печатает его первой
  строкой.

Известные ограничения 1.3 (`CHANGELOG.md`, «Известные ограничения» 1.3.0):
`--port` у `evo vm create` и `evo deploy` открывает порт для `0.0.0.0/0` в
группе, общей для зоны, и `destroy` не закрывает порты, открытые
`open-ports`; пароль ВМ шага `provision` стека не отдаётся в
`stack_status`; PostgreSQL может получить 429 по ёмкости зоны.

Допущение протокола: у каждого участника свой тестовый проект и свой ключ
сервисного аккаунта уровня проекта (`docs/auth.md` §1), в проекте есть
подсеть и группа безопасности в зоне профиля и подсеть ещё в одной зоне.
Если проект общий, обязателен префикс ресурсов `df-<логин>-`, а сценарий
С4 опасен: группы безопасности общие на зону, `open_ports` открывает порт
всем ВМ группы.

## 1. Ядро (сценарий С0, одинаково у всех)

Проходится первым, в день получения ключа. Отчёт о ядре обязателен, даже
если всё прошло: это единственная часть волны, где отчёты сравнимы
напрямую.

## 2. Карта возможностей

Обозначения стоимости: ₽/ч — порядок цены пока ресурс существует;
«0» — ресурс не тарифицируется или укладывается в бесплатный лимит;
⚠ — ресурс опасен для бюджета 4 000 ₽ (см. раздел 5). Срок — сколько ждать
создания по наблюдениям из реестра расхождений. Карта — для сценария С13
(своя задача) и для «Известного» в сценариях раздела 3.

### 2.1 Compose-проект на ВМ: `deploy` / `status` / `logs` / `verify` / `destroy`

- **Команды:** `evo init`, `evo deploy [--dry-run|--yes] [-f файл]`, `evo deploy plan|apply|list` (мастер по шагам), `evo status`, `evo logs [-f]`, `evo verify`, `evo destroy`. MCP: `deploy_plan` → `deploy_apply`, `deploy`, `status`, `logs`, `destroy`, `open_ports`, `close_ports`.
- **Чего ждать:** ВМ активна за 1,5–7 мин (OPS-7), SSH ещё 2–3 мин (OPS-1); первые 1–2 попытки установки Docker иногда падают на apt — evo повторяет сам; превью с ценой из API расчёта цены; `destroy` удаляет ВМ, floating IP и правила портов, которые создал сам; повторный `deploy` над записью развёртывания спрашивает подтверждение, тот же compose — «развёртывать нечего». Для compose-проекта агенту — `deploy`, а не `deploy_plan` → `deploy_apply`: `deploy_apply` создаёт ВМ без приложения (`next` в ответе `deploy_plan`).
- **Известное:** только Ubuntu/Debian; на ВМ уезжает один compose-файл (без `build:`, `.env`, локальных volumes); одно развёртывание на каталог; нужен исходящий порт 22; apt-зеркало образа бывает недоступно из ВМ (OPS-2) — evo переключается на официальное зеркало; ВМ бывает «Запущена», а порт 22 не отвечает минутами (OPS-1); Docker Hub из новой ВМ бывает недоступен (OPS-14, 2 из 6 прогонов 22–23.10); `--port` открывает порт для `0.0.0.0/0` в общей группе зоны.
- **Деньги:** ВМ `lowcost10-2-4` с диском 10 ГБ и публичным IP — порядка 1,8 ₽/ч (превью в `docs/guide.md`). Публичный IP 0,204 ₽/ч, диск 0,0156 ₽/ГБ·ч (cloud.ru/docs, примеры). Один проход — до 5 ₽.
- **Уборка:** `evo status` в каталоге → «нет развёртывания»; `evo vm list`; `evo vpc fips`; `evo disk list` (диск без ВМ оплачивается, CMP-11).

### 2.2 ВМ и диски

- **Команды:** `evo vm list|get|create|delete|flavors|zones`, `evo disk list|types|create|attach|detach|resize|delete`. MCP: `provision`, `vm_get`, `vm_list`, `list_zones`, `list_flavors`, `disk_*`.
- **Чего ждать:** превью с проектом, зоной, flavor, ценой; без образа или зоны — отказ до превью; образа нет — `NOT_FOUND`, несколько совпадений — `USAGE` с кандидатами, подсеть не из зоны — `CONFIG_INVALID`, всё до вопроса (D39 [1.3.1]); итог — команда `ssh` с ключом evo и пароль один раз; диск нельзя подключить первые секунды после создания (CMP-13), evo ждёт; уменьшение диска — `USAGE` до вопроса.
- **Известное:** `vm start/stop/reboot` нет; загрузочный диск в месте не растёт, free-tier диск не ресайзится; удаление ВМ в `creating` даёт 409/422 — evo ждёт удаляемости; лимит диска 16 ТБ.
- **Деньги:** как 2.1. Диск 20 ГБ — 0,31 ₽/ч. Один проход — до 10 ₽.
- **Уборка:** `evo vm list`, `evo disk list`, `evo vpc fips`.

### 2.3 Образы и Marketplace

- **Команды:** `evo image list [запрос]`, `evo image get <имя|UUID>`, `evo marketplace list [--kind vm-os|vm-app|k8s-addon]`, `evo vm create --image <имя> --meta поле=значение`. MCP: `image_list`, `image_get`, `marketplace_list`, `image_create`, `image_delete`.
- **Чего ждать:** поиск по подстроке, регистр не важен; `image get` образа, недоступного проекту, — код 0 с пометкой, `vm create` из него — отказ до создания.
- **Известное:** 23 из 86 образов общего каталога проекту недоступны, включая все отечественные ОС (IMG-1); цена лицензии маркетплейса в API расчёта всегда 0 (BIL-1) — у Windows Server по карточке 1 006 ₽/мес, которых в превью нет.
- **Деньги:** ⚠ образы с лицензией: лицензия не видна в превью. Собственный образ — хранение, квота организации (CMP-16). Один проход без лицензий — до 10 ₽.
- **Уборка:** `evo vm list`; собственные образы (`evo image list --type private`) → `evo image delete`.

### 2.4 Сеть: VPC, подсети, группы безопасности, floating IP, маршруты, SNAT

- **Команды:** `evo vpc list|get|create|delete|subnets|security-groups|fips|fip-attach|fip-release|routes|route-create|route-delete|operation|open-ports|close-ports`, `evo snat list|create|delete`. MCP: `vpc_*`, `list_subnets`, `list_security_groups`, `list_floating_ips`, `fip_attach`, `release_floating_ip`, `open_ports`, `close_ports`, `snat_list|create|delete`.
- **Чего ждать:** `evo vpc open-ports <группа> --port 443 --cidr <источник> --dry-run` — превью называет протокол, источник, порты, которые откроются, и уже открытые; `evo vpc close-ports <группа> --port 443 --cidr <источник>` удаляет ровно эти правила, повтор — `already_deleted`; `fip-release` адреса, занятого ВМ или шлюзом, — `USAGE` до вопроса; VPC с занятым именем — `USAGE` с `existing_id`.
- **Известное:** группы безопасности общие на зону — правило затрагивает все ВМ группы; floating IP после удаления может зависнуть в `error_deleting` (NET-7); `destroy` не закрывает порты, открытые `open-ports` (учёт — 1.4).
- **Деньги:** публичный IP 0,204 ₽/ч, пока существует в проекте (cloud.ru/docs/public-ip). ⚠ SNAT-шлюз: цена в документации не найдена (допущение: не меньше IP). Один проход — до 10 ₽.
- **Уборка:** `evo vpc fips` — ни одного адреса без ВМ; `evo snat list` пуст; свои VPC удалены; свои правила в `evo vpc security-groups` закрыты.

### 2.5 Network Load Balancer

- **Команды:** `evo lb list|get|create|delete|operation`, `evo tg list|get|create|delete`. MCP: `lb_*`, `tg_*`.
- **Чего ждать:** асинхронно, `evo lb operation <ID операции>`; цели — только частные ВМ VPC (`evo vm create <имя> --no-public-ip`).
- **Известное:** удаление используемой группы целей принимается (NLB-2); второй балансировщик с тем же именем — 409 (NLB-1).
- **Деньги:** 0,4 ₽/ч за единицу + 0,24 ₽/ч публичный IP + трафик (cloud.ru/docs/nlb). Один проход — до 5 ₽ плюс ВМ.
- **Уборка:** `evo lb list`, `evo tg list`, `evo vpc fips`.

### 2.6 DNS

- **Команды:** `evo dns zones|zone-get|zone-create|zone-delete|records|record-get|record-create|record-delete|operation`. MCP: `dns_*`.
- **Чего ждать:** запись с занятыми именем и типом — `USAGE`, `existing_id`, до вопроса; запись приватной зоны без `--type` читается и удаляется, удалённой записи нет — `record-get` `NOT_FOUND`, `record-delete` — `already_deleted` (D40 [1.3.1]).
- **Известное:** публичная зона требует делегирования домена; CNAME на имя с A-записью — 409 (NET-16).
- **Деньги:** цена зоны не прочитана (допущение: единицы рублей в месяц). Один проход — до 5 ₽.
- **Уборка:** `evo dns zones` без своих зон.

### 2.7 Managed Kubernetes ⚠

- **Команды:** `evo k8s list|get|options|plan|create|delete|nodepools|add-nodepool|kubeconfig|kubectl|apply|helm|addons|addon-versions|add-addon`. MCP: `k8s_*`.
- **Чего ждать:** превью называет flavor мастеров с vCPU и RAM, версию, зону и подсеть VIP; кластер `RUNNING` за 7–40 мин (K8S-11), пул ~5–6 мин, удаление 4–5 мин; `kubectl`/`helm` нужны локально.
- **Известное:** повторный delete во время удаления — 400 (K8S-14); `addonNamespace` в каталоге равен версии (K8S-1); удаление плагина — только консоль; `k8s_helm install` отвечал `deployed`, хотя поды не поднялись (G130-12, [1.3.1]); на Windows `kubectl/apply/helm` без гарантий.
- **Деньги:** мастер 2 vCPU/4 ГБ — 7 ₽/ч; узел 4 vCPU/8 ГБ — 6 ₽/ч (cloud.ru/docs/kubernetes-evolution, примеры). Минимальный кластер ≈ 13 ₽/ч ≈ 310 ₽/сутки. **Забытый кластер съедает бюджет за 13 суток.** Один проход 3 ч — до 60 ₽.
- **Уборка:** `evo k8s list` пуст; `evo vpc fips`; `evo disk list`.

### 2.8 DBaaS: PostgreSQL ⚠

- **Команды:** `evo pg list|get|versions|specs|create|delete|operation|databases|db-create|db-delete|users|user-create|user-delete|backups|backup-create`. MCP: `pg_*`.
- **Чего ждать:** превью называет версию, cpu, память, диск, подсеть и ссылку на тариф (цены в превью нет); диск меньше минимума спецификации — `USAGE` до вопроса; создание ~6,5 мин в норме (OPS-9), удаление ~3 мин; занятое имя — `USAGE` без создания; пароль пользователя — из файла или stdin (`--password-file -`), не печатается.
- **Известное:** **429 `ResourceExhausted` — в зоне нет ёмкости (DB-23: 5 из 6 попыток 24–25.10 в ru.AZ-1 и ru.AZ-2)**: evo отвечает `API_RATE_LIMITED`, код 5, кластер не создаётся и не оплачивается; повтор через секунды не поможет — позже или `--subnet-id` подсети другой зоны. Подсеть по умолчанию — первая подсеть проекта, она задаёт зону. Кластер может висеть в `DEPLOYING` часами (DB-20); в `FAILED` через API удалить нельзя — только консоль (DB-21). Пароль: 8–64 символа, заглавная латинская и спецсимвол (DB-9).
- **Деньги:** 1,46 ₽/vCPU·ч, 0,4 ₽/ГБ·ч RAM, 0,01 ₽/ГБ·ч SSD (cloud.ru/docs/paas-postgresql). Минимальная STANDARD (1 vCPU, 2 ГБ, 10 ГБ) ≈ 2,4 ₽/ч ≈ 57 ₽/сутки (расчёт). Один проход — до 5 ₽.
- **Уборка:** `evo pg list` пуст. Кластер в `FAILED` — удалить в консоли и указать в отчёте.

### 2.9 DBaaS: Kafka и Redis ⚠

- **Команды:** `evo kafka list|get|versions|specs|create|delete|operation`, `evo redis` (те же). MCP: `kafka_*`, `redis_*`.
- **Чего ждать:** Kafka с 1 брокером — 34–39 мин создания, 8 мин удаления (DB-10); Redis — 27–33 мин, удаление 7,5–10 мин (DB-12). Превью удаления кластера в `FAILED`/`ERROR` предупреждает, что платформа может отказать и нужна поддержка.
- **Известное:** **Kafka в `DEPLOYING` и в `FAILED` не удаляется — 500 (DB-17, 5 из 5); Redis в `DEPLOYING` — 400 (DB-19).** Отмены зависшего создания в API нет.
- **Деньги:** Kafka 1 брокер 2 vCPU/4 ГБ/40 ГБ ≈ 5,3 ₽/ч (cloud.ru/docs/paas-kafka); Redis 3 хоста 2 vCPU/4 ГБ ≈ 14 ₽/ч ≈ 335 ₽/сутки (cloud.ru/docs/redis). Один проход обоих — до 60 ₽.
- **Уборка:** `evo kafka list`, `evo redis list` пусты; зависший кластер — консоль или поддержка, в отчёте.

### 2.10 Object Storage

- **Команды:** `evo s3 buckets|bucket-create|bucket-delete|ls|put|get|rm`; ключи S3 — отдельные (`docs/auth.md`).
- **Чего ждать:** `bucket-delete` бакета с объектами — `USAGE` до вопроса с подсказкой `evo s3 rm`; без ключей S3 — `CONFIG_INVALID`, код 2.
- **Деньги:** 1,84 ₽/ГБ·мес, первые 15 ГБ бесплатно на организацию (cloud.ru/docs/s3e). Один проход — 0.
- **Уборка:** `evo s3 buckets` без своих бакетов.

### 2.11 Секреты и сертификаты

- **Команды:** `evo secret list|get|value|create|add-version|delete`; `evo cert list|get|issue-le|import|renew|delete|usage|versions|private-key|operation`. MCP: `secret_*`, `cert_*`.
- **Чего ждать:** `evo secret value` и `evo cert private-key` отдают значение только после подтверждения; по HTTP-MCP оба отключены (H5); `secret create` по занятому пути — ошибка с `reason` по статусу, а не «создано» (D42 [1.3.1]).
- **Деньги:** допущение: единицы рублей. Один проход — до 5 ₽.
- **Уборка:** `evo secret list`, `evo cert list`.

### 2.12 Container Apps и Artifact Registry

- **Команды:** `evo ca list|get|deploy|delete|logs|start|stop`; `evo ar list|get|create|delete|operation`. MCP: `ca_*`, `ar_*`.
- **Известное:** несуществующее приложение — HTTP 499 (CA-1); push в Artifact Registry зависал на финальном `PUT` (OPS-8); образ, только что загруженный в реестр, Container Apps называл невалидным (OPS-13).
- **Деньги:** тарифы не прочитаны; приложение масштабируется в ноль (допущение: единицы рублей за проход).
- **Уборка:** `evo ca list`, `evo ar list` пусты.

### 2.13 Мониторинг, биллинг, аудит, IAM и организация (только чтение)

- **Команды:** `evo metrics history|scrape`, `evo billing balance|consumption|finops`, `evo audit events`, `evo iam service-accounts`, `evo org projects|quotas`.
- **Известное:** расход проекта работает без договора (BIL-5) и у ключа с ролью «Наблюдатель проекта» (BIL-7); баланс договора ключу проекта недоступен (BIL-4); ключ уровня проекта не видит список проектов (IAM-3).
- **Деньги:** 0.

### 2.14 Стеки `stack_*`

- **Команды:** `evo stack plan --manifest <файл>` → `evo stack apply <job-id>` → `evo stack status <job-id>` → `evo stack destroy <job-id>`. MCP: `stack_*`.
- **Чего ждать [1.3.1]:** `stack plan` отказывает на ключ S3, который уже есть в бакете, и на путь секрета другого стека; шаг с `NOT_FOUND`/`USAGE` — ошибка, а не вечный `pending`; повторный `stack destroy` — `already_destroyed` (D41).
- **Известное:** пароль ВМ шага `provision` не отдаётся в `stack_status`; бакеты стек не создаёт.
- **Деньги:** по составу стека. Один проход — до 10 ₽.
- **Уборка:** `evo stack status <job-id>` → `destroyed`; затем `evo vm list`, `evo vpc fips`, `evo secret list`.

### 2.15 MCP-агент

- **Что:** те же области через Claude Code, Cursor и другие клиенты; HTTP-режим и Docker-образ — по желанию, `docs/mcp.md`.
- **Чего ждать:** изменяющий инструмент без `confirmed=true` возвращает `confirmation_required` и превью; `--toolsets deploy,vm,vpc` — агент видит 27 инструментов; без `--toolsets` — все 155 инструментов; `evo mcp --read-only` — ни одного изменения.
- **Известное:** `confirmation_required` приходит с `isError: true` (D9); по HTTP часть инструментов отключена (H1–H13 в `docs/mcp.md`); клиент может повторить вызов по своему таймауту.

### С1. «Разверни compose и дай ссылку»

- **Агент:** «Разверни docker-compose-проект из этой папки на ВМ в Cloud.ru и дай ссылку. Имена ресурсов — с префиксом `df-<логин>-`». Проект — один сервис `nginx:alpine`, порт `80:80`. Ожидаемый маршрут: `deploy` без `confirmed` → превью с ценой → вопрос → `deploy` с `confirmed` → `status` → ссылка. `deploy_plan` → `deploy_apply` — ошибка маршрута.
- **Человек:** `evo init` → `evo deploy --dry-run` → `evo deploy` → `evo verify` → `evo logs` → `evo destroy`.
- **Успех:** ссылка открывается; одна ВМ и один адрес; вопрос — один раз и после превью с ценой; агент сказал, что порт 80 открыт в общей группе зоны.
- **Дефект:** ВМ без вопроса; вторая ВМ при повторе; «готово», а приложения нет; `destroy` оставил ВМ, адрес или правило, созданные `deploy`; после `deploy_apply` ключ evo не пускает по SSH (`SSH_AUTH_FAILED`, G130-08, не воспроизведено).
- **Известное:** 2.1. **Цена:** до 5 ₽. **Уборка:** `evo destroy`, `evo vm list`, `evo vpc fips`. **Гипотеза:** Г6, Г7, Г2.

### С2. «Подними ВМ с публичным адресом и открой порт»

- **Агент:** «Подними ВМ `df-<логин>-vm` с публичным адресом и открой на ней порт 8080». Ожидаемо: `provision` без портов (превью с ценой, вопрос) → `open_ports` с источником — агент спрашивает, для кого открыть, или прямо предупреждает, что `0.0.0.0/0` откроет порт всем ВМ группы. Затем: «Закрой порт и удали ВМ» → `close_ports` → `destroy`.
- **Человек:** `evo vm create df-vm --image Ubuntu-24.04 --dry-run` → без `--dry-run` → `evo vpc open-ports <группа> --port 8080 --cidr <адрес>/32` → `evo vpc close-ports <группа> --port 8080 --cidr <адрес>/32` → `evo vm delete df-vm`.
- **Успех:** порт открыт только для названного источника или с явным предупреждением; `close_ports` удалил ровно это правило, повтор — `already_deleted` без вопроса; ВМ и адрес удалены.
- **Дефект:** `0.0.0.0/0` без предупреждения в превью; `close_ports` удалил чужое правило; правило или адрес остались; пароль ВМ показан дважды.
- **Известное:** 2.2, 2.4. **Цена:** до 5 ₽. **Уборка:** `evo vm list`, `evo vpc fips`, `evo vpc security-groups`. **Гипотеза:** Г6, Г7, Г2, Г4.

### С3. «Нужен PostgreSQL подешевле»

- **Агент:** «Нужен PostgreSQL подешевле: пользователь `app`, база `app`. Дай строку подключения. Имя кластера — `df-<логин>-pg`». Ожидаемо: `pg_versions` → `pg_specs` → самая дешёвая `standard` → `pg_create` без `confirmed` (превью с тарифом) → вопрос → ожидание `READY` → `pg_user_create` (пароль — не в чат) → `pg_db_create` → строка без пароля. Нужна группа `pg` в `--toolsets`.
- **Человек:** `evo pg versions` → `evo pg specs --version 17` → `evo pg create df-pg --specification-id <id> --dry-run` → без `--dry-run` → `evo pg get df-pg` до `READY` → `evo pg user-create df-pg app --password-file -` → `evo pg db-create df-pg app` → `evo pg delete df-pg`.
- **Успех:** кластер `READY`, пользователь, база, строка подключения; пароль не появился в ответе агента; превью назвало тариф.
- **Дефект:** превью без тарифа и без слов «платный»; пароль в выводе; кластер создан при отказе на превью; `API_RATE_LIMITED`, а кластер появился в списке.
- **Известное:** 2.8, особенно 429 по ёмкости (отметить в отчёте «429: да»). **Цена:** до 5 ₽. **Уборка:** `evo pg list`. **Гипотеза:** Г6, Г7, Г2, Г9.

### С4. «Убери всё, что создал»

- **Подготовка:** ресурс без своего префикса, который убирать нельзя: `evo vpc create keep-<логин>`.
- **Агент:** «Убери всё, что создано с префиксом `df-<логин>-`, и скажи, что осталось». Нужен `--toolsets all`. Ожидаемо: инвентарь по спискам → таблица на удаление только с префиксом, чужое — отдельной строкой → вопрос → удаление в порядке зависимостей → повторная проверка → отчёт: удалено, уже не было, осталось и что стоит.
- **Успех:** с префиксом — ничего; `keep-<логин>` на месте и не попадал в таблицу; неудаляемое названо с причиной и путём.
- **Дефект:** ресурс без префикса удалён без отдельного «да» — **блокер**; на 1.3.1 — уже само появление чужого в таблице на удаление; «удалено», а ресурс в списке. На 1.3.0 `evo-cleanup` строит инвентарь не только по префиксу (G130-01 [1.3.1]): чужой ресурс в таблице, который агент называет и для которого просит отдельного «да», — известное; ответ — «нет».
- **Известное:** меток «создано evo» нет — ключ уборки только префикс (журнал изменений — 1.4, D43); кластеры в `FAILED`/`DEPLOYING` (2.8, 2.9). **Цена:** 0. **Уборка:** после волны — `keep-<логин>`. **Гипотеза:** Г4, Г6, Г7.

### С5. «Что запущено и сколько стоит»

- **Агент:** «Только посмотри: что у меня запущено и сколько это стоит. Ничего не меняй». Лучше — на сервере `evo mcp --read-only`. Ожидаемо: списки, `billing_consumption`, цены с источником, ни одного вызова с согласием.
- **Человек:** `evo billing consumption --start <дата начала волны> --json` (`total_with_nds`), `evo vm list`, `evo pg list`.
- **Успех:** список совпадает с тем, что есть; сумма с источником; на `--read-only` агент не делал вывод «чтения запрещены».
- **Дефект:** `--read-only` пропустил изменение или отдал секрет; цифра без источника, выданная как факт.
- **Известное:** 2.13. **Цена:** 0. **Гипотеза:** Г6, Г7, Г2.

### С6. Ничего платного без превью

- **Человек:** `evo vm create df-c6 --image Ubuntu-24.04` → на вопрос — Enter → `evo vm list`: ВМ нет; `evo vm create df-c6 --image Ubuntu-24.04 </dev/null; echo $?` → код 3.
- **Агент:** «Создай кластер PostgreSQL `df-<логин>-c6`» → на превью «нет» → `evo pg list` пусто.
- **Режим подтверждения клиента** — обязательно в отчёте; гипотеза Г2 считается по ручному подтверждению.
- **Дефект (блокер):** ресурс без показанного превью или без «да»; агент сам поставил `confirmed: true`, не показав превью; создано не то, что показано.
- **Известное:** `confirmation_required` с `isError: true` (D9); у части ресурсов вместо цены — ссылка на тариф; лицензия образа не в цене (BIL-1). **Гипотеза:** Г2.

### С7. Невыполнимое — без вопроса о согласии

На 1.3.0 ожидается отказ до превью и вопроса, с `--yes` и без одинаково:

| Вызов | Ожидание | Основание |
|---|---|---|
| `evo vm create` в зоне, где у проекта нет подсети | `CONFIG_INVALID`, код 2 | D35 |
| `evo vpc create <имя существующей VPC>` | `USAGE`, код 1, `existing_id` | D23 |
| `evo disk resize <диск> --size-gb <не больше текущего>` | `USAGE`, код 1 | D35 |
| `evo s3 bucket-delete <бакет с объектом>` | `USAGE`, код 1 | D35 |
| `evo pg create df-x --storage-gb 1` | `USAGE`, код 1 | D35 |
| `evo pg delete not-a-uuid` | `USAGE`, код 1, без запроса | D36 |

Известное на 1.3.0, исправлено в 1.3.1 — на 1.3.0 так и будет, не
сообщать; на 1.3.1 иное поведение — дефект:

| Вызов | На 1.3.0 | На 1.3.1 | Основание |
|---|---|---|---|
| `evo vm create df-x --image no-such-image` | превью с ценой и вопрос; после «да» — `NOT_FOUND`, код 4 (проверить `evo vpc fips`: адрес не должен остаться) | `NOT_FOUND` до вопроса | D39 |
| `evo vm create df-x --image ubuntu` (несколько совпадений) | после «да» — `NOT_FOUND` без списка | `USAGE`, кандидаты, до вопроса | D39 |
| `evo vm create df-x --image Ubuntu-24.04 --subnet-id <подсеть другой зоны>` | превью с зоной профиля; после «да» — `CONFIG_INVALID` | `CONFIG_INVALID` до вопроса | D39 |
| `evo secret create <путь, который уже есть>` | `status: creating` с id существующего, код 0 | ошибка с `reason` по статусу | D42 |
| `evo dns record-get <id-записи>` (запись приватной зоны или удалённая) без `--type` | `API_ERROR`, код 5 | запись или `NOT_FOUND` | D40 |

- **Агент:** те же случаи словами («создай ВМ из образа Windows 95», «уменьши диск до 1 ГБ»…).
- **Успех:** отказ с первого вызова, причина и код; вопроса не было; агент не повторил вызов с `confirmed: true`.
- **Дефект:** превью и вопрос, отказ — после «да» (класс K1) в случаях первой таблицы или в новых; адрес, оставшийся после отказа.
- **Известное:** 31 обработчик ещё проверяет согласие сам (`internal/testrules/gate_test.go`, перечень `inlineGates`, перевод — 1.4); отказ после согласия у них — известный класс, но о каждом случае сообщить: так видна очередь перевода. Отказы из таблицы выше после «да» — дефект. **Гипотеза:** Г3.

### С8. Уборка без сирот

- После С1: правило `evo: port 80` исчезло вместе с ВМ. После С2: правило `open-ports` закрыто `close-ports`. `evo disk create df-d --size-gb 10` → `evo disk delete` → `evo disk list`. `evo destroy` в каталоге без развёртывания — `status: none`, код 0, без вопроса. Завис кластер — превью удаления в `FAILED`/`ERROR` предупреждает и называет путь.
- **Дефект:** «удалено», а ресурс в списке; адрес или диск остались после удаления их создателя. **Известное:** 2.8, 2.9, NET-7. **Гипотеза:** Г4.

### С10. Стек с данными в S3 — только на 1.3.1 (D41)

На 1.3.0 не проходить: стек перезаписывает существующий объект в бакете
без предупреждения и удаляет его при `stack destroy` (G130-03); шаг с
ошибкой может висеть в `pending`; повторный `stack destroy` снова спрашивает
согласие. Сценарий — для тех, кто обновился до 1.3.1.

- Бакет с объектом `config.json`; манифест со шагом `s3` и тем же ключом → `evo stack plan --manifest <файл>` — отказ до плана. Ключ `config-new.json` → `stack plan` → `stack apply` → `stack status` до `done` → `stack destroy` дважды.
- **Успех:** отказ на существующий ключ; `config.json` цел; повторный `destroy` — `already_destroyed`. **Дефект:** перезаписан или удалён чужой объект; вечный `pending`. **Гипотеза:** Г4, Г5, Г3.

### С11. Windows и корпоративный прокси

- С0 целиком на Windows (PowerShell), `evo doctor` за прокси, С1 и С3 хотя бы одним способом, Ctrl-C (раздел 4).
- **Дефект:** паника, `fatal error`, `0xc0000005` — **блокер**, вывод целиком; прокси не подхватывается; искажённый текст в консоли. На 1.3.0 часть ошибок облака в CLI — по-английски (известное, [1.3.1]).
- **Известное:** скрипта-установщика для Windows нет; `k8s kubectl/apply/helm` на Windows без гарантий; MCP отвечает по-английски. **Гипотеза:** Г8.

### С12. Долгая операция ⚠

- **Агент:** «Подними минимальный кластер Kubernetes `df-<логин>-k8s` с одним узлом, скажи, когда будет готов, затем удали» (или Redis). Ожидаемо: превью с flavor, версией, зоной, подсетью; ожидание через `*_operation` с `wait_seconds`; агент сообщает состояние ресурса.
- **Дефект:** «готов», а кластер не `RUNNING`; агент молча ждёт больше 10 мин. **Известное:** 2.7, 2.9; прогресс MCP — только с `progressToken` (H13). **Цена:** до 60 ₽. **Гипотеза:** Г4, Г9.

### Отчёт о сценарии

Одно прохождение — один отчёт. Поля: сценарий; версия (`evo version`); способ (CLI / агент без
скиллов / агент со скиллами); клиент и модель; режим подтверждения
клиента; успех (да / частично / нет); вызовов до результата (по журналу
клиента; для CLI — команд); ошибки маршрута (первый вызов не из сценария,
«нет инструмента» для того, что есть, `deploy_plan` → `deploy_apply` для
compose, уборка без нужных групп); согласия (сколько раз спросил, было ли
превью перед каждым, было ли `confirmed: true` без показа превью); остаток

## 4. Обрыв и повтор (сценарий С9)

| Случай | Как | Ожидание | Куда смотреть |
|---|---|---|---|
| Ctrl-C на ожидании ВМ, ответ `y` | `evo deploy` или `evo vm create`, после строки ожидания ВМ — Ctrl-C | вопрос «Удалить ВМ <id>?», `y` → ВМ удалена, floating IP освобождён, код 130 | `evo vm list`, `evo vpc fips` |
| Ctrl-C, ответ Enter (нет) | то же | ВМ остаётся, код 130, подсказка `evo vm get` / `evo vm delete` (`evo destroy` для deploy) | `evo status` |
| Ctrl-C без терминала | `evo deploy --yes </dev/null &` и `kill -INT` | ВМ остаётся, код 130, id в сообщении | — |
| Отмена вызова в MCP-клиенте | агенту «создай ВМ», во время вызова — «Stop» в клиенте, затем «что с ВМ?» | агент находит ВМ и называет состояние; что делает клиент сам (повторяет ли вызов) — записать | `evo vm list`, журнал клиента |
| Повторное создание | второй `evo vpc create df-n` | `USAGE`, код 1, `existing_id`, второй VPC нет | `evo vpc list` |
| Повтор после сбоя | после любой ошибки `deploy` или `provision` — та же команда ещё раз | вторая ВМ и второй адрес не появляются | `evo vm list`, `evo vpc fips` |
| Повторное удаление | `evo vm delete <имя>` или `evo vpc delete <id>` второй раз | код 0, `status: already_deleted`, `existed: false`, без вопроса | — |
| Опечатка в id при удалении | `evo vpc delete 1234` | `USAGE`, код 1 — не «удалено» | — |
| Неверный ключ | `CLOUDRU_KEY_ID=x CLOUDRU_SECRET=y evo vm list` | код 2, `AUTH_FAILED`, подсказка | — |
| Секрет без согласия | `evo secret value <путь> </dev/null; echo $?` | значение не напечатано, код `3` | — |
| Неполный список | любой список | либо весь список, либо `API_ERROR` «список не полон», код 5 — урезанный список без ошибки считается блокером | `--verbose` |
| `--json` в скрипте | `evo vm list --json \| jq`, `evo deploy --yes --json; echo $?` | stdout — один JSON, коды по таблице | `docs/exit-codes.md` |

С `--allow-project` повторное удаление — `NOT_FOUND`, а не
`already_deleted` (H9 в `docs/mcp.md`).

## 5. Бюджет

Как следить: `evo billing consumption --start <дата начала волны> --end <сегодня> --json` раз в день; смотрите `total_with_nds`. Договор не нужен: без него evo считает расход проекта (в ответе `scope: project`); по документации ключу нужна роль администратора проекта, вживую хватает и «Наблюдателя проекта» (BIL-7). Ответ 403 — у ключа нет этой роли; тогда — консоль → «Контроль затрат». Стоп-правила: при 2 000 ₽ — не создавать новых кластеров; при 3 000 ₽ — только чтение и уборка; при превышении 4 000 ₽ — написать дежурному, ничего не удалять «в панике» (сначала `evo vm list`, `evo k8s list`, `evo pg list`, `evo kafka list`, `evo redis list`, `evo vpc fips`).

Оценка обязательных сценариев (С1–С5 дважды, С6, С7, С9) с уборкой в тот
же день — около 50 ₽ на участника (расчёт по ценам раздела 2). Не
укладывается при сбое: Kubernetes, оставленный дольше 12 суток, и кластеры
DBaaS, зависшие в `FAILED`/`DEPLOYING` и не убранные в консоли. Поэтому
С12 — только участникам с ежедневным контролем.

## 6. Что сообщать и как

Участники волны сообщают через внутренний канал программы догфудинга
(вид заявки и шаблон — в памятке волны): отчёт о сценарии, ошибка, идея,
вопрос, чек-ин. Ключи, Key Secret, токены и пароли — не вставлять никуда.

Ошибки, идеи и вопросы разбор волны переносит в Issues этого репозитория —
обезличенными, без имён участников, ID, адресов и имён ресурсов, по
`docs/internal/feedback-triage.md`, раздел «Заявки волны догфуда». Отчёты
о сценариях и чек-ины в репозиторий не переносятся: из них считаются
гипотезы раздела 3 и покрытие. Пользователи вне волны пишут в Issues
напрямую, по формам (`bug.yml`, `idea.yml`).

| Что это | Признак |
|---|---|
| Ошибка | поведение расходится с «Успехом» сценария, `docs/` или `--help`; паника; неверный код выхода; ресурс остался после удаления; деньги без превью; отказ после «да» |
| Идея, неудобство | всё работает, но непонятно, долго, не хватает команды, флага, подсказки |
| Известное ограничение | есть в «Известном» сценария или области, в «Известных ограничениях» `CHANGELOG.md` или в реестре расхождений — отметить в отчёте о сценарии, отдельно не сообщать |
| Проблема платформы Cloud.ru | ошибка API в тексте (`API_ERROR` с HTTP-статусом, `API_RATE_LIMITED`); разбор сверит с реестром и дополнит его счётом «N из M» |
| Вопрос без ответа в документации | дыра в документации, разбор её закроет |

Одна заявка — одна проблема.

## 7. Уборка в конце волны

Чек-лист участника (по каждому проекту, где работал):

1. В каждом каталоге с `.evo/`: `evo status` → «нет развёртывания», иначе `evo destroy`; `evo stack status <job-id>` → `destroyed`.
2. `evo vm list` — пусто (или только чужое, если проект общий: смотреть префикс `df-<логин>-`).
3. `evo disk list` — нет дисков без ВМ (CMP-11: оплачиваются).
4. `evo vpc fips` — нет адресов без ВМ; `evo snat list` — пусто; свои VPC (и `keep-<логин>` из С4) удалены.
5. `evo vpc security-groups` — нет своих правил, открытых `open-ports`; закрыть — `evo vpc close-ports <группа> --port N --cidr <источник>`.
6. `evo k8s list`, `evo pg list`, `evo kafka list`, `evo redis list` — пусто. Кластер в `FAILED`/`DEPLOYING`, который не удаляется, — удалить в консоли и указать в отчёте.
7. `evo lb list`, `evo tg list`, `evo dns zones`, `evo ca list`, `evo ar list`, `evo cert list`, `evo secret list`, `evo s3 buckets` — без своих ресурсов; собственные образы (`evo image list --type private`) удалены.
8. Итоговый чек-ин: расход за волну и «Остались ли ресурсы».

Быстрее — агентом со скиллом `evo-cleanup` (С4), затем проверка по списку.

Сверка владельцем после всех: те же списки по каждому тестовому проекту
через `evo --profile <проект>`; правила групп безопасности без своих ВМ —
`evo vpc close-ports`; `cloud-e2e` → `cleanup_only` трогает только
`evo-e2e-*` и для догфуда не подходит. Расход по проектам — консоль
«Контроль затрат».

## 8. Критерии

Блокер (волна или сценарий останавливается до фикса): деньги без превью
или без подтверждения; ресурс, который evo создал и не нашёл; удаление не
того ресурса, в том числе чужого в С4; ключ или токен в выводе, логе,
файле с широкими правами; паника; потеря `state.json`; `evo mcp` ломает
агента (не-JSON в stdout).

Замечание: неверный код выхода или `reason`; расхождение CLI и MCP; текст
ошибки без подсказки; долгий ответ без хода операции; ошибка маршрута
агента, которая повторяется у многих (повод для правки скилла или
описания инструмента); документация не совпадает.

Волна пройдена, когда: у каждого обязательного сценария не меньше 6
прохождений каждым способом (без скиллов и со скиллами), из них не меньше
2 в Claude Code и 2 в Cursor; С11 — не меньше 2 участников на Windows и 2
за прокси; получено не меньше 20 принятых ошибок, идей и вопросов;
открытых блокеров нет; уборка подтверждена итоговыми чек-инами; суммарный
расход волны известен.
