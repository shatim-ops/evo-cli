## 1. Цели

1. Каждый инструмент реестра имеет ровно одну команду CLI с флагами,
   выведенными из его схемы, русской справкой и тем же JSON-ответом, что
   в MCP. Каждая команда CLI либо вызывает инструмент, либо стоит в
   закрытом списке локальных команд с причиной.
2. Паритет проверяется тестами, а не глазами: тест-ограничитель на
   покрытие, тест превью для всех изменяющих инструментов, тест равенства
   `--json` и JSON инструмента, закрытый список различий HTTP-режима.
3. Справка CLI (RU/EN) и описание инструмента (EN) — из одного источника
   в реестре.
4. Существующие команды, флаги, коды выхода и форматы `--json` не
   ломаются; неизбежные изменения — в разделе «Миграция» по правилам
   `docs/RELEASING.md`.

Мера успеха: контракт C1–C10 из analysis.md §6 выполняется, расхождения
PAR-1…PAR-38 закрыты или внесены в список исключений с причиной.

## 2. Не-цели

- Переименование существующих инструментов (`provision`, `list_zones`,
  `open_ports` и т. д.): имена знают агенты и конфиги, выигрыш нулевой.
- Унификация семантики `provision`, `deploy_plan`/`deploy_apply` и
  `engine.Deploy` (три пути создания ВМ из `command-model.md` §5) — это
  разные инструменты, а не одна операция на двух поверхностях.
- Ослабление политики HTTP (H1–H6, H8 в analysis.md §5).
- Русский язык в MCP.
- Потоковые ответы в MCP (`logs -f`).

### REQ-1. Реестр — единственный источник команд CLI

Закрывает: PAR-1, PAR-2 (механизм), C1, C3.

Что сделать. В `tools.Tool` добавить поле описания CLI, заполняемое при
регистрации инструмента (`tools/tools*.go`), например:

```go
type CLISpec struct {
    Group   string            // "vm"; "" — команда корня (status, deploy)
    Verb    string            // "create"; "list"
    Args    []string          // позиционные, как сегодня в treeCmd.Args
    Rename  map[string]string
    Omit    map[string]bool
    Pairs   map[string]bool
    Files   map[string]bool
    Columns []string
    Render  string            // имя рендера из закрытого набора ("image-list"), "" — таблица
    Raw     bool
    // CLIOnly — флаги, которых нет в схеме, с причиной (logs: follow).
    CLIOnly []CLIFlag
    // None — команды нет; причина обязательна (сейчас таких нет и быть не должно).
    None string
}
```

`cli/trees.go` строит команды обходом реестра, а не литерала
`treeGroups`; литерал удаляется. Презентация (русские заголовки
колонок, рендеры `image list`, `k8s addons`) остаётся в `internal/cli`,
но привязана по имени из `CLISpec.Render`.

Критерии приёмки:

- `treeGroups` в `cli/trees.go` отсутствует; 72 существующие команды
  строятся из `CLISpec` и дают тот же `--help`, те же флаги и тот же
  `--json` (регрессия: `docs/commands.md` не меняется, кроме порядка
  секций, если он изменился).
- Инструмент без `CLISpec` (и без `None`) не компилируется или валит
  тест при построении реестра.
- `CLISpec.Render` ссылается только на зарегистрированный рендер.

Тесты: существующие `TestTrees_MatchRegistry`, `TestTrees_BuildAndHelp`,
`TestCommandsDoc` остаются зелёными; новый `TestRegistry_EveryToolHasCLISpec`
(в `internal/tools`): у каждого инструмента `Group+Verb` или `None` с
непустой причиной; пара `Group+Verb` уникальна; каждый позиционный и
каждый ключ `Rename/Omit/Pairs/Files` — аргумент схемы.

Оценка: 2–3 дня.

### REQ-4. Команды движка — через реестр

Закрывает: PAR-5…PAR-13, C8.

Что сделать. `evo deploy`, `evo status`, `evo logs`, `evo destroy`,
`evo list-zones`, `evo project list`, `evo list-images` перестают
вызывать `engine` напрямую и становятся командами инструментов `deploy`,
`status`, `logs`, `destroy`, `list_zones`, `org_projects`,
`list_images` (`CLISpec.Group == ""` для корневых). Что для этого нужно
на стороне инструментов:

- `status`: добавить в ответ имена ВМ, зоны и flavor (`withNames`),
  которые сейчас даёт только CLI (PAR-7) — поля добавляются, ничего не
  удаляется; таблица CLI строится из этого JSON.
- `deploy`: превью с ценой и признаком «обновление/новая ВМ» (PAR-6,
  REQ-7); гейт — один для обеих поверхностей (вопрос Q1).
- `logs`: флаг `--follow` объявляется `CLIOnly` с причиной «поток
  невозможен в MCP»; без него CLI и MCP идут одним путём. Ответ
  инструмента остаётся текстом (вопрос Q7).
- `destroy`: `evo destroy` = инструмент без `vm_id`/`name`; превью
  инструмента должно нести то же, что `destroyPreview` (ВМ, FIP,
  правила) — перенести сборку превью в инструмент; флаг `--release-ip`
  появляется у `evo destroy` из схемы; скрытый `--force` остаётся как
  `CLIOnly` до v2.0.
- `list_zones`: `evo vm zones` — основная команда; `evo list-zones` —
  скрытый алиас с предупреждением; его `--json` (массив) сохраняется до
  v2.0 через `CLIOnly`-режим совместимости (см. §4).
- `org_projects`: `evo project list` — алиас `evo org projects`; поля
  `active` и `note` добавляются в ответ инструмента (аддитивно), поле
  `organization_unit_id` появляется в CLI (аддитивно).
- `list_images`: `evo list-images` скрыта и устарела — оставить как
  есть до v2.0, пометить в `localCommands` «устаревший алиас».

Критерии приёмки:

- В `internal/cli` нет вызовов `eng.Deploy`, `eng.Status`, `eng.Logs`,
  `eng.Destroy`, `eng.ListImages`, `Cloud.ListAvailabilityZones`,
  `listProjects` вне `evo configure`/`evo project use` (статический
  тест по AST, по образцу `codeEnvVars` в `cli/docs_test.go`).
- `evo status --json` ⊇ прежние поля; `evo deploy --json`, `evo destroy
  --json` при `--dry-run` — конверт `dry_run` с `preview.details` =
  ответ инструмента (REQ-6).
- Коды выхода прежние (таблица `docs/exit-codes.md`), кроме записанных в
  «Миграции».

Тесты: `TestParity_NoEngineCallsInCLI` (AST); REQ-6 и REQ-8 для этих
семи инструментов; существующие тесты `status`, `destroy`, `deploy` в
`internal/cli` и `internal/engine` остаются зелёными.

Оценка: 3–4 дня.

### REQ-5. Описания инструментов на двух языках из одного места

Закрывает: PAR-14, PAR-15, PAR-16, C7.

Что сделать. В реестре описание инструмента и каждого аргумента —
пара EN/RU: `Description` остаётся английским (MCP, `tools describe`
с `EVO_LANG=en`), добавляется `DescriptionRU`; у свойств схемы —
`x-description-ru` **не** в `inputSchema` (MCP-клиенты получают схему
как есть; лишнее поле раздувает `tools/list` на ~100 КБ и может не
пройти валидацию клиента), а в параллельной карте
`Tool.ArgDescriptionsRU map[string]string`. Карты `toolShortRU`,
`toolLongRU`, `flagShortRU` из `cli/trees_ru.go` переезжают в реестр и
становятся обязательными для всех 152 инструментов. Краткое описание
(`Short`) — первая фраза; подробное — остальное.

Текст превью (`message` в `confirmation_required`) не содержит
инструкции «call again with confirmed=true»: её добавляет транспорт
(MCP уже добавляет `approval`; CLI печатает подсказку `--yes`). Поле
`message` описывает действие.

`evo tools describe` и `evo tools list` показывают описание на языке CLI
(`--json` — оба поля).

Критерии приёмки:

- У каждого инструмента и каждого аргумента схемы RU-текст непустой и
  без слова `confirmed` (по образцу `TestTrees_RussianFlags`, но на
  весь реестр).
- `message` ни одного `confirmation_required` не содержит `confirmed`
  (обход всех изменяющих инструментов с поддельным облаком, как в
  `TestQA_MutatingToolsWriteNothingWithoutConfirmed`).
- Таблицы всех деревьев — на языке CLI (`russianTrees` → все).
- `docs/tools.md` получает столбец с русским описанием; `docs/commands.md`
  не меняется по содержанию для 72 команд (тексты переезжают дословно).

Тесты: `TestRegistry_DescriptionsBothLanguages`,
`TestContract_PreviewMessageHasNoConfirmedHint`, `TestToolsDoc`.

Оценка: 2–3 дня, из них ~1,5 дня — русские тексты для 80 инструментов
и ~250 аргументов (объём виден в `docs/tools.md`).

### REQ-6. Превью всех изменяющих инструментов совпадает на четырёх поверхностях

### REQ-7. Цена в превью инструмента, а не в CLI

Закрывает: PAR-28, PAR-6.

Что сделать. `provision` и `deploy` в ветке без `confirmed` выполняют
те же чтения, что `deploy_plan` (каталог flavor, зона, образ, расчёт
цены с тайм-аутом 5 с) и кладут результат в `preview` (`cost`, имена
зоны и flavor). `engine.CompletePreview` вызывается из инструмента;
`cli/tools.go:createPreview` только рендерит. Превью не создаёт
ресурсов — инвариант `TestContract_GatePreviewDoesNotWrite` сохраняется.

Критерии приёмки: `evo vm create web --dry-run --json` и ответ
`provision` по stdio совпадают, включая `cost`; при недоступном API цены
— оценка по таблице тарифов и `price_api_error`, как у `deploy_plan`.

Тесты: REQ-6; `TestContract_GatePreviewDoesNotWrite` (чтения разрешены,
записи — нет).

Оценка: 1–2 дня.

### REQ-8. `--json` команды = JSON инструмента

Закрывает: PAR-7…PAR-11, PAR-18, C4, C6.

Что сделать. Тест по реестру: для каждого инструмента с `CLISpec` —
аргументы из той же таблицы `parityArgs` (плюс записи для чтений),
поддельное облако; сравнение stdout `evo <команда> --json --yes` с
текстом обработчика при тех же аргументах и `confirmed=true`, байт в
байт. Для инструментов, чей ответ — не JSON (`logs`), сравнение текста.
Ошибки: при одинаковом входе `reason` в stderr-конверте CLI равен
`reason` ответа инструмента, код выхода — по таблице.

Одна проверка типов аргументов: `tools.CheckArgs` (экспорт `checkedArgs`
без обработчика) используется и в `evo tools call`, и в деревьях;
собственный `checkArgType` в `cli/tools.go` удаляется. Правило — у
инструмента (строка для массива допустима, как в `docs/mcp.md`).

Критерии приёмки: тест покрывает все инструменты с командой; ноль
исключений, кроме явного списка `jsonAliasCompat` для `evo list-zones`
(массив) до v2.0.

Тесты: `TestParity_JSONEqualsTool`, `TestParity_ErrorReasonEqualsTool`;
`TestContract_ArgForms` обновляется под общий валидатор.

Оценка: 2 дня.

### REQ-9. Закрытый список различий HTTP-режима

Оценка: 1 день.

### REQ-12. Один гейт `deploy` (по решению владельца, Q1)

Закрывает: PAR-5.

Вариант (рекомендуемый): `deploy` требует согласия и при обновлении ВМ
в обеих поверхностях; превью несёт `update: true`, `vm_id`,

## 4. Совместимость и миграция

Правило `docs/RELEASING.md`: ломающие изменения CLI (команды, флаги,
коды выхода, формат `--json`) — только в major; исключение — исправления
ошибок и безопасности с разделом «Миграция» в CHANGELOG.

Что **не** ломается (и это критерий приёмки каждого PR):

- 108 существующих команд, их флаги, позиционные и `--help`;
- имена всех 152 инструментов и их схемы (`inputSchema` байт в байт,
  тест `TestContract_Schema` расширить снимком);
- коды выхода по `docs/exit-codes.md`;
- форматы `--json`: только добавление полей (`status`, `project list`,
  `destroy`), ничего не удаляется и не переименовывается;
- `evo tools call`, `--arg`, `--args-json`, `--wait`;
- `evo list-zones`, `evo list-images`, `destroy --force` — работают до
  v2.0 как сейчас.

Что ломается и идёт в «Миграцию» (нужно решение владельца, §7):

| Изменение | Был | Станет | Основание для 1.x |
|---|---|---|---|
| `evo deploy` на существующей ВМ без `--yes` и без терминала (Q1) | 0, обновляет | 3, не обновляет | пробел согласия: обновление прод-ВМ без вопроса — тот же класс, что `secret value` в 1.1.0 |
| `message` превью без фразы `confirmed=true` (REQ-5) | текст с инструкцией | текст без инструкции; инструкция в `approval` (MCP) и `hint` (CLI) | агент читает `approval` (есть с 1.1.0); текст `message` контрактом не объявлен |
| `redacted` в ответах по HTTP (REQ-9) | поля молча заменены | + поле `redacted` | аддитивно |

В v2.0 (отдельно, вне этого ТЗ): удалить `evo list-zones`,
`evo list-images`, `destroy --force`, alias `cloudru-vm`; `evo project
list --json` → формат `org_projects`.

## 7. Вопросы владельцу

Каждый — с вариантами и рекомендацией; решение нужно до PR 5 (Q1, Q7),
PR 3 (Q4), PR 7 (Q5), PR 9 (Q2).

**Q1. Гейт `deploy` при обновлении существующей ВМ.** Сейчас CLI не
спрашивает, MCP требует `confirmed` всегда (PAR-5).
(а) Оба спрашивают — одно правило «изменяющий инструмент → согласие»;
ломает `evo deploy` без `--yes` в скриптах (код 3 вместо 0), идёт в
«Миграцию» как исправление пробела согласия.
(б) Оба не спрашивают, когда ничего платного не создаётся — совпадает с
CLI; агент обновляет прод-ВМ без вопроса человеку.
(в) Оставить как есть и записать в исключения — противоречит
«недопустимы».
Рекомендация: **(а)**.

**Q2. Локальные команды.** Какие остаются без инструмента.
(а) `configure*`, `project use`, `init`, `completion`, `version`, `mcp`,
`tools` — локальные; `whoami`, `doctor` — инструменты (REQ-11);
`verify` — локальная (проверка с машины оператора).
(б) Всё перечисленное локальное, инструментов не добавлять.
(в) И `verify` как инструмент (проверка с хоста сервера).
Рекомендация: **(а)**: `whoami`/`doctor` агенту нужны для диагностики,
`verify` с сервера — другой результат.

**Q3. Упаковка релизов.** Паритет целиком — в 1.x с одной записью
«Миграции» (Q1), а удаление алиасов (`list-zones`, `list-images`,
`--force`) — в v2.0; или всё в v2.0 одним major.
Рекомендация: **1.x** (ветками PR 1–8 как minor-релизы 1.2–1.3), v2.0
— только удаления: так агенты и скрипты получают команды раньше, а
major не раздувается.

**Q4. Имена команд для групп, чьё имя инструмента не совпадает с
группой.** `evo lb`/`evo tg` (как имена инструментов) или
`evo nlb lb-create`/`evo nlb tg-create` (как группа); `evo metrics` или
`evo monitoring metrics-history`.
Рекомендация: **по префиксу имени инструмента** (`evo lb`, `evo tg`,
`evo metrics`): короче и соответствует правилу «команда ↔ имя
инструмента»; группа остаётся для `--toolsets`.

**Q5. Маскирование по HTTP (H7).** Оставить молчаливым; добавить поле
`redacted`; сузить до известных полей и добавить `redacted`.
Рекомендация: **третье** — честнее для агента, меньше ложных
срабатываний на чтениях.

**Q6. Цена в превью `provision`/`deploy` в MCP** (один-три read-only
запроса в гейте, до 5 с). Да / нет (оставить цену только в
`deploy_plan`).
Рекомендация: **да** — иначе агент одобряет платный ресурс без цены, а
CLI её показывает (PAR-28); инвариант «превью ничего не создаёт»
сохраняется.

**Q7. Ответ `logs` — текст, а не JSON** (PAR-11). Оставить (исключение
контракта: «ответ инструмента — текст журнала») или обернуть в
`{"log": "…"}` (ломает агентов, читающих текст; «Миграция»).
Рекомендация: **оставить**, записать как единственное исключение C4 с
причиной.

**Q8. Поле `CLISpec` в `tools.Tool` или отдельная карта в `internal/cli`**
(R5). Рекомендация: **в реестре**: одна точка регистрации, компилятор и
тест ловят пропуск; архитектурный принцип «реестр не знает о транспорте»
уточнить до «реестр не знает о транспортах MCP; представление в CLI —
часть описания инструмента».
