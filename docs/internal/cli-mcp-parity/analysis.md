# Паритет CLI ↔ MCP: анализ

Дата: 20.10.2026. Код: `main` на `431851d` (релиз v1.1.0). Пути без
префикса — от `internal/`. Ссылки `файл:строка` — на этот коммит.

Решение владельца продукта, которое документ принимает за требование:
«Инструментарий CLI и MCP должен совпадать. Расхождения CLI и MCP
недопустимы.» Здесь — что совпадает сейчас, что нет, и какое правило
можно проверять автоматически. ТЗ на доработку — [spec.md](spec.md).

Всё ниже выведено из кода, тестов и запуска бинаря без облака
(`HTTPS_PROXY=http://127.0.0.1:9`, пустой `CLOUDRU_CONFIG_DIR`). Каждая
запись помечена: **факт** (код или тест) или **гипотеза** (вывод по
коду, вживую не воспроизведено). Цифры анализа — на момент до PR 1;
текущие таблицы инвентаризации — в [inventory.md](inventory.md), их
генерирует тест `TestParityInventory` (`internal/cli/inventory_test.go`,
REQ-10; до PR 8 — скрипт `inventory/main.go`, удалён).

## 1. Сводка

Цифры (из [inventory.md](inventory.md), сгенерировано из кода):

| Что | Сколько |
|---|---|
| Инструментов в реестре `tools` | 152 (65 изменяющих, 22 группы) |
| Инструментов со своей командой дерева (`trees.go`) | 72 (34 изменяющих) |
| Инструментов, закрытых командой движка со своим кодом (`deploy`, `status`, `logs`, `project list`, скрытая `list-images`) | 5 (1 изменяющий) |
| Инструментов, доступных из CLI только как `evo tools call <имя>` | 75 (30 изменяющих) |
| Команд CLI без инструмента (локальные и мета) | 20 видимых + 2 скрытых |
| Инструментов с русской справкой | 72 из 152 (ровно те, что в деревьях) |
| Инструментов, у которых совпадение превью проверяет тест | 6 из 65 изменяющих (`TestContract_PreviewParity`) |

Расхождений в реестре: **38**: блокер — 4, важно — 13, косметика — 17,
по замыслу или совпадает — 4. Фактов — 36, гипотез — 2.

Главное:

1. **Половина инструментария в CLI есть только формально.** 75 из 152
   инструментов (Kafka, Redis, AR, Container Apps, сертификаты, DNS,
   NLB, SNAT, биллинг, аудит, IAM/org, мониторинг, стек, `open_ports`,
   `image_create/delete`, `deploy_plan/apply`, `list`) вызываются
   только `evo tools call`: сырой JSON, английские описания,
   `--arg k=v` вместо флагов. Тест `TestTrees_MatchRegistry` проверяет
   покрытие только 7 групп из 22 (`cli/trees_test.go:67`), поэтому
   новый инструмент вне этих групп команду не получает и никто этого
   не замечает (PAR-1).
2. **Пять операций живут в двух кодовых путях.** `evo deploy`,
   `status`, `logs`, `destroy`, `list-zones` написаны поверх `engine`
   напрямую, а инструменты `deploy`, `status`, `logs`, `destroy`,
   `list_zones` — поверх того же `engine`, но со своими аргументами,
   превью и форматом ответа. Отсюда самые серьёзные расхождения:
   `evo deploy` не спрашивает подтверждения при обновлении ВМ, MCP
   `deploy` — всегда (PAR-5); `evo status --json` и `status` отдают
   разные поля (PAR-7); `evo list-zones --json` и `evo vm zones --json`
   — разный JSON одного списка (PAR-9).
3. **Язык и подтверждение.** Текст превью инструмента попадает в CLI
   как есть: `evo disk delete … --dry-run` печатает «вызовите снова с
   confirmed=true», хотя в CLI согласие — `--yes` (PAR-15). Описания
   инструментов, в том числе в `evo tools describe`, только английские;
   русская справка есть у 72 инструментов и хранится отдельной картой
   строк (PAR-14).
4. **HTTP-режим MCP отличается от stdio и CLI по 9 пунктам** (раздел
   5). Семь из них — защита хоста общего сервера и обязаны остаться,
   два (`SERVER_BUSY`, маскирование полей в ответах всех инструментов) —
   обсуждаемые. Сейчас перечень не закрыт тестом: добавить новое
   ограничение можно без следа в документации (PAR-33).
5. **Паритет сегодня не измеряется.** Нет теста, который сравнивает
   `--json` команды с JSON инструмента; `TestContract_PreviewParity`
   покрывает 6 инструментов из 65 и для двух из них (`vm create`,
   `k8s add-addon`) сравнивает не CLI с MCP, а только три агентских
   поверхности между собой (`cli/contract_preview_test.go:107`).

Рекомендация в одной строке: не писать 75 команд руками, а генерировать
деревья из реестра с обязательной регистрацией каждого инструмента в
одном месте (команда, глагол, позиционные, русский текст) и закрыть это
тестом «нет инструмента без команды, нет команды без инструмента или
без записи в списке локальных». Детали — [spec.md](spec.md).

## 2. Как устроено сейчас

Три поверхности поверх одного реестра:

```
                 internal/tools (152 инструмента: имя, схема, обработчик)
                 ┌──────────────┬───────────────────┬──────────────────┐
                 │              │                   │                  │
         evo <дерево> <глагол>  evo tools call   evo mcp (stdio)   evo mcp --http
         cli/trees.go           cli/tools.go     mcp/server.go     mcp/http.go + http_policy.go
         флаги из схемы,        --arg k=v,       tools/list,       + политика хоста,
         RU-справка из карт,    сырой JSON       tools/call,       маскирование,
         confirm.Ask            confirm.Ask      approval          --allow-project

         evo deploy/status/logs/destroy/list-zones/project list
         cli/main.go, cli/project.go — свой код cobra → engine, минуя реестр
```

- Реестр не знает о транспортах (`tools/registry.go:5-16`). Обработчик
  получает `map[string]any` и возвращает текст JSON и флаг ошибки.
- Команда дерева — запись в `treeGroups` (`cli/trees.go:77-171`): глагол,
  инструмент, позиционные аргументы, `Rename`, `Omit`, `Pairs`, `Files`,
  колонки, `Render`/`Raw`. Остальные аргументы схемы становятся флагами
  (`cli/trees.go:234-249`); `project_id`, `region`, `confirmed` берутся
  из корневых флагов (`cli/trees.go:176`). Изменённые флаги уходят в
  инструмент (`cli/trees.go:495-498`).
- Подтверждение: `confirm.Ask` (`confirm/confirm.go:108`) — один для
  деревьев, `tools call` и команд движка. Дерево дополняет превью
  инструмента ценой и именами (`cli/tools.go:704-730`); `tools call`
  показывает ответ инструмента как есть (`cli/tools.go:626-665`).
- MCP: `tools/list` отдаёт имя, описание, схему и аннотации
  (`mcp/server.go:98-108`), `tools/call` добавляет к
  `confirmation_required` поле `approval` (`mcp/server.go:595-615`).
  Сервер всегда говорит по-английски (`cli/mcp.go:177`, `cli/main.go:128-133`).
- Язык: CLI по умолчанию русский (`i18n`), `EVO_LANG=en` — английский.
  Ошибки инструментов идут через `i18n.T` и потому в CLI русские, а
  в MCP английские (проверено запуском: `evo tools call vm_get --arg
  vm_id=… --arg name=web` — «укажите vm_id или name, не оба», тот же
  вызов по stdio — «pass vm_id or name, not both»). Описания
  инструментов и схем — только английские; русская справка 72 команд —
  карты `toolShortRU`, `toolLongRU`, `flagShortRU`
  (`cli/trees_ru.go:34`, `:120`, `:340`).
- Документация: `docs/commands.md` генерируется из дерева cobra
  (`cli/docs_test.go:59`), `docs/tools.md` — из реестра
  (`cli/tools_doc_test.go:29`); CI сверяет оба.

## 4. Реестр расхождений PAR-N

Серьёзность: **блокер** — разное поведение изменяющей операции или
потеря данных/безопасности; **важно** — разный контракт (поля JSON,
аргументы, коды), который ломает скрипт или агента при переходе между
поверхностями; **косметика** — текст, форма, именование.

Обозначения: CLI — команда дерева или движка; TC — `evo tools call`;
MCP — stdio (HTTP отдельно в разделе 5).

### 4.1. Наличие и регистрация

| ID | Вход | CLI | MCP | Где | Серьёзность | Статус |
|---|---|---|---|---|---|---|
| PAR-1 | 75 инструментов из 16 групп | только `evo tools call <имя> --arg k=v`: сырой JSON, английское описание, нет позиционных, нет русской справки, нет таблицы | полноценный инструмент | `cli/trees.go:77-171` (9 деревьев); `cli/trees_test.go:67` проверяет покрытие только `vm, disk, vpc, k8s, pg, s3, secret` | блокер | факт (inventory.md §2) |
| PAR-2 | новый инструмент в группе вне 7 проверяемых | команды не получает, тест не падает | появляется в `tools/list` | `cli/trees_test.go:67-73`; группы `image`, `deploy` и 13 других не проверяются | блокер | факт |

## 5. HTTP-режим: где различие обязано быть

`evo mcp --http` — общий сервер: аргументы приходят от удалённого
клиента, а исполняются на хосте, где лежат ключ Cloud.ru, kubeconfig и
рабочий каталог. Поэтому различие с stdio — не «CLI против MCP», а
«локальный процесс против сетевого сервиса». Решение «недопустимы»
здесь надо трактовать так: **различий нет в наборе инструментов и
схемах** (это выполняется: `restrictForHTTP` меняет только обработчики,
`mcp/http_policy.go:22-24`), а каждое различие в поведении — из
закрытого перечня, который проверяет тест.

| # | Ограничение | Где | Зачем | Оценка |
|---|---|---|---|---|
| H1 | `k8s_kubectl`, `k8s_apply`, `k8s_helm` — ошибка, если бинаря нет на сервере | `http_policy.go:40-56` | Docker-образ без kubectl/helm | обязано: это не политика, а факт среды; по stdio ошибка была бы та же |

## 7. Конвенция именования

Правило: `evo <группа> <глагол> [позиционные]` ↔ `<группа>_<глагол>`.
Группа — из `tools.Groups()`; глагол — остаток имени, `_` → `-`
(`vpc_route_create` ↔ `evo vpc route-create` — уже так). Обратное
правило для нового инструмента: имя строится из команды, а не наоборот.

Инструменты, чьё имя не ложится в схему (30 из 152), и что с ними
делать. Принцип: **имена инструментов не меняем** (их знают агенты и

## 8. Где полное совпадение вредит

Позиция оппонента: требование «недопустимы» правильно для
**инструментария** (набор операций, аргументы, ответы, превью) и
неправильно, если его читать как «одинаковое всё». Ниже — различия,
которые предлагаю оставить, с аргументом и альтернативой. Решение за
владельцем; каждое попадает в закрытый список исключений контракта.

1. **Локальные команды без инструмента** (`configure`, `project use`,
   `whoami`, `doctor`, `init`, `verify`, `version`, `completion`).
   Аргумент: `configure`/`project use` пишут ключ и проект на диск
   **сервера** — инструмент, который меняет учётные данные общего
   MCP-сервера по просьбе агента, это дыра, а не паритет (агент одного
   клиента переключает проект всем). `init` интерактивен по замыслу
   (выбор из списка). `verify` проверяет доступность с машины оператора,
   а не с сервера. Альтернатива для `whoami`/`doctor`: read-only
   инструменты `whoami` (профиль, маскированный Key ID, проект,
   видимые проекты) и `doctor` (связь с IAM/Compute, kubectl/helm) —
   агенту это полезно для диагностики «почему не работает». `verify`
   как инструмент возможен (проверка с сервера), но это другой
   результат, и так его и надо назвать. Рекомендация: `whoami`,
   `doctor` — сделать инструментами (REQ-11); `configure`, `project
   use`, `init`, `completion`, `version` — в список локальных.
2. **HTTP-ограничения H1–H6, H8** — обязаны остаться (§5). Совпадение
   stdio и HTTP здесь означало бы либо открыть файлы хоста общего
   сервера, либо запретить `-f` и локальному kubectl. Альтернативы нет;
   нужен закрытый список и тест.
3. **Маскирование ответов (H7)** — вредит паритету чтений и ничего не
   говорит агенту. Рекомендация: оставить, но помечать ответ
   (`"redacted": ["admin_password"]`) и сузить до известных полей.
4. **Язык.** MCP всегда EN — правильно: агент один на всех, а
   `EVO_LANG` сервера — не выбор клиента. Но русские ошибки в CLI
   против английских в MCP при **одинаковом `reason`** — нормально, это
   локализация, а не расхождение. Требование: тексты обеих версий — из
   одного места (REQ-5), `reason` и `hint`-структура совпадают.
5. **`--dry-run` и конверт `confirmation_required` в CLI.** В MCP
   превью — это ответ инструмента; в CLI `--dry-run` печатает конверт с
   `preview.details`. Унифицировать до байта нельзя без потери
   `summary`/`action` для человека. Предлагаю зафиксировать конверт как
   часть контракта: `details` = ответ инструмента байт в байт (C5), а
   `action`/`summary` — CLI-надстройка.
6. **Дополнение превью ценой в CLI (PAR-28).** Сейчас цена считается в
   `cli/tools.go`, и поэтому MCP её не видит. Это как раз вредное
   расхождение: агент принимает решение о платном ресурсе без цены.
   Правильное место — инструмент (`provision` может сделать тот же
   read-only запрос, что `deploy_plan`), тогда CLI ничего не дополняет.
   Контраргумент из BACKLOG [03] («гейт не ходит в облако») слабый:
   чтение каталога flavor не создаёт ресурсов, а `vm delete` уже ходит в
   облако за превью (`destroyTargeted`).
7. **`evo logs -f`.** Потоковый ответ в MCP невозможен (один результат
   на вызов). Оставить `follow` только в CLI, но как флаг, объявленный
   в реестре как `CLI-only` с причиной, а не как свободный код.
8. **`--toolsets`, `--allow-project`, `SERVER_BUSY`** — свойства
   сервера, не инструментария. В контракт не входят; фиксируются в
   списке «режим сервера».

Чего делать **не** стоит, даже ради буквы требования: переименовывать
существующие инструменты под схему `группа_глагол` (ломает агентов,
даёт major без пользы), убирать корневые `evo deploy/status/logs/
destroy` (ломает скрипты и README; достаточно сделать их алиасами
команд реестра), заставлять MCP говорить по-русски.
