# Место движка во внутренней системе

Перенесено из README на этапе 9: внешнему пользователю это не нужно, а для
сопровождающих объясняет, откуда в коде следы внутренней системы.

evo (до этапа 10 — `cloudru-vm`) вырос из движка инфраструктуры внутренней
системы. Это единственный путь, которым та система трогает облако: создание и
удаление ВМ, диски, сети, кластеры, образы, секреты, сертификаты, S3. Её
компоненты не ходят в облачное API сами — они зовут движок по MCP.

    внутренняя система ──MCP──▶ ДВИЖОК ──API──▶ Cloud.ru

Отсюда главное свойство: если движок ошибается, ошибка происходит в чужой
инфраструктуре и стоит денег. Поэтому изменяющие операции закрыты
подтверждением (`confirmed=true` в MCP, `--yes` в CLI), а не полагаются на
осторожность вызывающего. Согласие даёт человек — в описаниях инструментов
он называется «the user» (до v1.0 там было слово внутренней системы
«captain»; файл `.evo/captain_authorized_keys` читается под старым именем
до v2.0, новое — `.evo/user_authorized_keys`).

Тонкий MCP-клиент той системы лежит в другом, внутреннем репозитории. Он
различает исход «нужно подтверждение» отдельным кодом возврата (`3`), чтобы
скрипт на bash не принял превью за выполненную работу; CLI держит тот же код.

## История репозитория

История начинается с версии 0.3.0: база (0.1–0.2) писалась до того, как код
завели под git, и её коммитов здесь нет. Путь модуля до 12.08.2026 указывал на
`github.com/dzhechko/cloudru-vm-cli` — остаток рабочего окружения, а не чужой
проект; такого публичного репозитория не существует. Путь приведён к
настоящему месту кода.

## Планы

`standalone/` — аудит, план и брифы этапов превращения движка в
самостоятельный инструмент; решения владельца — `standalone/DECISIONS.md`,
найденное вне scope этапов — `standalone/BACKLOG.md`.
