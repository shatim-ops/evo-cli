## Что проверено и не найдено

### 1. Секреты из файла и stdin

Оба флага сразу, отсутствие обоих, пустой файл и пустой stdin — `USAGE` (`TestSecretFiles_Refusals`, REL12-9). Хвостовой `\r\n` снимается одним срезом, значение совпадает с литеральным флагом (`TestSecretFiles_SameArgumentAsValueFlag`). Нечитаемый путь и каталог дают `USAGE` с текстом «файл не прочитан», секрет в текст ошибки не попадает. Файл с пробелами по краям их сохраняет: `TrimSpace` есть только на терминале (B12-6). Симлинк `os.ReadFile` проходит: путь назвал сам вызывающий, это не граница «чужой ключ в `.evo`».

`os.ReadFile` не смотрит на контекст и не ограничивает размер. Именованный FIFO или `/dev/zero` могут заблокировать процесс или занять память. Отдельного теста нет: зависший `Read` не отпускает `go test`. Это остаточный риск, не находка с красным тестом.

Эхо. Отмена контекста вызывает `restore()` (`configure.go:185`). Ошибка самого `term.ReadPassword` восстанавливает терминал внутри библиотеки; второй `restore` на этой ветке продукт не вызывает. Мок, который лишь проверяет «restore не вызван», терминал не показывает, поэтому тестом это не закреплялось. Путь один на Linux, macOS и Windows (`CONIN$` прячет `golang.org/x/term`).

### 2. `evo mcp --read-only` (H11)

Команда, которая начинается с флага (`--namespace x apply`, `-- apply`, `--context … delete`), не является чтением: `kubectlReadOnly` смотрит на первое слово, `NeedsConsent` истинен, H11 отказывает до обработчика. `rollout restart` и `auth reconcile` не входят в `readOnlySubcommands` (`tools_kube.go:62`), H11 их отказывает. `helm rollback` и `helm template` попадают в `default` (`tools_kube.go:265`) и получают `USAGE` до kubeconfig. `install` / `upgrade` / `uninstall` требуют согласия.

Уже закрыто прежними тестами и кодом: `kubectl config`, `--raw`, `get secret -o yaml`, `describe secret`, `-v` (H3/H6); `KUBERC=off`; `k8s_kubeconfig` с `embed_token` по умолчанию (H6); вызов спрятанного инструмента — `USAGE`, не исполнение (`TestReadOnly_Calls`); H11 остаётся внешним слоем после `SetReadOnly` (`Server.gated`, REL12-5). `stack_status` работающий стек не продвигает (`tools_stack.go:841`, `:890`). Дыра этого пункта — короткое имя `sec` (B12-1) и локальная запись `deploy_plan` (B12-9).

### 3. `--allow-project`, кроме REL12-3

`checkAllowedProject` (`mcp.go:286`) сравнивает проект побайтно. Другой регистр UUID и пробелы вокруг — отказ `CONFIG_INVALID`, в облако такой вызов не уходит. `project_id` инструмента проходит через override движка и ту же проверку. `billing_consumption` / `billing_finops` без `project_id` при `SetProjectBound` читают проект сервера (RP-1). `org_projects` оставляет строку только при точном `id`; несовпадение регистра отбрасывает все строки, чужой проект в ответ не попадает. `audit_*` и метрики берут `ProjectID` движка, аргументом его не подменяют. Баланс соглашения у `billing_balance` и чтение других проектов у `org_quotas` и `iam_service_accounts` с `project_id` — записанные исключения. Ресурс чужого проекта по id (REL12-3) вне этой атаки.

### 4. Маскирование (H7)

Держатся уже закрытые случаи: замена поля `redacted` (RP-2), число под ключом-секретом и bool как флаг (RP-3), ключ с точкой и пробелом `private.key` / `Private Key` (RP-4), пара `name`/`value` и `key`/`value` в нижнем регистре (REL12-2), эхо строки длиной от 8 (REL12-10). Короткие значения и bool отдельным тестом не преследовались: changelog прямо оставляет `"status":"ok"` при `"password":"ok"`. Новые дыры — регистр ключей пары (B12-2), секрет внутри JSON-строки (B12-3), эхо числа (B12-4), `tls.key` и `id_rsa` (B12-5).

### 5. Повторный `evo deploy` и `deploy plan` → `deploy apply`

Без терминала и без `--yes` повторный `evo deploy` выходит с кодом 3 и состояние не меняет: `--json`, `--force`, `--non-interactive` идут через `confirm.Ask` с `NoPrompt` (`TestEngineCommands_RepeatedDeployGate`). `--dry-run` печатает превью и выходит с 0, в облако ничего не пишет — так устроен `Ask`. Тот же compose на работающей ВМ CLI не спрашивает (код 0), MCP `deploy` по-прежнему отвечает `unchanged: true`; сведение ждёт v2.0 (Q14).

`plan_id` с `../` и неверной длиной отвергает `validPlanID` до открытия файла. Два `deploy_apply` одного плана сразу: второй получает `ErrFileLocked` (`TestDeployApply_OverlapRefused`). `ApplyWithTimeout` файл compose не перечитывает. Образ уходит по имени (`apply.go:148`), повторной проверки «образ ещё в проекте» нет; создание — один POST, 4xx становится `CreateRejected`, плавающий IP до создания ВМ код evo не резервирует. Отдельный красный тест на предпроверку образа не ставился: отказ API уже не создаёт чужую ВМ. Расхождение цены между plan и apply в гейте не показано, потому что гейт план не читает (B12-8).

### 6. `tools.CheckArgs` и разбор флагов CLI

Целое JSON с `.0` или экспонентой (`50.0`, `5e1`, `1e3`) MCP и `--args-json` принимают, флаг и `--arg` — только десятичную запись. Это записано в changelog 1.2.0 как прежний RP-8, заново не закреплялось. Регистр enum обе стороны приводят к каноническому написанию. Пустая строка и пропущенный аргумент для строк сходятся через `stringArg`. Bool флага принимает формы pflag (`1`, `t`, `true`), MCP ждёт JSON bool — разный синтаксис носителя, не второй смысл. `NaN` флаг типа number отвергает; стандартный JSON его не переносит. Массивы и объекты `CheckArgs` по-прежнему не разбирает по элементам — так описано в `argcheck.go`.
