## Новые пункты

#### DB-22. PostgreSQL: список копий удалённого кластера — 400 FailedPrecondition вместо 404
Ошибка API · подтверждено вживую, 3 из 3 (внешняя проверка 24.10; cloud-e2e `dbaas_smoke` 24.10, run 40093421741, ru.AZ-2; cloud-e2e `dbaas_smoke` 24.10, run 40127262119, ru.AZ-1)
- **Док:** [удаление кластера](https://cloud.ru/docs/paas-postgresql/ug/topics/guides__deleting-cluster): «Будут удалены все базы данных, размещенные в кластере, а также резервные копии кластера». **Спека:** у `BackupService` нет удаления копии и списка копий по проекту — только список и чтение внутри кластера.
- **Живое:** до удаления кластера список копий отвечает; после — и список копий, и копия по имени → 400 FailedPrecondition, тело не JSON. В run 40127262119 причина видна: `FailedPrecondition desc = validate cluster readiness` — платформа проверяет готовность удалённого кластера, а не отвечает «нет». Начислений за хранение копий после удаления нет (детализация расходов, 24.10) — с документацией сходится.
- **Влияние:** клиент не отличает «кластера и копий больше нет» от ошибки запроса.
- **Просим:** 404 для копий удалённого кластера.

#### DB-23. PostgreSQL: нехватка ёмкости зоны — 429 ResourceExhausted, без описания
Ошибка API · подтверждено вживую, 5 из 6 в двух зонах (ru.AZ-2, 3 из 3: cloud-e2e `dbaas_smoke` 24.10, run 40118457142 — две попытки, run 40123320696; ru.AZ-1, 2 из 3: внешний прогон 25.10)
- **Док:** в документации и спецификации PostgreSQL ответа на нехватку ресурсов зоны при создании нет; 429 не описан.
- **Живое:** `POST` кластера STANDARD минимальной спецификации (1 vCPU, 2 ГБ, 10 ГБ) → 429 `rpc error: code = ResourceExhausted desc = reserve resources: reserve shared cluster resources: service-inventory ReserveV2: … shared cluster with required resources not found`, кластер не создаётся. ru.AZ-2, 24.10: тот же вызов в 12:24 UTC проходил, Kafka и Redis в той же зоне в 17:59 и 19:02 UTC создавались. ru.AZ-1, 25.10, около 21:39 UTC: две попытки подряд — 429, третья через несколько минут создалась и удалена; накануне (run 40127262119) зона была свободна.
- **Влияние:** 429 обычно значит «слишком много запросов», здесь — нехватка ёмкости: клиент и агент повторяют вызов через секунды, а это не помогает; когда ёмкость вернётся, ответ не говорит.
- **Просим:** отдельный код или поле причины для нехватки ёмкости (например, 503 с `Retry-After`); как узнать, в каких зонах спецификация доступна для создания сейчас.

#### NET-15. DNS: запись по несуществующему id — 400 «precondition» вместо 404
Ошибка API · подтверждено вживую, 4 из 4 (внешняя проверка 24.10; cloud-e2e `dbaas_smoke` 24.10; внешний прогон 25.10 — 2)
- **Живое:** `GET` и `DELETE` DNS-записи по id верной формы, которой нет, → 400 с текстом «precondition», а не 404. 25.10: `DELETE` существующей записи **приватной** зоны через публичный API (без `visibility`) → тот же 400; повторный `DELETE` уже удалённой записи с `visibility=private` → тот же 400.
- **Влияние:** клиент не отличает «записи нет», «запись в другом API (приватном)» и ошибку запроса; повторное удаление нельзя признать успешным.
- **Просим:** 404 для записи, которой нет в этом API.

#### NET-16. DNS: CNAME на имя с существующей A-записью — 409
Нет в документации · подтверждено вживую, 1 из 1 (внешний прогон 25.10); правило в документации DNS не искали — проверить
- **Живое:** `POST` записи CNAME на имя приватной зоны, у которого уже есть запись A, → 409 «already exists».
- **Влияние:** клиент проверяет занятость имени только по записям того же типа и узнаёт о конфликте типов из 409.
- **Просим:** описать правило совместимости типов записей на одном имени и код ответа.

#### K8S-14. Повторный `DELETE` во время удаления — 400 «cluster is already deleting»
Нет в документации · подтверждено вживую, 1 из 1 (внешний прогон 25.10, ru.AZ-1)
- **Док:** ответ на повторное удаление в [спецификации](https://cloud.ru/docs/api/specs/kubernetes-evolution/ug/_specs/openapi-v3.yaml) не описан.
- **Живое:** второй `DELETE` кластера через секунду после первого (`DELETING`) → 400 «cluster is already deleting». У VPC тот же случай отдаёт id той же операции. По отчёту прогона — ещё kubeconfig кластера в `PROVISIONING` → 400 «not allowed to get kubeconfig» и разовый 500 на чтение сразу после удаления namespace; эти ответы не записаны, в счёт не входят.
- **Влияние:** клиент не отличает «уже удаляется» (успех повтора) от ошибки запроса.
- **Просим:** 409 или 202 с id идущей операции.

#### BIL-8. Тариф хранения пользовательского образа ВМ не найден
Нет в документации · подтверждено по тексту тарифа (сверка 22.10)
- **Док:** создание образа из диска ВМ описано, хранение образа платное, но в тарифе [Evolution Compute](https://cloud.ru/documents/tariffs/evolution/evolution-compute) (страница и PDF) строки «хранение образа» нет — есть диски HDD и SSD NVMe и хранение резервных копий.
- **Влияние:** клиент соглашается на создание образа, не зная его цены.
- **Просим:** строку хранения пользовательского образа в тарифе или указание, по какой строке оно тарифицируется.

#### NET-14. Уникальность имени шлюза SNAT не описана
Нет в документации · гипотеза (сверка спецификации 22.10)
- **Спека:** `POST /api/v1/nat-gateways` (compute) — 409 на дубль имени нет. **Док:** об уникальности имени не говорит. Вживую не проверялось: нужно создать два платных шлюза.
- **Влияние:** повтор создания (тайм-аут, повтор агента) может создать второй платный шлюз.
- **Просим:** 409 на дубль имени или явное «имя не уникально», как у ВМ (CMP-13).

#### K8S-13. Уникальность имени кластера не описана
Нет в документации · гипотеза (сверка спецификации 22.10)
- **Спека:** `POST /v3/clusters` — ответы 200 и `default`, 409 на дубль имени нет. **Док:** об уникальности имени не говорит.
- **Влияние:** повтор создания может создать второй платный кластер с тем же именем.
- **Просим:** 409 на дубль имени в проекте или явное «имя не уникально».

#### NET-17. SNAT-шлюз: VPC не задаётся при создании
Нет в документации · гипотеза (внешний прогон 25.10, 1 из 1)
- **Живое:** запрос `POST /nat-gateways` с именем, типом, проектом и зоной, без сети → ответ содержит `vpc_id`; по отчёту прогона это VPC проекта по умолчанию.
- **Что проверить:** есть ли в спецификации compute поле VPC или подсети в запросе создания.
- **Влияние:** в проекте с несколькими VPC шлюз нельзя направить в нужную сеть.
- **Просим:** поле VPC или подсети в запросе либо описание правила выбора сети.

#### NLB-3. `target_group_id` не UUID — 500
Ошибка API · гипотеза (по отчёту внешнего прогона 25.10; вызовы в журнале есть, ответы не записаны)
- **Заявлено:** `POST` балансировщика с `target_group_id` не в форме UUID → 500; с UUID, которого нет, → 404 «product not found».
- **Влияние, если подтвердится:** 500 читается клиентом как сбой сервиса и повторяется.
- **Просим:** 400 с именем поля.

#### CAP-3. Допустимые источники образа не описаны
Нет в документации · гипотеза (внешняя проверка 24.10)
- **Живое:** создание контейнера с `nginx:alpine`, `docker.io/…` и с несуществующим тегом → одинаково «Container image is invalid» (499, CAP-1).
- **Гипотеза:** принимаются только образы из Artifact Registry Cloud.ru; публичные реестры — нет. По документации и пробой не проверено.
- **Просим:** перечислить допустимые реестры и требования к образу; причину в ошибке (реестр не поддерживается / тег не найден / нет доступа).

#### CAP-4. Повторный `DELETE` во время удаления — новая операция
Нет в документации · гипотеза (по отчёту внешнего прогона 25.10; записан ответ только первого из трёх вызовов — `deleting` с id операции)
- **Заявлено:** второй `DELETE` приложения, которое уже удаляется, принят, создаётся новая операция «deleting».
- **Просим:** 409 или ответ с id идущей операции.

#### SEC-1. Отсутствующий секрет в существующей папке — 404 «folder not found»
Нет в документации · гипотеза (по отчёту внешнего прогона 25.10; вызовы в журнале есть, ответ не записан)
- **Заявлено:** `GET` секрета по пути `папка/имя`, которого нет, при том что другой секрет той же папки читается, → 404 «folder not found».
- **Влияние:** текст указывает не на ту причину.
- **Просим:** «secret not found» для секрета, «folder not found» — только для папки.

#### DB-17. Kafka: кластер в `DEPLOYING` не удаляется — 500
- **Живое, 24.10 (внешняя проверка):** кластер (40 ГиБ) больше 60 мин в `DEPLOYING`, затем `FAILED`; `DELETE` в `FAILED` → 500 «not properly created, no successful create tasks were found in PSI» (1 из 1, сырой ответ не сохранён). Кластер остался в списке, удаление — через поддержку или консоль.
- **Живое, 25.10 (внешний прогон, ru.AZ-1):** `DELETE` кластера минимальной спецификации в `DEPLOYING` → 500 «call to paas engine [DeleteEvolutionKafka] failed: … failed to get delete metadata» — с 17.10 5 из 5. По отчёту прогона тот же кластер через ~82 мин ушёл в `FAILED`, и `DELETE` в `FAILED` трижды ответил тем же 500 «not properly created…» — ответ не записан, в счёт не входит. Кластер остался в проекте.
- **Просим (как в v1):** 409 «нельзя удалить во время создания» или отмена создания; удаление кластера в `FAILED`.

## Эксплуатационные наблюдения

Не расхождения документации; адресаты — эксплуатация сервисов.

- **OPS-13. Container Apps, ru.AZ-2, 22.10: образ, только что загруженный в Artifact Registry, — «Container image is invalid».** cloud-e2e `live (ca)`: реестр создан, `docker push` прошёл, через несколько секунд (в одном случае — через 7 с) создание контейнера → 499 «Container image is invalid» — runs 39838101751 (19:21 UTC) и 39844928752 (20:10 UTC); в 20:33 UTC (run 39849582941) тот же путь прошёл целиком. 2 из 3. Гипотеза: образ становится виден Container Apps с задержкой после push; ни задержка, ни повторяемость не описаны, а код 499 (CAP-1) не отличает этот случай от неверного адреса образа.
- **OPS-14. ru.AZ-2, 22–23.10: новая ВМ не достучалась до Docker Hub.** cloud-e2e run 39849582941 (22.10, около 20:38 UTC): `docker compose up` → `registry-1.docker.io … TLS handshake timeout`; за полчаса до того тот же план прошёл. 23.10 около 18:32 UTC (run 39999599386, попытка 1): `dial tcp [<ipv6>]:443: connect: network is unreachable` — у ВМ нет маршрута IPv6, а адрес Docker Hub разрешился в IPv6; повтор через 30 мин зелёный. За 22–23.10: 2 из 6 прогонов. Гипотеза не проверена на ВМ. **Просим:** описать в документации, есть ли у ВМ исходящий IPv6.
- **OPS-15. Secret Manager, 25.10 около 21:49 UTC: по отчёту внешнего прогона секрет исчез через ~10 с после создания без удаления.** В журнале вызовов: создание, затем чтение в 21:49:24 и запросы версий с 21:49:33; удаления нет. Ответы не записаны; по отчёту чтение в 21:49:24 видело секрет, а с 21:49:33 — 404 «folder not found» (SEC-1) и секрета нет в списке. Второй секрет той же папки, созданный позже, жил до своего удаления. Аудит-лог тестовому ключу недоступен, причину проверить нельзя. Не в счёт.
