Чек-лист `CLAUDE.md` §5 и `docs/RELEASING.md`. Основание — строка плана
1.9 «Промежуточный дельта-аудит 1.9 — сейчас, не дожидаясь rc.1» (решение
владельца 13.11, #1589). Диапазон — `v1.8.2..bb98f9b4` (`main` на 13.11,
~04:20 UTC): 217 коммитов; вне `docs/` — 445 файлов, +30 508/−2 481;
продуктовых PR — 54. Отдельная сессия, только чтение продукта; в облако не

«релиз». Полный аудит перед тегом этим отчётом не заменяется. Серия
находок — FB19I, с FB19I-1.

Метод: семь параллельных чтений с чистого листа, каждое в своём рабочем
дереве на `bb98f9b4` — обработчик, схема, объявления реестра, команда CLI,

репозитория или запуском собранного `evo` без ключа (в репозиторий пробы
не вошли). Неподтверждённое помечено «по коду». Утверждения о платформе
без прогона и спецификации — «гипотеза».

**Итог: тег сейчас не решается, блокеров в смысле «дефект, запрещающий тег»
аудит не выставляет; но две находки high — FB19I-30 и FB19I-31 — путь ко
второму платному диску по одному согласию, и до rc.1 они должны быть
закрыты или вынесены владельцу.** Обе — в слое намерений D92, в правках
12–13.11; о них «1.9 — релизу» сообщено отдельно до отчёта. Ломающее
диапазона сверено механически (выгрузка схем `v1.8.2` против головы) и по
фрагментам: каждое названо «Миграцией» и решением D100–D105; ломающего без
«Миграции» в прочитанном нет.

Общий корень находок medium — тот же класс, что в журнале пропусков 1.9,
но в трёх новых местах, которых меры журнала не покрывают:

1. **Окно «запрос принят, ресурса ещё нет» и «ответ потерян»** — у
   `sg_rule_create`, `s3_bucket_create`, `backup_restore`, питания ВМ,
   `k8s_nodepool_delete` (FB19I-2, -3, -11, -12, -18, -36). Мир автора в

   стоит в бэклоге после #1580 — по итогам аудита это не один случай, а
   класс у каждого создающего инструмента.
2. **Запись намерения уже́ или шире вызова** — запись называет родителя, а
   не часть (правило — группой, `kubectl` — кластером), закрывается чужим
   вызовом той же цели, стирается соседним вызовом в полёте, а на CLI с
   `--yes` закрывается превью (FB19I-13, -30, -31, -33, -34).
3. **Текст из облака вне `_untrusted`** — три новых ответа, перечень полей

## Находки

Уровни: blocker — запрещает rc; high — путь к деньгам, удалению чужого или
утечке без согласия; medium — неверный ответ, на котором агент ошибётся,
или нарушение оси контракта §6; low — текст, пометка, краевой случай.
«Проба» — временный тест в мире репозитория или запуск `evo` без ключа.

## Гипотезы

О платформе (без прогона и спецификации):

- **Г1.** Принимает ли `set-power` команду из `error` и сколько держит
  прежнее состояние после 204 — от этого зависит FB19I-3.
- **Г2.** Отвечает ли Compute 408 на POST копии и восстановления —
  условие FB19I-19.
- **Г3.** Дублирует ли платформа два одинаковых правила группы или
  отвечает 409 — тяжесть FB19I-12; допускает ли два диска с одним именем —
  на этом стоят У5 и FB19I-18.
- **Г4.** Диск восстановления попадает в проект копии: запрос проекта не
  несёт. 30 минут ожидания диска — число без замера; диск, появившийся
  позже, останется без следа.
- **Г5.** Правило без источника в ответе списка: `OpenToInternet` его в
  «останется открытым» не называет, `sg_rule_delete` пишет о нём
  «0.0.0.0/0» — после пробы Г-11 чтение источника свести и для `OpenLeft`.
  Что платформа отдаёт в `port_range` у правила «все порты»: при пустом
  значении правило не считается ни открывающим порт, ни последним
  правилом SSH.
- **Г6.** Форма `error` у операции mk8s: `"error": {}` у идущей операции
  закончит ожидание на первом чтении; `{"code":0,"message":""}` у успешной
  даст отказ с пустым текстом (в мире — так). Причина «квота» у
  `k8s_operation`: формы взяты из прогонов PostgreSQL, для mk8s прогона
  нет.
- **Г7.** Формат `last_restore_time` и `created_at` копии — RFC3339 с
  зоной; иначе предупреждение о недавнем восстановлении и возраст копии
  молча пропадают.

О коде (без пробы):

- **Г8.** Зависшая удержанная запись: шаг из `next_args` получил вопрос
  (ВМ вернули обратно), `settleHeld` её не закрывает; позже чужой переход
  и вызов без согласия найдут её через `heldSince` и ответят «evo больше
  не ждёт» раньше времени.
- **Г9.** «Do not stop the VM this server runs on» — только текст
  описания `vm_stop`; для `evo mcp` по HTTP на той же ВМ это остановка
  сервера посреди вызова с оставшейся записью.
- **Г10.** `pending_operations` для `vm_stop` и `vm_start` называет
  чтением сам инструмент («check "vm_stop" for …»): `listToolOf` не
  находит списка; `vm_get` был бы чтением без вопроса.
- **Г11.** `backupRestored` глотает ошибку чтения списка дисков — ответ
  скажет «диска в списке ещё нет»; матричный мир
  `fault_backup_world_test.go` делает диск сразу `available`, окно в
  матрице сбоев не исполняется.
- **Г12.** У отказа по квоте `errAnswer` заменяет подсказку ошибки общей;
  если отказ придёт после частичного создания, подсказка об оставшемся
  ресурсе потеряется (поле id останется). Фраза «ресурс остался в FAILED»
  срабатывает только при `resource_status == "FAILED"` буквально — у
  сервисов с префиксом состояния не появится.
- **Г13.** Подсказка операции при `FAILED` называет `pg_delete`,
  `kafka_delete`, `redis_delete` («removes it after their approval»): на
  грани правила волны D99 «подсказки не называют удаление шагом» — вопрос
  «Риску».
- **Г14.** Сторожа «каждый `http.Client` продукта стоит на базе TLS» нет:
  тест проверяет саму базу. `provision.IsQuotaError` (вне диапазона) —
  подстрока «quota» в любом тексте, класс FB19I-28.
- **Г15.** `kubectl config view --raw` идёт без согласия и печатает токен
  встроенного kubeconfig — столько же отдаёт `k8s_kubeconfig` (вне дельты).
- **Г16.** `addResourceStatus` читает id операции группы сначала как
  кластер: не-404 на это чтение даст `resource_status_error` без чтения
  группы.
- **Г17.** `beginIntent` молча пропускает запись при любой ошибке
  `newEngine(nil)`, не только «проект не разрешён» (FB19I-32): есть ли
  другие случаи, когда движок без аргументов вызова не строится, а с ними
  строится, — не установлено.
- **Г18.** `checkByID` на подложенной записи с `"key":{}` читает облако по
  чужому id ключом пользователя и печатает «ещё есть / нет» в вывод
  `doctor`; вывод видит только пользователь.
- **Г19.** `stack_status` продвигает стек без согласия, шаги — глубже
  первого уровня и записей D92 не пишут: след обрыва — только файл задания
  стека; хватает ли его при `kill -9` посреди платного шага — не проверено.
- **Г20.** Создание с проектом профиля в теле и родителем по id из другого
  проекта (`subnet_create` и `dns_zone_create` с `vpc_id`, `lb_create`,
  `image_create` с `disk_id`, `backup_create`): превью называет проект
  вызова, аргумент целью не объявлен. Куда платформа кладёт ресурс —
  гипотеза о платформе.
- **Г21.** Задание стека, спланированное evo 1.8.x с `zone: ""` в
  манифесте и применяемое 1.9: отказ `stack_plan` его не видел, шаг получит
  `USAGE` посреди стека.
- **Г22.** Потерянный ответ у `sg_rule_create` и такое же правило,
  созданное в тот же момент другим вызовом: ответ будет `created` с чужим
  `rule_id` (кроме 409).
- **Г23.** NAT64 (`64:ff9b::/96`) `sgrules.Internet` интернетом не
  считает; есть ли NAT64 на платформе — неизвестно.
