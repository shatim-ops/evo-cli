## Цикл одного PR (учтён в оценках ниже)

Каждый PR проходит полный цикл §4 `CLAUDE.md`, не только написание кода:

1. тест, падающий без правки → gofmt, vet, staticcheck, `go test -race` локально;
2. PR → ревью Qwen: до PR 2 запускает владелец комментарием `/qwen review`,
   после PR 2 — автоматически при открытии; 5–15 мин ожидания;
3. разбор каждой находки Qwen в ответном комментарии: исправлено или
   опровергнуто с обоснованием; при исправлении — повторный push и CI;
4. CI на трёх ОС (10 мин до PR 1, 2–3 мин после);
5. squash-merge по полному SHA — релизная сессия.

Цена цикла сверх кода: 20–40 мин Claude на PR (ожидание Qwen и разбор),
один комментарий владельца на PR до автоматизации. Поэтому автозапуск Qwen
идёт вторым PR, а не седьмым: он убирает ручной шаг у восьми следующих.

## Кто делает: правило делегирования

1. Сессия Claude планирует первую волну и для каждой задачи отмечает,
   можно ли её передать Cursor (реализация по брифу) или Grok (атака по
   брифу). Критерий передачи: ясный критерий приёмки, не нужен контекст
   фейков, реестра и инвариантов, нет правок живого облака.
2. Перед стартом каждой передаваемой задачи сессия спрашивает владельца:
   «делаю сама или отдаём по брифу?» Без ответа — делает сама.
3. Тесты обязательны в любом случае: кто бы ни делал задачу, PR содержит
   тест, падающий без правки, проходит Qwen и CI. Бриф Cursor повторяет
   это требование; находки Qwen по PR Cursor разбирает Cursor в том же PR.
4. Атака Grok — дополнение, а не замена: то, что Grok проверяет чёрным
   ящиком, сессия Claude закрепляет тестом в репозитории независимо от
   того, выдан бриф или нет.

Кандидаты на передачу в первой волне: PR 6, 7, 10 (Cursor); проверка
«документация против бинаря» после PR 6 (Cursor, бриф 2А); атака на вынос
ключа наблюдателя из `cloud-readonly` с ветки `claude/*` после В3 и PR 9,
на подмену классов после PR 8, на наборы и режим без удалений перед 1.3
(Grok). PR 1, 3, 4, 5, 8, 9 и вторая волна — только Claude.

## Как устроены новые тесты

Три правила, из которых всё следует:

1. **Размеры и факты, а не время.** Сравнение настенных часов с порогом
   падает на загруженном раннере без дефекта (21.10 — дважды на Windows).
   Бюджеты — в байтах, числах вызовов и инвариантах состояния; время
   измеряется бенчмарками руками.
2. **Список проверяемого — из реестра.** Тест обходит `r.Tools()` и
   фильтрует по `Mutating`, цене, аннотациям. Новый инструмент попадает под
   проверку в момент регистрации. Так уже устроены `TestReadOnly_EveryTool`
   и `TestContract_PreviewParity`.
3. **Закрывать класс, а не экземпляр.** Один тест с порогом времени чинится
   за час, следующий напишут через неделю; мета-тест запрещает паттерн.

### Тестовые `Timings` для тестов CLI (PR 1)

Факт: `TestEngineCommands_RepeatedDeployGate` (`internal/cli/engine_commands_test.go:296`)
идёт 450 с из 486 с всего набора. На шаге `runCLI(t, "", "deploy", "--yes")`
команда строит движок через боевую фабрику, и движок берёт продовые
интервалы из `internal/engine/timings.go:15–29` (опрос ВМ 5 с, SSH 5 с,
Docker 10 с, `sshSlowNote` 5 мин). Фейк отвечает мгновенно, движок спит
между опросами.

Что есть: `fastTimings` (`internal/engine/engine_test.go:393`) и
`faultTimings` (`internal/engine/fault_test.go:38`); `Timings.withDefaults()`
заполняет только нулевые поля.

Сделать: тестовое окружение `runCLI` подставляет `engine.Timings` в фабрику
движка — один механизм для всех тестов CLI, не правка одного теста.
Поведение продукта не меняется. Проверка: `go test ./internal/cli` локально
меньше минуты (руками, не тестом — правило 1).

### Мета-тест порогов времени (PR 4)

`TestNoWallClockAssertions` читает все `*_test.go` репозитория (`filepath.WalkDir`
от корня модуля, как `TestFaultFakeCopiesMatch` читает чужой файл) и падает
на строке, где `time.Since(` или `time.Now().Sub(` сравнивается с константой
через `<`, `>`, `<=`, `>=`, если в той же строке или строкой выше нет
пометки `// wall-clock: <обоснование>`. Сообщение называет файл и строку.
Регулярное выражение достаточно; разбор AST не нужен. Плюс `-shuffle=on`
в шаге `go test` на `main`: seed печатается, зависимость от порядка видна.

### Инварианты (PR 5, три PR)

- **Ссылки на решения.** Регулярное выражение `\bD(\d+)\b` по `docs/**/*.md`
  и `CLAUDE.md`; каждый номер должен быть строкой `| D<n> |` в
  `docs/internal/standalone/DECISIONS.md`. Сегодня D17 упомянут в
  `release-plan.md:72`, записи нет: тест падает, пока её не добавят.
  Исключить `docs/internal/audits/` и `archive/`.
- **Бюджет `tools/list`.** Сервер MCP на фейке отвечает на `tools/list`;
  длина JSON ответа не больше константы `maxToolsListBytes` (сейчас 117 КБ;
  бюджет 160 КБ). Рядом — существующие пределы на описание
  (`internal/mcp/limits_test.go:17–19`). Падение означает: описания
  раздуты или пора делить на наборы (1.3).
- **Цена в превью.** Расширить `TestContract_PreviewPriceInTool`: для
  каждого `Mutating` инструмента реестра превью на фейке содержит либо
  `preview.cost`, либо `preview.tariff_url`. Инструменты, у которых нет
  ни того, ни другого по природе (удаления, остановки), — закрытый список
  с причиной в тесте, как `localCommands`.
- **Ответ списка на 500 ресурсах.** Фейк отдаёт 500 объектов; ответ
  каждого `*_list` не больше константы либо содержит `next`/`*_truncated`.
  Проверяет, что страницы не забыты.
- **Имена из облака только в полях данных** (вторая волна). Фейк
  возвращает имя ресурса из корпуса: с переводами строк, кавычками,
  фразой «ignore previous instructions», управляющими символами. Тест:
  имя встречается в полях данных как есть; в `message`, `next`, `hint`
  — только в одну строку и в кавычках (нормализация в одной функции,
  как `redact`). Это защита от инъекции через данные облака силами evo,
  а не агента.

### Матрица «сбой на шаге k» (вторая волна)

Что есть: `faultCloud` (`internal/tools/fault_fake_test.go`) взводит отказ
на N-м вызове любого метода (`failAt`, `failNth`) восьми видов: отмена
контекста, обрыв, потерянный ответ, пустой id, 401, 409, 500, потерянный
ответ без имени. Мир фейка переживает потерянный ответ. Восемь сценарных
тестов (`fault_test.go:112–261`) выбирают точку сбоя руками и покрывают
только provision, deploy_apply, stack.

Сделать, по шагам:

1. Список платных инструментов — из реестра: `Mutating` с `preview.cost`
   или `tariff_url` (тот же фильтр, что в инварианте цены).
2. Запись счастливого пути: один прогон на фейке без отказов,
   `faultCloud.log` даёт последовательность вызовов длиной N.
3. Перебор: для k от 1 до N и каждого вида сбоя — `failAt(k, вид)`, вызов
   с `confirmed: true`. На фейке каждый вызов — миллисекунды, с
   `faultTimings`.
4. Два инварианта вместо ожиданий на каждый случай: (а) каждый платный
   объект в мире фейка после вызова либо назван в ответе своим id и
   записан в state, либо удалён; (б) повторный вызов с теми же аргументами
   после `disarm()` сходится — число платных объектов не растёт.
5. Новый вид `faultSlow`: метод спит до истечения контекста. С тестовыми
   `Timings` — миллисекунды. Проверяет таймауты, не только обрывы.
6. После зелёной матрицы — один транспорт повторов: цикл из
   `internal/provision/adapter.go:400–470` переезжает в `httpretry`,
   политика не меняется (POST не повторяется). Матрица — сетка
   безопасности для переезда; `TestNoHandBuiltTransport` расширяется на
   адаптер.

Где стоимость: не в тестах, а в фейке. Сегодня его мир знает ВМ,
floating IP и правила групп; для кластеров (k8s, pg, kafka, redis),
приложений (ca), NLB и DNS мир нужно расширить. Это и есть 2–3 дня. После
этого новый сервис требует только расширения фейка, тесты пишутся сами.
Найденные падения — настоящие дефекты; закладывать неделю на разбор.

### Еженедельные job (PR 9, 10, вторая волна)

Не блокируют PR; красное — issue с логом. `-race -count=3 -shuffle=on` на
трёх ОС ловит flaky до PR. Fuzz: каждая из 10 целей по 5 мин настоящего
фаззинга (`go test -fuzz=^FuzzX$ -fuzztime=5m`), падение — issue с
корпусом; новые цели: `internal/stack` (867 строк кода, 199 тестов),
`deployplan`, ответы API нестандартной формы. cloud-e2e дешёвого набора —
из `main`, с одобрением владельца.

### Чего не делать

Мутационное тестирование; карантин и автоповтор flaky; временные бюджеты

состояние тестов CLI сделает параллелизм источником новых flaky).
