Источники: `process-1.2.1.md` (аудит), `process-1.2.1-brief.md` (ТЗ сессии
разработки). Здесь — только последовательность и действия владельца с
указанием, где именно. Этап закрыт, когда выполнен его критерий.

## Этап 1. Настройки GitHub (владелец, 20–30 минут, один раз)

Делается до первых PR первой волны, иначе required checks не совпадут с
именами job. Все пункты — Settings репозитория `shatim-ops/evo-cli`.

| # | Действие | Где | Решение |
|---|---|---|---|
| 1.1 | Secret scanning → Enable; Push protection → Enable | Settings → Code security → Secret scanning | В6 |
| 1.2 | Защита `main`: Require a pull request before merging (approvals: 0); Require status checks to pass before merging — `test (ubuntu-latest)`, `test (macos-latest)`, `test (windows-latest)`, `docker`, флажок «Require branches to be up to date» выключен; Require linear history; Block force pushes; Restrict deletions | Settings → Rules → Rulesets → New branch ruleset, target `main` (или Settings → Branches → классическое правило) | В6 |
| 1.3 | Окружение `cloud-readonly`: Deployment branches and tags → Selected branches and tags → добавить `main` и `claude/**` | Settings → Environments → cloud-readonly | В3 |
| 1.4 | Проверить окружения `cloud-e2e` и `release`: Required reviewers — владелец; `release` — только теги `v*`; `cloud-e2e` — без ограничения ветки (платные job с ветки по одобрению) | Settings → Environments | как есть, сверка |
| 1.5 | Не включать: CodeQL (В7 не решён), Dependabot security updates сверх текущих | — | — |

Проверка 1.2: следующий PR показывает четыре обязательных check'а и не
сливается при красном. Проверка 1.3: `cloud-e2e` → Run workflow с ветки
`claude/*` → job `readonly` запускается, а не пропускается.

Критерий: пункты 1.1–1.3 включены.

## Этап 2. Старт сессии разработки (владелец, 5 минут)

1. Дождаться тега `v1.2.2` и слияния handoff 1.2.2.
2. Открыть сессию с названием `CLI+MCP · Процесс — разработка`.
3. Первое сообщение:

   ```
   Работаем по docs/internal/audits/process-1.2.1-brief.md. Роль — разработка:
   ветки и PR, в main не сливаешь. Начни с PR 1. Перед каждой задачей,
   которую бриф отмечает как передаваемую, спрашивай: делаю сама или отдаём
   по брифу Cursor/Grok.
   ```

4. Релизная сессия 1.2.3 (или 1.3) сливает PR этой сессии в обычном
   порядке.

Критерий: сессия прочитала §0 `CLAUDE.md`, план и handoff, открыла PR 1.

## Этап 3. Первая волна, PR 1–3 (быстрые выигрыши, 1 день)

| PR | Что делает сессия | Что делает владелец |
|---|---|---|
| 1 — тестовые `Timings` | один механизм для тестов CLI; `go test ./internal/cli` < 1 мин | комментарий `/qwen review` в PR; разбор находок — сессия; squash-merge — релизная сессия |
| 2 — автозапуск Qwen | `qwen-review.yml` на `opened` / `ready_for_review` для PR своего репозитория | последний ручной `/qwen review`; далее Qwen приходит сам |
| 3 — триггеры и concurrency | CI только `main` + PR; отмена устаревших прогонов; `-count=1` только на `main` и теге | убедиться, что четыре required check'а из 1.2 зелёные на этом PR |

Критерий: CI на PR идёт 2–3 минуты вместо 10; Qwen появляется на PR без
команды; один прогон на push вместо двух.
