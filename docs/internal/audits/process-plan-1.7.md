## 1. Инвариант D69 «ни один вызов MCP не дольше предела»

### Что показала проба мира (факт, 31.10)

Мир «медленного облака» поверх фейков матрицы сбоев (`faultCloud`,
`faultAPI`): ВМ всегда `creating`, операции `done: false`, ресурсы
`CREATING`; интервалы — производственные (`engine.Timings{}`), сторож 3 с.

| Что | Итог |
|---|---|
| `provision` | держит вызов дольше 3 с (ждёт ВМ до `VMPollTimeout`, 25 мин); отменён сторожем — `VM_PROVISION_FAILED` «interrupted (context canceled)» с `vm_id` |
| 23 create матрицы по HTTP (`kafka_create`, `pg_create`, `k8s_create`, `lb_create`, `disk_create`, `cert_issue_le` и др.) | ответ за 0,2–1,3 мс: операция и `creating` сразу — с планом «разработки» §1 совпадает |
| `deploy_apply` | ответ за 1 мс — **мир неполон**: `GetVMDetail` фейка отдаёт состояние из записи ВМ, а не `creating`; ожидание SSH не смоделировано. Вывода о `deploy_apply` проба не даёт |

Из схем реестра (факт): `wait_seconds` есть у восьми `*_operation` и у
`stack_status`; ни у одного в схеме нет `maximum`. Предел стоит только в коде:
`opWaitMaxSeconds = 300` у `*_operation`, у `stack_status` — 20 с
(`tools_stack.go:1058`).

**Находка для «разработки» (факт, не D69):** схема `stack_status` говорит
агенту «default 90, max 240» (`tools.go:1365`, `descriptions_ru.go:1633`), а
обработчик берёт по умолчанию 20 и режет до 20. Описание расходится с
поведением. Предложение — строка плана «разработке», заодно с D69:
предел из одной константы и в схеме (`maximum`), и в обработчике.

### Устройство инварианта (предложение)

Один тест в `internal/tools`, рабочее имя `TestMCP_NoCallOutlivesTheBudget`.
Четыре части:

1. **Охват из реестра.** Каждый инструмент MCP-реестра, который изменяет
   (`Mutating`), ждёт (`wait_seconds` в схеме) или ходит в кластер
   (`k8s_kubectl`, `k8s_helm`), — случай мира или строка закрытого перечня
   `mcpBudgetOut` с причиной («ответ без ожидания: удаление по одному
   DELETE»). Новый инструмент без случая и без строки роняет сборку — как
   `TestFault_MatrixCoversTheRegistry`.
2. **Мир «медленного облака»** — расширение фейков матрицы сбоев, а не
   третий фейк: ВМ `creating` (`GetVM` и `GetVMDetail`), операция не
   кончается, шаг стека ждёт ВМ, SSH не отвечает (`noDial`), удаление ВМ —
   `deleting` (для `destroy`, `stack_destroy`). Копии `faultCloud` в
   `engine` и `tools` держит `TestFaultFakeCopiesMatch`; правка общая для
   обеих или — после выноса в общий пакет (очередь, п. 5).
3. **Граница.** Реестр под `SetCallBudget(малый)` (точка «разработки», план
   D69 §2), интервалы облака — производственные: вызов может кончиться
   только по бюджету. Тест требует ответа не позже бюджета плюс запас
   (`wall-clock:` — доля бюджета, `internal/testrules`). Без бюджета ожидание
   длилось бы минуты, поэтому тест и падает без правки D69.
4. **Содержание ответа** при исчерпанном бюджете: не ошибка
   (`isError=false`); `status` — не конечный (`creating`); id созданного (или
   `plan_id`, `job_id`); `operation_id`, где его даёт платформа, иначе id ресурса и состояние (#717, п. 8); последнее
   прочитанное состояние (ось 2); `next` называет **инструмент**, а не
   команду CLI (D6); пароль — ровно один раз, если evo его сгенерировал.

CLI (H14) не ограничен. Проверка — структурная: реестр `internal/cli`
собирается без `SetCallBudget`. Плюс мир паритета: `--wait=false` у команды и
`wait: false` у инструмента дают один JSON.

## 2. Отмена: `INTERRUPTED` на обеих поверхностях (#704)

Обход реестра против мира «отмена после записи» (сейчас — ручные тесты на
`provision`, `deploy`, `deploy_apply`, стек: `cancel_test.go`,
`cancel_repeat_test.go`):

- каждый create, отменённый после POST (`notifications/cancelled`, клиент
  ушёл, Ctrl-C), отвечает `reason: INTERRUPTED`. Если ресурс создан — с его id
  в ответе или в state. Повтор второй ресурс не создаёт;
- CLI — код 130 и тот же `reason`, что у инструмента (мир паритета);
- каждое ожидание (`*_operation`, `dns_zone_delete`, ожидание ВМ) при отмене
  — `INTERRUPTED`, а не `API_UNREACHABLE` с «проверьте сеть» (план D69 §1:
  корень — `unreachable()` в `errreason.go`).

Порядок тот же: сначала красный с перечнем, PR 1 разработки сокращает
перечень. Смена `reason` — ломающее, покрыто «да» владельца (#597, п. 47).

## 3. Пароль ВМ не теряется (план D69 §6, п. 3; FB121-7)

Во всех исходах, где ВМ с паролем evo уже создана (успех, `creating` по
бюджету, отмена, срок, шаг стека), пароль есть в ответе ровно один раз.
Повтор, который подхватывает ВМ, честно говорит, что пароля не знает. По HTTP
пароль маскирует H7 — проверка «по HTTP значение замаскировано» тем же
обходом.

## 4. Ответы на вопросы плана D69 «разработки»

- **§6, п. 4 — строка H14 в `HTTPRestrictions` «и по stdio».** «Процесс» не
  против. Таблица уже несёт такие правила (H9, H11), `TestHTTPPolicy_ClosedList`
  сверяет строку.
- **§6, п. 5 — пределы клиентов, кроме Claude Code.** В облачной сессии
  агентного прогона есть только Claude Code. Пределы других клиентов бриф
  померить не может. Предложение: бриф проверяет режим по умолчанию (60 с,
  без `MCP_TOOL_TIMEOUT`); другие клиенты — догфуд владельца или строка
  бэклога 1.8.
- **§7, вопрос 3 — хвост после `running`.** Предложение «Процесса» — строгий
  предел: клиент обрывает весь вызов, а не ожидание ВМ. Инвариант меряет вызов
  целиком; хвост FIP и ключей, который не помещается, — строка перечня до
  PR, который его закрывает. Решение — за «разработкой» и «релизом».
- **§7, вопрос 1 — `k8s_helm`, `k8s_kubectl`.** Решено (#717, п. 6): оба в
  D69, без исключений. Мир — helm и kubectl дольше предела; до правки — строки
  перечня `mcpOverBudget`.
