### 1.5. Фоновые задачи клиента и ход долгих вызовов evo (вопрос владельца 28.10)

Владелец спросил, как у Gemini CLI устроен «живой» блок команды, от
которого можно отойти и вернуться, и нужно ли то же в evo. Разобрано по
документации Gemini CLI (`geminicli.com/docs/tools/shell`,
`docs/reference/keyboard-shortcuts`, журнал выпусков, PR #18472).

**Как это устроено у клиента.**
- Интерактивная оболочка (с v0.9.0, 10.2025): каждая команда инструмента
  `run_shell_command` идёт в псевдотерминале `node-pty`; снимки состояния
  PTY (текст, цвета, курсор) транслируются в блок интерфейса, нажатия
  клавиш пробрасываются в процесс. Настройка
  `tools.shell.enableInteractiveShell`.
- Фокус: Tab — в активную оболочку, Shift+Tab — обратно в Gemini (в
  промпте Shift+Tab циклит режимы одобрения). До v0.24 (01.2026) фокус был
  на Ctrl+F.
- Фоновые задачи (с v0.28, 02.2026): команда с `&` или
  `is_background: true` возвращает управление сразу, PID — в
  `Background PIDs`; Ctrl+B показывает фоновую оболочку, Ctrl+L — список,
  Ctrl+K — убить, Shift+Tab — выйти. Обычный, не фоновый вызов держит ход
  агента до завершения (документация обратного не утверждает).
- `tools.shell.inactivityTimeout` убивает процесс без вывода N секунд —
  это и оборвало `provision` в C2 (п. 12).

**Вывод для evo.** Блок, фон и фокус — слой клиента, не evo: evo
вызывается на одну команду, пишет в stdout и stderr, определяет терминал;
в PTY клиента текстовый режим перерисовывает строку ожидания раз в
секунду, Ctrl-C в сфокусированном блоке доходит до `handleInterrupt`. То
же даёт обычная оболочка: `evo vm create … --yes &`, Ctrl-Z/`bg`/`fg`;
фоновому вызову нужен `--yes` (вопрос согласия читает терминал) и
`2>/dev/null` или `--json`, иначе строка ожидания мешается с вводом. Свой
«визуальный режим» в evo (TUI с менеджером задач) не нужен: у него нет
пары в MCP (§1), и он дублирует клиент. Дёшево и по делу — В1 (строка
ожидания в stderr при `--json`: агент видит ход, тайм-аут по бездействию
не срабатывает) и В2 (`wait=false`: агент сам решает, уходить ли в фон);
MCP уже шлёт `notifications/progress`. Безопасность: в момент ожидания
ВМ уже создана, обрыв клиента теряет только ответ с адресом и паролем,
ресурс находится через `vm_list` (подтверждено C2).

## Вопросы владельцу (формат issue `решение`)

**В1. Строка ожидания в stderr при `--json`.** Подтверждение 28.10 (п. 12): молчание в `--json` не только скрывает ход, но и роняет вызов у клиента с тайм-аутом по бездействию. Сейчас `--json` молчит
(по замыслу 1.3), агент по скиллу работает в `--json` и не отличает
медленную зону от зависания (ось 2 §6; Gemini п. 5). Варианты:
(а) как есть; (б) в `--json` без TTY печатать строку ожидания в stderr при
смене состояния и раз в 30 с, stdout — только JSON, в документации — «stdout
— ответ, stderr — ход»; (в) флаг `--progress`. Умолчание — (а) до 1.5.
Рекомендация — (б) в 1.5 вместе со строкой «честный ход операции»: stderr
по соглашению — диагностика, а `2>&1 | jq` ломается уже на любом
предупреждении; ломающим по `RELEASING.md` не является (stderr не в списке).

**В2. `wait=false` у `provision`/`deploy_apply` (п. 12).** Факт
подтверждён снимком экрана 28.10: вызов C2 оборвал тайм-аут агента, ВМ
осталась и нашлась по `vm_list`. Варианты (а) оставить синхронное ожидание, (б) необязательный
`wait=false` (`--no-wait`) с ответом `creating` + `vm_id` и ожиданием через
`vm_get`; умолчание — (а); рекомендация — (б) в 1.5, в строке «долгое
создание», без смены умолчания (не ломающее).

**В3. Алиас `vm_create` для `provision`.** Gemini (и класс G130-41: `id`
против `certificate_id`) — агент ищет `vm_create` по аналогии с
`disk_create`, `vpc_create`. Варианты: (а) ждать 2.0 (строка плана:
единые имена); (б) алиас в 1.5 механизмом `list_images` (+1 запись в
`tools/list`, ≈ 200 токенов налога для всех); (в) алиас только в описании
`provision` («also known as vm_create» — ноль записей, слабым моделям не
поможет при поиске по имени). Умолчание — (а). Рекомендация — (а) до
итога матрицы Grok C0/M0: если без скилла агент промахивается по имени,
(б) в 1.5.

**В4. Подсказка «сузьте список» (A): 1.4.1 или 1.5.** Варианты: (а)
1.4.1 — объявление в реестре, в патче заполняет только `image_list`
(«релиз»); (б) 1.5 — вместе с функцией ответа списка, `limit`,
`truncated`, `--fields`, один номер D («разработка»). В 1.4.1 в любом
случае — D (строка встроенного скилла, S). Умолчание — (б). Рекомендация
— (б): без подсказки остаются только агенты без скилла (C0/M0), сигнал по
ним даст матрица Grok и журнал D46; патч не раздувается.

**В5. Целевой добор прогона Grok.** Бриф не закрыл цель J (журнал
D46), атаки A–F, вторую ОС, права без ключа и сравнение с 1.3.0.
Варианты: (а) не добирать, следующая волна — на 1.4.1 (патч закрывает
G140-1/-2/-3, добор покажет держится ли); (б) добор сейчас только J и
Windows (без создания ресурсов — дёшево); (в) полный добор A–F. Умолчание
— (а). Рекомендация — (б): J считается по уже собранным
`grok-diag-*.jsonl` без облака, Windows — установка и чтения.
