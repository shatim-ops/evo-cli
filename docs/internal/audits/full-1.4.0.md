### FB140-1 (после тега; журнал, точность данных) — согласие команд движка в журнале не видно
- **Путь:** `evo deploy` и `evo destroy` (команды движка,
  `engine_commands.go:49`) зовут `callEngineTool` → `t.Handler` с
  `Caller.Gate` (`:113`); согласие (терминал, `--yes`) спрашивает
  `engineGate` внутри `engineGated` (`gate.go:78`, ветка `liveCaller`), а
  в `args` ключа `confirmed` нет. `journaled` берёт `confirmed` только из
  `args` (`internal/tools/journal.go:50`), поэтому выполненный после «да»
  `deploy` записан как `confirmed: false`, `preview: false`, `error: false`
  — неотличим от … ничего: превью у этой цепочки отдельной записью не
  бывает. По MCP (`confirmed=true`) и в цепочке `invokeTool` (`evo vm
  create --yes`: превью, затем вызов с `confirmed: true`) согласие видно.
- **Оценка:** безопасности и ответов не касается (журнал ничего не
  решает). Для догфуда это слепое пятно по двум самым частым командам
  сценария `evo-deploy`: по журналу не отличить `evo deploy --dry-run`
  (ответ — превью, но `status` движка не `confirmation_required`) и
  `evo deploy --yes`. Тег не блокирует: данные волны по `deploy` будут
  беднее, не ложными.
- **Исправление («1.4 — разработка», 1.4.x):** одна точка — `engineGated`
  после «да» гейта помечает контекст (значение в `ctx`, как
  `journalDepthKey`), `journaled` читает его в `Confirmed`; превью
  `--dry-run` — в `Preview` по тому же признаку. Инвариант («Процесс ·
  1.4»): для каждого инструмента с согласием подтверждённый вызов даёт
  запись `confirmed: true` на обеих поверхностях — расширение
  `TestDiag_OnRecordStatusExport` на `evo deploy --yes` в мире паритета.

## Гипотезы (не проверял вживую)
- **Задержка ответа при занятой блокировке журнала.** `journaled` пишет
  запись синхронно до возврата ответа (`internal/tools/journal.go:58`), а
  `Write` ждёт блокировку ОС до 2 с под `mu` процесса (`journal.go:135,
  200`). Процесс, держащий `journal.lock` дольше (приостановленный
  Ctrl-Z `evo diag status` на большом файле, зависший диск), задерживает
  каждый ответ сервера MCP на 2 с и теряет записи; содержимое ответа не
  меняется (инвариант #407). На практике держатель держит блокировку
  миллисекунды. Кандидат 1.4.x, если волна покажет: запись в канал с
  одной горутиной-писателем, ответ не ждёт.
- **Переполнение на границе.** Порог `limit - fullReserve` (512 байт) и
  хвост в 512 байт для `endsFull` рассчитаны на запись `journal_full`
  без аргументов (~170 байт). Запись с длинным списком имён аргументов
  (`k8s_apply`, `provision` — до ~400 байт) на границе может «не влезть»
  и вызвать `journal_full` на несколько сотен байт раньше 16 МБ — не
  дефект, но граница неточная; тест `TestWrite_FullJournalSaysSo` на
  4 КБ это покрывает только для коротких записей.
- **`Describe` без версии формата.** `evo diag status` читает любой
  JSONL-файл на этом пути; запись из будущей версии с новыми полями
  читается молча, старая — тоже. Пока формат один (1.4.0), версия
  формата не нужна; если D43 (1.5) добавит поля, различать их по `evo`
  записи, а не по версии файла.
