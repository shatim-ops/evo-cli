### 2.3 Дублирование и то, что не окупается для одного человека

1. **Двойной прогон CI на каждый push в PR.** `on: push: branches: ["**"]` и
   `pull_request` (`ci.yml:3–7`): в списке прогонов 21.10 пары с одинаковым
   временем (20:18, 19:28, 19:12, 18:59, 18:34…). Ф. Вдвое больше очереди на
   macOS-раннер (в прогоне 39644590164 macOS ждал раннера 5 минут). Убрать push-триггер
   для веток, оставить `main` и PR.
2. **`-race` на трёх ОС.** Детектор гонок проверяет код, а не ОС; ОС-зависимого
   кода мало (`keylinks_*`, ACL Windows). `go test -race` — 8–8,5 мин из 10. М:
   `-race` на Linux, обычный `go test` на macOS/Windows сократит прогон вдвое
   на двух платформах и уменьшит ложные красные Windows (порог времени под
   `-race` растягивается сильнее). Противоречит §4 `CLAUDE.md` — вопрос В1.
3. **Полный аудит Fable на каждый patch.** 8 релизов за 4 дня (1.0.0 → 1.2.1,
   `CHANGELOG.md:10–304`). Полный аудит каждого — дорого и повторяет сам себя.
   М: полный на minor/major, дельта по чек-листу на patch (§8).
4. **api-probe как накопитель одноразовых проб** (680 строк, P13–P28): проба,
   ответ на которую уже записан в реестр расхождений, остаётся в workflow и
   протухает, как L-32. М: после записи ответа шаг удалять.
5. **`cloud-readonly-os`** отдельным workflow — оправдано (нет гейта одобрения),
   но запускается «нерегулярно». М: привязать к событию «перед minor».
6. **Ручной `/qwen review`.** Шаг цикла «ревью Qwen» нужен на каждом PR, а
   запуск — руками владельца. Автозапуск на `opened`/`ready_for_review`
   (только для PR из этого репозитория) убирает ручной шаг без шума:
   один комментарий на PR, а не на каждый push.
7. **Не дублирование, а разрыв:** шаги цикла, которых нет в CI, —
   `deadcode`, `actionlint`, скрипт утечки внутренних сведений, прогон
   `TestParity_*` «на каждой правке» (они и так в `go test`, это не разрыв).
   `actionlint` и `deadcode` — по одному шагу в `ci.yml` на Linux, 15 минут
   работы, шум нулевой (deadcode — только отчёт, не провал, пока не очищено).

## 3. Предложения подробно

Формат: проблема → доказательство → предложение → что поймает → стоимость
(разработка / ежедневный труд владельца) → шум → риск без этого → версия → роль.

### П1. Триггеры и кэш CI
- **Проблема.** Каждый push в PR запускает CI дважды; устаревшие прогоны не
  отменяются; `-count=1` заставляет перегонять все 42 пакета, хотя setup-go
  кэширует `GOCACHE` (включая результаты тестов).
- **Доказательство.** Ф: `ci.yml:3–9` (push `**` + pull_request), нет блока
  `concurrency`; `ci.yml:59` `-count=1`; `ci.yml:35–42` `setup-go` с кэшем по `go.sum`.
- **Предложение.** `on.push.branches: [main]` + `pull_request` + `workflow_call`;
  `concurrency: {group: ci-${{ github.ref }}, cancel-in-progress: ${{ github.ref != 'refs/heads/main' }}}`;
  на PR — `go test -race ./...` без `-count=1` (кэш результатов неизменённых пакетов),
  на `main` и в `release.yml` — с `-count=1`.
- **Поймает.** Ничего нового; освобождает очередь раннеров и минуты.
- **Стоимость.** 1 ч / 0.
- **Шум.** Нет. Г: кэш тестов не скрывает flaky — кэшируется только успех,
  а на `main` прогон полный.
- **Риск без этого.** CI остаётся узким местом при 20 PR/день; очередь macOS.
- **Версия.** 1.2.2. **Роль.** SRE.

### П2. Время тестов: сначала `internal/cli`, потом матрица `-race`
- **Главный факт (измерено после написания П1).** Локально без `-race` весь
  набор идёт 8 мин 06 с при 1 мин 43 с CPU; 471 с из них — пакет
  `internal/cli`, а в нём 450 с — один тест
  `TestEngineCommands_RepeatedDeployGate` (`engine_commands_test.go:296`),
  который на шаге `deploy --yes` ждёт продовые интервалы движка
  (`engine/timings.go:15–29`) поверх мгновенного фейка. Прогон ждёт, а не
  считает. Исправление — тестовые `Timings` для этого теста (один PR,
  ≤ 1 ч). Ожидаемо: CI 10 → 2–3 мин на всех трёх ОС без изменения правил
  §4. Следом, уже необязательно: `t.Parallel()` в `internal/cli`, фейковое
  время вместо `Timeout: 5 * time.Second`, один бинарь на пакет для
  `docs_examples_test.go`. Это предложение важнее, чем снятие `-race` с
  macOS/Windows, и не требует решения владельца.
- **Проблема (вторая).** Три прогона с `-race` по 8–8,5 мин; Windows под `-race` чаще
  упирается в пороги времени.
- **Доказательство.** Ф: job-таймлайны прогонов 39661893213 и 39644590164:
  шаг `go test -race` 8:23 (Linux), 8:45 (macOS), 8:42 и 8:40 (Windows,
  оба красные); остальные шаги job — < 1,5 мин.
- **Предложение.** Матрица: Linux `-race`, macOS и Windows — `go test ./...`.
  Раз в неделю (вместе с api-contract) — `-race -count=3 -shuffle=on` на всех трёх ОС
  как «охотник за flaky», результат — issue, не блокер.
- **Поймает.** Гонки — по-прежнему (Linux); ОС-специфику — по-прежнему;

- **Стоимость.** 0,5 ч / 0. **Шум.** Еженедельный job может быть красным по
  вине платформы раннера — 1 issue в неделю максимум.
- **Риск без этого.** 10 мин на PR навсегда; красные Windows без дефекта.
- **Версия.** 1.2.2 (нужно решение по §4 `CLAUDE.md`, В1). **Роль.** SRE, QA.

- **Предложение.** Генератор на существующем фейке: записать

- **Риск без этого.** Деньги участников догфуда и клиентов при обрыве на

- **Версия.** 1.3 (до наборов для автономных агентов). **Роль.** QA, CTO.

### Как сделать матрицу исполняемой

Job `classify` в `ci.yml` (Linux, < 1 мин), выходы — список классов:

1. **По путям** (`git diff --name-only base...head`): `internal/mcp/http_policy.go|readonly.go`, `internal/tools/registry.go|project_bound.go|argcheck.go`, `internal/confirm/**` → `policy`; `internal/httpretry/**`, `internal/*/adapter.go`, `internal/tools/opwait.go` → `transport`; `internal/mcp/http_redact.go`, `internal/config/**`, `internal/auth/**`, `internal/cli/credentials.go` → `secrets`; `go.mod|go.sum|Dockerfile|.github/**|.goreleaser.yaml|install.sh` → `deps-ci`; `docs/**|README.md|CHANGELOG.md` → `docs`; `CHANGELOG.md` с новым пунктом под «Миграция» → `breaking`.
2. **По реестру** (точнее путей): собрать `evo` на base и head, `evo tools list --json` оба, diff: новое имя → `new-tool`; у существующего изменились `annotations`, наличие `confirmed`, `required` → `policy`; изменилась схема → `tool-change`.
3. Классы — в `GITHUB_OUTPUT`, метки PR (`pull-requests: write` для PR из своего репозитория) и summary с чек-листом ручных шагов для класса (внешний аудит, cloud-e2e область).
4. Зависимые job: `contract` (api-contract) — по `transport|new-tool|tool-change` вместо широкого `internal/**/*.go`; fuzz-набор целей — по `policy|secrets|transport` на PR (5 мин), полный — по расписанию; `live-plan` берёт области по классу при запуске с ветки.

Что CI не сделает: не заставит владельца провести внешний аудит. Это
остаётся правилом, но правило теперь печатается там, где принимается
решение о слиянии, а не живёт в `CLAUDE.md`.

## 6. Быстродействие и отказоустойчивость (SRE, QA)

### 6.1 Измерения (Ф, dev-сборка в контейнере аудита, Linux amd64)

| Что | Значение |
|---|---|
| `evo version` | 22–27 мс |
| `evo tools list --json` | 24–26 мс, 55 КБ |
| MCP stdio `initialize` + `tools/list` | 28 мс, RSS ≈ 21 МБ |
| `tools/list` | 154 инструмента, 117 КБ, ≈ 29 тыс. токенов; 87 `readOnlyHint`, 29 `destructiveHint`, 67 с `confirmed`; описание до 1 008 байт, в среднем 257 |
| `go test -race ./...` в CI | 8–8,5 мин на ОС |
| `go test ./...` локально (без `-race`) | 8 мин 06 с настенного времени при 1 мин 43 с CPU; из них `internal/cli` — 471 с, `internal/tools` — 31 с, остальные 40 пакетов — < 8 с каждый |
| `go build ./...` холодный | 31 с |

Вывод из двух последних строк (Ф → М): прогон тестов ограничен не
процессором и не `-race`, а ожиданием внутри одного пакета `internal/cli`
(CPU занят 20 % времени). Значит, `-race` на трёх ОС — не главная причина
10 минут; главная — последовательные тесты `internal/cli` с таймерами и
запуском бинаря (`docs_examples_test.go`, `version_test.go` используют
`exec.Command` — Ф). `t.Parallel()` в этом пакете (0 файлов сейчас) и
фейковое время вместо реальных таймаутов (`project_pages_test.go:62`,
`parity_json_fixtures_test.go:307–310`) способны сократить CI в разы
дешевле, чем любая перестройка матрицы.

Профиль `go test -v ./internal/cli` (Ф): один тест —
`TestEngineCommands_RepeatedDeployGate` (`internal/cli/engine_commands_test.go:296`)
— **450 с из 471 с**; следующий по времени — 4,8 с
(`TestParity_ErrorReasonEqualsTool`), остальные ≤ 2 с. Шаг `deploy --yes`
этого теста гонит движок через `runCLI` с продовыми интервалами ожидания
(`internal/engine/timings.go:15–29`: опрос ВМ 5 с, SSH 5 с, Docker 10 с,
`sshSlowNote` 5 мин). Г: тест ждёт на реальных таймерах то, что фейк
отвечает мгновенно. Исправление — подменить `Timings` в тесте (механизм
`def(&t.VMPollInterval, …)` в `timings.go:74–75` уже допускает
переопределение) — один PR, и CI на всех трёх ОС сокращается примерно с
10 до 2–3 минут без изменения §4 `CLAUDE.md`.

### 6.2 Бюджеты и как закрепить
- **М: не закреплять время в CI.** Урок Windows — пороги времени на общих
  раннерах дают ложные красные. Закреплять **размеры** (детерминированно):
  `tools/list` ≤ 160 КБ; описание инструмента ≤ 1 024 (есть); ответ любого
  `*_list` на 500 ресурсов фейка ≤ 256 КБ или страница с `next`; ответ
  `logs`/`ca_logs`/`k8s_kubectl` — обрезка с пометкой (проверить, что есть
  везде — Г).
- **Время и память** — тремя `Benchmark*` (`tools/list`, `redact` на 1 МБ
  JSON, `CheckArgs`), запуск руками перед minor и запись чисел в handoff.
  Защита от алгоритмического взрыва — один тест с 100-кратным запасом
  (`redact` 16 МБ ≤ 60 с): не шумит.
- **Старт бинаря** — 25 мс, бюджета не требует; появится, если в `main.go`
  придёт сетевой вызов (уведомление о версии в 1.3 — по плану не
  задерживает команду, проверить тестом: `evo version` без сети ≤ N вызовов
  фейка, не ≤ N мс).

### 6.3 Нагрузка
- 32 параллельных вызова и 33-й — `SERVER_BUSY`: тест есть
  (`sec_surface_test.go`). Долгие операции: `WriteTimeout` нет по дизайну
  (`http.go:609`), keep-alive SSE 15 с. Сотни ресурсов: `pager` и `*_truncated`.
- М: отдельная нагрузочная инфраструктура (k6 и т. п.) одному человеку не
  окупается. Достаточно Go-теста: 32 клиента × 100 вызовов на фейке, проверка
  отсутствия утечки горутин и памяти (`runtime.NumGoroutine` до/после) — без
  времени.

### 6.4 Отказы
- Есть: повтор GET/HEAD на обрыв и 5xx, 429 на любой replayable метод, Retry-After ≤ 30 с, отмена по контексту (`httpretry.go:23–40`); HTML как 502 (`HTMLAsBadGateway`); отмена по stdio-уведомлению, сигналу, закрытию HTTP-сессии (`cancel_test.go`); потерянный create находится по имени и времени (`FindCreatedVM`); state пишется до ожидания.
- Пробелы: медленный ответ (не обрыв) не инжектируется; Ctrl-C на шаге k не перебирается; два цикла повторов (П4); нет jitter в backoff (Г: для одного клиента не важно; для 32 параллельных вызовов MCP-сервера после 429 — все проснутся вместе; добавить ±20 % — 10 строк).

### Сознательно не внедрять
| Что | Почему |
|---|---|
| Мутационное тестирование (go-mutesting и т. п.) | часы на прогон, сотни «выживших» мутантов на разбор, большинство — эквивалентные; одному человеку не по силам; fault-матрица и fuzz дают больше |
| gosec, semgrep, gitleaks в CI | шум на фикстурах и Go-идиомах; CodeQL + тесты-инварианты закрывают класс |
| Merge queue, rc на patch, nightly платный e2e | нет параллельных авторов; лишние циклы и клики; ночной красный без причины в evo |
| Пороги времени и бенчмарки как блокеры CI | ложные красные на общих раннерах (уже доказано Windows) |
| k6/нагрузочный стенд, multi-arch образ, нотаризация | нет спроса; появится — делать |
| Автоматические исправления по находкам Qwen без разбора | находки — гипотезы, их уже положено опровергать или исправлять вручную; это правильно |

## 10. Что убрать или упростить

1. `push: branches: ["**"]` в `ci.yml` → только `main` (П1).
2. `-race` на macOS/Windows на каждом PR → еженедельно (П2, решение В1).
3. `-count=1` на PR → только `main`/тег (П1).
4. Полный аудит Fable на каждый patch → дельта (П10).
5. `api-probe`: удалять пробы, ответ на которые записан в реестр; оставлять только открытые вопросы (сейчас 680 строк).
6. Ручной `/qwen review` → автозапуск при открытии PR; команда остаётся для повтора.
7. `docs/internal/standalone/{00-audit,FINAL_AUDIT,KICKOFF,stages,01-plan}` → `docs/internal/archive/` (контекст сессий и ревьюеров короче; `DECISIONS.md` и `BACKLOG.md` остаются).
8. Два реестра расхождений (`cloudru-discrepancies.md` и `-v2.md`) → один с датами.
9. Bash внутри `cloud-e2e.yml` (88 шагов) → скрипты в `.github/scripts` по образцу `cloud-live.sh` (shellcheck их уже проверяет, YAML — нет), по одному job за PR, без спешки.
10. Не убирать: `cloud-readonly-os`, grok-review (спит, но безвреден), hadolint, redact-тесты — они дёшевы и ловят реальное.
