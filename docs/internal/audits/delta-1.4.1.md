### 6. Часы (правило §5 из ретро 1.4.0, #437) — #435
`Token.IsValid` (стенка, `time.Until`) и `Token.TTL` (`clock.Now`, значение
ответа) были разведены в 1.4.0 (`clock.Since`, #388). #435 меняет часы
одной функции — предполётной проверки в `IAMProvider.Token`
(`iam.go:184`): было `tok.TTL() < minAcceptableTTL` (часы ответов), стало
`!tok.IsValid(minAcceptableTTL)` (стенка). Разбор вызовов:
- решение по стенке: `Token` — обновление по `refreshTTL` (`:168,172`,
  `IsValid`, как было) и предполётная проверка (`:184`, теперь `IsValid`);
- значение ответа: текст отказа предполётной проверки («осталось %s»,
  `tok.TTL()`, `:187`), `whoami`/`doctor` (`TTL()` — не менялись).
`ExpiresAt.Round(0)` снимает монотонную часть у обменянного токена; из
файла она и не читалась (JSON). `exp` JWT — `time.Unix`, без монотонной
части; `exp.Before(expires)` сравнивает по стенке. Описание PR #435 разбирает вызовы по правилу: «решения — `iam.go:118, 122, 135` на `IsValid`; значения — `tools_auth.go:81, 82, 146` и текст отказа на `TTL`/`ExpiresAt`» — совпадает с разбором выше (номера строк — до слияния; сейчас `:168, 172, 184`).
`TestToken_PreFlightOnTheWallClock` держит решение (часы ответов на час
вперёд — токен на 11 минут проходит), `TestWallClockReadsDeclared` зелёный.
Журнал (#444): `deadline := time.Now().Add(wait)` — граница ожидания,
была; меняется длина ожидания, а не часы функции, поэтому разбор вызовов

### 7. Конкурентность
- **Журнал (#444).** `Write` держит `mu` на время `appendRecord`
  (`journal.go:124–131`), `appendRecord` ждёт OS-блокировку до `writeWait`
  0,1 с (`:160`, `lock` с опросом по 10 мс); `Describe`/`Export` —
  `readWait` 2 с. Один вызов ждёт не дольше 0,1 с; несколько одновременных
  вызовов одного процесса под чужой блокировкой ждут в очереди за `mu` —
  FB141-2 (проверено пробой: 8 записей — последняя через 0,83 с).
- **Провайдеры токенов (#435).** Реестр `live` — `weak.Pointer`
  (Go 1.24+, go.mod — 1.26) под `liveMu`; `forgetRejected` собирает список
  под `liveMu`, отпускает его и только потом зовёт `Forget` → `p.mu`:
  порядок `liveMu` → `p.mu` один, обратного нет. `Token` держит `p.mu` на
  время обмена (`exchangeOnce`), но запрос в IAM идёт без `Authorization:
  Bearer` (ключ в теле) — хук 401 в `answer` на него не срабатывает
  (`TestTokenRejectedIsReported`: `Basic`, без заголовка, 403, 200 — ничего
  не сообщают), значит `Forget` из-под `Token` того же провайдера не
  вызывается — взаимной блокировки при 401 во время обмена нет. 401

## Гипотезы (не проверял вживую)
- **Срок токена IAM меньше `expires_in`.** `min(expires_in, exp)` закрывает
  расхождение, если оно есть; проба `api-probe` (#436) печатает
  `exp − iat` и `exp − now` — первый прогон покажет, расходятся ли они. Если
  `exp − iat` заметно меньше `expires_in`, это пункт реестра расхождений
  (платформа), не дефект evo.
- **Связь 401 «Jwt is expired» с паузой ВМ стенда** — гипотеза плана
  (п. 1) остаётся гипотезой: `Round(0)` и `Forget` закрывают оба пути
  (монотонные часы и любой другой 401), живой прогон Windows на кандидате
  покажет, повторяется ли серия 401.
- **Повторный 401 от сервиса при живом ключе** (ключ выключен после
  выдачи токена): каждый вызов — обмен + 401, по вызову; подсказка ведёт к
  `evo doctor`. Цикла нет, но IAM получает по запросу на каждый вызов
  агента, пока тот не остановится. Если такое увидит догфуд — ограничить
  повторный обмен одного ключа после 401 (например, не чаще раза в минуту).
- **`FileCache.Delete` между процессами.** Между `Load` и `Remove` другой
  процесс мог записать свежий токен — он удалится, следующий вызов обменяет
  ключ лишний раз. Цена — один обмен; данных не теряет.
