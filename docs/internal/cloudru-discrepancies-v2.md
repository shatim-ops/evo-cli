## Подтверждено и дополнено

#### BIL-5. Потребление по проекту без договора работает; спецификация не говорит, что нужен один из фильтров
Расхождение (спецификация) · подтверждено вживую (api-probe 19.10, P20)
- **Док:** спецификация «Контроль затрат» v2 ([`swagger.yaml`](https://cloud.ru/docs/api/specs/billing/ug/_specs/swagger.yaml)): в `GET /v2/consumption` и `agreement_id`, и `project_ids` — `required: false` («Фильтр по идентификаторам проектов.»). [Начало работы с API](https://cloud.ru/docs/billing/ug/topics/api-ref_start): «администратор проекта (platform.project.admin) — для запроса данных потребления по проекту». [FAQ](https://cloud.ru/docs/billing/ug/topics/faq__api_id_agreement): ID договора видят только «Администратор организации» и «Администратор затрат».
- **Живое:** `?project_ids=P&start_date=…&end_date=…&page_filter.page_size=10` (30 дней) → 200, 10 строк и `next_page_token`. Поля строки: `amount`, `amount_nds`, `cost`, `encode_id`, `id`, `is_delete`, `platform`, `product_instance_id`, `resource_id`, `resource_name`, `servname`, `sku`, `unit`, `updated_dt`, `usedate`, `usefact`. Тот же запрос без `project_ids` и без `agreement_id` → 400 «rpc error: code = InvalidArgument desc = Either agreement_id or project_ids must be provided».
- **Влияние:** обещание документации выполняется: ключ проекта видит расход проекта без договора. Клиент, написанный по спецификации, узнаёт, что один из двух фильтров обязателен, только из 400.
- **Просим:** указать в спецификации, что нужен `agreement_id` или `project_ids`; описать `is_delete` (учитывать ли такие строки в сумме).
- **В evo:** `billing_consumption` и `billing_finops` без договора запрашивают расход по проекту (#126). Заодно исправлена ошибка evo: `billing_finops` суммировал `cost`, а это по спецификации тариф («Тариф потребления облачного сервиса без НДС»), не стоимость строки (`amount`).

#### CRT-1. Пример инструкции с `page.limit` отвергается: 415
Расхождение · подтверждено вживую (api-probe 19.10, P24; пункт v1 — 400 без `pageSize`)
- **Док:** [Просмотреть версии](https://cloud.ru/docs/certificate-manager/ug/topics/guides_version_all_view), вкладка API: `…/versions?page.limit=10`, «page.limit — допустимое количество записей в одном запросе. Максимальное значение — 1000, по умолчанию — 100». **Спека:** [`ccm.swagger.yaml`](https://cloud.ru/docs/api/specs/certificate-manager/ug/_specs/ccm.swagger.yaml) — `pageSize`/`pageToken`.
- **Живое:** сертификатов в проекте нет, запросы шли к несуществующему ID. Без параметров → 400 `invalid ListVersionsRequest.PageSize: value must be inside range [1, 1000]` (как в v1); `pageSize=10` → 403 «permission denied» (CRT-2 v1); `page.limit=10` и `page.limit=10&page.offset=0` → 415 «invalid gRPC request content-type ""»; контрольный `pageSize=10&bogus=1` → тоже 415.
- **Вывод:** неизвестный параметр отвергается раньше проверки доступа (как AUD-2 v1), поэтому вывод не зависит от ID: пример инструкции с `page.limit` не работает ни для какого сертификата. Код 415 и текст про content-type не говорят клиенту, что дело в имени параметра.
- **Просим:** в инструкции — `pageSize`/`pageToken`, как в спецификации и API; на неизвестный параметр — 400 с его именем.

## Новые пункты

#### IAM-5. Параметр `resource` (RFC 8707) при выдаче токена молча игнорируется
Нет в документации · подтверждено вживую (api-probe 19.10, P26)
- **Док:** ни документация, ни discovery `id.cloud.ru/auth/system/.well-known/openid-configuration` не говорят, поддерживаются ли индикаторы ресурса (RFC 8707): `resource` не упомянут. Для Cloud.ru это не нарушение собственной документации; пункт — про пробел, важный для публичного MCP-сервера.
- **Живое:** `POST id.cloud.ru/auth/system/openid/token` (`client_credentials`) и обмен `access_key` на `auth.iam` — с `resource` и без: все четыре → 200, `invalid_target` нет; в access- и id-токене `aud = ["iam"]` во всех случаях, значение `resource` в `aud` не попадает.
- **Влияние:** токен нельзя привязать к получателю. [Спецификация авторизации MCP](https://modelcontextprotocol.io/specification/draft/basic/authorization) требует, чтобы клиент передавал `resource`, а MCP-сервер принимал только токены, выпущенные для него: без этого токен, выданный для MCP-сервера Cloud.ru, действует во всём API. Для evo в режиме stdio это не важно; для публичного MCP Cloud.ru — блокер, вместе с отсутствием регистрации клиентов (`registration_endpoint` в discovery нет).
- **Просим:** поддержать `resource` (аудитория токена) или явно написать, что параметр не поддерживается.

#### BIL-7. Расход проекта отдаётся ключу наблюдателя, хотя документация называет только администратора проекта
Расхождение (права доступа) · подтверждено вживую (api-probe 19.10, P20; cloud-readonly-os 19.10)
- **Док:** [Начало работы с API «Контроля затрат»](https://cloud.ru/docs/billing/ug/topics/api-ref_start): «Запрос доступен только ролям: администратор организации (platform.customer.admin) и администратор затрат (platform.customer.expense-admin) — для запроса данных потребления по всем договорам и проектам организации; администратор проекта (platform.project.admin) — для запроса данных потребления по проекту».
- **Живое:** ключ окружения `cloud-readonly` (сервисный аккаунт с ролью «Наблюдатель проекта»; роль ключа в прогонах не печатается, она задана при настройке окружения) получает 200 на `GET /v2/consumption?project_ids=P` (P20) и полный отчёт `billing_finops` по проекту (cloud-readonly-os: Windows и macOS).
- **Влияние:** либо документация неполна (расход проекта доступен и наблюдателю), либо права шире задуманных: стоимость ресурсов проекта видит роль только для чтения. Для клиента важно знать, какую роль выдавать агенту или FinOps-инструменту.
- **Просим:** подтвердить, какие роли читают потребление по проекту, и привести документацию или права к одному.
- **В evo:** подсказка при 403 называет `platform.project.admin`, как документация; если наблюдатель — штатный случай, подсказку стоит расширить.

## Снято

#### CMP-12. Предел размера диска — 16384 ГБ: снят
- **Было (v1):** документация и спецификация — 16 ТБ (`size: maximum 16384`), в старой записи evo — 65536.
- **Живое (P15, P27):** `GET /disk-types` — `min_size: 1`, `max_size: 16384` у SSD и HDD; `price-calculation` с диском 16384 ГБ → 200, с 16385, 65536 и 65537 → 422 `wrong_disk_size` «Disk size must be between disk_type min and max sizes».
- **Итог:** API совпадает с документацией; ошибка была в старой записи evo.

#### DB-10. `min_brokers` и `max_brokers` в ответе есть: часть пункта снята
- **Было (v1):** срок создания Kafka не указан; в `GET /v1/specifications` нет `min_brokers`, хотя он есть в спецификации.
- **Живое (P25):** `GET /v1/specifications?version_id=<4.2.0>&availability_zone_id=<ru.AZ-2>` → 200, у всех 10 спецификаций есть `min_brokers` (1) и `max_brokers` (10).
- **Итог:** вторая часть пункта не воспроизводится — возможно, исправлено. Срок создания по-прежнему не описан (v1: 34–39 мин на кластер из одного брокера).

- **Живое:** ключ уровня проекта: `GET organization.api.cloud.ru/v3/agreements` без параметров и с `customer_ids` → 403 «dont have permissions to customers»; `GET billing.api.cloud.ru/v1/agreement/<несуществующий>` → 403 «permission denied to agreement»; корень `billing.api.cloud.ru` → 404.

## Кандидаты: подтвердить ближайшим прогоном

Найдены сверкой с документацией 19.10; наблюдения — из прогонов v1 (OPS-1,
OPS-2). В реестр войдут, когда ближайший cloud-e2e (`e2e`, `ca_smoke`) даст
живое подтверждение.

- **IMG-6. Образы переключают apt на зеркало платформы при первой загрузке — не описано.** Шаблон [cloud-init](https://cloud.ru/docs/images/ug/topics/concepts__cloud-init) содержит только `package_update: true`, `package_upgrade: true`. На страницах [Публичные образы](https://cloud.ru/docs/images/ug/topics/concepts__public-images), [FAQ cloud-init](https://cloud.ru/docs/images/ug/topics/faq__cloud-init) и [Решение проблем](https://cloud.ru/docs/virtual-machines/ug/topics/troubleshooting) нет ни «apt», ни «зеркало», ни «mirror». А образы Ubuntu и Debian шагом bootcmd `configure-apt-mirrors` переключают apt на `repo.mng.sbercloud…`, и с новой ВМ это зеркало часто не отвечает (OPS-2…2c v1). При этом `apt-get update` выходит с кодом 0. Что проверить: строку переключения на официальное зеркало в выводе `deploy` (evo с #126) и состав apt-источников образа на ВМ.
- **CMP-17. Когда ВМ доступна по SSH после «Запущена» — не описано.** [Подключиться по SSH](https://cloud.ru/docs/virtual-machines/ug/topics/guides__ssh-connection) говорит: «Убедитесь, что: Статус виртуальной машины — «Запущена». Виртуальной машине назначен публичный IP-адрес. Подключение к виртуальной машине по SSH разрешено в группах безопасности». Ни срок готовности SSH, ни случай «ВМ запущена, порт 22 не отвечает» не описаны (OPS-1, 1a, 1b v1: 60 попыток за ~14 мин без ответа). Что проверить: диагноз evo по порту 22 (таймаут, refused или EOF) и помогает ли [перезагрузка](https://cloud.ru/docs/virtual-machines/ug/topics/guides__restart).
- **CAP-3. Логи контейнера: порядок, размер страницы и `total` в API не описаны.** В спецификации Container Apps ([`openapi.yaml`](https://cloud.ru/docs/api/specs/container-apps-evolution/ug/_specs/openapi.yaml)) у `GET /v2/containers/{name}/logs` не указаны умолчание `pageSize` и порядок строк, а `filter` дан без описания. `ListContainerLogsResponse.total` описан как «Общее число контейнеров.». У `…/systemLogs` нет пагинации, а `serverlessId` дан без описания. [Логирование](https://cloud.ru/docs/container-apps-evolution/ug/topics/concepts__logging) описывает только консоль: системные логи «в хронологическом порядке, начиная с самого позднего», «Отображаются последние 1000 записей». Что проверить: в `ca_smoke` число строк, их порядок и `total` (18.10 `ca_logs` вернул 0 строк у работающего контейнера).
