## evo 1.10.0

### Что появилось в CLI и MCP

| Задача | Команда CLI | Инструмент MCP | Что можно узнать или сделать |
|---|---|---|---|
| Проверить диск | `evo disk get <disk_id>` | `disk_get` | Размер, состояние, тип, зона, признаки шифрования и подключённые ВМ. Отсутствующие в ответе платформы сведения перечислены в `not_checked`. |
| Посмотреть конфигурацию и историю ВМ | `evo vm get`, `evo vm history <vm_id>` | `vm_get`, `vm_history` | В карточке появились ID и название конфигурации (flavor). История показывает действие, состояние и время задач. При ошибке следующей страницы видны уже прочитанные записи и причина неполноты. |
| Найти сетевой интерфейс | `evo vpc interfaces`, `evo vpc interface-get <interface_id>` | `interface_list`, `interface_get` | Список включает свободные интерфейсы. Карточка показывает ВМ, адреса, подсеть и группы безопасности. |
| Обновить Kubernetes | `evo k8s upgrade`, `evo k8s nodepool-upgrade` | `k8s_upgrade`, `k8s_nodepool_upgrade` | Сначала обновите управляющую часть и проверьте фактическую версию. Затем отдельным действием обновите выбранную группу узлов. В MCP для каждого действия покажите превью человеку и после согласия верните его `preview_id` в той же сессии. |

### Что проверить при обновлении

Проверьте автоматизации, которые выбирают ресурс по имени, повторяют запись после обрыва связи или используют результаты списков для следующего действия. Ниже приведены изменения для SNAT, фильтров по VPC, списков, сетевых операций и восстановления квитанций. Для балансировщиков отдельно описано продолжение остановленного стека. При переходе с 1.9.0 проверьте также обработку ошибок списков Redis и Kafka.

При создании платного шлюза по имени зоны `evo snat create` и MCP `snat_create` проверяют весь каталог. Раньше первое совпадение могло выбрать другую зону. Теперь нужны одно совпадение и признак `enabled: true`. При изменении UUID после превью старое подтверждение возвращает новое размещение без создания шлюза (CLI — код 3). В терминале запустите команду без `--yes`, проверьте UUID и ответьте на вопрос. В скрипте после нового согласия передайте `--availability-zone-id` с показанным UUID, в MCP — `availability_zone_id` из `will_create` и `confirmed: true`. Первый прямой вызов с согласием и явный UUID доступны как прежде.

После обновления с версии до 1.10 или перехода в другую папку состояния либо на другую машину отбросьте незавершённые подтверждения создания SNAT по имени зоны. Сверка возможна только при наличии локальной записи с UUID показанной зоны. Прежние версии эту запись не создавали, а в новой папке она может отсутствовать. В таком случае повтор со старым согласием может создать шлюз как первый подтверждённый вызов. Запросите свежее превью (в CLI запустите команду без `--yes`, в MCP вызовите `snat_create` без `confirmed`), проверьте показанный UUID и получите новое согласие.

При отборе по имени VPC команды `evo vpc subnets`, `evo lb list` и `evo tg list` проверяют все страницы каталога сетей выбранного проекта. Раньше совпадение на первой странице могло дать выборку и код 0 при повреждённой следующей странице. Теперь в таком случае запрос к целевому списку не выполняется. CLI возвращает код 5 (`API_ERROR`). Инструменты MCP `list_subnets`, `lb_list` и `tg_list` возвращают `result.isError: true` с причиной `API_ERROR`.

В скрипте проверяйте код выхода до обработки строк, в MCP — `result.isError`. При ошибке повторите чтение после восстановления каталога. Если UUID сети уже известен, передайте его в `--vpc-id` или в аргумент MCP `vpc_id`. Фильтры по UUID обходятся без поиска сети по имени.

При чтении списка ресурсов, прав, событий аудита или расходов HTTP 200 с телом `null` или строкой `null` раньше мог дать код 0 и неполный результат. Теперь CLI завершает чтение с кодом 5 (`API_ERROR`), MCP возвращает ошибку. Скрипту следует повторить чтение после восстановления API, прежде чем выбирать имя ресурса или складывать расходы. Корректные пустые списки по-прежнему принимаются.

После обрыва создания DNS-записи, статического маршрута или платного шлюза SNAT повтор мог создать второй ресурс. Теперь при неизвестном исходе все клиенты удерживают повтор даже с новым подтверждением. CLI сообщает код 3. Проверьте список записей зоны, маршрутов VPC или шлюзов проекта. Если цель уже видна, повтор сообщает её ID. Для дальнейшей сверки по HTTP используйте `Mcp-Session-Id`, выданный при `initialize`. Пустой список или смена сессии не доказывают отказ. [Порядок восстановления](../mcp.md#network-create-recovery).

При сверке создания по имени `evo doctor` и инструмент MCP `doctor` сохраняют квитанцию, если её владелец или проект не подтверждены. Раньше одноимённый ресурс в списке мог закрыть старую квитанцию. Проверьте ресурс в исходном проекте с соответствующим ключом. Предупреждение означает, что исход операции остаётся неизвестным.

Подробности перехода — в разделе «Миграция» версии 1.10.0 в [CHANGELOG.md](../../CHANGELOG.md). При обновлении с 1.9.0 учтите также [изменение списков Redis и Kafka в 1.9.1](v1.9.1.md).

### Согласие на размещение балансировщика

Платное размещение балансировщика привязано к проекту, VPC, зоне и подсети. Для прямого вызова MCP запросите `lb_create` без подтверждения, покажите человеку превью и после его согласия передайте `preview_id` с `confirmed: true` в той же сессии. В HTTP сначала выполните `initialize` и передавайте `Mcp-Session-Id`. При изменении размещения покажите новое превью. Первый явный `evo lb create --yes` доступен человеку. Если стек остановился с `awaiting_lb_approval`, сохраните `job_id` и ID готовых ресурсов, запросите `stack_apply` для этого задания и подтвердите фактическое размещение. В MCP верните выданный `preview_id`. Опрос `stack_status` оставляет шаг на паузе.
