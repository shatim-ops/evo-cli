## evo 1.9.1

При переходе на 1.9.1 проверьте скрипты, которые используют `evo redis list` и `evo kafka list`. В 1.9.0 тело страницы `null` или элемент `null` в массиве `clusters` могли дать успешный, но неполный результат. В 1.9.1 обрыв ответа, `{"clusters":null}` и некорректный токен продолжения также останавливают чтение. Уже полученные страницы не используются для выбора кластера. CLI возвращает код 5 (`API_ERROR`), а инструменты MCP `redis_list` и `kafka_list` возвращают `result.isError: true`. Успешная пустая последняя страница с `{"clusters":[]}` по-прежнему завершает выдачу.

Проверьте код выхода или `result.isError` до чтения строк. При ошибке остановите действия, зависящие от списка, и повторите чтение, когда сервис сможет вернуть все страницы.

Перед созданием `evo redis create` и `evo kafka create` проверяют имя по полному списку. Если страница неполна, CLI возвращает код 5, а инструменты `redis_create` и `kafka_create` — ошибку до отправки запроса на создание. При `evo mcp --allow-project` проверка принадлежности ID кластера Redis или Kafka проекту также требует полного списка. При ошибке вызываемая операция не выполняется.

Для PostgreSQL ошибка в форме любой страницы или обрыв её тела теперь останавливают `evo pg list` и `evo pg create` с кодом 5 (`API_ERROR`). Раньше неверный тип поля `clusters` мог скрыть занятое имя. После ошибки `pg_list` или `pg_create` в MCP повторите чтение перед созданием.

При удалении Container Apps явный `evo ca delete <имя> --wait` ждёт до 2 минут. Без флага и в MCP при `ca_delete(wait=true)` предел — 45 секунд. При `deleting` проверяйте состояние командой `evo ca get <имя>` либо вызывайте `ca_get` с аргументами из `next_args` до `NOT_FOUND`.

После удаления ВМ `evo destroy --json` сообщает `status: partial` и `cleanup_pending: true`, когда остался адрес или правило либо их уборку не удалось подтвердить. Код выхода по-прежнему 0. В скрипте проверяйте `status == "destroyed"` перед следующим шагом. После запроса на освобождение плавающего IP evo проверяет этот ID отдельным GET. Пока освобождение не подтверждено, квитанция сохраняется для повтора. Старую квитанцию или потерянный ответ на создание теперь можно разобрать командами `evo cleanup receipts` и `evo cleanup resolve`. Если облако вновь показывает привязку адреса к ВМ, квитанция открывается снова. Последующие вызовы `evo destroy` в том же каталоге предупреждают о возможной оплате до новой независимой сверки. Если ВМ исчезла из списка проекта, MCP с `--allow-project` вернёт `NOT_FOUND`. Продолжите уборку в терминале на машине MCP в том же каталоге состояния. Команда `evo cleanup resolve` проверяет пригодность `--evidence` до запроса согласия, включая `--dry-run`. После подтверждения исхода повторите `evo destroy` в том же каталоге. [Как завершить уборку](../guide.md#если-после-удаления-вм-осталась-квитанция-плавающего-ip).

Если в старой квитанции нет сведений о создателе или сохранена только маска ключа, удаление группы нельзя подтвердить по 404. Квитанция остаётся открытой. Если группа доступна, полный список правил без сохранённого ID подтверждает уборку.

У правил, найденных по метке ВМ, поля `security_group_rules.closed` и `security_group_rules.failed` содержат массивы строк. В таблице показаны строки **после разбора JSON**. Во втором примере ID состоит из `vm-"1` и перевода строки.

| Поле | Обычный ID `vm-1` в 1.9.0 и 1.9.1 | ID с кавычкой и переводом строки в 1.9.1 |
|---|---|---|
| `closed` | `80 (vm vm-1)` | `80 (vm "vm-\"1\n")` |
| `failed` | `53/udp (vm vm-1): service unavailable` | `53/udp (vm "vm-\"1\n"): service unavailable` |

UUID и другие ID из букв ASCII, цифр, дефисов, точек и подчёркиваний сохраняют прежнюю форму. Фильтры по таким ID продолжат работать. Если в ID есть другой символ, evo заключает ID в двойные кавычки и экранирует кавычки, обратную косую черту и управляющие символы. Для решения о продолжении уборки проверяйте `cleanup_pending`.

Если в `evo deploy plan` или `deploy_plan` явно указан образ, проверьте обработку кода 4. После полного поиска без совпадения и при скрывающем 404 сервиса на первой странице ответ одинаковый (`NOT_FOUND`, код 4). Если предыдущая страница обещала продолжение и сервис вернул 404 на второй или более поздней странице, каталог не удалось дочитать (`API_ERROR`, код 5). Даже при совпадении на первой странице evo не выбирает образ и не сохраняет план. Повторите чтение.

Ошибка маршрута шлюза с ответом 404 на любой странице также даёт `API_ERROR`, код 5. В этом случае обновите evo и проверьте базовый URL API, если он переопределён. При тайм-ауте CLI возвращает 1, при ошибке авторизации — 2, при ограничении частоты запросов, сбое сервиса или неполной выдаче — 5. В MCP эти случаи различаются по `reason`. При отказе доступа остановите подбор и проверьте права.

Подробности перехода — в разделе «Миграция» версии 1.9.1 в [CHANGELOG.md](../../CHANGELOG.md#миграция).
