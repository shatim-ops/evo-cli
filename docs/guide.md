# Руководство: Cloud.ru Evolution CLI CREW edition (evo) за 20 минут

Для тех, кто запускает `evo` впервые. Здесь — как поставить, настроить и
сделать первые полезные вещи; справочники по каждой теме — по ссылкам.

## Что такое evo

`evo` (Cloud.ru Evolution CLI CREW edition) — командная строка и MCP-сервер для облака
[Cloud.ru Evolution](https://cloud.ru). Две задачи:

1. **Управлять ресурсами проекта из терминала и скриптов**: ВМ, диски, сети,
   Managed Kubernetes, PostgreSQL, Object Storage, Secret Manager и ещё
   ~150 операций (DNS, балансировщики, Kafka, Redis, реестр образов,
   сертификаты, мониторинг, биллинг).
2. **Развернуть `docker-compose`-проект на ВМ одной командой** — `evo deploy`
   создаёт ВМ с публичным IP, ставит Docker и поднимает контейнеры;
   `evo destroy` всё это удаляет.

Те же операции доступны AI-агентам (Claude Code, Cursor) через MCP-сервер
`evo mcp`.

Главное правило: **ничего платного и ничего необратимого без согласия.**
Создание ресурсов и удаление данных сначала показывают превью (что будет
сделано, в каком проекте, цена) и ждут подтверждения.

## 1. Что нужно заранее

| Что | Где взять |
|---|---|
| Сервисный аккаунт Cloud.ru с ролями в проекте | создаёт администратор проекта: [auth.md → сервисный аккаунт](auth.md#1-сервисный-аккаунт) |
| Ключ доступа этого аккаунта: **Key ID** и **Key Secret** | [auth.md → ключ доступа](auth.md#2-ключ-доступа); Secret показывается один раз |
| UUID проекта (вида `3f2a8c1e-…`) | консоль Cloud.ru, сведения о проекте |
| Для `deploy`: исходящий доступ к порту 22 из вашей сети | корпоративный VPN часто его закрывает — проверьте заранее |

**Какой ключ просить.** Для работы с одним проектом — ключ сервисного
аккаунта **уровня проекта**: тогда `evo` физически не может затронуть другие
проекты. Ключ с ролью «Администратор организации» видит все проекты
организации — с ним `evo` работает в проекте из настроек, а `evo whoami`
предупредит, сколько проектов видно ключу (см. [раздел 9](#9-несколько-проектов)).

## 2. Установка

**macOS и Linux:**

```sh
curl -fsSL https://raw.githubusercontent.com/shatim-ops/evo-cli/main/install.sh | sh
evo version
```

Скрипт проверяет контрольную сумму архива (и подпись, если установлен
`cosign`) и кладёт бинарь в `~/.local/bin`. Если этого каталога нет в `PATH`,
скрипт подскажет строку для профиля оболочки. Без `CLOUDRU_VM_VERSION` ставится
последний стабильный релиз.

Строки, которые начинаются с `#`, — пояснения к командам. В zsh (оболочка по
умолчанию на macOS) скопированный комментарий без настройки даёт ошибку
«command not found: #»: включите комментарии один раз —
`echo 'setopt interactivecomments' >> ~/.zshrc && source ~/.zshrc` — или
копируйте только сами команды.

**Windows:** установщика пока нет — скачайте zip из
[релизов](https://github.com/shatim-ops/evo-cli/releases) и добавьте каталог в
`Path`, по шагам — [install.md → Windows](install.md#windows).

macOS может не дать запустить бинарь из интернета (Gatekeeper), Windows —
показать SmartScreen: что делать — [install.md](install.md#gatekeeper-macos-и-smartscreen-windows).

## 3. Первый запуск: ключ, проект и зона

```sh
evo configure
```

Команда спросит Key ID и Key Secret (секрет не отображается при вводе),
проверит их в IAM и сохранит в профиль `default` — файлы с правами только для
вас. Cloud.ru не отдаёт сервисному аккаунту список проектов, поэтому UUID
проекта `configure` попросит ввести вручную — это ожидаемо.

Затем `configure` спросит зону доступности для новых ВМ — из тех, что
показывает `evo vm zones`, первой предложит зону с подсетью проекта
(ru.AZ-2, если подсеть есть и в ней); Enter берёт её. Зону evo сам не
выбирает: без неё `evo vm create` откажет сразу, до вопроса о согласии. Не
получилось прочитать список зон — шаг пропускается, зону можно задать позже:
`evo configure --region ru.AZ-2` (имя или UUID).

Проверьте:

```sh
# ключ принят, какой проект выбран и откуда он взят
evo whoami
# файлы настроек и их права, доступность API, ключ
evo doctor
```

`doctor` с кодом `0` — всё готово. Иначе он назовёт, что не так; типовые
случаи — в [troubleshooting.md](troubleshooting.md).

Несколько ключей или проектов — несколько профилей:
`evo configure --profile test`, затем `evo --profile test …` или
`CLOUDRU_PROFILE=test`. Для CI ключ можно передать переменными
`CLOUDRU_KEY_ID`, `CLOUDRU_SECRET`, `CLOUDRU_PROJECT_ID` — все варианты в
[auth.md](auth.md#7-переменные-окружения).

## 4. Посмотреть, что есть в проекте

Чтение ничего не меняет и подтверждения не требует:

```sh
# ВМ проекта
evo vm list
# диски
evo disk list
# сети; evo vpc --help — подсети, группы безопасности, floating IP
evo vpc list
# кластеры Kubernetes
evo k8s list
# каталог плагинов Kubernetes (раздел 7)
evo k8s addons
# кластеры PostgreSQL, Kafka, Redis
evo pg list
evo kafka list
evo redis list
# зоны DNS, балансировщики, сертификаты
evo dns zones
evo lb list
evo cert list
# бакеты Object Storage
evo s3 buckets
# образы ВМ: ОС и продукты маркетплейса (раздел 6)
evo image list ubuntu
# витрина: образы и плагины одним списком (раздел 7)
evo marketplace list
# зоны доступности
evo vm zones
```

Каждая команда понимает `--json` — для скриптов и `jq`:

```sh
evo vm list --json | jq -r '.vms[] | "\(.name)\t\(.state)"'
```

Всё, что есть у MCP-сервера, доступно и из CLI: у каждого инструмента —
своя команда, по префиксу его имени (`dns_zones` — `evo dns zones`,
`kafka_create` — `evo kafka create`, `stack_plan` — `evo stack plan`), а
`evo tools` вызывает инструмент по имени, как агент:

```sh
# все инструменты с кратким описанием
evo tools list
# аргументы инструмента
evo tools describe dns_zones
# вызвать
evo tools call dns_zones
```

## 5. Развернуть docker-compose-проект

В каталоге с `docker-compose.yml`:

```sh
# создаёт .evo.yaml: зона, образ, размер ВМ
evo init
# превью: что будет создано, в каком проекте, сколько стоит; ничего не создаёт
evo deploy --dry-run
# покажет то же превью и спросит подтверждение
evo deploy
```

`deploy` создаёт ВМ, публичный floating IP, открывает в группе безопасности
порты из `ports:` compose-файла, ставит Docker и запускает
`docker compose up -d`. Новая ВМ создаётся несколько минут; `deploy` ждёт до
25 минут (`CLOUDRU_TIMEOUT`, секунды) и показывает, сколько прошло и в каком
состоянии ВМ: в терминале — одной обновляемой строкой
(`ожидание ВМ… 1м20с (creating)`), в файл или конвейер — такой же строкой раз
в 30 секунд и при смене состояния, с `--json` — ничего.

Дальше:

```sh
# ВМ, IP, состояние по state и в облаке
evo status
# порты приложения отвечают снаружи
evo verify
# логи контейнеров
evo logs -f
# после правки compose-файла: покажет превью обновления той же ВМ и спросит
evo deploy
# удалить ВМ, освободить IP, закрыть открытые порты
evo destroy
```

**Пока ВМ существует, она оплачивается.** Закончили — `evo destroy`.

Что важно знать:

- Состояние развёртывания и SSH-ключ к ВМ лежат в `./.evo/` **этого
  каталога**. Запускайте `status`, `logs`, `destroy` отсюда же; не удаляйте
  `.evo/` и не коммитьте его в git (там приватный ключ).
- `status` показывает запись из `./.evo/state.json` и строку «В облаке» —
  живое состояние ВМ по одному запросу к Cloud.ru (не дольше 8 с). ВМ,
  удалённую в консоли, `status` покажет как «не найдена (удалена вне evo)»;
  запись (и её floating IP, правила портов) уберёт `evo destroy`. Если облако
  спросить не удалось — нет ключа, сети, ошибка API, — `status` не падает:
  показывает state и пишет «не проверено: причина». `evo status --no-refresh`
  читает только state, без запроса. С `--json` к записи добавляются поля
  `cloud_checked`, `cloud_state`, `not_found_in_cloud`, `cloud_error` и
  `cloud_reason`. `status` state не меняет.
- На ВМ попадает **только compose-файл**. Образы должны быть в реестре
  (`image:`); `build:`, файл `.env` и локальные файлы, примонтированные через
  `volumes:`, на ВМ не переносятся. Про `build:`, `env_file:`, такие
  `volumes:` и файлы `secrets:`/`configs:` `deploy` предупреждает до превью.
  Переменные `${VAR}` работают только со значением по умолчанию
  (`${VAR:-значение}`).
- Один каталог — одно развёртывание в одном проекте. ВМ из `evo vm create`
  (MCP `provision`) записывается в тот же каталог; если там уже есть
  развёртывание, `destroy` без указания ВМ откажет и перечислит обе —
  удаляйте каждую по ID: `evo vm delete <ID>`.
- Повторный `deploy` обновляет ВМ развёртывания только с согласием — как
  первый перед созданием ВМ и как MCP `deploy`: превью обновления и вопрос;
  в скрипте или CI — `evo deploy --yes`, без терминала и без `--yes` — код
  `3`, ничего не меняется. Если compose-файл не изменился и развёртывание
  работает, `deploy` ничего не делает и ничего не спрашивает («развёртывать
  нечего», код `0`); `--force` — обновить всё равно, тоже с согласием.
- Развёртывание по шагам — тот же мастер, что у агента в MCP (`deploy_plan`
  → `deploy_apply`): `evo deploy plan --product web --cpu 2 --ram-gb 4 --port 80`
  рассчитывает ВМ и цену, ничего не создавая, и возвращает `plan_id`;
  `evo deploy apply <plan-id>` выполняет план после подтверждения;
  `evo deploy list` — записи развёртываний этого каталога.
- Зона: `evo init` берёт зону, где у проекта есть подсеть (в новом проекте
  подсеть `Default_ru.AZ-1` создаётся только в ru.AZ-1): **ru.AZ-2**, если
  подсеть есть и в ней, иначе зону основной подсети. ru.AZ-2 — потому что вечером 15.10.2026 в
  тестовом проекте она прошла все проверки, а в ru.AZ-1 ВМ по 10–20 минут
  висели в `creating` или не поднимали SSH. Зоны Cloud.ru меняются: утром
  того же дня было наоборот. Если ВМ не создаётся — смените зону:
  `evo deploy --region ru.AZ-2` (имя или UUID) или `region:` в `.evo.yaml`
  (список — `evo vm zones`).
- Группа безопасности: в ней `deploy` открывает порты compose для всего
  интернета (`0.0.0.0/0`), и это касается всех ВМ в группе. По умолчанию
  берётся группа зоны по умолчанию — её отмечает сам API, у Cloud.ru она
  называется `SSH-access_<зона>` и не удаляется; если такой нет — первая по
  имени, с предупреждением и списком групп. Свою группу задаёт `security_group:` в `.evo.yaml` (имя или
  UUID; список — `evo vpc security-groups`).
- Подсеть: основная подсеть зоны (её отмечает API), иначе маршрутизируемая —
  только к ней привязывается публичный IP, иначе первая в зоне. Если в
  подсети не указаны DNS-серверы, `deploy` предупредит: ВМ не будет разрешать
  имена, Docker и образы не скачаются.

## 6. ВМ с ОС или продуктом из маркетплейса

ВМ создаётся из образа: операционной системы (тип `public`) или продукта
маркетплейса Cloud.ru (`marketplace`; Astra Linux, Альт, РЕД ОС есть только
там). Образ ищется по части имени или отображаемого имени, без учёта
регистра:

```sh
# имя, отображаемое имя, тип, зоны, минимальный диск
evo image list astra
# только ОС; --type private — образы проекта
evo image list --type public
# карточка: минимум, зоны, поля образа и кто их заполнит
evo image get AstraLinuxSmolensk1.8.3KES
```

Образы, которые не готовы ни в одной зоне, список скрывает: в общем каталоге
есть тестовые и сломанные. `--all` показывает все.

Каталог Cloud.ru — общий, но **не каждый его образ доступен проекту**. evo
сверяет общий каталог с тем, каким его видит проект (тот же поиск с
`project_id`), и образы, которых проекту не видно, тоже скрывает; итог
списка называет обе причины — «не готовы ни в одной зоне: N; недоступны
проекту: M». С `--all` такие образы видны с колонкой «ДОСТУПЕН ПРОЕКТУ» =
«НЕТ», в `--json` — с `available_in_project: false`; `image get` показывает
карточку с пометкой «НЕ доступен» и без команды создания ВМ. Создать ВМ из
такого образа API не даёт (ответ 422 `wrong_image`), поэтому `vm create`,
`deploy`, `init --image` отказывают **до** вопроса и до создания чего-либо,
код 4. 16.10.2026 тестовому проекту были недоступны все образы Astra Linux,
Альт, РЕД ОС и SberLinux общего каталога (а также Windows 11 VDI, Ubuntu
24.04 Desktop, NGFW). Почему — не проверено: вероятно, продукт маркетплейса
нужно сначала подключить к проекту. Если каталог проекта прочитать не
удалось, evo ничего не помечает и печатает предупреждение.

`image get` принимает имя, отображаемое имя или UUID и печатает UUID образа
и команду создания. `vm create --image` принимает то же самое: точное имя
(регистр не важен), отображаемое имя, UUID или часть имени, если она
подходит одному образу. Несколько совпадений — ошибка со списком кандидатов
(код 1), ни одного — код 4; в обоих случаях — подсказка `evo image list`.

```sh
evo vm create astra-1 --image 'Astra Linux SE 1.8' --dry-run
evo vm create astra-1 --image AstraLinuxSmolensk1.8.3KES
evo vm create web-1 --image Ubuntu-24.04 --port 80 --port 443
```

`--image-id <UUID>` работает, как раньше.

После согласия `vm create` показывает в stderr, что делает: «Создаю ВМ
web-1…», зарезервированный floating IP, принятый запрос с id ВМ, ожидание
(`ожидание ВМ… 1м20с (creating)` — той же строкой, что у `deploy`: в
терминале одной обновляемой строкой, без терминала — раз в 30 секунд и при
смене состояния), «ВМ активна», внешний IP, открытые порты и итог — имя,
зону, IP, сколько заняло, команду `ssh`. stdout — только ответ (таблица или
`--json`); с `--json` хода выполнения нет. Ждёт `vm create`,
как `deploy`, до 25 минут (`CLOUDRU_TIMEOUT`, секунды).

Под таблицей ответа — как войти на ВМ и где она записана:

```
SSH: ssh -i /home/me/proj/.evo/id_ed25519 -o UserKnownHostsFile=/home/me/proj/.evo/known_hosts -o StrictHostKeyChecking=accept-new user1@203.0.113.7
Пароль ВМ: <пароль> (записан только здесь — сохраните: evo его не хранит)
Ключ SSH и state — в /home/me/proj/.evo: evo status и evo vm delete запускайте из /home/me/proj.
```

ВМ получает ключ развёртывания evo из `.evo/id_ed25519` каталога, где
запущена команда, поэтому `ssh user1@<IP>` без `-i` пробует `~/.ssh/id_*` и
получает отказ — входите командой из ответа. Ключ хоста ВМ она проверяет по
`.evo/known_hosts` проекта: первое подключение его записывает, а запись
прежней ВМ на том же адресе (Cloud.ru выдаёт адреса повторно) evo удаляет,
как `deploy apply`. Строки `SSH:` нет у ВМ без внешнего IP и у ВМ со своим
ключом (`--meta public_key=…`) — тогда `ssh` настраиваете вы. Пароль, который
evo сгенерировал для образа, показывается один раз — в этом ответе (в
`--json` — поле `password`) — и больше нигде не хранится; заданный через
`--meta` пароль не показывается. Ключ и state лежат в `.evo` каталога
запуска: `evo status` и `evo vm delete` берут запись ВМ (её floating IP и
открытые порты) из state — запускайте их из того же каталога. В `--json` —
поля `ssh`, `password` и `state_dir`.

ВМ, созданная до Ctrl-C, по таймауту или в состоянии `error_creating`,
остаётся в облаке, оплачивается и записана в state; evo говорит, что дальше:

```
ВМ 4f1c… продолжает создаваться и оплачивается; проверить: evo vm get 4f1c…; удалить: evo vm delete 4f1c…
```

Повтор с тем же именем после Ctrl-C получит от Cloud.ru 409 «уже есть»: это
та самая ВМ — смотрите `evo vm get <имя>`.

Логин, SSH-ключ, пароль и имя хоста evo заполняет сам. Если у образа есть
обязательное поле, которое evo заполнить не может (в `image get` — «ВЫ:
обязательное»), значение передаётся флагом `--meta поле=значение` (можно
несколько раз):

```sh
evo vm create dash-1 --image OpensearchDashboards --meta opensearch_host=10.0.0.5
```

Без него `vm create` отказывает **до** создания чего-либо и называет поля.
Поле, которого у образа нет, — тоже ошибка со списком полей образа.
`--meta` перекрывает и то, что evo заполняет сам (например,
`--meta hostname=web-01`).

Пароль и другие секреты не пишите в командную строку: она остаётся в
истории оболочки и видна в списке процессов. `--meta поле=@файл` берёт
значение из файла, `--meta поле=-` — из stdin (так — только одно поле; без
терминала нужен `--yes`); завершающий перевод строки и BOM в начале файла
отрезаются, пробелы — часть значения, и с терминала тоже. Значение,
которое само начинается с `@` или равно `-`, тоже передаётся через файл.

```sh
evo vm create dash-1 --image OpensearchDashboards --meta opensearch_host=10.0.0.5 \
  --meta opensearch_password=@./opensearch.pass
pass show opensearch | evo vm create dash-2 --image OpensearchDashboards \
  --meta opensearch_host=10.0.0.5 --meta opensearch_password=- --yes
```

Так же — у секретов других команд: `evo secret create` и `add-version`
(`--value-file`), `evo pg user-create` (`--password-file`), `evo cert import`
(`--private-key-file`) берут значение из файла, `-` — из stdin, по тем же
правилам: инструмент получает то же значение, что из самого флага.

`--port` открывает входящие порты для `0.0.0.0/0` в группе безопасности ВМ
после её загрузки: `80`, `8080/tcp`, `53/udp`, можно через запятую. Группа
общая для всех ВМ в ней; `evo vm delete` (`destroy`) закрывает правила,
которые создал evo, и освобождает floating IP ВМ; оставить адрес —
`evo vm delete <ВМ> --release-ip=false`.

Цена: в расчёте цены API Cloud.ru образ маркетплейса стоит 0, но как
оплачивается лицензия продукта (например, Astra Linux), API не говорит —
вопрос открыт, условия смотрите в карточке продукта в маркетплейсе. Цена в
превью — ВМ, диск и floating IP без лицензии; для образа маркетплейса превью
добавляет об этом строку «лицензия» (раздел 8).

`deploy` (docker compose) — только для образов Ubuntu и Debian: Docker
ставится из apt-репозитория Docker (download.docker.com), а для Astra Linux,
Альт и РЕД ОС Docker пакетов не выпускает. На таких образах `deploy` (и
`evo init --image`) отказывает до создания ВМ — для них есть `evo vm create`. Образ для `deploy` задаётся в
`.evo.yaml` именем или UUID (`image: Ubuntu-24.04` или `image_id: <UUID>`;
`evo init --image debian-12` пишет имя так, как в каталоге), флагом
`evo deploy --image`; значения обязательных полей образа — в
`image_metadata:`:

```yaml
image: Ubuntu-24.04
image_metadata:
  hostname: web-01
```

## 7. Плагины Managed Kubernetes

В кластер Managed Kubernetes можно поставить плагин из каталога Cloud.ru:
ingress-контроллер, cert-manager, мониторинг, драйверы хранилищ и другие.
Каталог общий, его чтение ничего не меняет:

```sh
evo k8s addons                       # весь каталог: имя, отображаемое имя, категории, платный ли
evo k8s addons cert                  # поиск по имени, отображаемому имени и описанию
evo k8s addons --category Сети       # категории — как в консоли: Сети, Безопасность, Мониторинг…
evo k8s addon-versions cert-manager  # версии, поддержка, требования к кластеру
```

У каждой версии есть требования: подходящие версии Kubernetes (колонка
KUBERNETES, например `>=1.26.0-0`) и сколько готовых рабочих узлов нужно
(УЗЛОВ). Звёздочкой отмечена версия, которую `add-addon` ставит без
`--version`, — новейшая активная. Схема настроек версии — `--full` (с
`--json` — объектом JSON).

Установка — с подтверждением, как у других изменяющих команд:

```sh
evo k8s add-addon <id-кластера> cert-manager --dry-run     # превью: версия, требования, проверки кластера
evo k8s add-addon <id-кластера> cert-manager               # спросит подтверждение
evo k8s add-addon <id-кластера> cert-manager --version <версия из addon-versions> --config settings.json
```

`--config` — файл JSON с настройками по схеме версии (`-` — из stdin); в
значениях можно писать `{{clusterID}}`, `{{clusterName}}`,
`{{productInstanceID}}`, `{{nodeCIDR}}` и `{{serviceCIDR}}` — Cloud.ru
подставит их сам. Без `--config` API берёт последнюю конфигурацию плагина в
кластере (при первой установке — настройки по умолчанию). `--resolve-mode` решает, что делать с объектами плагина,
которые уже есть в кластере (поставлены вручную): `NONE` (по умолчанию) их не
трогает — установка тогда может не пройти; `OVERWRITE` откатывает их к
рекомендованным значениям.

Перед установкой evo сверяет версию Kubernetes кластера и число узлов в его
группах с требованиями версии. Если требование точно не выполнено, команда
откажет до подтверждения (код `1`) и подскажет, что делать; то, что
проверить не удалось, превью называет в строке «не проверено». Установка
асинхронная: команда отвечает статусом `installing`, поды плагина
появляются в его namespace по умолчанию (у cert-manager — `cert-manager`)
обычно за минуту-другую. Готовность — по подам:

```sh
evo k8s kubectl <id-кластера> get pods -n cert-manager    # или get pods -A
```

Готов плагин, когда его поды `Running` и в колонке READY все контейнеры
(условие `Ready=True`); поды задания (Job), например
`cert-manager-startupapicheck`, заканчиваются в `Completed`. Namespace из
ответа API evo не показывает: API повторяет в нём версию плагина. Если поды
остаются в `ImagePullBackOff`, у кластера, вероятно, нет выхода в интернет:
по [документации Cloud.ru](https://cloud.ru/docs/kubernetes-evolution/ug/topics/overview__limitations)
для этого нужен публичный SNAT-шлюз в зоне узлов (16.10.2026 в тестовом
проекте cert-manager встал и без него). Неизвестное имя плагина или
версии — код `4` и подсказка `evo k8s addons <подстрока>`. Удалить плагин
evo пока не умеет: это делается в консоли Cloud.ru, а с кластером
(`evo k8s delete`) плагин уходит сам.

### Витрина: образы и плагины одним списком

`evo marketplace list` показывает всё, что можно развернуть, одной
таблицей: образы ВМ общего каталога (ОС и продукты маркетплейса; образы
проекта — нет) и плагины Managed Kubernetes. Команда только читает; ставить
по-прежнему каждым своим деревом — у каждой строки в колонке «КАК
РАЗВЕРНУТЬ» готовая команда:

```sh
evo marketplace list                       # всё: ВИД, ИМЯ, ОТОБРАЖАЕМОЕ ИМЯ, КАК РАЗВЕРНУТЬ
evo marketplace list nginx                 # подстрока имени или отображаемого имени (у плагинов — и описания)
evo marketplace list --kind vm-app         # только продукты на ВМ; vm-os — ОС, k8s-addon — плагины
evo marketplace list astra --all           # со скрытыми образами, с пометкой
```

```text
ВИД        ИМЯ                 ОТОБРАЖАЕМОЕ ИМЯ  КАК РАЗВЕРНУТЬ
vm-os      Ubuntu-24.04        Ubuntu 24.04      evo vm create <имя-вм> --image Ubuntu-24.04
vm-app     nginx-ubuntu-22.04  Nginx             evo vm create <имя-вм> --image nginx-ubuntu-22.04
k8s-addon  cert-manager        Cert Manager      evo k8s add-addon <id-кластера> cert-manager
```

Строки идут по виду, внутри — по отображаемому имени; итог считает строки
каждого вида. Вид образа — **эвристика**: в каталоге такого поля нет. Тип
`public` — всегда `vm-os`; образ маркетплейса — `vm-os`, если его имя или
отображаемое имя начинается со слова семейства ОС (Ubuntu, Debian, CentOS,
Rocky, Alma, Fedora, openSUSE, Astra, Alt/Альт, RED OS/РЕД ОС, SberLinux,
ROSA/РОСА, Windows), иначе `vm-app`: `AstraLinuxSmolensk1.8.3KES` — ОС,
`nginx-ubuntu-22.04` — продукт на Ubuntu.

Образы скрываются, как в `image list`: недоступные проекту и не готовые ни
в одной зоне; итог называет обе причины, `--all` показывает их с пометкой
«недоступен проекту» или «не готов ни в одной зоне» вместо команды. Платен
ли плагин, видно в `evo k8s addons`; платна ли лицензия образа, API не
говорит: в расчёте цены любой образ стоит 0 (раздел 6). Если один из
каталогов не прочитан (например, недоступен Managed Kubernetes), витрина
показывает другой и печатает предупреждение; ошибка — только когда не
прочитан ни один.

## 8. Подтверждения

| Ситуация | Что происходит |
|---|---|
| В терминале | превью и вопрос; без согласия ничего не делается |
| `--dry-run` | только превью, код выхода `0` |
| `--yes` (`-y`) | согласие заранее — для скриптов и CI |
| Без терминала и без `--yes` | ничего не делается, код выхода `3` |

Коды выхода стабильны и пригодны для скриптов: `0` — успех, `1` — ошибка
использования, `2` — ключ или настройки, `3` — нужно подтверждение, `4` — не
найдено, `5` — ошибка API Cloud.ru ([exit-codes.md](exit-codes.md)). С `--json`
ошибка приходит объектом с кодом причины (`AUTH_FAILED`, `CONFIG_INVALID`, …).

### Цена в превью

Превью `vm create`, `deploy` и `deploy --dry-run` (и MCP `deploy_plan`,
`provision`, `deploy`) спрашивают цену у API расчёта цены Cloud.ru
(`POST /api/v1/projects/{project_id}/price-calculation`). Это только расчёт:
ничего не создаётся и не резервируется. Цена — за ВМ (flavor), загрузочный
диск и floating IP, за месяц и за час:

```text
  цена:       ~1308.16 RUB в месяц, 1.79 в час (ВМ 1022.00 + диск 140.16 + floating IP 146.00), по API расчёта цены Cloud.ru, а не счёт; без лицензии образа
```

Если API не ответил за 5 секунд, вернул ошибку или отказал (так отвечают,
например, два образа Astra Linux: `422 sku_identifier cannot be blank`, у них
нет SKU в биллинге), показывается **оценка** по встроенной таблице тарифов, как
раньше, и причина:

```text
  цена:       ~2184.00 RUB в месяц (вычисления 2044.00 + диск 140.00), оценка по тарифной карте evo, а не счёт
  цена API:   не получена (HTTP 422: sku_list[1]: (sku_identifier: cannot be blank.).), показана оценка
```

Оценка учитывает ВМ и диск, без floating IP; таблицу можно переопределить
файлом `~/.evo/pricing.json`. Ни один источник не включает **лицензию образа**:
API отвечает за любой образ 0, в том числе за образы маркетплейса (Astra
Linux KES). Для образа маркетплейса превью добавляет строку
`лицензия: образ маркетплейса: лицензии в цене нет …`. Новый диск оценивается по
той же таблице. Цену кластеров Kubernetes и PostgreSQL, групп узлов,
бакетов и расширения диска evo не рассчитывает: превью говорит, что ресурс
платный, и даёт ссылку на публичный тариф Cloud.ru (`цена: evo её не
рассчитывает, ресурс платный: тариф https://cloud.ru/documents/tariffs/evolution/…`;
в ответе MCP — `preview.tariff_url`). У плагина кластера своей цены нет: он
работает на узлах кластера, они оплачиваются по тарифу Managed Kubernetes.

## 9. Несколько проектов

Если ключ видит несколько проектов (ключ администратора организации):

- команды работают в проекте из профиля; посмотреть проекты и сменить
  проект профиля — `evo project list` и `evo project use <UUID или имя>`;
  другой проект на одну команду — `--project-id <UUID>`;
- если `./.evo.yaml` или `CLOUDRU_PROJECT_ID` подменяют проект профиля,
  команда предупреждает об этом;
- `evo whoami` показывает, откуда взят проект (профиль, переменная,
  `.evo.yaml`), и сколько проектов видит ключ;
- превью `deploy` и `destroy` называют проект и откуда он взят (профиль,
  `.evo.yaml`, переменная, флаг, запись развёртывания);
- развёртывание запоминает свой проект: `destroy` удаляет ресурсы там, где
  они созданы, а повторный `deploy` из того же каталога с другим проектом
  откажется, а не отправит приложение на чужую ВМ.

## 10. Подключить к AI-агенту

**Claude Code** (в каталоге проекта):

```sh
claude mcp add --transport stdio --scope project evo -- evo mcp
```

**Cursor** — файл `.cursor/mcp.json`, пример в [mcp.md](mcp.md#cursor).

Агент получает те же инструменты, что `evo tools list`, и тот же ключ, что
CLI. Изменяющий инструмент без `confirmed=true` возвращает превью — агент
должен показать его вам и вызвать повторно только после вашего согласия. Не
переводите клиента в режим «выполнять всё без вопросов» для изменяющих
инструментов.

Общий MCP-сервер по HTTP для команды (`evo mcp --http`), Docker-образ и
ограничения HTTP-режима — [mcp.md](mcp.md#streamable-http). Для общего сервера
берите ключ уровня проекта или ограничьте проекты флагом `--allow-project`.

## 11. Текущие ограничения

| Область | Ограничение |
|---|---|
| Образы | часть общего каталога недоступна проекту (16.10.2026 в тестовом проекте — все Astra Linux, Альт, РЕД ОС, SberLinux): `image list` их скрывает, создание ВМ из них отклоняется с кодом 4; как сделать образ доступным, не проверено (вероятно, подключить продукт в маркетплейсе) |
| `deploy` | только образы Ubuntu и Debian (Astra Linux, Альт, РЕД ОС — через `vm create`); нужен исходящий порт 22; на ВМ попадает только compose-файл (без `build:`, `.env`, локальных volumes); одно развёртывание на каталог |
| Зоны | состояние зон меняется; 15.10.2026 утром в ru.AZ-2 у новых ВМ не было DNS, вечером не создавались ВМ в ru.AZ-1. По умолчанию `init` берёт ru.AZ-2, если в ней есть подсеть проекта; не создаётся — смените зону (раздел 5) |
| Проекты | `configure` не показывает сервисному аккаунту список проектов — UUID вводится вручную; `evo project list` для такого ключа сообщает, что список недоступен, и показывает активный проект (код выхода 0) |
| Роли | минимальный набор ролей не опубликован Cloud.ru и не проверен; проверенный вариант — права на уровне проекта |
| Цены | цена ВМ — из API расчёта цены Cloud.ru, при его отказе — оценка по встроенной таблице; лицензия образа маркетплейса не входит ни туда, ни туда (API отвечает за образ 0); остальные ресурсы — оценка или без цены |
| Kubernetes | `k8s kubectl`/`apply`/`helm` требуют установленных `kubectl` и `helm`; на Windows — без гарантий; плагины: каталог, версии и установка (раздел 7), удаление — в консоли; поды плагина в `ImagePullBackOff` — вероятно, у кластера нет выхода в интернет (публичный SNAT-шлюз в зоне узлов) |
| Хранение ключа | файл с правами `0600` (на Windows — ACL); системное хранилище ключей (Keychain и др.) пока не поддерживается |
| Установка | для Windows нет установщика; бинарь macOS не нотаризован |
| Язык | CLI — на русском, справка инструментов MCP и их ответы — на английском; `EVO_LANG=en` переключает CLI на английский |
| Версия | `v1.x` — стабильная: ломающие изменения CLI (команды, флаги, коды выхода, `--json`) — только в major. Совместимость со старым именем `cloudru-vm` (alias, `.cloudru-vm.yaml`, каталоги `.cloudru-vm/`) — до v2.0, см. [rename.md](rename.md). Исключения: v1.1.0 и v1.2.0 меняют коды выхода и ответы там, где это исправление ошибки или безопасности, — см. «Миграция» в [CHANGELOG](../CHANGELOG.md) |

## 12. Если что-то не так

1. `evo doctor` — чаще всего он называет причину сам.
2. [troubleshooting.md](troubleshooting.md) — типовые ошибки по кодам.
3. Ошибка или отзыв об `evo` — в Telegram [@shatim](https://t.me/shatim) и в
   [чат тестировщиков](https://t.me/+SYvXziA4G9c1Y2Ni), ошибку можно завести и
   в [Issues](https://github.com/shatim-ops/evo-cli/issues);
   проблемы облака (квоты, ресурс в ошибке) — поддержка Cloud.ru.

К обращению приложите `evo version --json`, `evo doctor --json` (секретов там
нет), команду, её вывод с `--json` и код выхода. **Никогда не прикладывайте**
Key Secret, файлы из каталога настроек `evo` и содержимое `.evo/`.

## Шпаргалка

```sh
evo configure / whoami / doctor        # ключ, проект, зона, проверка окружения
evo vm list | disk list | k8s list     # что есть в проекте
evo image list <часть имени> / image get <имя>   # образы ВМ и их UUID
evo vm create <имя> --image <образ> [--meta поле=значение] [--port 80]   # ВМ из образа
evo k8s addons <часть имени> / k8s add-addon <кластер> <имя>   # плагины Kubernetes
evo marketplace list [часть имени] [--kind vm-os|vm-app|k8s-addon]   # витрина с командами развёртывания
evo <команда> --help                   # справка по команде
evo <команда> --json                   # вывод для скриптов
evo <команда> --dry-run                # только превью
evo init → deploy → verify → logs → destroy   # compose на ВМ
evo project list / project use <UUID>  # проекты ключа и проект профиля
evo --project-id <UUID> <команда>      # другой проект на одну команду
evo mcp                                # MCP-сервер для агента
```
