# Типовые проблемы

Первое, что стоит запустить при любой проблеме:

```sh
# конфиг, права файлов, откуда взята каждая настройка, IAM/Compute API, ключ, kubectl/helm
evo doctor
# принимает ли IAM ключ, какой проект выбран
evo whoami
```

Коды выхода — в [exit-codes.md](exit-codes.md).

Сообщения ниже — как их печатает CLI по-русски (по умолчанию). С
`EVO_LANG=en` и в ответах MCP-сервера они английские — английский вариант
указан в скобках; символьные коды (`AUTH_FAILED`) одинаковы в обоих языках,
в JSON они в поле `reason`.

## Ключ и права

### `AUTH_REQUIRED` (код 2): «не задан ключ доступа Cloud.ru» (Cloud.ru credentials not set)

Ключ не найден ни в переменных, ни в профиле. `evo configure` или
`CLOUDRU_KEY_ID` + `CLOUDRU_SECRET`. Если вы задали `--profile` /
`CLOUDRU_PROFILE` — проверьте `evo configure list`: профиль из другого
`CLOUDRU_CONFIG_DIR` не виден.

Частый случай — в окружении задана только одна переменная из пары:
`CLOUDRU_SECRET` без `CLOUDRU_KEY_ID` (или наоборот). Пара из окружения
берётся целиком и заменяет ключ профиля, даже если вторая половина пуста:
смешивать Key ID из окружения с секретом из профиля evo не станет — IAM
отклонил бы такую пару без понятной причины. Поэтому ключ профиля не
используется, и ответ — `AUTH_REQUIRED`, а не `AUTH_FAILED`. Так задумано.
Задайте обе переменные или уберите обе (`unset CLOUDRU_KEY_ID
CLOUDRU_SECRET`) — тогда возьмётся профиль. Признак: `evo doctor` пишет
«ключ доступа не задан», хотя `evo configure list` показывает у профиля и
Key ID, и секрет; имена заданных переменных (без значений) покажет
`env | grep -o '^CLOUDRU_[A-Z_]*'`.

### `AUTH_FAILED` (код 2): «IAM отклонил ключ доступа (статус 401/403)» (IAM rejected the credentials)

IAM не принял пару Key ID / Key Secret:

- опечатка или пробел в секрете — введите заново через `evo configure`;
- ключ удалён или истёк его срок жизни (задаётся при создании) — создайте
  новый ([auth.md → ротация](auth.md#ротация-ключа));
- сервисный аккаунт выключен;
- в окружении заданы `CLOUDRU_KEY_ID` и `CLOUDRU_SECRET` от другого ключа —
  они важнее профиля, и ключ профиля не используется вовсе: `evo doctor`
  покажет `key_id из env`. Если задана только одна из них, ответ —
  `AUTH_REQUIRED` (см. выше).

### `403 Forbidden` от сервиса (код 5)

Ключ принят, но у сервисного аккаунта нет прав на операцию в этом проекте
(или `project_id` — чужой проект); подсказка к ошибке говорит то же. Ответ
`401` того же сервиса — другое: токен не принят, ключ мог быть удалён или
истечь (подсказка — `evo doctor`, `evo configure`). Проверьте роли аккаунта в проекте
(«Пользователи» → «Сервисные аккаунты»). Точный минимальный набор ролей не
опубликован и не проверен — см. [auth.md → роли](auth.md#3-роли); на
аккаунте с правами на уровне проекта весь сценарий `deploy` работает.

У compute API (ВМ, диски, `deploy`, `destroy`) тот же отказ приходит как
`AUTH_FAILED: access denied (403)` с кодом `2`.

### `CONFIG_INVALID` (код 2): «не задан проект (project_id)» (no project is set)

Ключ задан, а проект — нет. Команды и инструменты, которые работают с
ресурсами проекта (`vm list`, `deploy`, `k8s list`, `pg create`, плагины
Kubernetes и др.), отказывают ещё до запроса в облако; `evo doctor` в этом
случае тоже выходит с кодом 2. Каталоги работают и без проекта:
`evo vm zones`, `evo image list`, `evo vm flavors`.

UUID проекта — в консоли Cloud.ru, в сведениях о проекте
([auth.md → UUID проекта](auth.md#4-uuid-проекта)). Задать его можно тремя
способами:

```sh
# в профиль
evo configure --project-id <UUID>
# на сеанс или в CI
export CLOUDRU_PROJECT_ID=<UUID>
# сменить проект текущего профиля
evo project use <UUID|имя>
```

### `configure` не показывает проекты: «Список проектов этому ключу недоступен» (The project list is not available to this key)

Ожидаемо для сервисного аккаунта: Organization API не отдаёт ему список
проектов (ответ `400` «user not found», проверено 14.10.2026). Введите UUID
проекта вручную или передайте `--project-id`. На ключ это не влияет — он уже
проверен до запроса списка. Сам ответ API показывает `--verbose`. До v1.0.1
здесь печаталось «Не удалось получить список проектов (…)».

ID проекта — только UUID (вида `00000000-0000-4000-8000-000000000001`): другой
текст `configure` не сохранит и спросит снова, а с `--project-id` ответит
`CONFIG_INVALID` (код 2). Проект по имени выбирает `evo project use <имя>`,
если ключу доступен список проектов.

### «CLOUDRU_API_KEY=keyId:secret устарел» (is deprecated)

Предупреждение, не ошибка. Замените на `CLOUDRU_KEY_ID` и `CLOUDRU_SECRET`
или на профиль.

### `legacy config` в `doctor`

Найден `~/.cloudru-vm.yaml` от старых версий — он больше не читается.
Перенесите значения: ключ и проект — `evo configure`, настройки проекта —
`./.evo.yaml` (`evo init`). Потом удалите старый файл.

### «используется старый каталог …/.cloudru-vm», «читается старый …/.cloudru-vm.yaml» (using the legacy directory, reading the legacy)

Проект развёрнут версией, которая называлась `cloudru-vm`. Предупреждение, не
ошибка: `evo` работает в старом каталоге — state с ВМ и SSH-ключ там. Когда в
этом каталоге не работает старая версия (в том числе MCP-сервер со старым
бинарём), переименуйте: `mv .cloudru-vm .evo && mv .cloudru-vm.yaml .evo.yaml`.
С v2.0 старые имена читаться не будут.

«state есть и в …, и в …» (both … and … have state) — есть оба каталога и в обоих `state.json`: `evo`
читает `./.evo/`, а ВМ из `./.cloudru-vm/state.json` не видит. Проверьте их
(`jq .deployments .cloudru-vm/state.json`) и удалите старой версией или в
консоли, прежде чем удалять каталог.

## Создание и удаление ВМ

### `CONFIG_INVALID` (код 2): «не задана зона доступности (region)» (no availability zone is set)

`evo vm create` (и MCP `provision`) не знает, в какой зоне создать ВМ: у
профиля нет зоны, `--region` не передан, `CLOUDRU_REGION` не задан. Так
бывает с профилем, созданным `evo configure` до 1.2.1, — тогда он зону не
спрашивал. Команда отказывает сразу, до превью и вопроса о согласии; ничего не
создаётся. Зону evo сам не выбирает.

```sh
# зоны: имена и UUID, какие открыты для новых ресурсов
evo vm zones
# зона для одной команды: имя или UUID
evo vm create my-vm --image Ubuntu-24.04 --region ru.AZ-2
# или один раз — в профиль (сохраняется UUID)
evo configure --region ru.AZ-2
```

Значение без флага (`evo vm create my-vm ru.AZ-2`) — лишний аргумент:
«лишние аргументы: "ru.AZ-2" — пропущен флаг?», код 1. Неизвестное имя зоны —
`USAGE` (код 1) со списком зон. Без образа — `USAGE` (код 1): «не задан образ»,
передайте `--image` (список — `evo image list`). Зону по имени понимают
`evo vm create`, `evo configure --region`, MCP `provision` и стеки;
`evo deploy --region` по-прежнему ждёт UUID и на имя отвечает подсказкой с ним.

### ВМ уходит в `error` / `error_creating`

14.10 и вечером 15.10.2026 в зоне **ru.AZ-1** новые ВМ уходили в
`error_creating` или по 20 минут висели в `creating`. Возьмите другую зону,
например **ru.AZ-2** (её `evo init` выбирает по умолчанию, если в ней есть
подсеть проекта; нет — создайте подсеть в этой зоне в консоли):

```sh
# ID и имена зон
evo vm zones
# или region: в .evo.yaml
evo deploy --region <UUID ru.AZ-2>
```

ВМ в ошибке удалите (`evo destroy` или `evo vm delete <id>`),
чтобы она не занимала квоту.

### `destroy` ждёт: «ВМ … пока нельзя удалить» (VM cannot be deleted yet)

ВМ, которая ещё создаётся (`creating`) или меняет состояние, Cloud.ru удалить
не даёт — API отвечает `409`/`422`. `evo destroy` в этом случае ждёт до
10 минут и повторяет удаление сам, раз в минуту сообщая состояние ВМ. Если
ВМ так и не стала удаляемой, `destroy` выходит с ошибкой, а запись в
`.evo/state.json` остаётся: повторите `evo destroy` позже (проверить ВМ —
`evo vm get <id>`). ВМ без записи (скрипт потерял каталог) удалите
`evo vm delete <id>`: floating IP ВМ освобождается вместе с ней
(`--release-ip=false` — оставить). Удалили в консоли — освободите IP
сами: `evo vpc fip-release <IP>`.

### `destroy`: «Cloud.ru принял удаление ВМ …, но … она всё ещё есть» (code 5, MCP `status: partial`)

Удаление принято облаком, но за 2 минуты ВМ не исчезла из списка. Это не
ошибка evo: Cloud.ru иногда удаляет ВМ дольше. Пока ВМ существует, она и её
floating IP оплачиваются, поэтому не откладывайте повтор. Пока ВМ может существовать,
evo не освобождает её floating IP и не закрывает порты, а запись в
`.evo/state.json` остаётся со статусом `destroying` — не трогайте её.
Проверьте ВМ (`evo vm get <id>`) и повторите `evo destroy` (у MCP —
`destroy` с тем же `vm_id`, и с `release_ip=false`, если адрес нужно
оставить): когда ВМ исчезнет, повтор освободит IP и закроет порты.

### `vm create` / MCP `provision`: `status: partial`, «ВМ работает, публичный IP не привязан»

ВМ создана и записана, но floating IP к ней не привязался (код 5, строки
`SSH: ssh user@IP` в ответе нет). Привяжите адрес (`evo vpc fip-attach` /
MCP `fip_attach`) или удалите ВМ (`evo destroy` / `vm delete`): созданный
floating IP записан и освободится вместе с ней.

### `deploy`, `vm create`: «ВМ … не стала активной за 25m0s» (did not become active within)

Новая ВМ создаётся несколько минут; 15.10.2026 в ru.AZ-1 это занимало около
5 минут, в октябре 2026 там же — до 20 минут. `deploy`, `vm create` и MCP
`provision` ждут 25 минут (`CLOUDRU_TIMEOUT`, секунды). ВМ после этого
продолжает создаваться и оплачивается; она уже записана в state, так что
`evo destroy` (или `evo vm delete <id>`) её удалит. Проверить её —
`evo vm get <id>`; ждать дольше — задайте `CLOUDRU_TIMEOUT`.

### Порты в группе безопасности после `destroy`

`deploy` открывает порты из `ports:` compose-файла правилом в **общей группе
безопасности зоны** (входящий TCP/UDP с `0.0.0.0/0`, описание
`evo: port N`) и записывает в `.evo/state.json` id группы и
id правил, которые создал сам. Правило, которое уже было в группе до
`deploy`, своим не считается и не удаляется. `destroy` удаляет свои правила
**после** удаления ВМ (если ВМ удалить не удалось, приложение продолжает
работать вместе с портами). Правило остаётся, если тот же порт в той же
группе нужен другому развёртыванию из этого же `state.json`.

Группа общая: ВМ, развёрнутая из **другого** каталога, могла полагаться на
правило, которое создал этот `deploy`, — превью `destroy` об этом
предупреждает. После такого `destroy` выполните в том каталоге
`evo deploy --force`: повторный `deploy` открывает недостающие порты.

Если правило удалить не удалось (например, оно ещё в состоянии `creating`),
`destroy` завершается успешно с предупреждением, а запись остаётся в
`state.json` со статусом `destroyed` и ошибкой у правила (`delete_error`).
Повторный `evo destroy` доудаляет правила. Посмотреть правила групп:

```sh
evo tools call list_security_groups --arg rules=true --json
```

Развёртывания, записанные версиями до этой, id правил не хранят: их правила
удалите вручную в консоли (группы безопасности VPC).

### «у ВМ нет внешнего IP-адреса» (VM has no public IP address)

Floating IP не назначился (квота на публичные IP, временная ошибка API).
Проверьте квоты (ниже), назначьте IP в консоли или выполните `destroy` и
`deploy` заново.

### Прерванный `deploy` (Ctrl-C, код 130)

Если ВМ уже создана, команда спросит, удалить ли её (в терминале), или
напишет её ID и команду для удаления. ВМ продолжает тарифицироваться, пока
вы её не удалите.

### `deploy`: «в этом каталоге уже есть развёртывание … в проекте A, а не в B» (this directory already has deployment)

Развёртывание запоминает проект, в котором создана ВМ (`project_id` в
`.evo/state.json`). Если ключ видит несколько проектов (например, ключ
администратора организации) и сейчас выбран другой проект, `deploy` не
отправит compose-файл на ВМ чужого проекта. Обновите развёртывание в его
проекте (`evo deploy --project-id <A>`) или удалите его (`evo destroy`) и
разверните заново в новом проекте. `destroy` всегда работает в проекте из
записи, какой бы проект ни был выбран сейчас. Записи старых версий проекта
не хранят — для них используется проект из настроек, как раньше.

## Квоты и лимиты

### Не хватает квоты

Ошибка API с текстом про квоту/лимит (код 5). Текущие лимиты и использование:

```sh
evo org quotas
```

Увеличение квоты — через поддержку Cloud.ru.

### `API_RATE_LIMITED` (код 5), HTTP 429

Cloud.ru ограничил частоту запросов. Запросы к compute повторяются с
нарастающей паузой сами; если ошибка дошла до вас, подождите минуту и
повторите. В скриптах не запускайте много команд параллельно.

### `API_UNREACHABLE` (код 1)

Нет связи с `*.api.cloud.ru`: сеть, DNS, прокси. `evo doctor`
покажет, какие API недоступны. Обрывы бывают и разовыми (при облачной
приёмке `list-zones` из контейнера падал так примерно в одном запуске из
трёх) — повторите команду.

### Прокси и сертификаты

Все запросы evo к Cloud.ru идут через прокси из окружения: `HTTPS_PROXY`
(или `HTTP_PROXY`), исключения — в `NO_PROXY`. Подсказка к
`API_UNREACHABLE` называет причину, если она понятна:

- «Запрос шёл через прокси `<адрес>` … и не прошёл» — прокси не отвечает или
  отказал (например, `407 Proxy Authentication Required`). Проверьте адрес
  и доступ; логин и пароль прокси evo в сообщениях не печатает.
- «Сертификат TLS у `iam.api.cloud.ru` не прошёл проверку (x509: certificate
  signed by unknown authority)» — обычно корпоративный прокси, который
  проверяет HTTPS и показывает свой сертификат. Добавьте его корневой
  сертификат (выдаёт ИТ-отдел): в Linux — `export SSL_CERT_FILE=/путь/к/ca.pem`
  (файл с корнем прокси и обычными корнями) или `SSL_CERT_DIR`; в macOS — в
  «Связку ключей» (System), в Windows — в хранилище «Доверенные корневые
  центры сертификации». Отключить проверку TLS в evo нельзя. Такой запрос
  не повторяется: сертификат от повтора не изменится.
- «В системе не найдены корневые сертификаты» — минимальный образ
  контейнера: установите `ca-certificates` (`apt-get install ca-certificates`,
  `apk add ca-certificates`) или задайте `SSL_CERT_FILE`.
- «Имя … не найдено в DNS» без прокси — сеть, где наружу можно только через
  прокси: задайте `HTTPS_PROXY`.

`evo doctor` в строках IAM API и Compute API пишет ту же подсказку.

## SSH и `deploy`

### `SSH_TIMEOUT`: не удаётся подключиться к ВМ

`deploy` ставит Docker и загружает compose-файлы по SSH **с вашей машины**.
Нужен **исходящий доступ к порту 22** публичного IP ВМ. Корпоративные сети и
VPN часто его закрывают — запустите с другой сети или с ВМ/раннера, где
порт 22 открыт наружу. Проверка: `nc -vz <IP> 22` (IP — в `evo status`).
Сразу после создания ВМ SSH поднимается не мгновенно; `deploy` ждёт и
повторяет подключение сам.

Новая ВМ обычно отвечает по SSH за 2–5 минут. Если дольше, `deploy` один раз
пишет, почему ещё ждёт, и продолжает попытки (на новой ВМ — 60, до
15 минут). Если SSH так и не ответил, ошибка начинается с диагноза по
последней попытке:

- **порт 22 не отвечает совсем** (таймаут) — сеть ВМ не поднялась при
  загрузке или пакеты отбрасываются по пути: межсетевой экран или VPN на
  вашей стороне, группа безопасности ВМ;
- **connection refused** — ВМ работает, но sshd не запущен: первая
  загрузка (cloud-init) зависла или ещё идёт;
- **EOF, connection reset** — sshd принимает подключение и обрывает его:
  ещё запускается или загрузка зависла.

Если порт 22 у вас открыт, а ВМ активна, но SSH не отвечает 15–20 минут
(или «Docker на ВМ … не готов» / `Docker is not ready` с
`Temporary failure in name resolution` в выводе), — первая загрузка образа не вышла в сеть: внутри ВМ нет DNS,
зеркало apt образа недоступно, и cloud-init образа задерживает или не
запускает sshd. Это сеть зоны или подсети, а не проект. Что можно сделать:

1. Повторить `evo deploy` через несколько минут — он возьмёт ту же ВМ; к ВМ,
   до которой SSH ещё ни разу не дошёл, — 30 попыток.
2. Перезагрузить ВМ в консоли Cloud.ru («Виртуальные машины» → меню ВМ →
   «Перезагрузить», [документация](https://cloud.ru/docs/virtual-machines/ug/topics/guides__restart))
   и снова `evo deploy`; журнал загрузки виден в серийной консоли ВМ. Своей
   команды перезагрузки в evo нет, и сам evo ВМ не перезагружает и не
   пересоздаёт.
3. `evo destroy` и `deploy` заново, при повторе — в другой зоне
   (`evo deploy --region …`, список — `evo vm zones`): на практике так
   вели себя ВМ одной зоны, а в соседней тот же сценарий проходил целиком.
   Если повторяется в одной зоне — проверьте DNS подсети в консоли Cloud.ru.

Проверьте и группу безопасности ВМ (`deploy` предупреждает об этом до
вопроса): нужны входящее правило TCP 22 и исходящий системный трафик — весь
исходящий или хотя бы сервис метаданных `169.254.169.254/32` и UDP 67 до
шлюза подсети. Без них ВМ не получит IP по DHCP, cloud-init не запустится,
SSH не поднимется ([документация](https://cloud.ru/docs/security-groups/ug/topics/overview__limitations),
требование с 07.2026). У группы зоны по умолчанию `SSH-access_<зона>` эти
правила есть, если их не меняли.

### «Docker на ВМ … не готов» (`Docker is not ready`): apt-зеркало образа

`deploy` ставит Docker на Ubuntu и Debian из apt-репозитория Docker
(`download.docker.com`, ключ подписи Docker встроен в evo), остальные
пакеты — из apt-источников образа. У образов Cloud.ru это зеркало
платформы, и с новой ВМ оно часто не отвечает:
`W: Failed to fetch https://repo.mng.sbercloud…`. Тогда evo:

1. если настройка зеркала при первой загрузке не завершилась, запускает её
   ещё раз (bootcmd cloud-init образа);
2. если apt всё равно не скачивает — ставит Docker с официального зеркала
   дистрибутива по HTTPS: `archive.ubuntu.com` и `security.ubuntu.com`
   (на arm64 — `ports.ubuntu.com`), `deb.debian.org`. В выводе —
   строка `evo: switching apt to the official mirror…`.

Подписи apt проверяет у всех источников, как обычно; официальное зеркало
привязано к ключам дистрибутива (`signed-by` с файлом из
`/usr/share/keyrings`), и если этого файла на ВМ нет, на официальное
зеркало evo не переходит. Источники образа evo не меняет — запасные лежат
отдельно, в `/var/lib/evo/apt`, и используются только для установки
Docker; символическую или жёсткую ссылку на месте
`/etc/apt/sources.list.d/docker.list` или `/etc/apt/keyrings/docker.asc`
evo удаляет и пишет новый файл, а не пишет по ссылке. Повторная попытка и повторный `deploy` на ту же ВМ сразу идут на
официальное зеркало. У apt короткие таймауты (20 с на соединение, две
повторные попытки), поэтому мёртвое зеркало обнаруживается за десятки
секунд; всего установка Docker ждёт до 15 минут. Завершения первой загрузки
(`cloud-init status --wait`) установка ждёт не больше 10 минут, затем идёт
дальше: блокировку apt, если cloud-init её ещё держит, apt ждёт сам.

Ошибка называет причину:

- «apt не справился ни с зеркалом образа, ни с официальным зеркалом» — у ВМ,
  скорее всего, нет выхода в интернет: проверьте исходящие правила группы
  безопасности и подсеть, или удалите ВМ и разверните в другой зоне;
- «apt не справился с репозиторием Docker download.docker.com» — пакеты
  дистрибутива скачиваются, а репозиторий Docker не отвечает или его
  подпись не сходится (строки apt в выводе говорят, что именно): повторите
  позже;
- «ВМ не разрешает имена» — внутри ВМ нет DNS (см. выше);
- «apt-зеркало образа не работает, а на ВМ нет keyring дистрибутива»
  (`evo: no keyring of the distribution…`) — проверить официальное
  зеркало нечем, и evo с него не ставит; повтор не поможет, ошибка приходит
  сразу. Разверните из стандартного образа Ubuntu или Debian или верните
  на ВМ пакет `ubuntu-keyring` / `debian-archive-keyring`.

На RPM-дистрибутивах (`ID` в `/etc/os-release` — `centos`, `rhel`,
`fedora`, `rocky`, `almalinux`, или `ID_LIKE` содержит `rhel` либо `fedora`)
Docker по-прежнему ставится скриптом `get.docker.com`, без запасного
зеркала: `curl -fsSL https://get.docker.com | sh`. На остальных
дистрибутивах (Alpine, Arch, openSUSE и др.) установка отказывает сразу:
«Docker install is supported on Ubuntu, Debian and RPM-based
distributions» — разверните из образа Ubuntu или Debian. Скрипт
скачивается только по TLS, но подписи у него нет: целостность держится на
сертификате `get.docker.com`. Если это не подходит, берите образ, где
Docker с `docker compose` уже установлен (тогда evo установку пропускает),
или образ Ubuntu/Debian: там пакеты проверяются подписью репозитория.

### `SSH_AUTH_FAILED`

SSH-ключ к ВМ лежит в `./.evo/id_ed25519` **каталога, из которого
делался `deploy`**. Запуск `status`, `logs`, `deploy` из другого каталога или
после удаления `.evo/` — это другой ключ, и ВМ его не примет.
Вернитесь в исходный каталог (или восстановите `.evo/`). Если ключ
потерян — `destroy` и новый `deploy`.

### `CONFIG_INVALID` (код 2): «НЕЗАЩИЩЁННЫЙ ЗАКРЫТЫЙ КЛЮЧ» (UNPROTECTED PRIVATE KEY FILE)

На Linux и macOS evo не использует ключ деплоя `./.evo/id_ed25519`, если его
могут читать группа или другие пользователи (как OpenSSH). evo сам создаёт
ключ с правами `0600`, поэтому ключ с `0644` обычно пришёл вместе с
репозиторием (`git clone` шаблона, где `.evo/` закоммичен): его открытая
половина попала бы в `authorized_keys` новой ВМ, и войти на неё смог бы
автор шаблона. Удалите `.evo/` — evo создаст новый ключ. Если ключ ваш (его
права сбились при копировании), верните права: `chmod 600 .evo/id_ed25519`.

### `SSH_HOST_KEY_CHANGED`

Первое подключение к новой ВМ — по доверию (TOFU): ключ хоста не с чем
сверить, и evo принимает тот, что ВМ показала, и закрепляет его отпечаток
(в state развёртывания для `deploy` CLI и MCP, в `./.evo/known_hosts` для
MCP `deploy_apply` и команды `ssh` из его ответа). Дальше каждое подключение
сверяется с закреплённым. Подмену ключа на самом первом подключении это не
ловит: она возможна, только если кто-то перехватывает трафик между вами и
публичным IP новой ВМ.

Ключ хоста ВМ не совпал с сохранённым при первом подключении. Обычно IP
достался другой ВМ (ВМ пересоздали вне evo). Если вы уверены, что это
ваша ВМ, — `destroy` и `deploy` заново; иначе не подключайтесь.

### `deploy` отвечает «Compose-файл не изменился», хотя приложение не запущено

Если `docker compose up` упал, запись остаётся в состоянии `running`, а хэш
compose-файла не изменился. Повторите с `evo deploy --force`.

### `verify`: `UNHEALTHY` (код 1)

Порт приложения не ответил снаружи: соединение не принято, не дождались
ответа или HTTP-сервис ответил кодом 4xx/5xx. Порт, который принимает
соединение, но говорит не по HTTP (база, кэш), считается здоровым — в
таблице `tcp открыт` (`tcp open`). Проверьте `evo logs`, что контейнер слушает `0.0.0.0`,
и что порт открыт в группе безопасности (`deploy` открывает только порты из
`ports:`).

## Kubernetes, S3

- `kubectl not found on the host` / `not available in this mode` — установите
  `kubectl`/`helm` ([install.md](install.md#kubectl-и-helm)); в Docker-образе
  их нет.
- `S3 credentials not configured` (код 2) — задайте ключи Object Storage
  (`CLOUDRU_S3_ACCESS_KEY`, `CLOUDRU_S3_SECRET_KEY` или секция `s3` профиля,
  [auth.md](auth.md#ключи-object-storage-s3)).
- Биллинг (`billing_*`), код 2, `reason: CONFIG_INVALID`: «не задан ни
  проект, ни договор» — задайте проект (`CLOUDRU_PROJECT_ID`, аргумент
  `project_id`), чтобы считать расход проекта, или `CLOUDRU_AGREEMENT_ID`
  для всего договора; «для баланса нужен договор» — `billing_balance`
  работает только с `CLOUDRU_AGREEMENT_ID`, баланса по проекту в API нет.
- Биллинг, код 5, «нет доступа к потреблению проекта» (HTTP 403) — у
  сервисного аккаунта нет роли администратора проекта
  (`platform.project.admin`); по договору нужны роли администратора
  организации или администратора затрат
  ([документация](https://cloud.ru/docs/billing/ug/topics/api-ref_start)).

## MCP-сервер

- `401 Unauthorized` от `evo mcp --http` — клиент не прислал заголовок
  `Authorization: Bearer <токен>` или токен не совпал с `MCP_BEARER_TOKEN`
  сервера целиком (лишний пробел, перевод строки, кавычки). Проверьте
  заголовок в конфигурации клиента и переменную на сервере
  ([mcp.md](mcp.md#streamable-http)).
- `… is refused: this server runs with --read-only` (`reason: USAGE`) —
  сервер запущен с `--read-only` и не выполняет вызовы, которым нужно
  согласие: изменения в облаке, `secret_value`, `cert_private_key`. Чтения
  работают; для изменений оператор перезапускает сервер без флага
  ([mcp.md](mcp.md#только-чтение---read-only)).
- Агент сообщает о тайм-ауте вызова, а ресурс в облаке создаётся или
  операция идёт — клиент прервал ожидание раньше инструмента (часто через
  60 с). Увеличьте тайм-аут вызова в настройках клиента
  ([mcp.md](mcp.md#автономный-агент-только-на-чтение)).

## Обращение в поддержку

Ошибки evo — в [Issues](https://github.com/shatim-ops/evo-cli/issues)
репозитория; проблемы самого облака (квоты, ресурсы в ошибке, биллинг) — в
[поддержку Cloud.ru](https://cloud.ru/docs/evolution/overview/contacts/technical-support).

Приложите:

1. `evo version --json`;
2. `evo doctor --json` — Key ID в нём маскирован, секретов нет;
3. точную команду, её вывод с `--json` и код выхода (`echo $?`);
4. время (с часовым поясом), зону, ID ВМ или ресурса (`evo status --json`).

**Не прикладывайте**: Key Secret, `credentials.yaml`, `CLOUDRU_SECRET`,
`MCP_BEARER_TOKEN`, ключи S3, содержимое `.evo/` (там приватный
SSH-ключ к вашим ВМ), kubeconfig со встроенным токеном. Если секрет всё же
попал в сообщение — удалите ключ в консоли и создайте новый.
