# Журнал изменений

Формат — [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/), версии —
[Semantic Versioning](https://semver.org/lang/ru/). Здесь — изменения, которые
видит пользователь CLI и MCP; внутренние (тесты, cloud-e2e, api-probe,
документы для разработки) не перечислены.

## [Не выпущено]

### Изменено

- `deploy` ставит Docker на Ubuntu и Debian из apt-репозитория Docker (`download.docker.com`) с ключом подписи, встроенным в evo, а не скриптом `curl https://get.docker.com | sh`. Набор пакетов тот же: `docker-ce`, `docker-ce-cli`, `containerd.io`, `docker-buildx-plugin`, `docker-compose-plugin`. На других ОС (CentOS, Fedora) — `get.docker.com`, как раньше.
- Ожидание установки Docker на ВМ — до 15 минут вместо 10: в него теперь входит переход на запасное зеркало.

### Исправлено

- `ca_logs` читал одну страницу логов без `pageSize` и оставлял последние 100 строк этой страницы по позиции: при пустой первой странице (так без `pageSize` отвечают другие списки Cloud.ru) ответ был `{"logs":[]}`, а при длинном логе «последние» строки могли оказаться старыми; системные логи обрезались так же. Теперь логи приложения читаются по страницам (`pageSize=100`, `pageToken`, не больше 50 страниц, конец — на пустой или повторной странице), и `ca_logs` отдаёт последние 100 строк по времени, старые первыми. Пустой ответ объясняет, что считается логами приложения (stdout/stderr контейнера) и что делать дальше (`note`); если лог не прочитан целиком — `truncated: true` (найдено живым прогоном 18.10: 0 строк после обслуженных запросов; [break-98] L-1).
- `deploy` падал с «Docker на ВМ … не готов», когда apt-зеркало образа не отвечало с новой ВМ (`W: Failed to fetch https://repo.mng.sbercloud…` — в живых прогонах 16–18.10 в 2–4 запусках из 10). Теперь apt ходит с короткими таймаутами, а если зеркало образа не отвечает, Docker ставится с официального зеркала дистрибутива по HTTPS (`archive.ubuntu.com`, `deb.debian.org`) с обычной проверкой подписей; источники apt образа не меняются. Ошибка различает «нет выхода в интернет» (не ответили оба зеркала) и сбой репозитория `download.docker.com`.
- SSH к ВМ, который так и не поднялся (`SSH_TIMEOUT`, 3 из 10 прогонов 18.10): ошибка теперь называет, что было с портом 22 (не отвечает совсем, connection refused, обрыв до входа), и подсказывает перезагрузить ВМ в консоли Cloud.ru и повторить `deploy`. После 5 минут ожидания `deploy` один раз объясняет, почему ещё ждёт. Повторный `deploy` к ВМ, до которой SSH ни разу не дошёл, ждёт 30 попыток, а не 12. Сам evo ВМ не перезагружает и не пересоздаёт.
- Отказ `deploy` на Astra Linux, Альт и РЕД ОС говорит, что Docker не выпускает для них пакетов, а не ссылается только на `get.docker.com`.
- `billing_consumption` (и `evo tools call billing_consumption`) без `CLOUDRU_AGREEMENT_ID` отказывал ещё до запроса (`CONFIG_INVALID`), а ID договора видят только администратор организации и администратор затрат — ключ уровня проекта расход не видел. Теперь без договора потребление читается по проекту (`project_ids`: аргумент `project_id` или проект конфигурации) — так [документация](https://cloud.ru/docs/billing/ug/topics/api-ref_start) разрешает администратору проекта (`platform.project.admin`); с договором — как раньше. В ответе новые поля: `scope` (`agreement` или `project`), `project_id`/`agreement_id` и `vat` — `total` без НДС (сумма `amount`), `total_with_nds` с НДС (`amount_nds`). Тариф `cost` больше не подставляется вместо отсутствующей `amount`. 403 по проекту — `API_ERROR` (код 5) с подсказкой о роли; нет ни договора, ни проекта — `CONFIG_INVALID` (код 2) с обоими вариантами (BIL-5).
- `billing_finops` суммировал `cost` — по спецификации это тариф (цена единицы), а не стоимость строки. Теперь `amount` (без НДС), как `billing_consumption`; без договора отчёт строится по проекту, баланс и запас дней — `null` с пояснением в `balance_error`.
- `billing_balance` без договора — по-прежнему отказ `CONFIG_INVALID` (баланса по проекту в API нет), но подсказка объясняет, кто видит ID договора, и называет `billing_consumption` для расхода проекта.

## [1.0.4] — 2026-10-19

### Изменено

- Обратная связь — по трём формам Issues: «Ошибка CLI» (теперь спрашивает ОС, окружение, область, где, по-вашему, проблема — в CLI или в платформе, и не остался ли платный ресурс), «Идея, неудобство или вопрос» и «Чек-ин» для участников догфуда. Метки области, ОС, платформы и денег ставятся по ответам автоматически.

### Исправлено

- Kubernetes (`k8s_kubectl`, `k8s_apply`, `k8s_helm` и др.): один ответ 502/503/504 шлюза IAM при обмене токена кластера (`OIDC token HTTP 502: <html>…`) сразу давал ошибку. Теперь обмен повторяется до 3 раз, как получение токена IAM; ответ 4xx — сразу ошибка (найдено живым прогоном 18.10).
- `stack_destroy`, вызванный повторно (как советует его ответ, пока ресурсы ещё удаляются), помечал уже удалённый стек `destroy_failed`: `destroy` удалённой ВМ отвечает `VM_NOT_FOUND` «no VM … nothing was deleted», а «уже удалено» узнавалось только по тексту ошибки. Теперь и по коду `VM_NOT_FOUND`/`NOT_FOUND` (найдено живым прогоном 18.10).
- `disk_attach` (и `evo disk attach`) сразу после создания диска падал с 422 «Disk has no openstack_id»: ждал готовности только `disk_create` с `attach_to`. Теперь и отдельная привязка ждёт, пока новый диск станет `available` (до 2 мин), и привязывает его; другие ошибки — как раньше, без ожидания (найдено живым прогоном 18.10).
- `ar_list` (и проверка имени в `ar_create`) не отвечали около 10 минут и падали с «more than 1000 pages»: Artifact Registry отдаёт новый `nextPageToken` на каждой странице, включая последнюю. Теперь список заканчивается на странице без новых реестров; `ar_create` снова проверяет имя и создаёт реестр (найдено живым прогоном 18.10).
- HTML-страница вместо ответа API с кодом 200 (страница шлюза или прокси) принималась за успех: `image_delete` отвечал «deleted», `ca_start` — «ok», хотя ничего не произошло. Теперь это ошибка API (`API_ERROR`, код 5) во всех клиентах, включая S3 (R3B-1, найдено атакующим тестированием).
- Ответ облака, который не удалось разобрать (`disk_resize`, `snat_create`, `tg_list`, пустые списки S3), давал `USAGE` (код 1), как будто запрос не уходил. Теперь `API_ERROR`, код 5 (R3B-2).
- `evo k8s kubectl <id> … --json`: отказ из-за `--json` после аргументов печатался текстом, а не JSON (R3B-3).
- MCP: строка с байтами не в UTF-8 разбиралась с подменой байта на U+FFFD, и инструмент выполнялся с другой строкой. Теперь это ошибка разбора (`-32700`), в облако ничего не уходит (R3B-4).
- DNS: инструменты по зоне и записи (`dns_zone_get`, `dns_zone_delete`, `dns_records`, `dns_record_get`, `dns_record_create`, `dns_record_delete`, шаг `dns` стека) без `type` всегда шли в API публичных зон, и приватная зона отвечала 403 — удалить её без `type=private` было нельзя. Теперь без `type` evo сам находит видимость по id (списки публичных и приватных зон, для записи — GET в обоих API); id, которого нет нигде, — `NOT_FOUND` (код 4). Явный `type` берётся как есть (найдено живым прогоном 18.10).
- `dns_zones` показывает состояние зоны: `state` (у публичной ещё `confirm_state`). Раньше удаляемая зона выглядела как обычная — в консоли «Удаляется», в списке evo без признаков (найдено живым прогоном 18.10).
- `cert_private_key` отдавал ключ в Base64, а не PEM, и без `key_format`: живой API называет поле `private_key`, а не `privateKey`, как спецификация, и evo декодировал только `privateKey`. Теперь PEM — в том поле, которое прислал API (найдено живым прогоном 18.10).
- Долгий `deploy` (ожидание ВМ до 10 минут и дольше) мог упереться в истёкший токен IAM: токен брался один раз в начале команды и не обновлялся. Теперь каждый запрос к compute API берёт текущий токен у провайдера, а тот обновляет его за 5 минут до истечения.
- `evo project list` (и выбор проекта в `configure`) падал с `API_UNREACHABLE` от одного обрыва соединения с Organization API. Теперь запрос списка повторяется, как у клиентов сервисов.

## [1.0.3] — 2026-10-18

### Исправлено

- Списки читали только первую страницу ответа API: `evo` и инструменты MCP `lb_list`, `tg_list`, `vpc_list`, `vpc_routes`, `dns_zones`, `dns_records`, `k8s_list`, `ca_list`, `pg_list`, `ar_list`, `org_projects`, `iam_service_accounts` (и выбор проекта в `configure`) теперь проходят все страницы по токену из ответа; список, который не кончается, — ошибка, а не молча обрезанный результат (#98, найдено атакующим тестированием).
- `pg_create` и `ar_create` отказывают по занятому имени, даже если ресурс с этим именем не на первой странице списка, — раньше уходил запрос на второй платный ресурс (#98).
- `destroy` без указания ВМ (CLI и MCP) в каталоге, где несколько активных развёртываний (например, `evo vm create` / MCP `provision` рядом с `evo deploy`), удалял первое и отвечал успехом, а вторая ВМ продолжала оплачиваться. Теперь — отказ с кодом `2` (`CONFIG_INVALID`) и списком ВМ; каждую удаляйте по ID (`evo vm delete <ID>`, MCP `destroy` с `vm_id`). `status` называет остальные активные ВМ (в `--json` — `other_active_vm_ids`) (R2-2, найдено атакующим тестированием, #101).
- `.evo` — символическая ссылка (может прийти с репозиторием) или `state.json` — ссылка: `destroy` шёл по ней и удалял ВМ из чужого состояния. Теперь `deploy`, `destroy`, `status` и инструменты MCP отказывают с кодом `2` (`CONFIG_INVALID`), как уже отказывал SSH-ключ (R2-1).
- Без `HOME` (systemd, launchd, контейнер) и без `CLOUDRU_CONFIG_DIR` профиль с ключом и кэш токена писались в `./.config/evo` и `./.cache/evo` текущего каталога, задания `stack_*` — в `./.evo/stack-jobs`. Теперь `configure` отказывает с кодом `2` и называет `CLOUDRU_CONFIG_DIR`, ключ из переменных окружения работает без кэша токена, задания стека не сохраняются (R2-3).
- Блокировка профилей старше 30 с отбиралась у живого `configure` — два процесса писали `credentials.yaml` одновременно. Теперь это блокировка ОС, как у `state.lock`: снимается с процессом, по возрасту не отбирается (R2-4).
- `docker-compose.yml` или `.evo.yaml` — не обычный файл (FIFO, устройство): чтение висело без отмены, а вызов MCP по HTTP держал слот. Теперь сразу `COMPOSE_INVALID` / `CONFIG_INVALID` (R2-5).
- Ответ на создание ВМ без её id (`[{}]`) принимался за созданную ВМ: `deploy`, MCP `provision` и `deploy_apply` записывали пустой id, а `destroy` не мог удалить уже оплачиваемую ВМ. Теперь такой ответ считается потерянным: ВМ ищется по имени и записывается под своим id (R3A-1, найдено атакующим тестированием, #104).
- После отказа 409 на создании ВМ и сбоя освобождения boot floating IP `deploy` говорил «ничего не создано», а повторный запуск заводил второй адрес. Теперь ошибка называет оставшийся адрес и команду освобождения, а следующий `deploy` этого каталога (и MCP `provision`) берёт свободный адрес своей ВМ вместо нового (R3A-2).
- Два одновременных MCP `deploy_apply` одного плана видели ВМ без адреса и резервировали по floating IP — один оставался лишним и оплачивался. Теперь второй вызов сразу отказывает, пока идёт первый; повтор после него подхватывает ВМ (R3A-3).
- Ключ, отклонённый (401/403) во время ожидания ВМ в `deploy`, выходил по таймауту с кодом `1` (`VM_PROVISION_FAILED`). Теперь сразу код `2` (`AUTH_EXPIRED` / `AUTH_FAILED`), ВМ названа и записана в state (R3A-4).

## [1.0.2] — 2026-10-18

### Изменено

- Авторство: `evo version` называет автора (в `--json` — поле `author`), он же указан в `NOTICE` и в SPDX-заголовке каждого файла исходного кода.

## [1.0.1] — 2026-10-18

По первому прогону на macOS (zsh, цветной терминал).

### Исправлено

- Таблицы на цветном терминале (`evo doctor`, `evo vm list`, `evo vm flavors`, `evo verify`, `evo status`, `evo list-zones`): заголовок съезжал относительно строк — ширину колонок считали вместе с escape-кодами жирного шрифта.
- `evo configure` сохранял любой текст как ID проекта (в поле «ID проекта:» попало `evo configure`). Теперь ID проекта — только UUID: в диалоге — пояснение и повторный вопрос, с `--project-id` — `CONFIG_INVALID` (код 2) с подсказкой ещё до проверки ключа. `evo project use` по-прежнему принимает и имя.
- `deploy` молчал о порте, который в группе безопасности уже открыт чужим правилом: теперь пишет «порт 80 уже открыт в группе SSH-access_ru.AZ-2 — правило не создавалось, destroy его не тронет» и запоминает это в state (`ports_already_open`); `destroy` в плане и по итогам говорит, что такой порт оставлен.

### Изменено

- Имена вместо одних UUID там, где человек подтверждает или читает о ВМ: `evo destroy` (первая строка, план и строка удаления) — «ВМ evo-web (a1b2…), 203.0.113.10, зона ru.AZ-2»; `evo status` — строка «Имя ВМ», flavor и зона по имени с ID в скобках; превью повторного `deploy` и строки `deploy` о ВМ. `deploy` записывает имена ВМ, зоны, flavor и группы безопасности в state (`vm_name`, `zone_name`, `flavor_name`, `security_group_name`); для записей v1.0.0 они ищутся в облаке по возможности, а без ответа показывается ID. `status --json`, `deploy --json` и `destroy --json` получили поля `vm_name`, `zone_name`, `flavor_name` (`destroy` — `vm_name` и `ports_left_open`); прежние ключи не изменились.
- `evo configure`: недоступный ключу список проектов (так Cloud.ru отвечает сервисному аккаунту проекта: 400 «user not found») — спокойная строка «Список проектов этому ключу недоступен — так Cloud.ru отвечает сервисным аккаунтам проекта. Введите UUID проекта…» вместо текста ошибки API; сама ошибка — с `--verbose`.
- `evo vm flavors` и MCP `list_flavors`: сначала flavor без GPU, затем по vCPU, RAM и имени (раньше — порядок API, большие GPU сверху).
- Деревья `vm` и `disk` по-русски и в таблицах: заголовки (у ВМ — «ID», «Имя», «Состояние», «Зона», «Создана»; у flavor — «Имя», «vCPU», «RAM, ГБ», «≈ руб./мес», «Бесплатный уровень» в этом порядке), «да/нет» вместо `true/false` и русское примечание о цене. `--json` и MCP — без изменений.
- `evo doctor`: доступность API — «доступен (66 мс)» без «HTTP 404» (корень API отвечает 404, что читалось как ошибка); код ответа — с `--verbose` и в `--json` (`http_status`).
- Превью `deploy` о портах: уже открытые порты остаются как есть, `destroy` удалит только правила, созданные этим `deploy`.

## [1.0.0] — 2026-10-18

### Изменено поведение

- По итогам релизного аудита (живой прогон всех 152 инструментов, 17.10):
  - без проекта команды и инструменты с проектным API отвечают `CONFIG_INVALID` (код 2) с подсказкой ещё до запроса в облако; раньше API отвечал 422, и выходил код 5. `evo doctor` без проекта пишет «project_id не задан» и выходит с кодом 2. Каталоги (зоны, флейворы, образы) работают без проекта; каталоги Managed Kubernetes (`k8s_options`, `k8s_addons`, `k8s_addon_versions`, `k8s_add_addon`) API читает по проекту — без него тоже `CONFIG_INVALID`;
  - ошибка инструмента без кода получает причину по происхождению: `API_ERROR` (код 5) — только ответ API, локальная ошибка — `USAGE` (код 1), сеть — `API_UNREACHABLE`;
  - аргумент инструмента не того типа (`"confirmed": "true"`, `"size_gb": "20"`) — `USAGE` с именем поля, а не молчаливое значение по умолчанию;
  - MCP: неизвестный инструмент — ошибка JSON-RPC -32602; схема `bearer` в `Authorization` — без учёта регистра; отказ по лимиту одновременных вызовов — новый код `SERVER_BUSY` вместо `API_RATE_LIMITED`;
  - `k8s_kubectl` отклоняет `--kuberc`; kubectl и helm под evo запускаются с `KUBERC=off`;
  - `evo vm delete` / `destroy vm_id=|name=`: превью называет ВМ (id, имя, зона, состояние, адрес), floating IP и правила портов; несуществующая ВМ — код 4 уже на превью; имя нескольких ВМ — `USAGE` со списком кандидатов. Превью `k8s_delete`, `pg_delete`, `kafka_delete`, `redis_delete`, `ar_delete`, `lb_delete`, `tg_delete`, `vpc_delete`, `snat_delete` называет ресурс (несуществующий — ошибка на превью, кластер в создании — предупреждение); превью `stack_destroy` перечисляет ресурсы стека;
  - `destroy` / `evo vm delete`: удаление не подтвердилось — код 5, у MCP `status: partial`; запись, floating IP и правила портов остаются до повторного удаления (при `release_ip=false` подсказка повтора сохраняет `release_ip=false`); подтверждения ждём 2 мин вместо 30 с;
  - `provision` (`evo vm create`): floating IP не привязался — `status: partial`, код 5, без строки SSH; FIP записан, его освобождает `destroy`;
  - `kafka_create`, `redis_create`, `pg_create`, `ar_create` отказывают (`USAGE`), если имя занято, — второй платный ресурс не создаётся; стек проверяет, что имя свободно, до первого создания шага и не подхватывает чужой ресурс с тем же именем и при повторе после сбоя;
  - `pg_create` без `subnet_id` берёт подсеть открытой зоны (сначала ru.AZ-2), как Kafka и Redis, и показывает зону в превью; подсеть зоны, закрытой для новых ресурсов, — `CONFIG_INVALID` до создания (раньше — первая подсеть проекта любой зоны, и кластер падал в `FAILED`, который через API не удалить);

  - `pg_create`, `kafka_create`, `redis_create` без подходящей спецификации — `USAGE` со списком спецификаций (раньше код 0); `pg_create` проверяет `instances` по спецификации; брокеров Kafka по умолчанию — минимум спецификации, иначе 1 с предупреждением;
  - `lb_create`: `vpc_id` не той VPC, что у группы целей, — `CONFIG_INVALID` до запроса;

  - `metrics_history`: `since` понимает дни (`1d`); больше 24 ч и неразборчивое значение — `USAGE` до запроса;
  - `cert_private_key` отдаёт ключ PEM-текстом (поле `key_format`);
  - `vpc_get`, `vpc_routes`, `pg_get`, `kafka_get`, `redis_get`: id не в формате UUID — `USAGE`; несуществующие VPC и объект или бакет S3 — `NOT_FOUND` (код 4);
  - `billing_*` без `CLOUDRU_AGREEMENT_ID` — `CONFIG_INVALID` (код 2) с подсказкой;

### Исправлено

- По итогам релизного аудита:
  - смоук-тест Docker-образа в релизе шлёт `Content-Type: application/json` (раньше 415 — образ не публиковался); проверки CI и релиза — один скрипт;
  - MCP `provision`: если ВМ не создалась, а загрузочный floating IP освободить не удалось, ответ называет адрес (`floating_ip_id`) и подсказывает `release_floating_ip` — раньше предупреждение видел только журнал сервера;
  - MCP по stdio: строки хода `destroy vm_id=` и `provision` (освобождён floating IP, IP привязан после загрузки) больше не попадают в stdout — канал JSON-RPC; движок MCP пишет их в stderr;
  - `redis_create` снова создаёт кластер: `replicas` — число реплик без мастера (по умолчанию 2, 3 хоста); тип, шарды и реплики проверяются до облака;
  - `cert_versions` работает (`pageSize=1000`, все страницы);
  - `lb_create` без региона в настройках: зона берётся из ВМ целевой группы, подсеть — из этой зоны и VPC группы; без зоны — `USAGE` до запроса (раньше 400); явный `subnet_id` другой VPC — `CONFIG_INVALID`;
  - `k8s plan/create`: мастера создаются в запрошенной зоне (`controlPlaneConfiguration.zones`); подсеть VIP другой зоны или зона без подсети — `CONFIG_INVALID` вместо кластера с узлами NotReady. `k8s add-nodepool`: зона — зона кластера, подсеть — из неё; если зону кластера прочитать не удалось, пул не создается без явной `zone`; превью без `--name` показывает `nodepool-1`;
  - стек с ВМ без образа или зоны, с неверной формой Redis (`replicas`, `type`, `shards`) или отрицательным числом брокеров Kafka отклоняется на `stack_plan`, до создания ресурсов (раньше падал на своём шаге, когда предыдущие ресурсы уже работали);
  - повтор `provision`/`deploy` с занятым именем (409) не подхватывает чужую ВМ и не перезаписывает её запись; floating IP повтора освобождается (раньше он утекал);
  - `disk_create attach_to=…` ждёт, пока диск станет доступен; не удалось — `status: partial` и подсказка `disk_attach`;
  - `security_group:` из `.evo.yaml` учитывается в `deploy`;
  - `dns_record_create` принимает тип записи в любом регистре;
  - `open_ports`: протокол — только `tcp` или `udp` (`USAGE` иначе); открытый tcp-порт не считается открытым для udp;
  - `k8s_helm`: неизвестный action, нехватка release/chart и относительный `repo_url` — `USAGE` до обращения к облаку;
  - `org_projects` без активного проекта подсказывает, где взять UUID; ошибка `evo configure` не повторяет код в тексте; ошибки `logs` и `destroy` без пустого поля `log`.

- MCP `provision`, `disk_create`, `image_create`, `snat_create`: имя, которое Cloud.ru не примет (не латинская буква первой, кириллица, пробел, длиннее 64), — `USAGE` до создания (раньше `provision` успевал зарезервировать floating IP).
- `deploy` и MCP `provision`: Ctrl-C во время резервирования floating IP — адрес, который платформа успела создать, всё равно находится по имени и освобождается (раньше поиск шёл отменённым контекстом, и адрес оставался платным без записи).
- MCP `destroy` без записи о FIP находил по имени и FIP ВМ `<имя>-2`: при двух ВМ `web` и `web-2` FIP ВМ `web` не освобождался; теперь имя сверяется точно, из нескольких — привязанный к ВМ.
- Kafka/Redis: список кластеров читается по страницам (`page_size=100`, `next_page_token`); группы узлов mk8s — тоже.
- `evo k8s kubectl/apply/helm` печатают вывод kubectl как есть, а не таблицей.
- Деревья с `--json`: при ошибке инструмента stdout пуст.
- Английская справка `deploy`, `logs`, `destroy` (`EVO_LANG=en`) больше не пустая.
- `evo doctor` без ключа — предупреждение в строке config, а не «ок».
- Первый опрос ВМ в `deploy` и `destroy` — сразу, а не через интервал.
- Стек: шаг `vm` не создаёт ВМ повторно после ответа-ошибки и не усыновляет чужую ВМ с тем же именем.
- ВМ в `error_creating` записывается в state со статусом `error`; отказ ключа SSH и смена ключа хоста — свои статусы, а не `ssh_timeout`.
- Диагностика установки Docker: вывод последней упавшей попытки и диагноз (DNS, apt-зеркало) в подсказке.
- Сообщения `STATE_CORRUPTED` и `STATE_LOCKED` — по-русски.
- `evo version` у сборки из checkout показывает версию модуля и коммит.
- `install.sh` проверяет подпись релиза и с cosign v2.
- Пароль образа — один на все парольные поля; обязательное `fqdn` РЕД ОС заполняется именем ВМ.
- Превью ВМ: проверка сети — после цены и в своём окне 5 с, медленный список правил не оставляет превью без цены.
