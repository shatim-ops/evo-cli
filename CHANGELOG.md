# Журнал изменений

Формат — [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/), версии —
[Semantic Versioning](https://semver.org/lang/ru/). Здесь — изменения, которые
видит пользователь CLI и MCP; внутренние (тесты, cloud-e2e, api-probe,
документы для разработки) не перечислены.

## [Не выпущено]

### Добавлено

- `evo agent setup --client <клиент>` подключает evo к MCP-клиенту одной командой: `claude-code` (`.mcp.json`, с `--scope user` — `~/.claude.json`), `cursor` (`.cursor/mcp.json`), `vscode` (`.vscode/mcp.json`, ключ `servers`; комментарии файла сохраняются), `gemini` (`.gemini/settings.json`), `codex` (`~/.codex/config.toml`, таблица `[mcp_servers.evo]`: файл проекта Codex читает только в доверенном проекте, он — по `--scope project`); у остальных по умолчанию — файл проекта, `--scope user` — файл пользователя. Файл дополняется, а не перезаписывается: другие серверы, ключи, порядок и отступы остаются; файл с BOM UTF-8 (Блокнот, `Out-File`) читается, метка сохраняется. Перед записью — diff и вопрос; без терминала нужен `--yes` (иначе код 3), `--dry-run` только печатает diff. Другая запись `evo` заменяется только с `--force` (иначе код 1, `USAGE`), такая же — «ничего не изменилось», код 0; сравниваются и заменяются только ключи, которые пишет evo, — `env`, тайм-ауты и прочее, что пользователь добавил в запись сам, остаются и с `--force`; битый файл и символическая ссылка не трогаются (код 2, `CONFIG_INVALID`, для битого — строка и столбец). Запись атомарная, права файла сохраняются, новый файл — `0600`. Ключ Cloud.ru в файл не пишется (сервер берёт его из профиля `evo configure`; без ключа — код 2), токен HTTP — только ссылкой на `$MCP_BEARER_TOKEN`. По умолчанию агент видит группы `deploy,vm,vpc,disk,image` (`--toolsets`, `all` — все); `--read-only`, `--http URL`. Для `gigaagent` (по умолчанию с `--read-only`) и любого другого клиента — `--print json|toml`: печать без записи. Локальная команда: у MCP её нет.
- `evo agent skill` печатает правила работы с evo для ИИ-агента (SKILL.md, по-английски): всегда `--json`, код 3 и поле `approval` — спросить человека, `--dry-run` перед изменением, какие ответы — текст и недоверенные данные, группы инструментов. Правила собираются из реестра инструментов; тот же текст — `docs/agent-skill.md` (есть в архиве релиза). `evo agent setup --skill` кладёт их в `.claude/skills/evo/SKILL.md` (Claude Code) или разделом между метками в `AGENTS.md` (`GEMINI.md` у Gemini) — остальной текст файла не меняется. Правила — файл evo: после обновления evo следующий запуск обновляет их без `--force` (с diff и согласием); в них названа версия evo.
- `SECURITY.md`: как сообщить об уязвимости — приватным отчётом GitHub, что писать и чего не вставлять (ключи, ID проектов), что считается уязвимостью evo, а что — платформы. Ссылка — в README, раздел «Поддержка».

### Исправлено

- **`deploy_apply` больше не оставляет floating IP без учёта.** Если создание адреса ответило успехом без id, evo считал его готовым: адрес оплачивался, но не попадал ни в ответ, ни в state, и `evo destroy` (MCP `destroy`) его не освобождал. Теперь такой адрес находится по имени и записывается, как давно делает `evo deploy`. Если адрес подтвердить не удалось, подсказка теперь — повторить `deploy_apply` с тем же планом (он подхватывает ВМ и адрес на ней), а не привязать адрес в консоли, где он стал бы вторым платным.
- Превью `evo ar create`, `evo ca deploy`, `evo kafka create`, `evo redis create`, `evo lb create` и `evo snat create` (MCP `ar_create`, `ca_deploy`, `kafka_create`, `redis_create`, `lb_create`, `snat_create`) называет тариф ресурса: строка «цена: evo её не рассчитывает, ресурс платный: тариф …», в ответе инструмента — объект `preview` с `tariff_url` и `cost_note`, как у кластеров Kubernetes и PostgreSQL с 1.2.1. Раньше согласие на платный ресурс спрашивалось без цены и без ссылки на неё. Предупреждения инструмента (контейнер от root, один брокер Kafka, все хосты Redis в одной зоне) — строками «внимание» превью CLI и в `preview.warnings`; поля `message`, `will_create`, `warning`, `warnings` ответа не изменились.

## [1.2.2] — 2026-10-22

### Миграция

- **`evo s3 put` и `evo s3 rm` (MCP `s3_put`, `s3_rm`) с именем бакета, которое S3 не примет (`../x`, `a/b`), отказывают до вопроса о согласии** (DECISIONS D19; исправление: согласие спрашивалось на вызов, который не мог пройти, как в D15). Было: превью и вопрос, без терминала и без `--yes` — код 3 (`CONFIRMATION_REQUIRED`), после согласия — ошибка клиента S3 по-английски. Стало: `USAGE`, код 1, «имя бакета "…" не подходит для S3»; в MCP — ошибка вместо `confirmation_required`. Что поменять: скрипту, который ждал код 3 на таком имени, — проверять код 1; имя бакета — из `evo s3 buckets`. Имена, которые принимает клиент S3, не затронуты.
- **MCP-сервер с `--allow-project` не отдаёт баланс договора** (решение владельца 21.10 по разбору догфуда №5, DECISIONS D18; исправление: агент в проекте видел деньги всей организации, хотя `--allow-project` ограничивает сервер проектом). Было: `billing_balance` возвращал баланс договора из `CLOUDRU_AGREEMENT_ID` в окружении сервера, `billing_finops` — баланс и запас дней. Стало: `billing_balance` — ошибка `CONFIG_INVALID` с подсказкой; `billing_finops` — расход проекта, `balance` и `active` — `null`, `balance_error` называет `--allow-project`, запроса баланса нет. Что поменять: баланс читайте `evo billing balance` с ключом договора или с сервера без `--allow-project`. CLI и сервер без флага не изменились.

### Изменено

- **`evo billing finops`, `consumption` и `balance` печатают отчёт для человека** (догфуд №5: в терминал шли сырые числа вроде `12498.330000000002` и английские поля ответа). Суммы — целыми рублями с разделителем разрядов и ₽ (меньше рубля — «< 1 ₽»), период — «22.09–21.10 (30 дн.)», подписи по-русски, «новое» вместо пустого роста, «показано 12 из 94» вместо `by_service_truncated`. Итоги — двумя суммами: «14 998 ₽ с НДС · 12 498 ₽ без НДС»; строки по сервисам и рост — с НДС, как в превью цены и в счёте. Запас дней и бюджет по-прежнему считаются по расходу без НДС, и отчёт это пишет. `--json` и ответ MCP — прежние, с полной точностью.

### Добавлено

- В ответе `billing_consumption` — `cost_with_nds` в строках `by_service`; в ответе `billing_finops` — `total_cost_with_nds`, `daily_burn_with_nds`, `cost_with_nds` в `by_service`, `prev_with_nds` и `now_with_nds` в `anomalies` (суммы с НДС, `amount_nds`). Прежние поля без НДС не изменились; аномалии по-прежнему ищутся по суммам без НДС.
- **Ошибка с `--json` несёт поля ответа инструмента** — новым ключом `details`, как в ответе MCP (паритет; cloud-e2e 1.2.1, аудит Fable FB121-1). Например, `evo vm create --json` после таймаута или Ctrl-C отдаёт в `{"error":{…,"details":{"vm_id":…,"password":…}}}` ВМ, которая продолжает создаваться и оплачиваться, и пароль, который evo для неё сгенерировал. Раньше скрипт получал только текст, а пароль терялся. Повторное создание кластера отдаёт `existing_id`. Без `--json` пароль печатается строкой «Пароль ВМ: …» после ошибки. Прежние ключи конверта не изменились; у ошибки без своих полей `details` нет.

### Исправлено

- `evo stack plan` и MCP `stack_plan`: объект `s3[]` манифеста с именем бакета, которое S3 не примет (`../x`, `a/b`), — отказ `USAGE` на плане, с указанием `s3[i].bucket`, задание не создаётся. Раньше план проходил, `stack_apply` после согласия создавал ВМ и остальные ресурсы стека, а падал только шаг s3 (то же правило, что D19 для `s3_*`).
- Имя существующего бакета, которое S3 не примет (`../x`, `a/b`, `a\b`), у `evo s3 ls|get|put|rm|bucket-delete` и MCP `s3_ls`, `s3_get`, `s3_put`, `s3_rm`, `s3_bucket_delete` — отказ `USAGE` (код 1) на языке CLI: «имя бакета "…" не подходит для S3» с подсказкой, до превью и до запроса. Раньше в ответ попадал английский текст клиента S3, а `s3_put` и `s3_rm` сначала спрашивали согласие на вызов, который не мог пройти. Правило имени — то же, что у клиента S3; имена, которые он принимал, не изменились.
- **`evo deploy --region` понимает имя зоны**, как `evo vm create` (ревью зоны 1.2.1): `--region ru.AZ-2`, `CLOUDRU_REGION`, `region:` в `.evo.yaml` и аргумент `region` MCP `deploy` принимают имя зоны в любом регистре или UUID — по одному правилу с `evo vm create` и MCP `provision`. ВМ, её floating IP и запись state получают UUID зоны, превью называет зону по имени. Раньше имя отклонялось: «region "ru.AZ-2" — имя зоны, а нужен её ID». Неизвестное имя — `USAGE` (код 1) со списком зон, уже на превью, до согласия; имя при непрочитанном списке зон — отказ с ошибкой списка. UUID — как раньше.
- **`evo k8s plan`, `evo k8s create` и `evo k8s add-nodepool` в примечании называют команды evo, а не инструменты MCP** (догфуд №4: в терминале было «call k8s_create with the same args + confirmed=true»). Теперь: «Создать — evo k8s create с теми же флагами (без терминала — с --yes)…», «Проверяйте evo k8s get <ID>…, затем — evo k8s kubeconfig <ID>», «Проверяйте evo k8s nodepools <ID>». Примечание для агента в MCP (по-английски) прежнее. С `EVO_LANG=en` CLI печатает английский текст агента, как и другие подсказки.
- `evo s3 bucket-create` и MCP `s3_bucket_create`: имя, которое проходит шаблон схемы, но не принимает клиент S3 (`a..b`, IP-адрес вида `192.168.1.1`), — отказ `USAGE` до превью и согласия. Раньше превью и вопрос о согласии проходили, а создание падало ошибкой клиента (ревью Cursor 1.2.2, CUR122-2).
- `evo deploy plan` и MCP `deploy_plan` находят зону по имени в любом регистре (`ru.az-2`), как `evo deploy`, `evo vm create` и `provision`. Раньше имя в другом регистре не находилось, и план отказывал (CUR122-3).
- Имя зоны при пустом списке зон — отказ `USAGE` до согласия. Раньше имя уходило в API вместо UUID (CUR122-4).
- Подсказки об ошибках `evo k8s nodepools`, `evo k8s add-nodepool` и выбора зоны k8s в русском CLI называют команды evo (`evo k8s list`, `evo k8s get`, `evo k8s options`, флаг `--zone`), а не инструменты MCP; подсказка о зонах k8s раньше была только по-английски (CUR122-5).
- Текстовый вид `evo billing …`: сумма `NaN` или бесконечность — «н/д»; сумма больше 9,2·10¹⁸ — верным числом. Раньше такие суммы печатались отрицательным числом из-за переполнения (CUR122-6).
- В ответе `k8s_plan` — новое поле `flavor`: имя конфигурации мастеров рядом с `flavor_id` (UUID), и таблица `evo k8s plan` его показывает.

## [1.2.1] — 2026-10-21

### Миграция

- **`evo vm create`, `evo tools call provision` и MCP `provision` без зоны, образа или проекта отказывают сразу, до превью и вопроса о согласии** (решение владельца «явная зона», DECISIONS D15; исправление: согласие спрашивалось на вызов, который не мог пройти). Было: превью с «не задано: зона (--region или CLOUDRU_REGION): без этого команда завершится ошибкой», вопрос «Продолжить?» (без терминала и без `--yes` — код 3, `CONFIRMATION_REQUIRED`), после согласия — отказ `USAGE` (код 1) текстом для MCP: «нужен region (UUID зоны доступности, см. list_zones): у сервера не задан CLOUDRU_REGION». Стало: без зоны — `CONFIG_INVALID`, код 2, «не задана зона доступности (region)» и подсказка «Задайте --region (список: evo vm zones) или evo configure --region <зона>.»; без образа — `USAGE`, код 1, «не задан образ (image или image_id)», «Задайте --image (список: evo image list), например --image Ubuntu-24.04.»; без проекта — `CONFIG_INVALID`, код 2, как после согласия раньше. С `--yes` без зоны код 2 вместо 1. В MCP — ошибка вместо `confirmation_required`, с тем же `reason` и полем `missing` (`["region"]` или `["image"]`); подсказка MCP называет аргумент и `CLOUDRU_REGION` сервера. Что поменять: скрипту, который ждал код 3 от `evo vm create` без `--yes`, — задать зону (`--region` или `evo configure --region`) и образ; `reason` и код теперь говорят, чего не хватает. Создание ВМ с зоной и образом не изменилось.
- **`evo deploy apply <plan-id>` (и MCP `deploy_apply`) с неизвестным, неверным или истёкшим `plan_id` без `--yes` / `confirmed`** — было: код 3 (`confirmation_required`, «цена — в плане»); стало: такой `plan_id` отклоняется до вопроса — `NOT_FOUND`, код 4, тот же, что с согласием. Превью действующего плана по-прежнему код 3. Что поменять: скрипт, который ждал 3 на любой `plan_id`, проверяет 4 — план надо построить заново (`deploy_plan`). Причина — дефект согласия B12-8: вопрос задавался без плана.
- **Секрет из файла, канала или терминала** (`--value-file`, `--password-file`, `--private-key-file`, `--meta поле=-`, `--env ИМЯ=-`) — было: с терминала пробелы по краям обрезались, BOM в начале файла оставался в значении; стало: значение одно и то же из любого источника — снимается только BOM и один завершающий перевод строки, пробелы — часть секрета. Что поменять: если пароль набирали на терминале с пробелами по краям — набрать без них (или передать файлом). Причина — дефект B12-6/B12-7: в облако уходил не тот пароль, что в файле.


### Изменено

- **`evo vm create` показывает, что делает** (отзыв догфуда 1.2.0: после «y» терминал минутами молчал, и было не понять, работает команда или зависла). После согласия в stderr идут этапы: «Создаю ВМ web…», зарезервированный floating IP, принятый запрос с id ВМ, ожидание той же строкой, что у `evo deploy` (`ожидание ВМ… 1м20с (creating)`: в терминале — одной обновляемой строкой, без терминала (файл, конвейер) — строкой раз в 30 секунд и при смене состояния, без `\r`), «ВМ активна», внешний IP, открытые порты и итог — имя, зона, IP, сколько заняло, команда `ssh`. stdout — ответ инструмента (таблица или `--json`; под таблицей — вход на ВМ, см. «Исправлено»); с `--json` хода выполнения нет. После Ctrl-C, по таймауту и в состоянии `error_creating` evo говорит, что дальше: «ВМ <id> продолжает создаваться и оплачивается; проверить: evo vm get <id>; удалить: evo vm delete <id>»; поведение Ctrl-C, ответ и код выхода не изменились (ВМ остаётся и записана в state). Подсказка к 409 «уже есть» при повторе с тем же именем ведёт к `evo vm get <имя>`. Ход показывают и другие команды деревьев и `evo tools call`: `*_operation` с `--wait-seconds` — строкой «ожидание операции… 40с (<статус>)». Ответ инструмента и MCP тот же (кроме сообщения о таймауте, см. ниже).
- **ВМ ждут 25 минут вместо 10** — одно значение для `evo deploy`, `evo vm create` и MCP `provision`, `deploy`, `deploy_apply` (решение владельца: в ru.AZ-1 ВМ была в `creating` около 20 минут; со строкой ожидания долгое ожидание не выглядит зависанием). `CLOUDRU_TIMEOUT` и `timeout` по-прежнему задают своё. Сообщение о таймауте говорит, что ВМ продолжает создаваться и оплачивается, как её проверить и как ждать дольше. Клиент MCP, который отменяет долгий вызов раньше, получает, как и прежде, ответ с `vm_id`, и ВМ записана в state.

### Исправлено

- Превью ресурса, цену которого evo не рассчитывает (`evo k8s create`, группы узлов, `evo pg create`, бакет, расширение диска), писало «цена: не оценивается: у evo нет тарифа для этого ресурса» — догфудер прочитал это как «бесплатно» и согласился на платный кластер. Теперь: «цена: evo её не рассчитывает, ресурс платный: тариф https://cloud.ru/documents/tariffs/evolution/…» со ссылкой на публичный тариф сервиса; в ответе MCP — `preview.cost_note` и новое поле `preview.tariff_url`. У плагина кластера — «своей нет: плагин работает на узлах кластера…». Оценка по публичным тарифам — в плане 1.3.
- **После `evo vm create` можно войти на ВМ** (отзыв догфуда 1.2.1, №3: войти не удалось). Подсказка была `ssh user1@<IP>` без ключа: ВМ получает ключ развёртывания evo из `.evo/id_ed25519` каталога запуска, а `ssh` пробовал `~/.ssh/id_*` и получал отказ. Пароль, который evo генерирует для образа, нигде не показывался и терялся. И ничто не говорило, что ключ и state — в каталоге, где запущена команда. Теперь под таблицей ответа `evo vm create` — строка `SSH: ssh -i <каталог>/.evo/id_ed25519 -o UserKnownHostsFile=<каталог>/.evo/known_hosts -o StrictHostKeyChecking=accept-new user1@<IP>` (та же команда — в итоговой строке «ВМ … готова: … SSH: …» в stderr), «Пароль ВМ: … (записан только здесь — сохраните: evo его не хранит)» и «Ключ SSH и state — в <каталог>/.evo: evo status и evo vm delete запускайте из <каталог>.» Команду `ssh` строит тот же код, что у `deploy_apply` (его ответ не изменился): ключ хоста проверяется по `known_hosts` проекта, запись прежней ВМ на том же адресе удаляется. MCP `provision` и `--json` — новые поля `ssh` (если у ВМ есть внешний IP и она получила ключ развёртывания), `password` (только сгенерированный evo; пароль из `--meta`/`image_metadata` не возвращается; есть и в ответе `timeout`, и в ответе прерванного вызова — Ctrl-C, отмена клиентом MCP) и `state_dir`; `message` называет ту же команду `ssh` и говорит, что пароль — только в этом ответе. По HTTP без `--allow-secret-export` `password` маскируется (H7), как у `deploy_apply`. ВМ без внешнего IP и ВМ со своим ключом — прежнее сообщение.
- Секрет, набранный на терминале в `--value-file -`, `--password-file -` или `--private-key-file -` (и в `--meta поле=-`, `--env ИМЯ=-`), терял пробелы в начале и в конце, а из файла, из канала и в самом флаге (`--password`) они сохранялись: один и тот же пароль давал разные значения (состязательный раунд 1.2, B12-6). Теперь со всех путей — то же значение, что получает инструмент MCP: отрезается только завершающий перевод строки, пробелы — часть секрета. `evo configure` по-прежнему обрезает пробелы вокруг вставленных Key ID, секрета и UUID проекта: в ключе их не бывает, а при вставке они попадают часто.
- Файл секрета, сохранённый с BOM (UTF-8 с сигнатурой — так пишут некоторые редакторы Windows и PowerShell 5 `Out-File -Encoding utf8`), передавал BOM в начале значения, и секрет в облаке не совпадал с секретом в файле (состязательный раунд 1.2, B12-7). Теперь BOM в начале файла или stdin отбрасывается — у `--value-file`, `--password-file`, `--private-key-file`, `--meta поле=@файл` и `--env ИМЯ=@файл`; файл, в котором только BOM и перевод строки, — как пустой: `…: the file is empty` («…: файл пуст»), код 1.
- Интерактивный `evo configure` спрашивает зону доступности после проекта: зоны, открытые для новых ресурсов (тот же список, что `evo vm zones`), в порядке `evo init` — первой зона с подсетью проекта, ru.AZ-2 среди них; Enter берёт показанную, ответ — номер, имя или UUID, в профиль пишется UUID. Список зон не прочитан (сеть, роль ключа) — шаг пропускается со строкой «зону можно задать позже: evo configure --region <зона>», ключ и проект сохраняются. Раньше профиль от `configure` оставался без зоны, и пример из справки `evo vm create` на нём падал (догфуд 1.2.0). `configure` без терминала не изменился.
- Зона по имени: `--region ru.AZ-2` у `evo vm create` и `evo configure`, аргумент `region` MCP `provision` и `CLOUDRU_REGION` для них принимают имя зоны (в любом регистре) или UUID — по тому же правилу, что `vm.zone` стеков; неизвестное имя — `USAGE` со списком зон. Раньше имя отклонялось после согласия: «region "ru.AZ-2" — имя зоны, а нужен её ID». `evo deploy --region` по-прежнему ждёт UUID. `evo configure --region <UUID>` записывает UUID, как раньше, без чтения списка зон.
- Подсказка к отказу `USAGE` без своей подсказки у команды называет её справку (`evo vm create --help`), а не `evo tools describe <инструмент>`; у `evo tools call` — по-прежнему `evo tools describe`.
- Лишний аргумент команды называется: «evo vm create: нужно <name>, передано аргументов: 3; лишние аргументы: "UUID:", "00000000-0000-4000-8000…" — пропущен флаг?» (код 1, как раньше).

### Безопасность

- MCP по HTTP без `--allow-secret-export` и на `--read-only`: пара «имя — значение» узнавалась, только если её поля названы строчными буквами (`name`/`key` и `value`). В env контейнера в стиле Go API — `{"Name": "DB_PASSWORD", "Value": …}`, `{"Key": "CLIENT_SECRET", "Value": …}` — значение уходило открытым (B12-2). Теперь поля пары сравниваются, как имена полей, — без учёта регистра и разделителей; `value` маскируется, только если имя — учётные данные: `{"Name": "LOG_LEVEL", "Value": "debug"}` не меняется (`docs/mcp.md`, H7).
- Там же: секрет внутри строки, которая сама — JSON (`user_data` ВМ, аннотация `last-applied-configuration`), не маскировался: `"user_data": "{\"admin_password\": …}"` отдавал пароль (B12-3). Теперь строка-объект или строка-массив JSON проверяется как часть ответа, по тем же правилам и с тем же поиском повторов; в `redacted` путь продолжается внутрь строки (`user_data.admin_password`). Строка с маской записывается заново — компактным JSON, по-прежнему строкой; строка без маски не меняется. base64 не раскодируется.
- Там же: повтор замаскированного значения скрывался, только если это строка. Число под ключом-секретом маскировалось, а то же число в другом поле — нет: `{"password": 123456789, "copies": 123456789}` отдавал `123456789` (B12-4). Теперь повтором считается и число, чей текст равен замаскированному значению от 8 символов (`123456789` и `"123456789"` — одно значение). Короткие значения и `true`/`false` по-прежнему не преследуются: `"password": "ok"` не скрывает `"status": "ok"`.
- Там же: закрытый ключ в данных Secret Kubernetes под именем `tls.key` и ключ SSH под именем файла `id_rsa` не маскировались — в этих именах нет корня вроде `private_key` (B12-5). Теперь среди полей-учётных данных — имена целиком `tls.key`, `id_rsa`, `id_dsa`, `id_ecdsa`, `id_ecdsa_sk`, `id_ed25519`, `id_ed25519_sk` (без учёта регистра и разделителей). Сертификат `tls.crt` и открытый ключ `id_rsa.pub` не маскируются.
- `deploy_apply` без `confirmed` (и `evo deploy apply <plan-id>` до вопроса) отвечал `confirmation_required` с общей фразой «цена — в плане», не прочитав план: человек одобрял создание платной ВМ, не видя, какой (break 1.2, B12-8). Теперь план читается до вопроса — только локальный файл, без токена и без запроса в облако, — и ответ называет, что будет создано: новые поля `plan_id`, `expires_at` и `preview` (как у `provision` и `deploy`: ВМ — имя, flavor, зона, образ, диск, — проект из плана, подсеть, floating IP, порты и цена `preview.cost` — та, что назвал `deploy_plan`, с источником в `preview.cost_note`; заново не запрашивается). `evo deploy apply` показывает то же превью на терминале словами `evo deploy` («проект: … (из плана)», «цена: ~… RUB в месяц»), `--json` — ответ инструмента, как MCP. Поля `status` и `message` остались. Неверный, неизвестный или истёкший `plan_id` теперь отклоняется и без `confirmed` — той же ошибкой, что и с ним (раньше без `confirmed` приходил `confirmation_required`).
- `evo mcp --read-only`: `deploy_plan` согласия не требует и проходил H11, но создавал ключ развёртывания `.evo/id_ed25519` и сохранял план в `.evo/plans/` — и `plan_id`, который мог выполнить другой процесс с тем же каталогом (break 1.2, B12-9). Теперь сервер с `--read-only` ничего не пишет: ключ не создаётся (план всё равно строится для ключа развёртывания — `ssh.key_name: "ssh-key (deploy)"`, образ, которому нужен только ключ, не отклоняется), план не сохраняется; ответ — тот же план с ценой, без `plan_id` и `expires_at`, с полем `note` о режиме только чтения. `deploy_apply` на таком сервере по-прежнему скрыт и отклоняется (H11). Без флага и в CLI — как раньше.
- MCP с `--allow-project` (REL12-3): инструменты, которые адресуют ресурс по id, действовали на ресурс любого проекта, который видит ключ, — проекта в их запросах нет (`GET` и `DELETE /v1/clusters/{id}` и т. п.), и с ключом организации `pg_get`, `kafka_delete`, `vm_get`, `disk_delete`, `dns_record_delete`, `cert_private_key`, `k8s_kubeconfig`, `*_operation` читали, меняли и удаляли ресурсы проектов не из списка. Теперь сервер с флагом до вызова — до чтения, превью и любого изменения — проверяет, чей ресурс: если ответ API называет проект (PostgreSQL, балансировщики и целевые группы NLB, VPC, Managed Kubernetes, Certificate Manager, образ ВМ по UUID), он должен быть в списке; если не называет (ВМ, диски, floating IP, шлюзы SNAT, подсети, группы безопасности, Kafka, Redis, зоны и записи DNS), ресурс должен быть в списке ресурсов проекта сервера. Ресурс не из разрешённых проектов отвечается как ресурс, которого нет: `NOT_FOUND`, «… is not found in the projects of this server (--allow-project)», с подсказкой, из какого `*_list` взять id, — один и тот же ответ для чужого и для уже удалённого, без проекта в тексте: перебором id клиент не узнает, есть ли ресурс и чей он, а повторный `*_delete` по-прежнему получает `NOT_FOUND`. Изменение не отправляется, данных ресурса в ответе нет; ответ API без проекта — `CONFIG_INVALID`. `*_operation` читают только операции, которые запустил этот сервер, и операции задания стека его проекта; операцию, запущенную до перезапуска сервера или в консоли, сервер не читает — состояние ресурса покажет его `*_get`. Проверка — одно-три чтения перед вызовом. Без `--allow-project` (и в CLI) — как раньше, без лишних запросов. Что проверяется и что нет, с причинами, — `docs/mcp.md` («Ресурс по id», строка H9 закрытого перечня).

### Безопасность

- Бинари и образ Docker собираются на Go 1.26.10: в нём исправлена GO-2026-6809 (`crypto/x509` перестаёт доверять скомпрометированным промежуточным сертификатам — evo проверяет ими TLS Cloud.ru API и сервера MCP).
- MCP с `--allow-project`: `billing_consumption` и `billing_finops` с аргументом `project_id` читали расход любого проекта, который видит ключ, в обход списка. Теперь проект аргумента проверяется так же, как у `deploy` и `provision`: не из списка — `CONFIG_INVALID`. Исключения по-прежнему только `org_quotas` и `iam_service_accounts` (`docs/mcp.md`).
- MCP с `--allow-project` и `CLOUDRU_AGREEMENT_ID`: `billing_consumption` и `billing_finops` без `project_id` читали расход всего договора — со строками проектов не из списка. Теперь сервер с флагом читает расход своего проекта в договоре (`project_ids` в запросе, `scope: project` в ответе); без своего проекта — `CONFIG_INVALID` с подсказкой передать `project_id`. Так же `org_projects` с флагом показывает только проект сервера, а не все проекты организации. Без `--allow-project` (и в CLI) — как раньше: без `project_id` с договором — весь договор (`docs/mcp.md`, H9).
- Маскирование учётных данных в ответах (MCP по HTTP без `--allow-secret-export` и `--read-only`, H7): поле `redacted`, которое уже было в ответе инструмента, копировалось в список как есть — и значение секрета в нём уходило наружу. Теперь `redacted` — только пути, найденные маскированием: своё поле ответа заменяется, а строка в любом месте ответа, равная замаскированному значению длиной от 8 символов, тоже маскируется (короче — только под своим ключом: `"password": "ok"` не скрывает `"status": "ok"`). Числа под полем-учётными данными (`"password": 1234`, и внутри объекта или массива под ним) маскируются, как строки; `true`/`false` — нет. Ключи с точкой или пробелом между словами (`private.key`, `api.key`) сравниваются с корнями так же, как с `_` и `-`.
- Маскирование (H7) смотрело только на имена ключей, и значения пар «имя — значение» уходили открытыми: `ca_get` и `ca_list` отдают env контейнера парами `{"name": "DB_PASSWORD", "value": "…"}`, и значение пароля приходило по HTTP без `--allow-secret-export` и на сервере `--read-only`. Теперь объект с полем `value` и строкой в `name` или `key` проверяется по имени, как поле: если имя — учётные данные по тем же правилам (корень, не исключение), `value` маскируется, в `redacted` — путь вроде `template.containers[].env[].value`. Так же — параметры превью и метаданные объекта облака (`{"key": …, "value": …}`); `{"name": "LOG_LEVEL", "value": "debug"}` не меняется (`docs/mcp.md`, H7).
- MCP по HTTP с `--read-only`: вызов, которому нужно согласие, отклонялся не первым — сначала шли проверки HTTP-режима (H1, H2, H4, H10), и, например, `deploy` с `compose_file=/etc/passwd` отвечал, есть ли такой файл на хосте, а `k8s_helm install` с `repo_url` разрешал имя хоста в DNS. Теперь отказ H11 — раньше всех проверок на обоих транспортах; ответ — тот же `USAGE` («… is refused: this server runs with --read-only …»).

Так `password_expires_at`, `private_key_id`, `secret_key_id` приходят как есть; `accessToken` и `idToken` в camelCase теперь маскируются, а под полем-секретом с массивом или объектом (`"passwords": ["a", "b"]`) — все строки и числа внутри. Поэтому `evo tools call` принимает и формы, которые MCP принимал всегда: массив строкой через запятую (`{"ports":"80,443"}`, `{"dns_names":"a.example.com,b.example.com"}`), объект строкой JSON там, где её принимает инструмент (`config` у `k8s_add_addon`); раньше CLI отказывал с кодом 1. Элементы массива JSON CLI по-прежнему сверяет с типом из схемы (`{"ports":[80,"x"]}` — код 1). Число JSON с дробной частью `.0` или с экспонентой (`{"size_gb":50.0}`, `{"size_gb":5e1}`) в `--args-json`, `--args-file` и MCP принимается как integer, если оно целое; `--arg` и флаги команд принимают integer только десятичной записью (`--arg size_gb=50`). Ничего из того, что CLI принимал, не отклоняется; у отказов прежние код выхода и `reason`, текст сообщения — тот же, что у инструмента в MCP (например, «size_gb must be an integer, got a string "50"»).

Код выхода `evo stack destroy` и `evo tools call stack_destroy` прежний.

## [1.1.0] — 2026-10-20

### Миграция

Версия меняет коды выхода и ответы там, где прежнее поведение было ошибкой или
дырой безопасности (исключение из правила «ломающие изменения — только в
major», docs/RELEASING.md). Что проверить в скриптах и агентах:

- `evo pg get` и `evo pg delete` больше не принимают `--id`: кластер — аргументом (`evo pg delete <cluster-id>`).
- `evo secret value` в скриптах — с `--yes` (без терминала и без него — код 3); MCP `secret_value` отвечает `confirmation_required`, значение — после повторного вызова с `confirmed=true`.
- `release_floating_ip` / `evo vpc fip-release` для адреса, занятого ВМ или SNAT-шлюзом, — код 1 (`USAGE`), а не 5.
- 404 на диск, floating IP, правило группы безопасности или образ — `reason: NOT_FOUND` (было `VM_NOT_FOUND`), код прежний — 4.
- `evo --json tools call` при ошибке пишет тело ошибки только в stderr; stdout пуст.
- `open_ports`, открывший часть портов, — `status: partial`, `isError: true` (код выхода не 0); ни одного — `status: error`.
- Список, прочитанный не целиком, — ошибка `API_ERROR` (код 5) «список не полон», а не короткий список.
- Отказ установки Docker из-за образа (не та ОС, нет keyring, нет `VERSION_CODENAME`, нет `curl`, у Docker нет пакетов для выпуска) — `CONFIG_INVALID` (код 2) сразу, без повторов до 15 минут.
- Пары аргументов «одно из» — оба сразу теперь `USAGE` (код 1): `destroy` (`vm_id` и `name`), `deploy`/`provision` (`image` и `image_id`), `vm_get`, `image_get`, `pg_get`/`pg_delete` (`id` и `cluster_id` с разными значениями), `release_floating_ip`, `vpc_route_create` (два следующих узла), `tg_create` (`vm_id` и `targets`), `dns_record_create` (`value` и `values`). Значение из одних пробелов — тоже `USAGE` «пустое значение …».
- `evo deploy` без проекта и `deploy_plan` с `disk_gb` < 0 отказывают до обмена ключа на токен: за недоступным IAM или прокси код теперь 2 (`CONFIG_INVALID`) и 1 (`USAGE`), а не 1 (`API_UNREACHABLE`).
- MCP по stdio: `k8s_kubectl` с `-f`/`-k`/`--output-directory`, `--cache-dir` или `-o …-file=…` требует `confirmed=true` и у команд чтения.
- MCP по HTTP: `k8s_kubectl describe secret` требует запуска сервера с `--allow-secret-export`; `apply edit-last-applied` и `create --edit` отклоняются.
- `billing_finops`: `days` — от 1 до 366, иначе `USAGE`.
- Alias `cloudru-vm`, `.cloudru-vm.yaml` и каталоги `.cloudru-vm/` работают до v2.0 (раньше было объявлено «до v1.1»), см. docs/rename.md.

### Безопасность

- MCP по HTTP: `k8s_kubectl` с флагом перед командой (`-n get cp …`) проходил проверку как `get`, а kubectl читал `get` как значение `-n` и выполнял `cp`, `proxy` или `kustomize` на хосте сервера (аудит безопасности 19.10, SEC-1). Теперь по HTTP команда kubectl должна идти первой; `create … token` и `apply … view-last-applied secret` отклоняются и с флагами перед подкомандой. Режим stdio не изменился.
- Ключ деплоя из репозитория: `deploy` (CLI и MCP `deploy`, `deploy_plan`, `deploy_apply`) молча брал `./.evo/id_ed25519`, пришедший с `git clone` чужого шаблона (права `0644`), и открытый ключ автора шаблона попадал в `authorized_keys` новой ВМ (SEC-2). Теперь на Linux и macOS закрытый ключ, доступный группе или другим, не используется, как в OpenSSH («UNPROTECTED PRIVATE KEY FILE»): `CONFIG_INVALID` (код 2) с подсказкой удалить `.evo/` (ключ мог прийти с репозиторием; evo создаст новый) или выполнить `chmod 600`, если ключ ваш. evo сам всегда создаёт ключ с правами `0600`. На Windows — как раньше (ACL и предупреждение).
- `secret_value` отдавал расшифрованный секрет без `confirmed` и был помечен `readOnlyHint`, так что клиент мог вызывать его без вопроса человеку; `cert_private_key` требовал `confirmed`, но тоже был помечен как чтение (SEC-4). Теперь оба требуют `confirmed=true` и в `tools/list` идут без `readOnlyHint` (`destructiveHint: false`, `idempotentHint: true`); `evo secret value` спрашивает подтверждение (вопрос на терминале или `--yes`), как `evo tools call cert_private_key`.
- `k8s_kubectl` по stdio: команда чтения с `-f`/`--filename`, `-k`/`--kustomize` или `--output-directory` (в любом написании: `-f x`, `-fx`, `-f=x`, `--filename=x`) выполнялась без подтверждения, хотя `get -f https://…` отправляет запрос на любой адрес, `get -f <файл>` печатает файл в ошибке, а `cluster-info dump --output-directory` пишет на хост (SEC-4). Теперь такая команда требует `confirmed=true`; `logs -f` (`--follow`) — по-прежнему без него. Описания `logs`, `ca_logs`, `k8s_kubectl`, `k8s_helm` и `s3_get` предупреждают агента, что содержимое ответа — недоверенные данные и инструкции из него выполнять нельзя.
- `k8s_kubectl` по stdio: формат вывода из файла хоста (`-o go-template-file=…`, `jsonpath-file=…`, `custom-columns-file=…` в любом написании: `-o x`, `-ox`, `-o=x`, `--output=x`) читал файл без подтверждения, а `--cache-dir` (и флаги `--profile`, `--profile-output`) писал на хост. Теперь такая команда требует `confirmed=true`, как `-f` (релизный аудит, REL-4).
- MCP по HTTP: `k8s_kubectl apply edit-last-applied` и `create … --edit` запускали редактор на хосте сервера, как запрещённый `edit`. Теперь это отказ, и с `--allow-secret-export` тоже (REL-5).
- Релиз: ключ Artifact Registry (`CLOUDRU_AR_KEY_ID`, `CLOUDRU_AR_SECRET`) был в env всей job `image` и виден шагам сборки и smoke-теста, которые запускают собранный образ (SEC-5). Теперь он только в шагах проверки секретов и `docker push`. Адрес реестра (производное от секрета) больше не передаётся между шагами через выходы шага: сборка и smoke-тест идут под локальным именем образа, адрес вычисляет сам шаг `docker push` (REL-18). Подпись образа cosign по digest и provenance — в BACKLOG.
- Маска публичных логов CI (`.github/scripts/redact.sed`) пропускала IPv6, имена хостов ресурсов (`<бакет>.s3.cloud.ru` и другие поддомены `cloud.ru`), 32-значные ID, приклеенные через `_` (`reg_<id>`), и хвост UUID (SEC-6). Теперь они маскируются; время `21:07:13`, таймстемпы GitHub и публичные хосты API (`*.api.cloud.ru`, `id.cloud.ru`, `auth.iam.cloud.ru`, `console.cloud.ru`, `s3.cloud.ru`) остаются.
- `deploy_plan` показывает ключи из `.evo/user_authorized_keys`, которые `deploy_apply` пустит на ВМ (`user_ssh_keys`: тип, отпечаток SHA256, комментарий): файл мог прийти с чужим репозиторием, и раньше эти ключи добавлялись молча.
- `evo mcp --http` предупреждает о `MCP_BEARER_TOKEN` короче 32 символов, а не 16 (только предупреждение, сервер стартует). В docs/mcp.md: встроенного TLS нет — loopback или TLS-прокси; токен — `openssl rand -hex 32`; остаточный риск SSRF у `k8s_helm` по HTTP (редиректы и URL из `index.yaml` не проверяются — ограничьте исходящую сеть); в docs/troubleshooting.md — TOFU первого SSH к новой ВМ и установка Docker через `get.docker.com` на RPM-дистрибутивах без подписи (SEC-3, SEC-7, SEC-8, SEC-9).

- MCP по HTTP: `k8s_kubectl describe` секрета (`describe secret x`, `describe secrets`, `secret/x`, `cm,secret`, `Secret.v1`) без `--allow-secret-export` выполнялся: значения `Data` он не печатает, но печатает все аннотации, а `last-applied-configuration` секрета, созданного через `apply`, содержит его данные — те же, что уже закрыты для `annotate --list` и `apply view-last-applied` (break r4, R4-1). Теперь по HTTP это отказ; `get secret x` (таблица) и `-o name` работают, по stdio — как раньше. Изменение закреплённого поведения: раньше `describe secret` по HTTP был разрешён.
- Ключ деплоя `.evo/id_ed25519` — жёсткая ссылка (у файла больше одной ссылки) принималась как обычный файл, хотя то же содержимое доступно по другому пути — это может быть чужой файл или чужой ключ (R4-9). Теперь, как для символической ссылки (SEC-2), — `CONFIG_INVALID` (код 2) с подсказкой удалить файл (evo создаст новый ключ) или копировать свой ключ, а не связывать. Linux, macOS и Windows (число ссылок NTFS).
- `.evo/user_authorized_keys`: строка с опциями (`command="…",no-agent-forwarding ssh-ed25519 …`) молча выбрасывалась, а строка с типом ключа в начале, но битым ключом, уходила на ВМ (R4-10). Теперь на ВМ уходит любая строка, которую принимает формат authorized_keys (`ssh.ParseAuthorizedKey`), с её опциями, и только она. `deploy_plan` показывает опции ключа в новом поле `options` (`user_ssh_keys[].options` — список строк; например, `command=` выполняется вместо оболочки входа), а строки, которые на ВМ не уйдут, — записью с `error` («line 4: not a valid ssh-rsa public key; not sent to the VM»); текст такой строки в план не попадает (закрытый ключ, вставленный по ошибке, — одной записью «a PRIVATE key»). Команда на ВМ дописывает строку через `grep -qxF --` и `printf`, так что ни кавычки, ни слово с `-` в начале её не меняют.
- Установка Docker (`deploy`): если зеркало образа не отвечало, а файла keyring дистрибутива на ВМ не было, официальное зеркало подключалось без `signed-by` — apt проверял подписи всеми ключами, которым доверяет (и теми, что добавил образ), а не ключами дистрибутива (R4-15). Теперь установка отказывает сразу: `no keyring of the distribution: cannot verify the official mirror`, диагноз — что сделать (стандартный образ или пакет `ubuntu-keyring` / `debian-archive-keyring`), без повторов до 15 минут.
- Установка Docker: символическая (или жёсткая) ссылка на месте `/etc/apt/sources.list.d/docker.list` или `/etc/apt/keyrings/docker.asc` — например, на `sources.list` образа — переписывалась вместе с файлом, на который вела (R4-16). Теперь ссылка удаляется и пишется новый файл; источники apt образа не меняются никогда.
- Установка Docker на дистрибутивах не Ubuntu и не Debian шла через `curl https://get.docker.com | sh` на любом из них, например на Alpine (R4-17). Теперь `get.docker.com` — только на RPM-дистрибутивах (`ID` — `centos`, `rhel`, `fedora`, `rocky`, `almalinux`, или `ID_LIKE` содержит `rhel`/`fedora`), как задокументировано (SEC-8); на остальных — отказ сразу: «Docker install is supported on Ubuntu, Debian and RPM-based distributions», с диагнозом и без повторов. Код выхода — `2` (`CONFIG_INVALID`): нужен другой образ; SSH при этом работал.

### Изменено

- Список, прочитанный не целиком, — всегда ошибка `API_ERROR` (код 5) «<список>: список не полон: <причина>», а не короче список: по нему evo удаляет остатки (`destroy`, уборка), проверяет занятое имя, считает квоты и деньги. Причины: ответ повторяет уже пройденный токен страницы (раньше это был молчаливый конец списка у всех списков по токену: VPC и маршруты, зоны и записи DNS, балансировщики и группы целей, PostgreSQL — кластеры, базы, пользователи, резервные копии, версии, спецификации, Kubernetes — кластеры, пулы узлов, плагины и их релизы, `ca_list`, `ar_list`, `org_projects`, `org_quotas`, `iam_service_accounts`, `kafka_list`, `redis_list`, `cert_versions`, выбор проекта в `configure`); пустая страница или страница из уже прочитанных объектов, пока `total` больше прочитанного; страница из уже прочитанных без `total` (сервер игнорирует `offset` или токен — у compute это раньше завершало список); страниц больше предела (у `kafka_list`, `redis_list`, правил групп безопасности и плагинов Kubernetes — раньше обрезанный список; у списков через общий pager и compute ошибка была, но без кода). Пустая страница без `total` — по-прежнему конец списка (так отвечает `ar_list`, реестр AR-4). У `ar_list` конец списка и страница из уже прочитанных реестров: живой API отдаёт после последней страницы те же реестры с новым токеном (cloud-e2e 20.10). `ca_logs` — хвост лога, а не список ресурсов: повторная страница или токен по-прежнему завершают чтение, обрезанный лог — `truncated: true` (break r4, R4-2…R4-8).
- Аргумент пары, переданный строкой из одних пробелов (`vm_get`/`destroy` `vm_id`/`name`, `image_get`/`provision`/`deploy` `image`/`image_id`, `pg_get`/`pg_delete` `id`/`cluster_id`, `release_floating_ip` `id`/`ip_address`, следующий узел `vpc_route_create`), — `USAGE` (код 1) «пустое значение …» до облака: раньше пробелы срезались и молча брался второй аргумент, `pg_delete id=" " cluster_id=X` удалял X. «Оба заданы» считается по переданным непустым строкам, пробелы — тоже значение. Пустая строка и `null` — по-прежнему «не задан». У `pg_get`/`pg_delete` пустое значение называется раньше расхождения пары: `id=" " cluster_id=X` — «пустое значение id», а не «id и cluster_id расходятся» (REL-10). `destroy` с `vm_id` и `name` вместе и `vpc_route_create` с двумя следующими узлами — `USAGE` «не оба» (раньше молча брался `vm_id` или первый узел); `deploy` с `image` и `image_id` отказывает до превью, а не после подтверждения (break r4, R4-11).
- `release_floating_ip` (и `evo vpc fip-release`) с адресом, занятым ВМ или SNAT-шлюзом, отвечал `status: refused` без `reason` и `error`, и CLI выходил с кодом 5 (`API_ERROR`), хотя запроса на удаление не было. Теперь это `USAGE` (код 1) с `error` и `hint`; поля `status: refused` и `message` остались (QA 20.10, QA-6). `id` и `ip_address` вместе — `USAGE` «id или ip_address, не оба» до подтверждения: раньше `id` молча побеждал (QA-8).
- `open_ports`: если ни одно правило не создалось, ответ был `status: ok` (`isError: false`, код выхода 0) без причины. Теперь это ошибка с `reason` первого отказа API (`status: error`); если открылась только часть портов — `status: partial`, `isError: true` (как у `disk_create` и `destroy`). Новое поле `failures` — причина по каждому порту; `opened`, `already_open`, `failed` — как раньше (QA-3).
- `org_quotas` без прав на квоты организации: в `reason` была фраза. Теперь `reason` — код (`API_ERROR`), фраза — в новом поле `note`; ответ по-прежнему не ошибка (`status: unavailable`) (QA-6).
- `evo pg get` и `evo pg delete` больше не принимают флаг `--id`: он дублировал аргумент `<cluster-id>` и побеждал его — `evo --yes pg delete A --id B` удалял кластер B. В MCP `pg_get`/`pg_delete` по-прежнему принимают `id` и `cluster_id`, но разные значения — `USAGE` «id и cluster_id расходятся» до облака (QA-1).
- Ошибки проверки аргументов в MCP больше не начинаются с имени инструмента (`unknown argument(s) vm` вместо `dns_record_create: unknown argument(s) vm`, `vm_id or name is required` вместо `vm_get requires vm_id or name`; так же «name already exists» и «needs a specification» у `pg_create`, `kafka_create`, `redis_create`, `ar_create`): CLI добавляет имя сам и печатал его дважды. `reason` и коды выхода не изменились (QA-13).

- MCP: `secret_value` без `confirmed=true` отвечает `{"status": "confirmation_required", …}` (как `cert_private_key`) вместо значения секрета; агент повторяет вызов с `confirmed=true` после согласия человека. `evo secret value` без терминала и без `--yes` завершается с кодом 3 (подтверждение нужно), с `--json` — тем же `confirmation_required`; в скриптах добавьте `--yes`. `k8s_kubectl` с `-f`/`-k`/`--output-directory` по stdio без `confirmed=true` тоже отвечает `confirmation_required`.
- `deploy` ставит Docker на Ubuntu и Debian из apt-репозитория Docker (`download.docker.com`) с ключом подписи, встроенным в evo, а не скриптом `curl https://get.docker.com | sh`. Набор пакетов тот же: `docker-ce`, `docker-ce-cli`, `containerd.io`, `docker-buildx-plugin`, `docker-compose-plugin`. На других ОС (CentOS, Fedora) — `get.docker.com`, как раньше.
- Ожидание установки Docker на ВМ — до 15 минут вместо 10: в него теперь входит переход на запасное зеркало.
- Совместимость со старым именем `cloudru-vm` (alias бинаря, `.cloudru-vm.yaml`, каталоги `.cloudru-vm/`) сохраняется до v2.0, а не до v1.1, как было объявлено: строка alias в stderr и предупреждения о старых каталогах называют v2.0.
- В архиве релиза — ещё `CHANGELOG.md`, `docs/guide.md`, `docs/tools.md` и `docs/rename.md`: README и документы в архиве ссылаются на них (REL-17).
- Справка деревьев `image`, `marketplace`, `vpc`, `k8s`, `pg`, `s3` и `secret` — по-русски, как у `vm` и `disk`: подробное описание каждой команды (59 команд) и все флаги (98) вместо английского описания инструмента MCP. Тексты написаны для CLI: подтверждение — вопрос или `--yes`, другие инструменты названы командами (`evo k8s options`, `evo tools call snat_create`). `evo help` в русской справке показывает `help [команда]`, а не `help [command]`. Английская справка (`EVO_LANG=en`), MCP и `evo tools describe` не изменились.

### Исправлено

- `deploy`: после успешной установки Docker evo показывает строки скрипта о том, что он делал по пути (`evo: switching apt to the official mirror…`, повтор настройки зеркала образа): раньше успешная установка ничего не печатала, и нельзя было понять, ставились ли пакеты с зеркала образа или с официального.

- `evo mcp`: отказы при старте (`--auth` или `--allow-secret-export` без `--http`, неверный адрес `--http`, нет `MCP_BEARER_TOKEN`, `--toolsets`) печатались на языке CLI, хотя docs/auth.md обещает, что `evo mcp` всегда отвечает по-английски (R4-12). Теперь сервер переходит на английский до первой проверки, в том числе до разбора флагов: `EVO_LANG=ru evo mcp --auth` (флаг без значения, неизвестный флаг) — тоже по-английски (REL-12). Справка `evo mcp --help` — на языке CLI, как у остальных команд.
- Маска публичных логов CI (`.github/scripts/redact.sed`) пропускала полную форму IPv6 без букв (`2001:0:0:0:0:0:0:1`), хосты `*.cloud.ru` в другом регистре (`MyApp.Containers.Cloud.RU`), имя бакета с `_` (`my_bucket.s3.cloud.ru` становился `my_<bucket>.s3.cloud.ru`) и hex-токены длиннее 32 цифр (64 — `openssl rand -hex 32`), а публичные хосты в другом регистре (`Console.cloud.ru`, `S3.cloud.ru`, `IAM.API.cloud.ru`) портила в `<host>.cloud.ru` (R4-13, R4-14). Теперь имена хостов сравниваются без учёта регистра, адрес из восьми групп и hex от 32 цифр маскируются; хэш коммита (40 цифр), короткие хэши, версии, время и таймстемпы остаются. Проверка — в `.github/scripts/redact_test.sh` (job ci).
- Установка Docker ждала завершения первой загрузки (`cloud-init status --wait`) без предела: зависший cloud-init держал её до срока `deploy` (R4-18). Теперь каждая попытка ждёт его не больше 5 минут (из общих 15 минут ожидания Docker, REL-6), затем установка идёт дальше; блокировку apt ждёт сам apt, а если cloud-init её так и держит, apt-get отказывает, и evo повторяет установку до общего срока.
- Список ВМ, дисков, подсетей и других объектов compute: пустая страница, пока `total` больше прочитанного, и сервер, игнорирующий `offset` (`total=300`, 100 разных ВМ), давали успех с частью списка (break r4, R4-2, R4-3). Правила группы безопасности: пустая страница до `total` и предел в 100 страниц давали обрезанный список без ошибки — по нему `deploy` и `destroy` решают, какое правило добавить или удалить (R4-4, R4-5). Теперь это ошибка «список не полон».
- `cert_versions`: цикл токенов A→(пустая страница с B)→A давал успех с одной версией дважды. Теперь цикл и страница из уже прочитанных версий — ошибка, каждая версия в ответе — один раз (R4-7).
- `kafka_list` и `redis_list` после 50 страниц возвращали 50 кластеров без ошибки; плагины, релизы и пулы узлов Kubernetes — так же после 50 страниц. Теперь — ошибка «больше 50 страниц» (R4-8).

- Сообщения подтверждения (`confirmation_required`: «provision creates a billable VM…», «… requires confirmed=true …» и остальные изменяющие инструменты, а также предупреждение «он ещё создаётся» у `*_delete`) в CLI были по-английски при русском языке. Теперь — на языке CLI; `evo mcp` по-прежнему отвечает по-английски (R4-20).

- MCP `provision`: нет подсети или группы безопасности в зоне — `CONFIG_INVALID` до резервирования floating IP и создания ВМ, как у `deploy` (раньше бралась подсеть или группа другой зоны, ВМ уходила в `error_creating`).
- `evo configure` без терминала и без единого флага — `CONFIG_INVALID` «нужны Key ID и секрет» (код 2), а не «Профиль сохранён» с кодом 0.
- `k8s_nodepools`: `cluster_id` обязателен (без него — `USAGE` с подсказкой `k8s_list`), как в API.
- `org_projects`: для ключа уровня проекта (ответ Organization API 400/403/404) — `projects: null`, активный проект и пояснение без ошибки (раньше `NOT_FOUND`, код 4); 401 — `AUTH_FAILED`, 5xx и прочие — `API_ERROR`.
- `audit_events`: размер страницы — `limit`, не больше 500; ответ 401 — «аудит не включён для проекта, обратитесь в поддержку Cloud.ru» (`API_ERROR`), 403 — «у роли ключа нет прав или аудит не включён».
- `s3_get` / `evo s3 get`: объект больше 10 МиБ — `USAGE` с подсказкой скачать S3-клиентом, без чтения целиком.
- Размер диска (`disk_create`, `disk_resize`) — не больше 16384 ГБ, проверка до обращения к облаку (раньше справка говорила «до 65536»).
- Имена загрузочного диска и floating IP — не длиннее 64 символов: длинная основа обрезается и получает короткий хеш.
- Булевы флаги деревьев, которые инструмент по умолчанию считает `true` (`--release-ip`, `--kube-api-internet`, `--embed-token`, `--force` у `secret delete`, `--public`, `--external`), объявлены со значением `true`; выключить — `--x=false`.
- Контракт ошибок MCP: у каждой ошибки инструмента есть `reason` (код из `docs/exit-codes.md`), `error` — фраза без префикса кода, `hint` — когда известен; коды выхода CLI не изменились.
- `evo status` сверяет запись с облаком (один `GET` ВМ, до 8 с): живое состояние, «не найдена (удалена вне evo)» или «не проверено: …»; `--no-refresh` — только state; запись другого проекта не проверяется (`CONFIG_INVALID`).
- `evo destroy` и MCP `destroy`: 404 по записи другого проекта не считается «ВМ уже удалена» — ничего не удаляется, запись сохраняется, подсказка — переключиться на проект записи.
- `destroy` с `vm_id`: ВМ, удалённая вне evo, — запись чистится (FIP освобождается, правила портов закрываются), ответ `already_deleted`; если `GET` не ответил 404 — ошибка, запись сохраняется.
- `evo destroy --force` — скрытый устаревший синоним `--yes` с предупреждением.
- Floating IP SNAT-шлюза не считается свободным: `release_floating_ip` его не освобождает, `fip_attach` не привязывает.
- MCP `list_images` — прежний ответ; компактный каталог с поиском — новый `image_list`.
- `deploy` отказывает до создания ВМ на образах Astra Linux, Альт и РЕД ОС (Docker из get.docker.com на них не ставится); `deploy_plan` с `compose_file` на таких образах — `USAGE`.
- Образ общего каталога, недоступный проекту, — `NOT_FOUND` (код 4) до создания ВМ (раньше 422 после подтверждения).
- Незаполненное обязательное поле образа — отказ до создания чего-либо (`USAGE` у `vm create`/`provision`, `CONFIG_INVALID` у `deploy`).
- `evo verify --json`: ключи `port`, `status_code`, `healthy`, `latency_ms`, `error`, `protocol` (раньше — имена полей Go и наносекунды).
- JSON-ошибка без подсказки — без ключа `hint` (раньше `"hint": ""`).
- `evo list-images` скрыта из справки (работает, с подсказкой про `evo image list`).
- Цена в превью ВМ (`vm create`, `deploy`, `deploy_plan`) — из API расчёта цены Cloud.ru, при отказе или тайм-ауте 5 с — оценка по тарифной карте с причиной; нулевой ответ API — не цена, кроме flavor бесплатного уровня без нового floating IP.
- `evo k8s add-addon` и `k8s_add_addon` — в v1.0 (установка плагина проверена вживую); `resolve_mode` по умолчанию `NONE`; удаление плагина — в консоли Cloud.ru.

### Исправлено

- По итогам релизного аудита:
  - смоук-тест Docker-образа в релизе шлёт `Content-Type: application/json` (раньше 415 — образ не публиковался); проверки CI и релиза — один скрипт;
  - MCP `provision`: если ВМ не создалась, а загрузочный floating IP освободить не удалось, ответ называет адрес (`floating_ip_id`) и подсказывает `release_floating_ip` — раньше предупреждение видел только журнал сервера;
  - MCP по stdio: строки хода `destroy vm_id=` и `provision` (освобождён floating IP, IP привязан после загрузки) больше не попадают в stdout — канал JSON-RPC; движок MCP пишет их в stderr;
  - `redis_create` снова создаёт кластер: `replicas` — число реплик без мастера (по умолчанию 2, 3 хоста); тип, шарды и реплики проверяются до облака;
  - `cert_versions` работает (`pageSize=1000`, все страницы);
  - `lb_create` без региона в настройках: зона берётся из ВМ целевой группы, подсеть — из этой зоны и VPC группы; без зоны — `USAGE` до запроса (раньше 400); явный `subnet_id` другой VPC — `CONFIG_INVALID`;
  - `k8s plan/create`: мастера создаются в запрошенной зоне (`controlPlaneConfiguration.zones`); подсеть VIP другой зоны или зона без подсети — `CONFIG_INVALID` вместо кластера с узлами NotReady. `k8s add-nodepool`: зона — зона кластера, подсеть — из неё; если зону кластера прочитать не удалось, пул не создается без явной `zone`; превью без `--name` показывает `nodepool-1`;
  - стек с ВМ без образа или зоны, с неверной формой Redis (`replicas`, `type`, `shards`) или отрицательным числом брокеров Kafka отклоняется на `stack_plan`, до создания ресурсов (раньше падал на своём шаге, когда предыдущие ресурсы уже работали);
  - повтор `provision`/`deploy` с занятым именем (409) не подхватывает чужую ВМ и не перезаписывает её запись; floating IP повтора освобождается (раньше он утекал);
  - `disk_create attach_to=…` ждёт, пока диск станет доступен; не удалось — `status: partial` и подсказка `disk_attach`;
  - `security_group:` из `.evo.yaml` учитывается в `deploy`;
  - `dns_record_create` принимает тип записи в любом регистре;
  - `open_ports`: протокол — только `tcp` или `udp` (`USAGE` иначе); открытый tcp-порт не считается открытым для udp;
  - `k8s_helm`: неизвестный action, нехватка release/chart и относительный `repo_url` — `USAGE` до обращения к облаку;
  - `org_projects` без активного проекта подсказывает, где взять UUID; ошибка `evo configure` не повторяет код в тексте; ошибки `logs` и `destroy` без пустого поля `log`.
