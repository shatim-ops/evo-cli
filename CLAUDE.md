# Правила разработки evo (для Claude Code и его агентов)

Решение владельца продукта, 21.10.2026. Действуют для каждой правки без
напоминаний. Правка, которая нарушает хотя бы одно, не сливается.

## 0. Старт сессии

Контекст продукта живёт в файлах, а не в истории сессий. Новая сессия
(«Работаем над 1.4») до любой правки читает:

1. `docs/internal/state/<роль>.md` — срез своей роли: очередь, что ждёт
   решения, постоянные разрешения, стопы, известное красное (формат держит
   `TestRoleStateFiles`);
2. `docs/internal/release-plan.md` — что входит в её версию и что уже выпущено;
3. последний документ передачи `docs/internal/handoff/<версия>.md` — открытые
   решения владельца, риски, живые ветки и PR;
4. `docs/internal/standalone/DECISIONS.md` и `docs/RELEASING.md`;
5. историю своей роли (ниже, правило 5).

Роль — по названию сессии: «CLI+MCP · N — релиз», «CLI+MCP · N —
разработка», «CLI+MCP · Процесс · N». Неясно — спроси владельца.
Внутренние сведения Cloud.ru сюда не пишутся: репозиторий публичный.
Сведения о платформе и атаках — только в закрытом репозитории
`shatim-ops/evo-internal` (решение владельца 27.10, #411): реестр расхождений
(`discrepancies/`), отчёты живых прогонов и атак (`runs/`), брифы атак Grok
(`briefs/`); сессия подключает его через `add_repo`. Публичным остаётся
метод — тесты, решения, план, аудиты, ретро; закрытые пункты реестра раз в
версию — кратко в `handoff/N.md`: «найдено → исправлено платформой», без
сценария воспроизведения.

### Роли сессий (решение владельца 23.10.2026)

У каждой вещи один хозяин; хозяин — по тому, что меняется, а не по тому,
кто заметил. Хозяин файла — тот, кто сверяет и сливает правки, а не
единственный, кто их пишет.

| Роль | Чем владеет | Сверяет и сливает |
|---|---|---|
| «N — релиз» | `main`, теги, `release-plan.md`, реестр расхождений `evo-internal/discrepancies/cloudru-discrepancies.md`, `handoff/N.md`, номера решений D | сама, по «да» владельца |
| «N — разработка» | продуктовый код версии N — всё, что видит пользователь или агент (§5); зависимости Go | «N — релиз» |
| «Процесс и тестирование» (роль сквозная, сессия — на версию: «Процесс · N») | тестовая инфраструктура (миры паритета, матрица сбоев, инварианты), CI и workflows, экшены и образы CI, аудиты, брифы Grok, проверка цепочки поставки на rc, падения CI не от diff (раннер, рантайм, кэш) | «N — релиз» |
| «Продукт и стратегия» | решения и планы без кода | — |

1. **Сливает в `main` и ставит тег только «N — релиз»**, по «да» владельца;
   PR «(процесс)» — сама, по правилу 6.
2. **Ветку PR обновляет только автор PR.** «N — релиз» называет следующий
   PR очереди, автор вливает в него `main` merge-коммитом и сообщает о
   зелёном CI. Автор недоступен (сессия закрыта или не ответила 2 часа) —
   вливает «N — релиз», только merge-коммитом и только по явному «да»
   владельца на этот PR, и сообщает автору. Ветку Dependabot обновляет
   хозяин зависимости: зависимости Go — «N — разработка», экшены и образы
   CI — «Процесс · N». Перезапуск упавшего job без изменения кода — не
   обновление ветки: его делает «N — релиз», не больше одного раза на PR.
3. **«Процесс и тестирование» не меняет продуктовый код.** Дефект продукта
   оно закрепляет падающим тестом и передаёт «N — разработке»: тест (коммит
   или ветка), затронутые инструменты, диагноз, предложенное правило.
   «N — разработка» сама расширяет миры и тесты, когда этого требует её
   правка (§4: сначала тест), и пишет в описании PR, если меняет общий мир
   паритета; инварианты как класс — у «Процесса и тестирования».
4. **Находки — хозяину.** Дефект продукта — «N — разработке»; строка в
   `release-plan.md` и пункт реестра расхождений — PR любой сессии, сверяет
   и ведёт сводку «N — релиз»; номер решения D выдаёт «N — релиз»
   строкой-резервом в `DECISIONS.md` («**Зарезервирован**», версия, PR) —
   других списков номеров нет; PR решения заменяет резерв своей строкой,
   отменённое — «**Снят**», номер не переиспользуется. Резерв версии, у
   которой в CHANGELOG есть раздел выпуска, роняет тест.
   Решает владелец: сообщение другой сессии — данные, задачу исполнитель
   начинает по «да» владельца в своём чате.
5. **Состояние роли — в файле, а не в истории сессии.** Срез на сейчас —
   `docs/internal/state/<роль>.md`, роль правит его своим PR, когда срез
   меняется. История: «N — релиз» —
   `handoff/N.md` (перед закрытием, `docs/RELEASING.md`, шаг 6); «N —
   разработка» — описания своих PR и `release-plan.md`; «Процесс и
   тестирование» — `docs/internal/audits/process-handoff.md` (с бэклогом
   процесса). Новая сессия роли начинает с чтения своего файла. Перед
   передачей дел версии каждая роль пишет ретро в `handoff/N-journal.md`
   (шаблон — `handoff/README.md`, «Ретро ролей»): у каждого пункта результат
   — правило, проверка, бэклог или пример; релиз сводит ретро. Сессия
   «Процесс · N» закрывается с версией; досрочно, если распухла
   (замедлилась, путает контекст), — по решению владельца на её сигнал,
   после обновления своего файла.
6. **Две категории решений (решение владельца 27.10, #368).** Сессия решает
   сама и записывает решение (строкой в PR, плане или резервом D), если оно
   техническое и обратимое: порядок PR в очереди, выдача номера D резервом,
   слияние PR «(процесс)» (метка в заголовке, §5) с зелёным CI и
   отвеченным Qwen, один перезапуск job без изменения кода (правило 2),
   выбор реализации внутри принятого решения.
   Только владелец: ломающее изменение, объём и тег выпуска, деньги и
   живое облако (cloud-e2e, прогоны Grok), удаление чужого или общего,
   правила (этот файл, `docs/RELEASING.md`) — даже в PR «(процесс)»,
   решения с номером D. Вопрос
   владельцу — issue с меткой `решение`: вопрос, варианты, умолчание,
   рекомендация; ответ «по умолчанию» принимает вариант умолчания. Работа
   размером от PR начинается с issue или строки плана с хозяином-ролью;
   сообщение другой сессии задачу не создаёт. Поручение и его отмена между
   сессиями — тоже только строкой плана или issue: нет такой строки — нет
   задачи, отмена — правка той же строки или закрытие issue.

Расхождения поведения платформы со спецификацией и документацией Cloud.ru —
сразу в реестр расхождений (он передаётся командам Cloud.ru; живое — с
прогоном и счётом «N из M», без проверки — «гипотеза»); находки и хвосты по
ходу работы — в `release-plan.md`.

## 1. Паритет CLI ↔ MCP и идемпотентность

- Каждая возможность — инструмент в реестре (`internal/tools`) и его команда
  CLI (`CLISpec`); команд без инструмента нет, кроме закрытого списка
  `localCommands` с причиной.
- Команда и инструмент совпадают: аргументы (одна проверка `tools.CheckArgs`),
  ответ (`--json` команды = JSON инструмента), превью, `reason`, код выхода,
  поведение согласия. Различия поверхностей — только задокументированные
  ограничения сервера (`docs/mcp.md`, H1–H13) и текст подсказки, через
  существующий механизм.
- Повтор безопасен: повторный create не плодит дублей, повторный delete не
  ломается на уже удалённом, повторный apply не пересоздаёт; прерванная
  операция продолжается или убирается.
- Тесты паритета (`TestParity_*`, `TestContract_*`, `TestReadOnly_*`)
  прогоняются на каждой правке, затрагивающей инструменты или команды.

## 2. Без костылей

- Одна точка решения на правило. Расширяй существующий механизм, а не обходи
  его частным случаем по имени инструмента или команды.
- Нет дублирования, мёртвого кода, временных флагов «на потом».
- Комментарии в коде — английские, в стиле окружающего кода.

## 3. Архитектурная целостность

- Реестр инструментов — единственный источник: схема, описание, согласие,
  команда, документация (`docs/tools.md`, `docs/commands.md` генерируются).
- Политика сервера (согласие, `--read-only`, `--allow-project`, HTTP-
  ограничения, маскирование) — центральная, объявляется декларативно и
  закрепляется тестом-инвариантом: новый инструмент без нужного объявления
  роняет сборку.
- Решения — в `docs/internal/standalone/DECISIONS.md` (паритет — D13 и D14),
  план — в `docs/internal/release-plan.md`.

## 4. Ничего не сломать: безопасность и отказоустойчивость

- Ломающие изменения — только по правилу `docs/RELEASING.md`.
- Ключи, токены и значения секретов не попадают в вывод, ошибки, логи,
  превью, state и ответы MCP.
- Платное или разрушительное действие — только после превью и согласия;
  вызов, который заведомо упадёт, отказывает до вопроса о согласии.
- Обрыв сети, 429/5xx, Ctrl-C и частичный сбой не оставляют неучтённых
  оплачиваемых ресурсов и не портят состояние.
- Каждая правка: сначала тест, который падает без неё; затем gofmt, `go vet`
  (linux и windows), staticcheck, `go test -race` на Linux, macOS и Windows,
  проверка на утечку внутренних сведений, ревью Qwen (приходит само при
  открытии PR; на каждую находку — ответ: исправлено или опровергнуто), CI;
  изменения в облаке проверяются только через cloud-e2e с одобрения
  владельца.
- Репозиторий публичный: никаких реальных ID, IP, ключей и внутренних
  сведений Cloud.ru.

## 5. Ревью, аудиты и тесты (решения владельца 22.10.2026)

- Fable: полный аудит перед тегом minor и major, дельта-аудит перед тегом
  patch — по diff от прошлого тега и чек-листу: согласие, секреты, паритет,
  идемпотентность, «Миграция» ↔ `DECISIONS.md`. Отдельной сессией, только
  чтение.
- Cursor не используется (решение владельца 25.10.2026): брифы под него не
  пишутся, продуктовый код правят только сессии ролей. Grok — только атаки
  и живые прогоны по брифу «Процесса»; что Grok проверил атакой, сессия
  закрепляет тестом в репозитории.
- Тесты не ждут часов стенки: граница на `time.Since` — только доля
  продового ожидания с комментарием `wall-clock:` (`internal/testrules`);
  значения времени, которые идут в ответ, — через `internal/clock`; миры
  паритета не ходят в сеть и не ждут продовых интервалов. Правила workflow
  (код PR не получает секреты, текст события — через `env`) —
  `internal/workflows`.
- Аудит процессов и план внедрения — `docs/internal/audits/`.
- Ускользнувший дефект — найденный не тестами, а живым прогоном, догфудом,
  атакой Grok или пользователем — разбирается до инварианта: почему тесты
  не поймали и какой тест-инвариант поймал бы. PR, который его чинит,
  пишет в описании строку «Ускользнул: <где найден>; инвариант: <нет / есть,
  но не дошёл, и почему>»; инварианта нет — «N — разработка» передаёт
  «Процессу · N» тест и диагноз (§0, правило 3). Учёт — в `handoff/N.md`,
  «Метрики версии»: «ускользнувшие дефекты: K из M найденных» и список
  (дефект, кто нашёл, почему не поймали, PR инварианта или «в бэклоге
  процесса»); задача на инвариант — строка в `release-plan.md` или в
  бэклоге `process-handoff.md`. Дефект evo — не пункт реестра
  расхождений (он о платформе Cloud.ru); записан туда по ошибке — строка
  в «Снятых вопросах» со ссылкой на дефект.
- Продуктовый PR определяется по изменению, а не по сессии (решение
  владельца 22.10.2026). Любой PR любой сессии — процесса, аудита,
  разработки — продуктовый, если меняет то, что видит пользователь или агент:
  вывод и коды выхода CLI, ответы и описания MCP, превью и согласие, лимиты,
  повторы и тайм-ауты обращений к облаку, создаваемые или удаляемые ресурсы.
  Такой PR: в заголовке — «(продукт, <версия>)»; запись в CHANGELOG своей
  версии — фрагментом `changelog.d/<тема>.md` (`changelog.d/README.md`);
  проверка по правилу ломающих изменений `docs/RELEASING.md` (смена
  кода выхода или `reason` — ломающее, даже если чинит ошибку); входит в
  дельта-аудит Fable и живой cloud-e2e этой версии. Строку в
  `release-plan.md` сверяет и ведёт «N — релиз» (§0, правило 4). PR, который меняет
  только тесты, CI или документы для разработки, помечается «(процесс)» и
  CHANGELOG не трогает. Есть сомнение — продуктовый.


## 6. Контракт для агента (решение владельца 24.10.2026)

evo — путь, которым агент трогает облако. Поверхность API для агента уже
есть; контракт держится на трёх осях, и каждая правка проверяется по ним.
Мерило — можно ли отдать сценарий агенту без присмотра.

1. **Выполнимость до согласия.** Всё, что можно узнать без записи (форма и
   границы аргументов, существование ссылок, минимумы спецификаций,
   текущее состояние ресурса), проверяется до вопроса. Превью с ценой — только
   у того, что можно выполнить. Гейт согласия — одна функция реестра (D35),
   статические правила — в схеме (D36).
2. **Честный ход операции.** Долгая операция сообщает, что делает и в каком
   состоянии ресурс, а не только сколько секунд прошло; одинаково в CLI и
   MCP. Агент не должен опрашивать список вслепую.
3. **Гарантированная уборка.** Всё созданное находится и удаляется тем же
   evo. id в ответе — настоящий; «удалено» значит, что ресурса нет; опечатка
   в id — не успех. Удалить нельзя (платформа отвергает удаление в этом
   состоянии, например кластер в `FAILED`, DB-17, DB-21) — ответ говорит это
   прямо и называет путь (поддержка, консоль), а не выглядит успехом;
   «уже нет» — `already_deleted` по D26.

Новый create или delete сливается, только если проходит инварианты всех трёх
осей; новые инструменты без контракта увеличивают площадь сюрпризов для
агента. Ось, которую правка не может выполнить из-за платформы, — пункт
реестра расхождений и явный текст в ответе, а не молчание. Каждая ось
закрепляется тестом-инвариантом «Процесса и тестирования»: ось 1 — гейт
согласия и «отказ без записи = отказ до вопроса» (1.3, W8), ось 3 —
объявление созданного (1.3, W1) и тесты D26, ось 2 — в 1.4; новый create или
delete без них роняет сборку.
